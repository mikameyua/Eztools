## 0. 结论先行（TL;DR）

| 问题 | 结论 |
|---|---|
| 全盘速度从哪来 | **只用 `FSCTL_ENUM_USN_DATA` 枚举 MFT**（不 `FindFirstFile` 递归）。100 万文件 ≈ 3~8 s 建索引，之后靠 USN Journal 增量，永不重扫 |
| 毫秒级查询靠什么 | 内存里是**扁平数组 + 紧凑字符串堆**（非 trie、非 对象数组），扫 100 万条 ≈ 5~15 ms；加**首字符位图**预筛后 ≈ 1~2 ms |
| 进程模型 | **独立常驻进程 `ezt-index.exe`**，不进 Core、不进工具进程。Core 只负责**一次提权 MFT 枚举**，索引自身以中完整性长期运行 |
| USN 读取要提权吗 | **不需要**。`FSCTL_READ_USN_JOURNAL` 在卷句柄只需 `FILE_READ_DATA`，中完整性可读 → **同步层零提权常驻**（关键结论，见 §4.1） |
| 刷新模型 | **WPF 侧只发"快照版本号 + query"，重算在索引进程**。若让 WPF 每键下发全量结果，1 万条 × 每次跨进程序列化 = 必然掉帧（§5.4 是本文最重要的坑） |
| 最大的坑 | ① USN 是无符号数却要做有符号比较 ② 进程重启后 USN 游标静默失效（**唯一解 = USN Journal ID**）③ 单字符前缀会撞上"匹配百万条" |

## 1. 架构总览

```
┌─────────────────────────────────────────────────────────────┐
│ VS Code 扩展（TypeScript）                                   │
│  TreeDataProvider / 独立 View · 输入框 · 高亮 · 打开/定位     │
└───────────────────────┬─────────────────────────────────────┘
                        │ ① JSON-RPC over stdio（长度前缀分帧）
                        │    search {q, limit, substr}
                        │    <-- {epoch, hits:[offset...]}  增量式
┌───────────────────────▼─────────────────────────────────────┐
│ ezt-index.exe（常驻 · 中完整性 · 框架依赖 ≈ 0.3 MB）          │
│  ├ QueryEngine    查询 + 排序 + Top-K 堆                     │
│  ├ IndexStore     扁平数组 + 紧凑字符串堆 + 首字符位图         │
│  ├ JournalTail    独占线程读 USN，120s 心跳打点               │
│  ├ VolumeWorker   MFT 枚举（**提权时**由 Core 代跑）           │
│  └ Persister      落盘 / 启动 mmap 复用                       │
└──────┬───────────────────────────────────┬──────────────────┘
       │                                   │
       │ 建索引：需提权                      │ 正常运行：零提权
       ▼                                   ▼
┌──────────────────┐              ┌─────────────────────────┐
│ ezt-core.exe     │              │ 卷句柄（中完整性）        │
│ （管理员令牌）    │              │ FSCTL_READ_USN_JOURNAL  │
│ FSCTL_ENUM_USN_  │              │ → 创建/删除/改名事件流    │
│ DATA 枚举 MFT     │              └─────────────────────────┘
└──────────────────┘
```

### 1.1 模块职责（单一职责，禁止越界）

| 模块 | 唯一职责 | 明确不做 |
|---|---|---|
| **VS Code 扩展** | UI + 输入防抖 + 显示 | ❌ 不做匹配算法、❌ 不持有全量结果 |
| **ezt-index.exe** | 索引的持有者、查询的执行者 | ❌ 不碰 UI、❌ 不弹权限 |
| **ezt-core.exe** | 仅"读 MFT"一次 | ❌ 不常驻索引、❌ 不解析 USN |
| **ezt-index 的 JournalTail** | 读 USN → 喂变更 | ❌ 不写回 USN、❌ 不重建索引 |

> **为什么索引进程必须独立于 Core**：Core 是**提权进程**，其代码应尽可能少（P3 §9.3 红线：只放有限原语）。把索引与查询放进去 = 把百万级数据结构塞进特权进程，攻击面爆炸。索引进程**中完整性**即可跑（§4.1 证明 USN 读取不需提权）。

## 2. 索引层

### 2.1 USN Journal 三个控制码（**别混**）

| 控制码 | 值 | 作用 | 本项目用途 |
|---|---|---|---|
| `FSCTL_ENUM_USN_DATA` | `0x0009_00B3` | 按 **FRN 顺序**枚举 MFT 现存条目 | **首次全量**（≤5000 条/次游标续传） |
| `FSCTL_QUERY_USN_JOURNAL` | `0x0009_00F4` | 取 `UsnJournalID` / `FirstUsn` / `NextUsn` | 启动对账（§4.2） |
| `FSCTL_READ_USN_JOURNAL` | `0x0009_00BB` | 读**变更流** | **增量同步**（§4） |
| `FSCTL_CREATE_USN_JOURNAL` | `0x0009_00E7` | 开启卷的 USN Journal | 卷未开启时 |

> 🔴 **本项目已有 `volume.readMft` = `FSCTL_ENUM_USN_DATA`**（`Eztools.Core/Primitives/VolumePrimitives.cs`）。
> 全量枚举**直接复用**，不重复实现。需要注意它是**固定的 64 KB 缓冲区 + ≤5000 条/次 + 游标续传**，
> 100 万文件 ≈ 200~330 次调用。**每次跨进程 JSON-RPC 调用有成本**，所以：
> 要么①接受（约 3~8 s，可接受），要么②给 Core 加一个**批量流式**原语（一次握手、多条流式返回）。
> **推荐②**，但作为 P3 增量，别改现有 `readMft` 语义（它已有验收断言）。

### 2.2 首次全量扫描策略（关键：**只跑一次**）

```
启动 → 读磁盘索引文件
  ├─ 不存在 / 卷序列号变了 / 结构版本变了
  │     └─ 全量：Core 枚举 MFT → 建索引 → 记下 nextUsn → 落盘   【唯一的重扫路径】
  └─ 存在且可用
        └─ 直接 mmap 复用 + QUERY_USN_JOURNAL 对账（§4.2）      【热启动，见 §6】
```

**扫描顺序与并发控制**：

| 维度 | 策略 | 理由 |
|---|---|---|
| 卷顺序 | **系统卷优先**（`C:` → 其余 → 外接卷） | 用户最常搜 `C:`，先可用比全部完成更值 |
| 卷内并发 | 每卷 **1 个** MFT 枚举任务，卷间并行 | MFT 枚举是设备 IO，单卷并行只会加剧寻道 |
| 线程优先级 | `BelowNormal` | 见 §6.1 |
| 内存缓冲 | 每卷 64 KB 读缓冲，**直接消费**不入队 | 避免"读得快、写得慢"堆积百万条中间对象 |

### 2.3 增量更新（USN Journal 是唯一真相源）

```
循环:
  read = FSCTL_READ_USN_JOURNAL(from = cursor, MinMajorVersion=2)
  for rec in read.records:
     switch rec.Reason & USN_REASON_MASK:
       FILE_CREATE / DATA_EXTEND / RENAME_NEW_NAME  → upsert(FRN, parent, name)
       FILE_DELETE / RENAME_OLD_NAME                → 按 FRN 索引反查删除
  cursor = read.NextUsn
  每 120s → FSCTL_WRITE_USN_CLOSE_RECORD（心跳，保 journal 不被截断）
```

| `Reason` 位 | 含义 | 处理 |
|---|---|---|
| `0x00000100` `FILE_CREATE` | 新建 | upsert |
| `0x00000200` `FILE_DELETE` | 删除 | remove by FRN |
| `0x00001000` `RENAME_OLD_NAME` | 改名（旧名） | remove by FRN + 记 pending，等 NEW 配对 |
| `0x00002000` `RENAME_NEW_NAME` | 改名后 | upsert（**新名字**）；同 FRN 有 pending ⇒ 折叠（丢弃 pending） |
| `0x00008000` `BASIC_INFO_CHANGE` | 基本信息变更 | 忽略（名字没变） |
| `0x80000000` `CLOSE` | 句柄关闭 | **高位标志**；与其它 reason 位同现（复合记录），可作"写完成"信号 |

> ⚠️ **2026-09-24 修正**：本表初版把 `RENAME_OLD_NAME`（0x1000）/`RENAME_NEW_NAME`（0x2000）
> **写反了**——已按 `winioctl.h` 权威值修正（USN_RECORD_V2 官方文档：OLD=0x00001000、
> NEW=0x00002000）。照初版实现会把改名折叠语义整个颠倒（删新名留旧名），幸在落码前核实。
> 另 `0x00008000` 初版误标 `CLOSE`——真实 `BASIC_INFO_CHANGE`，CLOSE 只在 0x80000000。

> 🔴 **`Reason` 是 32 位无符号，但常量定义里 `CLOSE = 0x80000000` 是"最高位标志"**。
> 判断时用 `reason & USN_REASON_XXX` 而不是 `==`（一条记录常带**多个** reason 位）。
> 本项目 P3 已有同源教训：**Win32 带符号类型填"最大值"必须用 `long.MaxValue`**。

### 2.4 VolumeWorker 落地契约 ✅（W3-a-3，2026-09-24 —— 全量枚举的执行语义）

> 实现于 `src/Eztools.Index/VolumeWorker.cs`；**复用不改** `volume.readMft`（`VolumePrimitives`，P3 §5）。

**读取注入**：`MftReader` 委托隔离响应来源（`{volume, cursor, done, count, records:[{frn,parent,name}]}`）。
真实适配（宿主 → Core `primitive.execute`，`PrimitiveException` → `MftReaderException` 翻译）**随 W3-b 宿主消费 `search.index` 接线**；测试注入假 reader 零进程、零提权可验。

**执行语义**：
- **游标续传**：逐批 ≤5000 条（= `HardMaxRecords`），cursor 语义照抄既有修正语义，**未改动**。
  🔴 **cursor 是不透明续传令牌，不保证跨批数值单调**（2026-09-24 真卷 C: 实测，踩坑全集 §2.14）：
  截断批 = 最后一条记录的完整 FRN（含高 16 位序列号位）；整批消费 = 系统缓冲区边界值——
  两种格式切换时数值**合法变小**。守卫只做行为判据（见 -32019 行），**禁止数值单调比较**。
  另实测：内核对 `StartFileReferenceNumber` 起始记录**不重放**，primitive 的 isReplay
  分支在真卷上不触发（其"两种语义都成立"的注释保留，selftest 假 reader 覆盖重放路径）。
- **对账三计数**：`Count`（新灌入）/ `Replays`（同 FRN+parent+name 内容比对通过的重放消化，不计重复）/ `Updates`（同 FRN 异内容 = 记录号复用 ⇒ 更新为新一代）。三计数都在报告里，缺一不可断言。
- **卷排序**：`OrderVolumes` —— 盘符归一（`"C"`/`"C:\"`/`"\\.\C:"` → `"C:"`）→ **C: 优先** → 其余字母序 → 去重。
- **并行模型**：卷间并行（`Task.WhenAll`）、**卷内单任务**（IndexStore 单线程契约，§3.6）；**每卷一个 IndexStore**（FRN 只在卷内唯一，持久化 per-volume）。
- **收尾校验**：每卷灌完必须 `ValidateSorted()`（§3.6 不变量 I1），结果进报告。

**内部错误码（fail-fast，均不静默）**：
| 码 | 名 | 触发 |
|---|---|---|
| `-32019` | cursor-stalled | **行为判据**（2026-09-24 修正）：未 done 却缺 cursor **或零记录** ⇒ 无法推进（真实 readMft 空批必 done）；`MaxBatches` 兜底。旧版数值单调守卫已删（会误杀合法令牌，踩坑全集 §2.14） |
| `-32020` | bad-batch-shape | 响应缺 `done`/`records`/记录字段——契约破坏；**`done` 缺失不许静默当 false**（S2 同族） |

**已知边界（显式登记，非静默降级）**：readMft 记录无 attributes ⇒ `flags=0`（目录/隐藏判定随 W3-c 变更流或扩展原语）；**`nextUsn` 不可得**（`FSCTL_ENUM_USN_DATA` 不含 journal 查询）⇒ 增量起点延后 W3-c，W3-a-4 持久化 header 该字段本阶段写 0。

## 3. 存储层

### 3.1 为什么不用 trie / 对象数组

| 方案 | 100 万文件内存 | 查询 | 结论 |
|---|---|---|---|
| `struct[]` 对象数组 | ≈ 150~250 MB | 快 | ❌ 超预算（本项目 220 MB 总预算） |
| Trie / Radix | ≈ 120~200 MB | 前缀快、子串/模糊仍需遍历 | ❌ 内存与收益不成比例 |
| **扁平数组 + 紧凑字符串堆 + 位图** | **≈ 25~40 MB** | 线性扫 + SIMD | ✅ **选它** |

### 3.2 三个核心结构

```csharp
// ① 名字堆：所有名字 UTF-8 连续拼接，一条 = offset + len
byte[]  _nameHeap;              // 只增不改（删除留洞，见 §3.4）
int[]   _nameOff;               // [n] 每条的偏移

// ② 条目并行数组（struct-of-arrays，缓存友好）
ulong[] _frn;                   // FRN（反查用）
ulong[] _parentFrn;             // 父目录 FRN → 拼全路径
byte[]  _nameLen;
byte    _flags;                 // bit0=目录 bit1=隐藏 bit2=系统

// ③ 首字符位图（预筛，把"必不可能匹配"整块跳过）
ulong[] _firstCharBits;         // 128 bit：某首字符是否存在（仅前缀模式用）
int[]   _charPosting[128];      // 可选：每字符倒排（内存换速度，见 §3.5）
```

**预计算**：每条名字在建索引时**一次**算好 `name.AsSpan().Trim()` 后的**首字符小写值** + **长度**，
查询时先按"长度 < q.Length"整块跳过。

### 3.3 查询内存预算核算（100 万条）

| 项 | 单条 | 合计 |
|---|---|---|
| 名字堆（平均 13 字节 UTF-8） | 13 B | 13 MB |
| `_nameOff` | 4 B | 4 MB |
| `_nameLen` + `_flags` | 2 B | 2 MB |
| `_frn` + `_parentFrn` | 16 B | 16 MB |
| **合计** | **≈ 35 B** | **≈ 35 MB** |

→ 加位图、路径缓存（LRU 512 条）后 **≈ 40 MB**，**在预算内**。
**通用层总线上限 = 74.51 MB 不得抬高**（本项目 20% 规则管的是审批流程，不是"超了砍功能"的闸门，但也别拿来当借口）。

### 3.4 持久化格式

```
<安装根>/index/vol-<serial>.ezidx
├─ Header (64 B): magic "EZIDX\0\0\0" · formatVersion(u32) · flags
│                 volumeSerial(u64) · usnJournalId(u64)
│                 nextUsn(i64) · entryCount(u64) · nameHeapSize(u64)
│                 createdUtcTicks · checksumCrc32C(u32)
├─ FRN 段：    entryCount × 8 B（**升序**，二分反查）
├─ Parent 段： entryCount × 8 B
├─ NameOff 段：entryCount × 4 B
├─ NameLen/Flags 段：entryCount × 2 B
└─ 名字堆（UTF-8，不改动，删除留洞）
```

**三条设计决策**：

1. **FRN 段必须升序** → 反查用二分，不用哈希表（省 8 MB，且局部性好）。
2. **删除不搬数据，只标洞**（`nameLen = 0xFFFF` 哨兵）。碎片率 > 25% 时才在**空闲时**做一次压缩重排。
3. **落盘只在**：① 首次全量完成 ② 每 30 s 有变更 ③ 每 5 min 无变更后的首次变更 ④ 退出前。

> 🔴 **持久化格式必须带 `formatVersion` 与 `usnJournalId`，且结构变更时递增。**
> 本项目 S1 的教训：**增量构建不拷新 DLL ⇒ 跑旧解析器、新字段静默忽略、退出 0**。
> 索引文件是同一类风险 —— **旧版本读新格式必须显式拒绝并重建，不许"尽力解析"**。

**✅ 落地记录（W3-a-4，2026-09-24 —— 精确 64 B 布局以 `Persister.cs` 文件头为准）**：

```
Header 64 B（little-endian）：
  0   8  magic "EZIDX\0\0\0"      8   4  formatVersion = 1
 12   4  flags（预留 0）          16   8  volumeSerial
 24   8  usnJournalId（W3-c 消费）32   8  nextUsn（本阶段恒 0，§2.4 已登记）
 40   8  entryCount（活条目）     48   4  slotCount（含洞）★新增
 52   8  nameHeapSize            60   4  crc32c（覆盖 [0..60) + 全部段 + 堆）
五段（slotCount × 宽度）：FRN 8B · Parent 8B · NameOff 4B · NameLen 2B · Flags 1B（= 23 B/条）
名字堆：UTF-8 原样，洞（死字节）不改动
```

- **两处偏差（对照上方草图）**：`createdUtcTicks` 不落盘（诊断用文件 mtime 即可，8 B 让给
  **`slotCount u32`** —— 洞是语义的一部分，只有 entryCount 推不出段长与墓碑布局）。
- **CRC32C 手写查表实现**（Castagnoli 0x82F63B78，流式 Update/Final）——零依赖，不引 System.IO.Hashing；
  Save 边写边算最后回填（32 MB 不走全量内存缓冲）。
- **加载 = mmap（MemoryMappedFile）** + 五级校验（FileMissing / BadMagic / BadVersion / BadShape /
  CrcMismatch / VolumeMismatch），结构化状态返回，**绝不尽力解析**；CRC 过但 `ValidateSorted()` 挂 =
  生成方 bug，同样按 BadShape 拒绝。位图是派生结构**不落盘**，加载后重建（§3.6 I4 路径共用）。
- **实测（selftest 落数字）**：100 万条落盘 **32.3 MB < 50 MB**（Save 140 ms）；**热启动 190 ms ≤ 1 s**。
- **运维口径**：回滚 = 删 `<安装根>/index/` 即回全量重建路径；落盘时机（决策 3 的四个时点）随 W3-b
  宿主消费 `search.index` 接线，本步只提供 Save/TryLoad 原语。
- **坑**：空库（slotCount=0 且 heap=0）加载时空段 `ReadArray` 的 position==capacity 会抛 —— 必须跳过空段；
  墓碑洞跨持久化保真，但**位图假阳性不跨持久化保真**（重建后归零，I4 仍满足——False 只出现在名字真不存在时）。

### 3.5 全路径是"查出来的"，不是"存的"

存全路径在 100 万条下要 60~100 MB → **只存 `parentFrn`**，显示时沿父链回溯拼接：

```csharp
cache.TryGetValue(frn, out path) ?? BuildPath(frn);   // LRU 512 条，按目录路径缓存
```
按**目录**缓存而不按文件缓存，命中率极高（同一目录下成百上千文件）。

### 3.6 IndexStore 落地结构定义 ✅（W3-a-2，2026-09-24 —— **W3-a-3 与 W3-b 的共同依据**）

> 实现于 `src/Eztools.Index/IndexStore.cs`；本节是**结构契约**，字段增删必须同步这里并递增落盘 `formatVersion`（§3.4）。

**字段表（内存布局）**：

| 字段 | 类型 | 宽/条 | 说明 |
|---|---|---|---|
| `_heap` | `byte[]` | — | 名字堆，全名字 UTF-8 连续拼接，**只增不改**（删除留洞） |
| `_frn` | `ulong[]` | 8 B | FRN，**槽位序严格升序**（含洞槽位——洞保留 FRN），二分反查 |
| `_parentFrn` | `ulong[]` | 8 B | 父目录 FRN → 全路径回溯（§3.5） |
| `_nameOff` | `int[]` | 4 B | 名字在堆内字节偏移 |
| `_nameLen` | `ushort[]` | 2 B | 名字字节数；**`0xFFFF` = 墓碑哨兵**；真实上限 `0xFFFE` 字节 |
| `_flags` | `byte[]` | 1 B | bit0=目录 bit1=隐藏 bit2=系统（`EntryFlags`） |
| `_firstCharBits` | `ulong[2]` | — | 首字符位图 128 bit；映射 = `char.ToLowerInvariant(c) & 0x7F` |

单条合计 ≈ 23 B + 名字堆 ≈ 13 B ≈ **36 B**；实测 100 万条 GC 托管增量 **39.0 MB**（selftest 断言口径 ≤ 60 MB，RSS 只报告——含 JIT/其他线程噪音，不确定）。

**与 §3.2/§3.3 草案的两处有意偏差（都在 60 MB 上限内）**：
1. `_nameLen` 用 `ushort` 而非 `byte`（实施计划 W3-a-2 风险行 🟡：NTFS 255 UTF-16 字符 = 最多 765 UTF-8 字节，`byte` 会溢出）。
2. `_flags` 独立成数组（2 B 变 3 B），换取墓哨兵 `0xFFFF` 语义干净。

**不变量（I1~I5，测试与突变验证守护）**：
- **I1 槽位升序**：`_frn[0..slotCount)` 严格升序（`ValidateSorted()` 全量校验；乱序插入走有序插入路径）。症状反向提示：升序破坏 ⇒ 二分**静默返回错误结果**（实施计划 🔴 风险），批量灌入方（W3-a-3）灌完必须调一次 `ValidateSorted()`。
- **I2 墓碑即洞**：`nameLen == 0xFFFF` 的槽位反查必须返回"无"（TryGet 显式排除；M-ST1 突变验证：去掉检查 ⇒ 墓碑按 0xFFFF 长度解码 ⇒ 越界异常，自检红）。
- **I3 堆只增不改**：删除/压缩前不回收堆字节；`Compact()` 是唯一重排点（碎片率 > 25% 时空闲调用，§3.4 决策 2）。
- **I4 位图绝无假阴性**：允许假阳性（删除后不清位、映射折叠 & 0x7F），**禁止假阴性**。坑已实测：Compact 重建位图时多字节首字符（中文 3 B UTF-8）必须按前导字节定长整段解码，只解 1 字节会得 U+FFFD ⇒ 设错位 ⇒ **中文假阴性**（selftest ⑦ 回归用例守护）。
- **I5 同 FRN 复用墓碑槽位**：删除后同 FRN 再插入不新开槽位（升序不破坏）；活条目重复 FRN 拒绝。

**API 一览**：`TryAdd(frn, parentFrn, name, flags)` / `Remove(frn)` / `TryGet(frn, out entry)` / `Contains(frn)` / `IsFirstCharPossible(char)` / `Compact()` / `ValidateSorted()`；观测量 `EntryCount / SlotCount / HoleCount / HeapUsedBytes / Fragmentation / NeedsCompact`。

**持久化访问面（internal，W3-a-4）**：五个槽位切片 `FrnSlots/ParentSlots/NameOffSlots/NameLenSlots/FlagsSlots`（`AsSpan(0, slotCount)`——**切片而非底层数组**，容量富余绝不外泄）+ `HeapBytes` + `FromRaw(...)` 静态构造（精确长度数组 → 重建位图）。消费方唯一：同程序集 `Persister`（`Save/TryLoad/GetIndexPath`，见 §3.4 落地记录）。

### 4.2 ⭐⭐ 进程重启后的游标失效（**最容易踩的坑**）

**USN Journal 可以被系统删除并重建，重建后 `UsnJournalID` 变了、USN 从 0 重新计数。**

| 你的行为 | 结果 |
|---|---|
| 只持久化 `nextUsn`，重启后直接用它作起点 | 🔴 **静默错**：新 journal 里某个 USN 恰好 ≥ 你的旧游标 → 从中间读，**永远丢失它之前的所有变更**，且**不报错** |
| 存 `(UsnJournalID, nextUsn)`，启动 `QUERY_USN_JOURNAL` 比对 ID | ✅ ID 不同 → 判定"journal 已重建" → **全量重扫该卷**（并告知用户） |
| `QUERY_USN_JOURNAL` 报 `ERROR_JOURNAL_NOT_ACTIVE` | ✅ 卷未开 journal → 尝试 `CREATE_USN_JOURNAL`（需提权）；失败则**该卷标记为"静态快照"** |

**加载流程必须完整走这套检查**：

```
1. QUERY_USN_JOURNAL(volume)
   ├─ ERROR_JOURNAL_DELETE_IN_PROGRESS / NOT_ACTIVE
   │     → 尝试 CREATE_USN_JOURNAL（提权）/ 标记静态快照，不再增量
   └─ ok → 拿 {UsnJournalID, FirstUsn, NextUsn}
2. 索引文件 header.usnJournalId == 刚取的 UsnJournalID ?
   ├─ 不等 → 【全量重扫】（journal 被重建，旧游标无意义）
   └─ 相等 → 继续
3. header.nextUsn >= queried.FirstUsn ?
   ├─ 否 → 【全量重扫】（journal 被截断/瘦身，游标已越界）
   └─ 是 → 从 header.nextUsn 增量补齐（差量可能很大，见 4.3）
```

### 4.3 增量补齐的三个退化阈值

| 条件 | 动作 |
|---|---|
| 落后量 < 10 万条变更 | 直接读 USN 补齐（秒级） |
| 落后量 10 万 ~ 100 万 | 补齐，但**进度提示 + 可取消** |
| `nextUsn` < `FirstUsn`（游标越界） | **全量重扫** |
| journal 被截断（`FirstUsn` 大幅前移） | **全量重扫** |

> 判"落后多少"：`NextUsn - nextUsn` 是**字节偏移**不是记录数（只能当量级估计），
> 精确量级按 §4.2 实际读一批估算。**别把字节数当条数报给用户。**

### 4.4 事件流顺序

USN 是**严格有序**的（每条有 USN 序号），但**同一 FRN 的多条记录可能语义重叠**（如 `RENAME_OLD` + `RENAME_NEW` 同批）。
处理必须**按批次内顺序逐条应用**，并对**同一 FRN 折叠**：

```
RENAME_OLD(Name=A)  → pending[A] = FRN
RENAME_NEW(Name=B)  → 同 FRN 有 pending → 直接 upsert(B)，丢弃 pending
```

## 5. 查询层

### 5.1 三种匹配模式

| 模式 | 触发 | 算法 | 100 万耗时 |
|---|---|---|---|
| **前缀** | 默认（`"doc"`） | 名字堆线性扫，`name.StartsWith(q)` | 5~15 ms |
| **子串** | 含 `*` 或用户切换（`"*doc*"`） | `IndexOf(q) >= 0`，用 `Span.IndexOf` (SIMD) | 8~20 ms |
| **模糊** | 查询含空格或显式开启 | GitHub 风格：`fzf` 式子序列匹配 + 得分 | 30~80 ms |

> 🔴 **`Span<char>.IndexOf` 走 SIMD（`Vector128`）比手写循环快 3~5 倍**，别自己写循环。
> 中文/宽字符场景下 UTF-16 比较天然正确，**不要先转 UTF-8 再比**（转换成本远超收益）。

### 5.2 结果排序规则（**这条决定"看起来对不对"**）

单纯按"匹配位置"排序在百万级下感受很差。采用**分层打分**：

| 优先级 | 规则 | 说明 |
|---|---|---|
| 1 | **匹配质量分**（前缀 1000 / 词首 800 / 子串 500 / 模糊按连续度） | 主序 |
| 2 | **路径深度浅者优先** | 修 `C:\a.doc` 排在 `C:\x\y\z\a.doc` 前 |
| 3 | **目录 vs 文件**：目录略优先 | 很多人搜目录名 |
| 4 | **名字短者优先** | 同分时更"精确" |
| 5 | **最近访问/修改时间**（可选，需额外 IO） | **默认关闭**（读时间要开句柄，百万级不可接受） |

**Top-K 用固定大小最小堆**（`limit` 默认 200、上限 2000）：

```csharp
// 关键：只在堆未满 或 score > heap.Peek().score 时才比较，
// 避免为每条候选都构造结果对象（百万次分配 = GC 灾难）
if (heap.Count < k || score > heap.Min) { heap.Push(new Hit(...)); if (heap.Count > k) heap.Pop(); }
```

### 5.3 递减式查询管道

```
用户输入 "a" → 命中 200,000（**不返回**，只记 epoch）
用户输入 "ab" → 200,000 中筛 → 8,000
用户输入 "abc" → 8,000 中筛 → 120 → ✅ 返回
```

**在上一轮结果集上做二次筛选**（命中数 < 阈值时）比全量重扫快一个数量级。
只有当**查询变短**或**命中数 > 全量 20%** 时才回退全量。

### 5.4 ⭐⭐ UI 集成：**不要把结果集送进 WPF**

| 方案 | 问题 |
|---|---|
| 每键把 1 万条结果序列化给 WPF | 🔴 1 万条 × 每次按键 = **尾延迟爆炸，必然掉帧**（这是本文最容易踩的 UI 坑） |
| ✅ **WPF 只发 query，索引进程内部筛选** | 跨进程只传 **Top-K 命中偏移（int[]）**，K ≤ 200 |
| ✅ 列表**虚拟化**（`VirtualizingStackPanel.IsVirtualizing=True`） | 只渲染可见 20 行 |

**跨进程协议**（⚠️ 下方只是**形状示意**；权威定义 = `docs/W3-搜索协议.md` **V1.0 已冻结**，
三方法为 `search.start` / `search.query` / `search.status`，此处不再重复字段表 —— **禁止两处定义同一件事**）：

```jsonc
// → ezt-index
{"jsonrpc":"2.0","id":7,"method":"search","params":{
  "q":"report","substr":false,"limit":200,"epoch":12,"pathFilter":"C:\\Users"}}
// ←
{"jsonrpc":"2.0","id":7,"result":{
  "epoch":12,"total":18421,"elapsedMs":6,"hits":[
    {"name":"report.docx","dir":true,"len":11,"frn":123456,"path":"C:\\Users\\ishe\\Desktop"}]}}
```

> ⚠️ **`epoch` 必须回传校验**：用户打字快时请求会乱序返回，**过期 epoch 的结果必须丢弃**，
> 否则会出现"打完 `report` 却显示了 `rep` 的结果"。

#### 5.4.1 ✅ **G1 已拍板：输入通道 = 面板 `input` 节点**（2026-09-23）

**问题**：`docs/P4-Wave2c-面板协议.md` §11 明文 —— 面板 V1 **只读 + 按钮**（第 1 条）、
**无键盘事件通道**（第 10 条）。⇒ 现有面板协议**做不出搜索框**。

### 5.5 落地偏差登记 ✅（W3-b，2026-09-24 —— 设计草案 → 实现的全部有意偏离）

> 本表是 §5 草案与 `src/Eztools.Index/QueryEngine.cs` 实现之间**全部已知偏差**的唯一清单。
> 断言面：selftest 118 条（Release/Debug 双口径全绿）+ 突变 M-Q1~Q5 全红验证。

| # | 草案说法 | 落地做法 | 理由 |
|---|---|---|---|
| D1 | §5.2 规则 2：路径深度参与排序 | **不参与扫描期打分**，收敛后对 ≤ K 个候选**精排**（父链回溯 + 深度浅者优先 + FRN 兜底全序） | 扫描期走父链 = 每候选二分 × 百万次，🔴 不可接受；≤ K 次回溯零预算压力。代价：深度极端条目可能被挤进/挤出堆边界 —— 已知且接受 |
| D2 | §5.1 耗时表"模糊 30~80 ms" vs 实施计划"各模式 P95 ≤ 20 ms"（两处矛盾） | **按模式分预算，断言落扫描段 P50**：前缀 20 / 子串 25 / 模糊 80 ms | 拆分计时（`LastScanMs`/`LastBuildMs` 常驻诊断）实测：构建段 P95 ≤ 0.5 ms 可忽略；前缀扫描 P50=16、子串 21.9~22.1（全名 `IndexOf` 无提前退出，**稳态超 20** ⇒ 登记放宽到 25）、模糊 65.7~66.3（在 §5.1 自留预算内）。P95 受 GC/调度噪声摆动（59~103）不作为断言面，仅报告留档 |

## 7. 边界处理

### 7.1 CPU / 磁盘占用控制

| 手段 | 具体做法 |
|---|---|
| 线程优先级 | MFT 枚举与 USN 读取线程 `BelowNormal` |
| IO 优先级 | `SetThreadPriority(THREAD_MODE_BACKGROUND_BEGIN)` → 磁盘空闲时才抢 IO |
| 限速 | 首次全量**每秒最多 N 次 DeviceIoControl**（可配置，默认不限但受后台 IO 优先级约束） |
| 空闲检测 | 系统有前台全屏应用/用户空闲 → 可加速；否则降速 |
| 可暂停 | UI 提供"暂停索引"（用户打游戏时） |
| 增量心跳 | 空闲时 `READ_USN_JOURNAL` 每次返回 0 条 → 睡 500 ms 轮询，不是忙等 |

> **不要为了"省资源"把 MFT 枚举降级成 `FindFirstFile` 递归** ——
> 后者在 100 万文件下要 10~60 分钟且**大量随机寻道**，对磁盘的压力远大于 MFT 顺序读。
> 本项目硬约束 §四.8：**功能完整性 > 预算限制**，禁止因"怕占资源"降级已规划方案。

### 7.2 无权限目录的跳过规则

**MFT 枚举绕过所有 ACL**（拿的是元数据，不是文件内容）→ **不需要逐个目录检查权限**。这是 MFT 相对 `FindFirstFile` 的另一大优势。

但以下情况**必须显式跳过并标注**：

| 情况 | 处理 |
|---|---|
| 卷未挂载 / 无盘符 | 跳过（`GetLogicalDrives` 自然给出） |
| 非 NTFS 卷（FAT/exFAT/ReFS/网络盘） | **跳过并标注"该卷不支持极速索引"**，不静默略过 |
| BitLocker 未解锁卷 | 跳过并标注 |
| 系统保留卷（无盘符的 EFI/恢复分区） | 跳过 |
| `$Recycle.Bin` / `System Volume Information` | **正常收录**（用户可能真的想搜回收站），但**默认在结果里降权** |

🔴 **"跳过"必须可见**。本项目 S 类静默失败清单里 S9′：**跳过不计入任何计数 ⇒ 数字随环境漂移**。
UI 上必须有"已索引 3 个卷 / 跳过 1 个卷（exFAT，不支持）"这样一行。

### 7.3 范围界定：**只搜文件名，不搜内容**

| 项 | 决定 |
|---|---|
| 索引对象 | **仅文件名**（含目录名） |
| 不索引 | ❌ 文件内容 ❌ 文件大小 ❌ 修改时间（可选但默认关）❌ 文件属性内容 |
| 元数据选择 | 体积证据优先：**名字堆是唯一"大"字段**，其余都是定长紧凑数组 |

**可选增量（不在本期）**：`Windows Search` 索引（`SystemIndex`）提供内容检索 ——
但它是**另一套系统**（`OLE DB` / `Windows.Storage.Search`），与本方案的"MFT 毫秒级"是**互补而非替代**。
若要做，**独立一期**，别混进本索引。

### 7.4 其他边界

| 边界 | 处理 | 实现状态（W3-e-3 收口） |
|---|---|---|
| 名字超长（>255） | 用 `ushort` 存长度，别用 `byte` | ✅ selftest 28.1（255 边界）+ W3-a-2（ASCII 259 / CJK 765 字节） |
| 非 BMP 字符（emoji / 生僻字） | UTF-16 代理对 —— `IndexOf` 天然正确；**高亮区间要按 UTF-16 code unit 算** | ✅ selftest 28.2（切出的子串 == 完整 emoji，高低代理成对）；突变 M-B1 背书 |
| 硬链接 | 同一 FRN 多路径 → 索引**只记 MFT 里的路径**（不解析硬链接） | ✅ selftest 28.3：索引按 FRN 建键 ⇒ 同 FRN 的第二条名字被拒，只保留首个。**已知行为**：别名不可搜（不是"搜到两条"） |
| 符号链接 / 联接点 | 收录但**不跟随**（防目录环） | ✅ selftest 28.4：按普通条目索引、可搜；全仓无 reparse 特判（MFT 直读天然不跟随） |
| 卷热插拔 | `WM_DEVICECHANGE` / 轮询 → 新增卷触发增量建索引，移除卷卸载索引 | 🔴 **V1 未实现（已知限制）** —— 见下方 §7.4.1 |
| 索引文件损坏 | CRC32C 校验失败 → **丢弃重建**，不"尽力解析"（同 §3.4） | ✅ selftest 23.4（损坏 .ezidx ⇒ 拒绝加载并重建） |
| 深层父链 / 断链 | 路径回溯拼全路径；父链缺失或超防御上限 ⇒ 可见的 `?\` 前缀 | ✅ selftest 28.5（30 层拼对 + 140 层截断 + 断链兜底）；突变 M-B2 背书 |

#### 7.4.1 卷热插拔：V1 已知限制（如实记录）

**设计意图**（上表）是 `WM_DEVICECHANGE` 触发新增卷增量建索引、移除卷卸载索引。
**V1 落地的实际行为**：卷清单在**自举时一次性确定**（`IndexBootstrap` 调用 `VolumeClassifier.ScanLocalDrives`），
运行期**不监听**设备变更 ⇒

- 运行中途插入的卷（如插上 U 盘/移动硬盘）**不会**自动纳入索引，直到**重启 `ezt-index`**；
- 运行中途拔出的卷，其索引数据**仍在内存/落盘**（不会崩，但结果里可能出现指向已拔出卷的路径）。

**为什么 V1 不做**（不是遗忘，是有意的范围界定）：

1. `WM_DEVICECHANGE` 是**窗口消息**，而 `ezt-index` 是**无消息循环的控制台进程** —— 要么补注册窗口类
   （给一个"本应无 UI"的进程引入 UI 依赖），要么走 `FindFirstChangeNotification`/轮询盘符（另一套机制）。
   两种都显著扩大本阶段的改动面，而收益（"插盘即搜"）对目标场景（搜索**本机固定盘**的文件）边际价值低。
2. 拔盘时的"卸载索引"要处理**并发查询正在遍历该 store**的时序 —— 需要与 `SearchService._gate` 的
   生命周期协同，属独立一期。
3. 本项目的硬约束是"**功能完整性 > 预算**，但**唯一例外是安全/正确性**"（`Eztools-设计方案.md` §15.4）——
   热插拔属**功能增量**而非"做了半截"，故**显式记为已知限制**而不是勉强实现一个半成品。

**V1 用户可用的替代**：需要索引新插入的卷时**重启工具**（托盘退出重开）⇒ 自举会重新扫描盘符。
**后续路线**（未排期）：优先做**轮询盘符集合差异**（无窗口消息依赖，与自举共用 `VolumeClassifier`），
比 `WM_DEVICECHANGE` 更契合"无消息循环进程"的现状。

> ⚠️ **可见性纪律**：这条限制必须**写明**（本节即是），不能只活在实现者脑子里 —— 否则用户
> "插了盘却搜不到"时无从知道是已知限制还是坏了（本项目 S9′ 家族的同款要求）。

## 8. 最容易踩的坑（按严重度排序）

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | **进程重启后 USN 游标失效** | 静默漏掉全部变更、**退出 0** | 存 `(UsnJournalID, nextUsn)`，启动比对 ID（§4.2） |
| 2 | **USN 是无符号 64 位却要做有符号比较** | 从中间读、恒空、不报错 | 用 `long` 语义；填最大值用 `long.MaxValue` ← **本项目已踩过**（§四 已有明文） |
| 3 | **结果集跨进程下发** | UI 掉帧、打字卡顿 | 重算放索引进程，只传 Top-K（§5.4） |
| 4 | **高亮区间按字节算** | 中文/emoji 高亮错位 | 按 UTF-16 code unit；索引进程回传区间 |
| 5 | **`Reason` 用 `==` 判断** | 漏掉复合 reason 事件 | 用位与 `reason & FLAG` |
| 6 | **`RENAME_OLD` / `RENAME_NEW` 未配对** | 改名后搜索结果里**两个名字都在** | 同 FRN 折叠（§4.4） |
| 7 | **索引文件格式无版本号** | 换版本后读到垃圾数据、静默错 | `formatVersion` + 显式拒绝重建（§3.4） |
| 8 | **单字符查询直接全量返回** | 输入 `a` 卡住 UI | 命中数超阈值 → 只显示计数不返回列表（§5.3） |
| 9 | **跳过非 NTFS 卷静默略过** | 用户以为"全盘都在索引里" | 显式标注（§7.2） |
| 10 | **`epoch` 不回传校验** | 显示旧查询的结果 | 每次请求带 epoch，过期丢弃（§5.4） |
| 11 | **把 USN journal 缓冲区当定长** | 末尾几条被丢 | 解析循环用 `while (offset + HeaderSize <= returned)`；本项目已有此守卫 |
| 12 | **卷序列号不校验** | 换了硬盘仍加载旧索引 | header 存卷序列号，不符则重建 |

## 9. 落地分期（建议）

| 阶段 | 交付 | 验收口径（数字化） |
|---|---|---|
| **W3-a 索引核心** | `ezt-index.exe` + MFT 全量 + 落盘 | `C:` 索引 100 万文件 ≤ 10 s；索引文件 ≤ 50 MB；内存 ≤ 60 MB |
| **W3-b 查询核心** | 前缀/子串/模糊 + Top-K + 排序 | 100 万条下单次查询 **P95 ≤ 20 ms** |
| **W3-c 同步层** | 增量 + journal 对账 | 新建/删除/改名文件 **≤ 2 s 反映**；journal 重建能自动识别（负向可测） |
| **W3-d UI** | 原生 WPF 搜索窗 + 高亮 + 打开/定位 | **匹配段**（扫描+构建）**P50 ≤ 50 ms** @2M；虚拟化下 1 万条不卡（端到端感知**仅报告**，见 §4.6 G6） |
| **W3-e 边界** | 优先级/暂停/多卷/边界标注 | 索引期间前台应用无卡顿感知；跳过项**在 UI 可见** |

**每阶段前置**：`validate_data.py` 通过 + 上一阶段断言全绿（本项目既有阶段门禁纪律）。

**断言纪律（本项目既有方法论）**：
- 性能断言落**具体数字 + 具体路径**，禁 `cmd | grep -q`
- **每个"跳过"必须有对应计数断言**（防 S9′）
- 负向路径必须断言**出的是哪个错**（§30.6：「只断言出错不够」）
- 新代码"没生效"先查 DLL 时间戳（本项目 S1）
