## 1. 需求与范围（来自设计文档 §12 P3）

| # | 需求 | 本文对应 |
|---|---|---|
| 1 | Core 特权原语服务（独立进程 + ACL + 完整性级别校验 + 审计） | §3 / §4 / §5 |
| 2 | 提权形态落地（服务 / 计划任务，二选一） | §6 |
| 3 | 首批原语：`handles.enumerate`、`volume.readMft`、`process.terminate` | §5（另加两个低风险配套） |
| 4 | `host.primitive.call` 通路（工具 → 宿主 → Core → 工具） | §7 |

**In / Out 边界**：

| 做 | 不做（明确出范围） |
|---|---|
| `Eztools.Core` 独立进程（`ezt-core.exe`，框架依赖 ≈ 0.3 MB） | Windows 服务形态（§6 说明取舍：计划任务已满足"免 UAC + 自启 + 用户会话"，服务带来 Session 0 复杂度，需要时再加） |
| 命名管道 JSON-RPC（NewLineDelimited，与 stdio 同一套分帧约定） | 通用"调任意 Win32 API"后门（§9.3 反模式，永久禁止） |
| 首批 5 原语：`process.enumerate` · `process.terminate` · `handles.enumerate` · `volume.enumerate` · `volume.readMft` | 🔴 高风险原语：`handles.close` / `input.installHook` / `registry.writeHklm` / `elevated.run` / `fs.readPrivileged` |
| 工具清单 `elevatedPrimitives` 声明门槛（未声明 = 宿主拒绝） | 工具代码进特权进程（§9.3 红线） |
| 计划任务形态（`ezt core install-task`，/RL HIGHEST） | 自动提权/UAC 静默弹窗（启动 Core 是显式动作） |

## 2. 架构与进程模型

```
工具进程 (Python, 中完整性)
   │  host.primitive.call {name, args}        ← stdio JSON-RPC（既有通路）
宿主 (ezt / 托盘，中完整性)
   │  校验 tool.json 已声明 elevatedPrimitives  ← 未声明 = PrimitiveNotDeclared(-32013)
   │  primitive.execute {name, args, toolId}   ← 命名管道 JSON-RPC（新）
Core (ezt-core.exe，可提权，仅第一方代码)
   │  ACL → 身份校验 → 参数校验 → 执行 → 审计
结果原路返回；工具拿不到任何特权句柄。
```

- **发现**：Core 启动后把 `{pipeName, pid, elevated, startedAt}` 原子写入 `<安装根>\core.json`（模型在 Contracts，两侧共用一份，杜绝字段漂移）。宿主读它连接；`core.json` 不存在/过期 = 未运行。
- **管道名**：`ezt.core.<安装根路径 SHA256 前 12 位>` —— 多安装根（测试共存）不冲突。
- **常驻策略**：Core **按需显式启动**（`ezt core start`），宿主**不自动拉起提权进程**（静默弹 UAC 是糟糕体验且违背"显式提权"）。Core 不可达返回结构化错误 `-32017 CoreUnavailable`，消息里带修复命令。
- **部署**：`ezt-core.exe` 随宿主铺进 `<安装根>\bin\`（CLI 的输出目录包含它；安装器现有 bin 复制逻辑零改动）。

## 3. Core 安全设计（§9.2 设计原则的落地）

每个连接与每条调用各过一道闸：

| 层 | 机制 | 说明 |
|---|---|---|
| 1. 管道 ACL | 仅允许**当前用户 SID** 与 SYSTEM；其余拒绝在连接层 | 用 `NamedPipeServerStreamAcl` 创建 |
| 2. 身份校验 | 连接后 `Impersonate()` → 客户端用户 SID 必须 == Core 用户 SID | 防 ACL 绕过（同用户但借道其他管道对象的情况） |
| 3. 完整性级别 | 调用方令牌完整性 **≥ Medium**（0x2000） | §9.2 原则 4"拒绝低完整性调用者"。**有意不要求 ≥ Core 自身级别**：提权 Core（High）若拒绝 Medium 调用方，"提权后 UI 正常调用"就废了——真正的边界是有限原语 + 审计，不是完整性对齐 |
| 4. 参数校验 | 每原语独立校验（类型/范围/必填），`process.terminate` 另有保护名单 | 见 §5 |
| 5. 审计 | `logs\audit-<yyyyMMdd>.log`，每调用一行 JSON：时间 / 调用方 PID / 工具 id / 原语 / 结果 / 耗时 / 错误 | 独立于普通宿主日志，事后可追责 |

## 4. 提权形态（需求 #2）：计划任务

设计文档 §9.4 三形态对照后选**计划任务（最高权限）**：免每次 UAC ✅ · 开机自启 ✅ · 用户会话（可开窗口）✅ · 部署复杂度低 ✅。Windows 服务形态唯一多出的"防篡改"暂无对抗场景（自用阶段）。

- `ezt core start` —— 同令牌启动（开发/低风险验证用；Core 会如实报告 `elevated: false`）
- `ezt core start --elevate` —— UAC runas
- `ezt core install-task` / `uninstall-task` —— `schtasks /Create /TN EztoolsCore /SC ONLOGON /RL HIGHEST /TR "<bin>\ezt-core.exe --from-task"`（**创建 /RL HIGHEST 任务需要管理员令牌**，非提权执行时明确报错）
- Core 启动时自检令牌提升状态写入 `core.json`，`ezt core status` 直接可读。

## 5. 首批原语（需求 #3）

| 原语 | 参数 | 返回 | 风险 | 提权 | 实现要点 |
|---|---|---|---|---|---|
| `process.enumerate` | `pid?` 过滤 | `[{pid, name, path}]` | 低 | 否 | `Process.GetProcesses`；path 非必得（部分进程拒绝读取） |
| `process.terminate` | `pid` 必填 | `{ok, killed}` | 中 | 是（杀高权限进程） | **保护名单**：csrss/wininit/winlogon/smss/services/lsass + Core 自身 + 宿主 PID 拒绝；其余 OpenProcess→Kill |
| `handles.enumerate` | `pid?` 过滤，`type?`（默认 File） | `[{pid, type, path}]` | 中 | 部分（全量句柄表需管理员） | **移植 PowerToys FileLocksmith `NtdllExtensions.cpp`（MIT，已登记于《参考来源.md》）**：`NtQuerySystemInformation(SystemExtendedHandleInformation)` → `DuplicateHandle` → `NtQueryObject`；内核路径 `\Device\HarddiskVolumeX\...` 经 `QueryDosDevice` 映射回盘符。NtQueryObject 可能永久挂起 ⇒ 专用后台线程 + 超时放弃（与 PowerToys 同策略，C# 用后台线程替代 TerminateThread，泄漏上界 = 挂起句柄数，进程退出自动回收） |
| `volume.enumerate` | — | `[{letter, label, fs, kernelDevice, adminRequired}]` | 低 | 否 | `GetLogicalDrives` + `QueryDosDevice` |
| `volume.readMft` | `volume`（如 `C:`）· `maxRecords?`(≤5000) · `cursor?` | `{cursor, done, records:[{frn, parent, name}]}` | 中 | **是** | `DeviceIoControl(FSCTL_ENUM_USN_DATA)` 遍历 USN 记录（MFT 枚举的标准入口，Everything 同法）；**游标语义（2026-09-20 修正）**：因 `maxRecords` 截断时游标 = 上一批最后一条已返回记录的 FRN，下一批从它重放一条并消化（调用方按 `frn` 对账即无漏无重）；缓冲区全消费时游标 = 系统给出的缓冲区边界。未提权时返回结构化 `ElevationRequired(-32015)`（**负向可测**） |

> 批量上限 5000 条/次 + 游标续传是刻意设计：不提供"一次读全盘"的通道，防审计日志被一次调用灌爆，也防 Core 长时间被单调用占用。

## 6. `host.primitive.call` 通路（需求 #4）

`ToolHostManager.HandleToolRequest` 的占位分支（原样抛 NotSupported）替换为：

1. `name` 缺失 → `InvalidParams`；
2. **声明门槛**：`tool.Manifest.ElevatedPrimitives` 必须包含 `name`，否则 `-32013`（消息列出已声明原语）——清单是唯一授权面，运行时不做第二套仲裁（§4.4 同理：不是伪安全）；
3. 经 `PrimitiveClient`（管道客户端，30s 超时）转发 `primitive.execute {name, args, toolId, callerPid}`；
4. Core 结果 / 错误原样映射回工具侧（错误码透传，工具能看到 `-32015` 这类语义错误）。

SDK 侧补 `Tool.primitive(name, args)`（`protocol.py` 的 `HOST_PRIMITIVE_CALL` 常量 P0 就已定义，这次才真正接通）。

## 8. 验收标准（交付标准）

自动化（`scripts/acceptance.sh` 第 9 步，非提权可验全部通过）：

1. `ezt core status` 未运行时如实报告（`running:false`，非报错）
2. `ezt core start` → `status` 报告 `running:true, elevated:false`
3. `ezt core ping` 往返 < 2s
4. `ezt primitive process.enumerate` 返回 ≥ 10 个进程
5. `ezt primitive process.terminate --args '{"pid":<自身>}'` 被**保护名单拒绝**（退出码 + 错误码双重断言）
6. `ezt primitive handles.enumerate --args '{"pid":<当前>}'` 返回条目 ≥ 0 且结构合法
7. `ezt primitive volume.enumerate` 返回 ≥ 1 卷
8. `ezt primitive volume.readMft --args '{"volume":"C:"}'` 未提权 → `-32015` 结构化错误（而非崩溃/超时）
9. 审计日志文件存在且最后一行含最近一次调用
10. `ezt invoke pinfo.list`（工具→宿主→Core→工具 全链路）返回 `count ≥ 10`；且安装形态 `bin\ezt-core.exe` 存在

手工（需管理员）：`--elevate` 启动后 `readMft` 真实返回记录 · `install-task` + 重启自启 · 中完整性外的连接被拒。

**预算**：基础盘 +~0.3 MB（ezt-core.exe，≈ +0.5%，远低于 20% 评审线）；`宿主可执行目录` 预算项不测 Core（独立输出目录），在 budget.sh 注释中说明。

## 9. 已知限制（如实记录）

- 句柄枚举的挂起放弃策略会留下后台线程（有上界、进程退出即回收）——PowerToys 同款取舍
- `process.terminate` 保护名单是**静态最小集**，不是完备的"绝不能杀"清单；审计日志是兜底
- `core.json` 是发现机制不是安全机制（管道 ACL + 身份校验才是）；文件可被同用户篡改，威胁模型内可接受
- Windows 服务形态未做（§1）
