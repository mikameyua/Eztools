## 二、发现与处置（🔴 RI-1 · 🟡 RI-2）

### RI-1 两处**未声明**的静默吞异常（裸空 `catch`）

| # | 位置 | 形态 |
|---|---|---|
| 1 | `src/Eztools.Cli/SelfTestCommand.cs` | `finally` 里删临时目录，`catch (IOException)` 连带解释性注释一起留在 `finally` 体内，`catch` 块本身**完全为空** |
| 2 | `src/Eztools.Desktop/ClipboardPanelProbe.cs` | 同模式（同文件的另两处有注释，仅这一处漏了） |

**为什么是阻断**：本仓红线第 3 条 —— 静默失败。这里的**行为是合理的**（临时目录清理失败不该影响断言结论，系统 temp 会兜底），
但"合理"是**脑子里的**，不是**机器能看见的**。按 §3.9.1 的纪律，刻意沉默必须变成显式声明。

**处置**（行为零改动，只把沉默变成声明）：

```csharp
catch (IOException)
{
    // 临时目录清理失败不阻塞 selftest，系统 temp 兜底
    // review-guards:allow-empty-catch :: 同上：清理失败不影响断言结论
}
```

### 建议做法（两条路，选一）

| 方案 | 做法 | 代价 |

## 五、守卫自身被突变验证抓出的 3 个缺陷（**机制有效的直接证据**）

这一节是本报告最有价值的部分：它证明"新检查必须带突变验证"这条纪律不是形式主义。

| # | 缺陷 | 怎么被发现的 | 教训 |
|---|---|---|---|
| 1 | **期望值写错 2 处** | 首次 `--selftest` 立即报红：一处是我把夹具写成两个空 catch 却只期望 1 条；一处是夹具里的反例根本不含 `A && B \|\| C && D` 的三段结构 | 夹具自己也要被验证 —— 否则"检查通过"只说明夹具不对 |
| 2 | **`end = -1` 哨兵值 TypeError** | 守卫自身的异常被**计为 FAIL 而不是静默通过**（`run_checks` 的异常兜底设计），于是暴露 | "守卫自己出错"必须响亮失败；若当时写成 `pass`，这个 bug 会永久潜伏 |
| 3 | **C# 11 原始字符串 `"""` 让词法剥离错位** + **插值串里的调用被洗掉** | `--selftest` **覆盖不到**（夹具里没有原始字符串）；是靠"守卫报的幽灵候选与 `grep` 对不上"人工追问才抓出 | **候选清单必须与 grep 交叉核对** —— 这也解释了为什么 G4 只敢定 WARN |

### 缺陷 3 的具体影响（值得记住的教训）

- `src/Eztools.Desktop/SearchWindow.cs` 与 `src/Eztools.Desktop/ClipboardHistoryPanel.cs` 各有一段
  `private const string VirtualizingListTemplateXaml = """…""";`（W3-d-2 虚拟化模板）。
  未处理原始字符串 ⇒ 剥离器从 `"""` 起**错位** ⇒ 后续真代码被当成"字符串"吃掉 ⇒
  真调用点在引用索引里消失 ⇒ **误报 4 处幽灵代码**（`RenderResults` / `RenderError` /
  `ScheduleThrottleFire` / `MakeHitTemplate`，经查 82/113/229/233 行**都有真调用点**）。
- 插值串 `$"{Describe(value)}"` 里的调用同样被洗掉 ⇒ 误报 `ConfigValues.Describe`。
- **修完词法后，命中数反而上升**：`ClipboardHistoryPanel.cs` 的 2 处空 catch 从"被吃掉"变成"可见"。
  即错位不仅会造成**误报**，也会造成**漏报** —— 两个方向都会。

### 10.3 守卫自身又抓出 2 个缺陷（**第二轮**）
