## 2. Wave 1：`host.invokeTool` 的设计

### 2.1 为什么不能直接复用 `InvokeCommandAsync`

宿主现有唯一的调用入口 `InvokeCommandAsync` 走 `InvokeAsync`，而 `InvokeAsync` **全程持有全局闸门 `_perToolGate`**：

```
宿主 → 工具A（InvokeAsync 持 _perToolGate，await A 的响应）
            A 在 handler 里发 host.invokeTool(B)
                宿主处理该请求 → 若走 InvokeAsync → 等 _perToolGate → 永不释放 → 三方死锁
```

这不是理论风险：`HandleCrashAsync` 的 resident 自动重启路径已经踩过同一形状的坑，代码里留着注释
「此刻调用方还持有 `_perToolGate`，同步 Acquire 会死锁」（`ToolHostManager.cs:444`）。

**所以嵌套调用必须走不取全局闸门的独立路径。**

### 2.2 死锁安全的充分条件：调用链无环

- 顶层调用被 `_perToolGate` **全局串行**，故任意时刻"宿主发起的调用"只有一条链。
- 因此：链外工具一定是空闲的（它在等宿主，而不是宿主在等它）。
- 于是**只要链上无重复工具，等待图就是无环的**，必定不会死锁。
- 反之若目标已在链上 → 直接拒绝（含自调用），而不是挂住。

**深度上限刻意不做**：链长天然被"已发现工具数"约束（链上工具必两两不同），额外的 `MaxDepth` 是永不可达的
分支——属"戒幽灵代码"。环检测即充分。

### 2.3 契约

| 项 | 定义 |
|---|---|
| 请求 | `host.invokeTool` `{ toolId, commandId, args? }` |
| 返回 | `{ result, toolId, commandId, elapsedMs }` |
| 超时 | 目标工具 `weight` 默认值（或命令自带 `timeoutMs`，与顶层同口径） |
| 归属校验 | 命令 id 必须归属于 `toolId`，否则拒绝（防"借别人的命令 id 调错工具"） |
| 新增错误码 | `-32004 InvokeCycle`（成环）· `-32005 WeightNotPermitted`（档位不支持该 API） |

### 2.4 `weight` 闸门（§5.1「仅基础 API」的落地）

| API | `script` | `lite` | `full` |
|---|---|---|---|
| `host.log` / `host.notify` | ✅ | ✅ | ✅ |
| `host.progress` | — | — | — |（**仅 `lifecycle: task`**，§5.3，与 weight 正交）
| `host.storage.*` | ❌ | ✅ | ✅ |
| `host.primitive.call` | ❌ | ✅ | ✅ |
| `host.invokeTool` | ❌ | ✅ | ✅ |

> `script` 被拒时回 `-32005` + 明确文案（告知是档位限制、换 `lite` 即可），不做静默降级。

## 6. 已知限制（诚实清单）

- `panels` / 安装器 / 打包形态**已定但 panels 未做**：事件总线（Wave 2a ✅）、安装器/更新器（Wave 2b ✅）、
  打包形态（D1 已拍 = 自包含）；`panels` 属 Wave 2c，**须先写面板协议文档再写码**。
- `host.progress` 收紧为 `lifecycle: task` 后：**正向路径当前无调用方**（没有 task 工具会上报进度），
  本轮只验了负向拒绝；将来若有 `resident` 工具想报进度，需重新评估该约束（§5.3 明文限定为 task）。
- **[实测发现的档位语义缺口]** `weight: script` 的「每次调用起进程、用完即退」（§5.1）在
  `IdleRecycle > 0` 时会退化——`ToolHostManager.ReleaseAsync` 的即用即走判据是 `IdleRecycle <= 0`，
  与档位无关，故 script 工具会像 lite 一样被复用直到空闲回收。
  当前产品**没有**走到该配置的路径（CLI 默认 0，Desktop 也走 `ToolHostOptions.ForCli`），
  因此**刻意未改代码**（改了也验证不了，属不可验证的改动），留待常驻宿主形态落地时一并处理。
- 嵌套调用的**并发语义**：目标工具 SDK 主循环是串行读帧，故同一工具被顶层与嵌套同时调用时后者排队——不阻塞、不报错，但有延迟。属设计取舍。
- `probe.progress` / `oneshot.*` 是**验收钩子**（故意要被拒绝的命令），出现在 `ezt list` 的贡献点里属预期；
  它们与 `probe.crash` / `probe.hang` 同类。
