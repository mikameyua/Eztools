## 一、内嵌 / 特权层专属坑（原 MEMORY §六 · P3 阶段）

> 对应落地记录：设计文档 **§20**（§20.3 句柄表布局 · §20.7 并行化看门狗）。

### 1.1 Win11 24H2+ 句柄表条目布局变更（§20.3）

**现象**：Win11 24H2+（`build >= 26100`）句柄表条目布局变了 —— **pid/handle 从 8 字节变 4 字节**。
老布局读新表 = **全部 pid 静默读成 0**，函数"正常返回"空结果，**不报错**。

**现状**：代码已按 build 双布局自适应，无需再改。**但这是典型"版本敏感 + 静默失败"组合**，
将来升级 Windows build 或换机器时要优先回归这一项。

### 1.2 父进程退出会杀死 stdio 被重定向的子进程

**结论**：Core 的输出**一律走 `CoreConsole`**（内部吞掉 IO 异常），不要直接写 `Console`。

**原因**：父进程一旦退出，stdio 被重定向的子进程会被连带杀掉；
直接写 `Console` 会在此时抛 IO 异常并把清理路径打断。

### 1.3 陈旧 `core.json` + ConnectAsync = 30s 假死

**现象**：`%LOCALAPPDATA%` 下残留一个陈旧的 `core.json`（登记了已死的 PID），
客户端仍按它去 `ConnectAsync` ⇒ **假死 30 秒**（等命名管道超时），而不是快速失败。

**对策**：**连接之前先查登记的 PID 是否存活**。存活才连；不存活就直接重新拉起 Core。

**同类教训**：任何"读到一个地址/令牌就去连"的逻辑，都要先验证**持有者还活着**。

### 1.4 并行化时看门狗必须复制进每个分片（§20.7 · 血的教训）

这是本项目最贵的一次并发 bug，四条结论**都是反直觉的**：

| # | 反直觉结论 | 说明 |
|---|---|---|
| ① | **`NtQueryObject` 挂住的是工作线程本身，它无法自救** | 所以"主线程超时兜底"救不了被挂住的线程 |
| ② | **`thread.Join(timeout)` 不能替代看门狗** | Join 只是"不等了"，挂住的线程仍在，占着资源与句柄 |
| ③ | **pid 分桶会把损失面从 1 个句柄放大到整进程** | 同 pid 的句柄集中在一个分片 ⇒ 该分片一挂，整个进程的句柄都读不到 |
| ④ | **正解 = 按下标区间切 + 每区间自带监督线程 + worker 可重启** | 切分维度要选**能均匀分散挂起点**的那个（下标区间），不是"语义上更自然"的那个（pid 桶） |

**提炼的通用规则**：**"逐项处理 + 挂起就跳过"的并行化，监督逻辑必须随分片走，不能只在顶层放一份。**
顶层看门狗管不到被卡住的工作线程 —— 它看到的只是"某个分片还没回"，而无法知道是哪一个、也无法重启它。

## 二、P4 / Wave 2 专属坑（原 MEMORY §七）

> 细节权威见设计文档 **§22.4 / §23 / §24**，以及 `docs/P4-实施方案.md`、`docs/P4-Wave2c-面板协议.md`。

### 2.1 工具间嵌套调用绝不能用 `InvokeCommandAsync`

**原因**：`InvokeCommandAsync` **全程持有 `_perToolGate`** ⇒ 工具 A 调 B、B 又调 A（或形成链）时，
第二层等第一层释放，第一层等第二层返回 ⇒ **三方死锁**。

**正解**：嵌套调用必须走 `InvokeToolAsync` + `_nestedGate`（独立的嵌套闸门）。
**判据**：凡是"工具调工具"的路径，都不该出现在 `_perToolGate` 的作用域内。

### 2.2 环检测即充分，不要加深度上限

**结论**：环检测已经足够，`MaxDepth` 是**幽灵代码**（永不可达分支）。

**推理**：顶层调用被**全局串行** ⇒ 一条调用链在跑时，链外的工具必然是空闲的 ⇒
不存在"深度爆炸"的路径，只要没有环就一定能终止。
加了深度上限反而会**误伤合法的深链**，且那条分支永远测不到。

**教训**：防御性代码也要能说清"什么输入才会到达这里"；说不清就是幽灵代码。

### 2.3 `weight` 闸门用白名单，`host.ready` 要先放行

- `weight` 闸门用**白名单**（只放行日志 / 通知类），**不要用黑名单** —— 黑名单漏一个就等于放行全部。
- **`host.ready` 是通知不是请求**，**必须先于闸门放行**，否则会被自己的一致性检查误伤（工具刚起来就被拒）。

### 2.4 事件总线：同步投递 + 逐订阅者 try/catch + 退订时序

| 要点 | 规则 |
|---|---|
| 投递方式 | **同步** + **逐订阅者 try/catch**，**绝不向上抛**（一个订阅者炸不能拖垮整条事件链） |
| 订阅句柄 | `Subscribe` 返回 `IDisposable`，调用方负责释放 |
| **退订时序** | **退订必须在 Dispose 宿主之前** —— 否则 `ToolStopped` 会发向**已销毁的托盘图标** |

### 2.5 更新/卸载的失败模式是"静默删多/删少"，且两者都退出 0

**这是最危险的一类**：出错时**退出码依然是 0**，脚本层面完全看不出来。

**对策**：断言**必须落在具体路径上** —— 删完后逐个断言"该在的在 / 该没的没了"，
**不能只看退出码**。（同 MEMORY §四.9：断言要落在数字或退出码上；此处补充 —— **退出码在这里失效**。）

### 2.6 便携包里没有 `src/` 树

**现象**：Core 探测逻辑在便携包环境下**误报"缺 `ezt-core.exe`"** —— 其实它已随 `bin/` 就位。

**原因**：探测假设了仓库布局（有 `src/`），便携包只有 `bin/`。

**对策**：判据须**先查源 `bin/`，再找构建输出**，两者都要覆盖。

### 2.7 `host.notify` 的两态契约

| 宿主形态 | 返回 | 说明 |
|---|---|---|
| 无 UI 宿主 | `delivered: false` | 且**要说明"当前宿主没有 UI"**（不是"未实现"） |
| 托盘宿主 | `delivered: true` | 正常投递 |

**别回恒定值** —— 两态是契约，恒定值等于把契约退化掉，且会让调用方无法区分"没 UI"与"没做"。

### 2.8 `NotifyIcon` 不是 `Control`

- `NotifyIcon` **没有 `Invoke` 方法**（它不是 `Control`）；
- `ShowBalloonTip` **从后台线程直接调并不会抛异常** ⇒ **不要做 UI 线程 marshal**；
- 曾因多此一举的 marshal 导致**死锁 30 秒**。

### 2.9 杂项（三条小坑）

| 症状 | 原因 / 对策 |
|---|---|
| `CS0246`（找不到类型） | XAML 里漏了 `using` |
| 输出串帧 / 协议错乱 | **探针必须写 `--out <文件>`** —— 往 stdout 打会和 JSON-RPC 帧混在一起 |
| `acceptance.sh` 报未定义变量 | 该脚本带 `set -u` ⇒ **内联 Python 断言必须放在 `PY` 变量定义之后** |

### 2.10 script 档「用完即退」在 `IdleRecycle>0` 时退化（已知未改）

**状态**：**已知、未改**。

**理由**：当前产品的配置走不到这个组合，改了也**无法验证**（无验证手段的改动不如不改）。
写在这里是为了**将来真遇到时能立刻对上号**，而不是当成待办去修。

### 2.11 ★★ SDK 的 `_panel_data` 是**死代码** —— 契约写在死代码里等于没写

**发现**：2026-09-23 实施 `input` 节点第 3 步（宿主拉取路径）时，靠**突变验证**查出。

**症状**：把部署好的 SDK 里 `_panel_data`（`TOOL_PANEL_DATA` 分支）改坏 ——
往里塞语法错误、删掉整段转发逻辑 —— **面板照样正常工作**。改**宿主**才红。

**根因**：宿主拉面板数据走的是 **`tool.invoke` + `handler: "panel_data"`**
（见 `ToolHostManager.InvokeHandlerAsync`），**不是** `tool.panel.data` 协议方法。
所以 SDK 里那条 `if method == _p.TOOL_PANEL_DATA: return self._panel_data(params)`
**从未被执行**；真正跑的是 `_invoke(params)` → `fn(params["args"])`。

**为什么差点被骗过去**：
1. 两处注释（`ToolHostManager.PanelDataHandler`、`tool.py::_panel_data`）都**明写**着
   "宿主发来的就是这个 handler 调用，`_dispatch` 里的 `tool.panel.data` 分支处理它" ——
   **注释是错的，而且写得很笃定**，读代码时不会去质疑。
2. 把 `inputs` 转发写进 `_panel_data` 后，测试**照样通过** —— 因为 `inputs` 是宿主拼进
   `args` 的，工具侧从 `args` 读，跟 `_panel_data` 毫无关系。**绿得毫无破绽**。
   （"改死代码测试还全绿"= 断言质量清单 §10.4 那条经典形状。）

**怎么发现的**：做突变验证。**故意把一段代码改坏，看断言会不会红** ——
不红就说明那段代码不在被测路径上（或者断言是假的）。这是唯一能发现这类问题的办法，
因为功能层面一切正常，没有任何运行时信号。

**修法**：
- 两处注释改成事实（"走 `tool.invoke`，`_panel_data` 从未被走到"）。
- 行为契约写进**真正执行的** `_invoke` 的 docstring。
- 保留 `_panel_data` 作为"将来若改成协议方法"的兼容分支，但**明确标注它不生效**。

**通用教训**：
> **契约与验证必须挂在"被走到的那条路"上。**
> 写注释的人读的是代码结构（"有这么个分支"），跑代码的是运行时（"这个分支到不到"）。
> 两者不一致时，**只有突变验证能发现** —— 因为它问的不是"有没有这段代码"，
> 而是"改了它会不会有反应"。

### 2.12 ★★ 验收脚本必须显式传 `--tools-dir`（S11 在 V1.3 复发）

**症状**：`verify-preview.py` 原本不传 `--tools-dir`，于是本机
`%LOCALAPPDATA%\Eztools\tools\` 里那份**陈旧安装**的 `paneltool` 遮蔽了仓库源 ——
新加的面板（`input`）**整条从报告里消失**，且**不报错、退出码正常**。

**判据**：新增面板后，`ezt panel` 列出的面板集合里没有它，但命令成功。
`_step15_w2c.sh` 的"完整期望集"断言会红（这正是它该做的）—— 但若那条断言写得弱
（如只判"⊇ 正例"），就会被静默吞掉。

**修法**：`_step16_preview.sh` 调用 `verify-preview.py` 时显式
`--tools-dir "$TOOLS_DIR_WIN"`。与 S11 同源：**"不传参数"也会把真实依赖藏起来**。

### 2.13 ★★ `PipeOptions.CurrentUserOnly` 在提权进程里静默死亡（2026-09-24 W3-a-3 手工验收①抓到）

**症状**：`ezt core start --elevate` 后 Core 写完 `core.json` 端点就**无声消失**——
无托管异常、无事件日志、无 trace；`\\.\pipe\` 命名空间里管道从未出现；
`core status` 报"已登记但无响应"。非提权同码完全正常。两次复现。

**定位**：死亡点夹在"端点写入"与"管道创建成功"两个 trace 里程碑之间（给
`CoreServer.RunAsync`/`AcceptLoopAsync` 加启动里程碑 trace 后锁定），即
`NamedPipeServerStream` 构造（含 `CurrentUserOnly`）内部原生层死亡。

**修法**：`CoreServer.CreatePipe` 按是否提权分流——非提权保持 `CurrentUserOnly`；
提权用**官方 `NamedPipeServerStreamAcl.Create` + 显式 PipeSecurity**（DACL = 当前用户
FullControl，Owner/Group 齐备，不留空给内核补默认）。纵深不受影响：闸 2
（`ValidateCaller`）在每条连接上仍核对对端 SID + 完整性级别。修后提权 Core 正常
服务（trace 见"管道连接到达"）。**教训：提权路径的进程存活/管道存在必须实测，
"编译过 + 端点写了"不等于"服务活着"。**

### 2.14 ★★ 真实游标是**不透明令牌**，"单调递增"是断言出来的假契约（同日抓到）

**症状**：探针与 `VolumeWorker` 都断言/守卫了"游标严格递增"。真卷（C:）实测：
截断批返回的 cursor = 最后一条记录的**完整 FRN（含高 16 位序列号）**，整批消费返回的
cursor = 系统缓冲区边界值——**两种格式切换时数值合法变小**，守卫 `next <= prev`
直接抛 -32019，真卷枚举会在半路崩溃。

**修法**：① `VolumeWorker` 守卫改为行为判据（未 done 却缺 cursor 或零记录 ⇒ -32019）；
② selftest 断言从"严格递增"改为「透传（下批入参 == 上批出参）+ 推进（出参 != 入参）」；
③ 探针删掉单调断言。**教训：S8 同族——"断言引用不存在的契约"；opaque token 的
数值性质不是契约。** 附：实测内核对 `StartFileReferenceNumber` 起始记录**不重放**，
primitive 的 isReplay 分支不触发（其注释已声明两种语义都成立，保留）。

### 2.15 WorkBuddy/沙箱包装器在命令结束时按进程树回收（同日定位）

**症状**：在本工作环境内启动的 `ezt-core.exe`（无论提权与否）在**单条命令/后台任务
结束的瞬间**静默死亡——任务存活期间 `core status` 正常，任务一结束即"已登记但无响应"。
用户自己终端里启动的进程不受影响。

**对策**：Core 生命周期验证（启动 → 服务 → 探针）必须放进**同一条命令**内完成，
或由用户在自己终端执行。凡"上一条命令起的服务、这一条命令来验"的流程在本环境
不可靠。

### 2.16 ★ M7 低完整性对抗测试的四连坑（2026-09-24 用户手跑实测）

> 起因：待决清单 C6 的 M7 在真实机器上首跑，一个"现成命令"连续撞出四个环境/文档坑。
> 全部已实测并绕行；**M7 安全目标（低完整性进程无法使用 Core）最终实测达成**。

| # | 坑 | 实测证据 | 对策 |
|---|---|---|---|
| ① | **Win11 25H2 `runas /trustlevel` 机制性失效**：报 `1168: 找不到元素` | seclogon 服务在跑（demand 且已启动），连裸 `runas /trustlevel:0x2000 cmd` 也 1168 | 别再用 runas /trustlevel；用降级令牌启动器（`scripts/launch-lowil.ps1`） |
| ② | **PsExec 2.43 `-low` 不降级**：进程照常 High | psexec -low cmd /c whoami → `Mandatory Label\High Mandatory Level (S-1-16-12288)` | 同上，自写 Add-Type 启动器（DuplicateTokenEx + SetTokenInformation(TokenIntegrityLevel) + CreateProcessWithTokenW） |
| ③ | **低完整性默认 no-write-up**：输出重定向到 Medium/High 标签目录**静默失败**（无文件、无报错） | psexec/首两轮 Add-Type 均"进程 OK 但输出文件不存在" | 输出目录先 `icacls <dir> /setintegritylevel L`；注意 `Remove-Item` 会连标签一起删，复测要重建重打 |
| ④ | **P/Invoke 调 W 结尾 API 必须 `CharSet = CharSet.Unicode`**（默认 Ansi） | `ConvertStringSidToSidW` 收到 ANSI 乱码 ⇒ `err=1337`（无效 SID） | DllImport 逐个核对 CharSet，别依赖默认值 |

**另两个连带发现**：

- **手册 M7 原预期 `[-32016]` 是未实测的假设（S8 同族）**。实测拒点在 **OS 层 MIC**：
  命名管道继承创建者完整性标签（提权 Core = High），低完整性客户端 open-for-write
  被 no-write-up 拒于 connect 之前，**代码级身份闸根本收不到连接**。
  差分证据：低完整性进程跑 `ezt core status`（纯文件读取）正常 ⇒ 拒点在管道 open。
  `-32016` 保留为纵深防御兜底（OS 层万一放行时才可达）。**实测现象 = `[错误] Access to the path is denied.`**
- **cmd 复合命令里 `%errorlevel%` 在整行解析时展开**：`cmd /c "a && b & echo %errorlevel%"`
  打出的是解析时的旧值（恒 0），不是 b 的退出码。要真值用 `!errorlevel!`（需
  `setlocal enabledelayedexpansion`）或拆成两条 cmd。

### 2.17 ★★ W3-b 性能与打分用例的四连坑（2026-09-24，selftest 排障实测）

> 起因：W3-b-1 验收①"100 万条 P95 ≤ 20 ms"在 Release 反复红（59~69 ms），旁路实验
> 定位 + 三轮夹具返工后才全绿。四条都值得下次写性能/打分用例前先读一遍。

| # | 坑 | 实测证据 | 对策 |
|---|---|---|---|

### 2.22 ★★★ 缺口①②③ 落地时抓到的三坑（2026-09-25，失败卷结构化 + 暂停三入口 + 自喂取证）

| # | 坑 | 症状 | 对策 / 教训 |
|---|---|---|---|
| ① | ★★★ **突变"以崩溃呈现"而不是"以 FAIL 呈现"** | 施加 **M-F1**（失败卷不落结构）后，selftest **不是报出一条 FAIL，而是整条命令 rc=3 + `Index was out of range`** —— 用例 31.2 的**明细插值**里写了 `$"…code={failedArr?[0]?["code"]}…"`；断言本体有 `failedArr?.Count == 1 &&` 短路保护，**但明细串是第三个实参、无条件求值**，空数组时当场抛 | **明细取值必须与断言同样抗空**：`failedArr is { Count: > 0 } fa ? fa[0]?["code"] : "-"`。**教训**：`?[0]` 不是空安全 —— `?` 只挡住 null 宿主，挡不住**空集合**。这与"突变必须以 FAIL 呈现"是同一纪律：**被测没红、测试先炸，等于这次突变白跑**（还会让人误以为代码有编译/运行时缺陷）。同类写法在 `SelfTestCommand.cs` 的 `skippedArr[0]` / `vols[0]` 处**有短路保护**（在 `&&` 链里），只有明细串是裸的 |

> ③是**标签**不严（把负数叫 Win32）。三者都不会让测试变红，只会在某一天让排查者走错方向。

### 2.28 ★★ 首个带原生资产的 NuGet 包打穿部署盲区 —— `runtimes/` 平铺拷贝缺席 + FTS5 语义坑（2026-09-26，W5-a 实测）

**坑 A（部署链）**：Microsoft.Data.Sqlite 是本项目**第一个携带原生库的 NuGet 包**
（`e_sqlite3.dll` 在 `runtimes/win-x64/native/`）。此前全部依赖纯托管 / GDI+ 走系统，
两处"只拷顶层"的部署路径从未暴露：
- `acceptance.sh` 铺 `$DEPLOY/bin` 用 `cp *.dll *.json` 平铺 → `runtimes/` 缺席 →
  已安装形态 selftest 崩 `SqliteConnection type initializer`（**S11 同族：缺席无信号**，
  错误表象在类型初始化，根因在文件缺席，相隔极远）。
- 修复：`cp -R "$BINDIR/runtimes" "$DEPLOY/bin/"`。`make-portable.sh` 用 `cp -r` 全量
  发布物，天然无此问题。
- **判据**：新增任何 NuGet 包前先问"带不带 `runtimes/` 原生资产"，带则所有"平铺拷贝
  bin"的路径（脚本、安装器、便携打包）都要过一遍。

**坑 B（FTS5 trigram 语义，两处反直觉）**：
1. **查询 <3 字符是硬盲区**——trigram 分词下两字中文词 MATCH 不到任何 token，
   不是"结果差"而是**结构性查不到** ⇒ 搜索层必须双路（≥3 走 FTS / <3 走 LIKE），
   且这是设计契约不是优化（selftest 三档断言锁死）。
2. **MATCH 子查询要整体引号包裹**（内部 `"` 双写），否则用户输入的空格/括号/引号
   会被当 FTS 语法解析（注入面 + 误报语法错）。

**坑 C（SQLite 事务对象传染）**：Microsoft.Data.Sqlite 的 `SqliteTransaction` 要求
**每个命令显式 `cmd.Transaction = tx`**——事务内混用未关联命令，行为不可靠（实测
事务内 COUNT/DELETE 静默不生效）。别给每个助手加 tx 参数（传染签名），直接用原生
`BEGIN IMMEDIATE` / `COMMIT` / `ROLLBACK` 三条语句：同连接上天然在事务内，零传染。

### 2.29 ★★★ 键盘终局：TSF 直写与 LL 钩子 —— "KEY 无 CHAR 有"镜像形态与供字者唯一化（2026-09-27，W5-b 面板三轮实测）

> ⚠️ **本节结论已被 §2.30 部分推翻（同日，换实现之后）**：这里第 1 条把"字母 WM_KEYDOWN 到不了窗口"
> 判为**环境级变化**，但换到原生 EDIT 后同一台机器上注入字母与 Enter **都正常到达**
> （`vkAfterLetter=65` / `vkAfterEnter=13`，Enter 还真驱动了打开动作）。也就是说，
> "某层死了"的观测是在**我们自己那套干预（合成层 + WPF TSF 文本栈）的污染下**取得的。
> 第 6 条"供字者唯一化"依然成立，但终局形态是**让系统成为唯一供字者**（原生 EDIT + 系统 IME），
> 而不是自建任一供字源。详见 §2.30。

**§2.26 修复在两天后失效的完整复盘**（自动化注入 + 四版迭代 + TEXTCH/FILTER 侦察定位）：

1. **形态镜像**：§2.26 当年 = "KEY 有 CHAR 无"（合成层有效前提）；两天后实机 = **"KEY 无 CHAR 有"**——字母 WM_KEYDOWN 在到达窗口**之前**就被 TSF/输入法层吃掉（对照实验：搜索窗同形态，证明是**环境级变化**非代码回归）。合成层（挂在 PreviewKeyDown）前提塌了，两个窗一起失效。**教训：移植修复方案时，其环境前提必须重新论证（§2.23① 同族）；环境级失效要用对照实验（双窗对比）区分"代码回归"与"环境变化"。**
2. **TSF TextStore 直写**（意外发现的主供字源）：`ImmSetOpenStatus(false)` 后，微软拼音英文模式的键盘 sink **绕过全部窗口消息与 WPF 事件**（KEY/CHAR/HOOK 全零）直接改写 TextBox 文本缓冲，每键先到 ~20ms、字符正确。它是有效的——**但与任何其它供字源并存即双份**。
3. **SetOpenStatus 陷阱**：① 管不住 TSF（open=false 后直写仍发生）；② **true→false 转换瞬间会 flush 已攒的组合串**（与轮询合成竞态双打）；③ open=false 时 ChsIME **吞键不透传**（TSF-only 版零输入的根因）。
4. **composition 批量 TextInput 放行是幻觉**：放行的 composition 更新**不进 TextBox**（QUERY 行证实）——它只是通知，不是数据。
5. **终局方案 = WH_KEYBOARD_LL 供字**（面板可见期间挂钩）：
   - 打字键（字母/数字/空格/符号/Backspace，无 Ctrl/Alt）→ **钩子内吃掉（返回 1）**——IME/TSF/消息层统统见不到，组合永不形成 → 字符由钩子回调投递 UI 线程插入；
   - 其余键（Enter/Esc/方向/Del/Ctrl 组合/Shift）放行走既有消息层+轮询兜底；
   - 钩子跟随 IsVisibleChanged（可见挂/隐藏摘，Esc 收窗后已验证摘除）；
   - **代价**：面板内字母被吃 = **打不了中文**（中文搜索走 `ezt clip search`；面板内中/英模式切换钮 = W5-d 候选）。
6. **供字者唯一化原则**（本轮最高优先级教训）：KEY 合成层、轮询打字、TSF 直写、CHAR 放行——**任何时刻只允许一个供字者**。双打的本质永远是"两个供字者并存"，无论它们各自多正确。
7. **轮询沿检测的被动期同步**：打字/沿检测的 pressed 集在"跳过期"（comp 抖动/KEY 活）**不能 Clear**（还按着的键被重判新沿 → 双打），要**按 MSB 同步**（抬起的移除、按下的保留）。

**自动化测试基建（本轮沉淀，键盘类问题必用）**：python ctypes `keybd_event` 真键注入（热键+逐键打字）+ 面板诊断日志（SUMMON hwnd/STATE/KEY/CHAR/TEXTCH/FILTER/POLL 行）+ FILTER 断言行（query 原文+items）。对照实验：同一注入打搜索窗 vs 面板，读各自日志区分环境/代码。

### 2.30 ★★★ 键盘链的终局是"换实现"而不是"再加一层" —— WPF TextBox → 宿主化原生 EDIT（2026-09-27，搜索窗 + 面板双窗换实现实测）

**用户决策**：不再打补丁，直接换输入框实现。评估过四条候选（RichTextBox / 原生 EDIT / WebView2 / 手接 IMM）后确认：
**换控件本身救不了"字符到不了"——所有失效点都在字符进入控件之前**；唯一实质不同的实现路径是把输入
**从 WPF/TSF 挪回 IMM32**（宿主化原生 EDIT）。于是两个窗口的输入框统一换成 `NativeInputBox`
（`WindowsFormsHost` + 原生 `EDIT`），并**连根删掉四层干预**：直通字符合成层、15ms `GetAsyncKeyState`
轮询、hwnd 消息钩子、`PreviewTextInput` 拦截（面板另有 LL 钩子）。分工归位为一句话：
**文本编辑归原生控件，命令键由它上报**。

| ④ | ★★ **焦点判据的层错了会给假绿** | `IsKeyboardFocusWithin`（WPF 层）在"WPF 说焦点在这、系统说不在"的分裂态下返回 true | 断言判据换成 **`GetFocus()==EDIT.hwnd`**（系统层，唯一真的能打进字的那个）；`ImmAssociateContextEx` 的目标也从 WPF 主窗改为 EDIT 的 hwnd（**WPF 是 TSF 窗口，`ImmGetContext` 恒 NULL，挂上去等于空转**） |
| ⑤ | ★★ **结构约束断言用朴素子串匹配会被注释误红** | 新加的反向断言（"干预符号不得复活"）当场被**自己的解释性注释**打红：`['SynthesizeDirectChar','PreviewKeyDown','GetAsyncKeyState']` 全是注释里提到的 | 断言先**剥注释行**再匹配。误红（注释提一句就失败）与误绿（代码删了、注释还在就假通过）都让断言失去可信度 —— **比不守更坏** |
| ⑥ | ★★★ **用"注入的负结果"给技术路线判死刑是本次最大的误判** | 换实现前那条"判决实验"（`WinFormsTypingProbe`：WinForms EDIT + `keybd_event` 注入 → `text=""`）曾据此把面板转成"免打字列表"。但它同时踩了三坑：探针进程抢不到前台（§2.26⑦）· `DoEvents` 在"无主窗 WinForms 线程 + 后台启动"上下文不喂键盘消息（§2.27⑤）· 只测了注入未测真实输入 | `text=""` 只能证明"**注入的键没进去**"，**不能证明"原生 EDIT 收不到真实按键"**。任何"某方案不行"的判决实验，必须先自证"刺激真的送达了"（对照实验 + 活性验证），否则结论无效 |

**自动化验收面的同步改造**（换实现不是"删代码"，是"换断言"）：
- 探针恢复/新增读数：`ProbeQueryFocused`（Win32 语义）、`ProbeLastHookVk`（改读原生控件）、`ProbeHwnd`（改指 EDIT）、
  面板新增 `paste` 契约段（打字过滤 → Enter → 断言隐藏 + 剪贴板逐字相等）。
- `--probe-clip-panel` 的注入姿势明确分两条并落盘 `resolvedBy`：① `keybd_event` 真键（与用户路径同源，**探针常常抢不到前台 ⇒ 结果只记录不断言**）；② `PostMessage` 直投 EDIT 句柄（不依赖前台，探针上下文的可靠姿势）。实测本次走的是 **`realKey`**，即真键注入直接生效。
- `verify-desktop.py` 的 SearchWindow 结构约束改为**正反双向**：正向要求原生输入框命令链三符号在；反向要求七件旧干预符号不在（剥注释后匹配）。
- 数字：桌面验收 **149 PASS / 0 FAIL**（原 148/1，失败项即上面第 ⑤ 条的误红）。

> **一句话教训**：**"键盘有问题"的第一反应应该是拆干预、并让系统成为唯一供字者**，而不是再加一层。
> §2.29⑥ 说"供字者唯一"，本节把它推到终局 —— **唯一供字者就是系统本身**（原生 EDIT + 系统 IME）。
> 所有"某层死了"的观测，都要先问：**这是在什么干预态下测的？**

### 2.31 ★★ "测试全绿/结论矛盾"先查你跑的是哪个二进制 —— 多 TFM 残留目录（2026-09-27，换实现自查时实测）

**现象**：新加的 2 条 selftest 用例死活不出现在结果里（自检 184，而不是预期的 202），
且"剪贴板历史库（W5-a）"整段连**段落标题都不打印** —— 看起来像"用例被静默跳过"，
排查方向一度指向异常吞掉 / 条件分支。

**真相**：`Cli` 项目有**两个** TFM 输出目录：
- `src/Eztools.Cli/bin/Debug/net10.0-windows10.0.19041.0/`（**现行**，acceptance 用的就是这个 —— `TFM="${EZTOOLS_TFM:-net10.0-windows10.0.19041.0}"`）；
- `src/Eztools.Cli/bin/Debug/net10.0/`（**2026-09-25 的残留死产物**，我却一直在跑它）。

那份旧二进制里当然没有今天的新用例，也没有……不，它连 W5-a 那段都没有 —— 于是"段落标题不打印"
就有了平凡解释：**我读的是一份不含该代码的旧构建**。换正确二进制后立刻是 **202/0**。

| # | 坑 | 教训 |
|---|---|---|
| ① | **手测/自查的二进制 ≠ 验收脚本的二进制** | 同一天已经踩过第三次（Desktop 的 `net10.0-windows\` 死目录两次、Cli 的 `net10.0\` 一次）。**动手排查前先 `ls -la --time-style` 看时间戳，并确认验收脚本里的 `$TFM`** —— 这比读代码快得多 |
| ② | **TFM 升级后旧目录不会自动消失** | `bin/` 下的旧 TFM 目录是**死产物**：目录名合法、exe 能跑、但代码是旧的。症状永远是"功能像没做/用例像没加"，极易误判成逻辑 bug |
| ③ | **"结论矛盾"是最强的线索** | acceptance 说 200、我手跑说 184 —— 两个数字不可能同时为真。**当两个观测面互相矛盾时，先怀疑"它们看的不是同一个东西"**，而不是去解释某一方为什么错 |

> **对策**：① 只认现行 TFM 路径（Desktop/CLI 各一条，见手工清单 §0 的警示块）；
> ② 每轮换实现/大改后，先跑一次"数字对得上"的哨兵（如 selftest 用例数），
> 再信任后续结论；③ 有条件时把旧 TFM 目录**删掉**（死产物留着只会误导）。

### 2.32 ★★★ "UIPI 读不到提权进程的剪贴板"是个**错误前提** —— 受信格式被白名单放行（2026-09-28，W5-d §D3 手工验收排障实测）

**现象**：管理员权限的记事本复制 `UIPI-TEST-9955` → 唤出剪贴板面板，出现的是**真实文字**
（`文本 · Notepad.exe · 17:11`），**没有占位条目、没有气泡**；托盘日志只有一行普通捕获：

```
17:11:09 INF [clip] 剪贴板已捕获：Text（来源 Notepad.exe，会话累计 1）
```

面板里内容读到了 ⇒ 代码里 `OwnerElevated && Text is null && …` 的占位判据不成立 ⇒ 不进占位分支。
第一反应是"记事本没真提权" —— **错。真相是设计前提本身错了。**

**真相（官方文档 + 本机注册表双证）**：UIPI 对剪贴板是**部分隔离**，不是全隔离：

> `GetClipboardData` / `EnumClipboardFormats` 只在「跨完整性级别 **且** 拿的是**非受信格式**」时被拦。
> 标准格式有白名单，允许跨 IL band —— 列表存在
> `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System\UIPI\Clipboard\ExceptionFormats`。

本机实测该注册表（2026-09-28）：

| 格式 | 值 |
|---|---|
| `CF_TEXT` | 1 |
| `CF_BITMAP` | 2 |
| `CF_OEMTEXT` | 7 |
| `CF_DIB` | 8 |
| `CF_PALETTE` | 9 |
| `CF_UNICODETEXT` | 13 |
| `CF_DIBV5` | 17 |

记事本 Ctrl+C 写的就是 `CF_UNICODETEXT(13)` ⇒ **被放行** ⇒ 普通权限托盘读得到 ⇒ **永远不触发占位**。
（这意味着 §D3 用"记事本 + 提权"验占位是**结构性验不出**，与功能好坏无关。）

| # | 坑 | 教训 |
|---|---|---|
| ① | **绝对化措辞的安全模型**："非提权进程读不到提权进程写入的剪贴板"（原设计 R1 原文）听着合理，实际只对**非受信格式**成立 | 安全模型要按**官方文档 + 本机注册表**核对到"什么条件成立"，不能停在"听起来对"。**绝对化的前提一定会被现实打脸** |
| ② | **拿受信格式验非受信分支** | 验一个分支前先问：**我这一路的输入，真的能走到那个分支吗？** 走不到就是"结构性验不出"，继续调环境是浪费时间 |
| ③ | **`echo X \| clip` 的 owner 是 NULL**（`clip.exe` 无窗口，`OpenClipboard(NULL)` ⇒ `GetClipboardOwner()` 为空） | 日志里"来源 `?`"= 判据所需的第一手信息（owner）压根不存在。**这不是"提权复制场景"，是"无 owner 场景"** —— 连 UIPI 判据的门都进不去 |
| ④ | **沙箱内进程枚举恒为 0**：Bash/PowerShell 工具里 `CreateToolhelp32Snapshot` / `tasklist` / `wmic` 全返回空（实测可见进程总数 = 0，连自己都列不出） | **"看不见"≠"不存在"**。当观测面本身是死的时候，一切"未运行/无进程"的读数都不可信（同 §2.27 "hook 计数恒 0 = 观测面是死的"）。判进程内外部事实要靠**让被测程序自己说话**（日志 / 探针 / 注册表） |
| ⑤ | **三次连续误判**（记事本没提权 → 黑名单拦了 → 该用管理员有窗口程序）每次都能自圆其说 | 自圆其说的解释不是证据。**要设计能证伪的对照实验**（见下），而不是继续换姿势重试 |

**对策（D3 的可复现触发法）**：
- 触发条件必须凑齐三件事：**owner 有窗口** + **owner 提权** + **内容只以非受信格式存在**。
- 工具：`_scratch/manual/clip_uipi_trigger.py [text|custom] [保持秒数]` —— 自建隐藏窗口当 owner，
  `custom` 模式用 `RegisterClipboardFormatW` 写非受信格式（提权运行 ⇒ 触发占位）；
  `text` 模式写 `CF_UNICODETEXT`（**A/B 对照**，必须被正常捕获、**不得**记占位）。
  脚本会自己打印 `提权=ELEVATED/NOT_ELEVATED`，顺手解决"记事本到底提权没有"这个判不了的问题。
- 已实跑的对照（非提权写入，2026-09-28）：`text` → 正常入库（ID 99）；`custom` → 日志无新行、搜索 0 条
  ⇒ 证明"非提权 + 非受信格式"走的是**静默丢弃**（判据里的 `OwnerElevated` 门是有效门）。
- 辅助探针：`_scratch/manual/elev_probe.py`（枚举指定进程提权位）/ `session_probe.py`（会话可见性）。
- **产品级推论（需拍板）**：既然受信格式跨 IL 可读，原设计"提权内容天然不入库"的隐私效果
  对文本/图片**并不存在**——管理员窗口复制的文本会正常入库。若要"提权内容一律不收"，
  判据必须从 `OwnerElevated && 内容全空` 改成 `OwnerElevated ⇒ 占位/跳过`（一行改动），
  这属于**策略选择**，不能靠 UIPI 白送。

> **一句话教训**：**"读不到"是个可证伪的断言 —— 先把它拆成"什么格式、什么 IL band、谁做 owner"三要素再去验**。
> 把安全模型的措辞写绝对了，验收清单就会跟着写出一条**永远无法通过**（或永远"通过"）的用例。
