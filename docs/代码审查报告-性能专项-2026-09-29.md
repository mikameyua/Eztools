## 一、★ RI-10 定性收口：线程句柄"增长"是 GC 有界锯齿，**不是泄漏**（🔴 → 💭 降级）

### 1.1 起疑与两次误判

RI-10 由安全面专项审第四轮在测 RI-6 时顺带发现：每轮 `handles.enumerate` 创建 2×workerCount 个线程，
Core 句柄数 **~+60/轮线性增长**（当时 0 stall 也在漏，且随 worker 数线性缩放 1→+7 / 4→+25 / 8→+49）。
当时定性为"新建线程 ⇒ 句柄泄漏"，修法候选 = 池化 / 可丢弃子进程，挂了台账。

**本次审查第一步先做定性实验**（`_scratch/perf/threadprobe`，独立于 Core）：同样的"每轮 8 线程即退"模式，

```
基线 217 → 6 轮后 364（+147）→ GC.Collect → 244（回落 120）
再 6 轮 → 388 → GC → 268
```

⇒ **`GC.Collect` 后句柄立即回落** —— 是 **GC 滞后**：托管 `Thread` 对象的 OS 句柄由终结器释放，
不是真泄漏。

### 1.2 真实 Core 验证（连续 15 轮，有界锯齿）

```
call 1-7:  435 → 494 → 554 → 615 → 673 → 733 → 785   （爬升 ~+58/轮）
call 8:    494                                          ← GC 在扫描的大分配压力下自然触发
call 9-14: 554 → 612 → 670 → 728 → 786 → 844           （再爬升）
call 15:   386                                          ← GC 又触发
静置 30s:  375                                          （回到基线区，基线 273）
```

耗时全程稳定 **1.5~1.7 s**（首跑 6.5 s 含 JIT 预热）。低点始终在基线区 ⇒ **有界**。

### 1.3 处置与教训

| 项 | 结论 |
|---|---|
| **处置** | **不修代码**。句柄数由 GC 周期自然回收，池化反而会被挂起线程污染（挂住的线程无法复用）；可丢弃子进程是给"泄漏副本"（另一个问题）准备的，不是给它 |
| **钉住** | `HandlePrimitives` 类注释已加 RI-10 定性段（含"别再据此改池化"的明确警示） |
| **教训 ①** | "**等了 12 秒没回落 = 真泄漏**"的推断是错的 —— 静置无分配压力，GC 根本不会跑。判别真泄漏/滞后的唯一办法是 **`GC.Collect` 对照**（或看锯齿） |
| **教训 ②** | 上一轮把 RI-10 定性为"真泄漏"时**没做 GC 对照实验** —— 与规范 §3.7"判据先行"同族。本报告已用实验补上 |

## 二、动态基线（非提权 Core，连续调用看斜率）

测量方法：同一 Core（pid 固定），首跑弃用（JIT 预热），每轮记 CLI 墙钟 + Core 进程句柄数 + 工作集。
外部测量器用 `GetProcessHandleCount` + `K32GetProcessMemoryInfo`（P/Invoke，见规范 §3.7
"泄漏类问题必须能自测量"）。

| 原语/命令 | 墙钟/轮 | 句柄斜率 | 工作集 | 判定 |
|---|---|---|---|---|
| `process.enumerate` ×8 | 1495~1525 ms（平稳） | 291→291（0，GC 锯齿内） | 42.9→46.1 MB 后持平 | ✅ 干净 |
| `volume.enumerate` ×8 | 691~764 ms（平稳） | 294→303（**+1.1/轮**） | 48 MB 持平 | ✅（+1/轮在 GC 锯齿量级，见 💭-1） |
| `handles.enumerate`（RI-6 修后） | 1.5~1.7 s | 锯齿有界（§一） | — | ✅（§一） |
| `filehash.hashMany`（57.6 MB） | 墙 1.03~1.14 s / 工具 290~368 ms | — | — | ✅ **~190 MB/s**（SHA-256 单线程合理值） |
| `wordcount.countFile`（57.6 MB） | 墙 3.7 s / 工具 ~2.9 s | — | — | 💭-2：**~20 MB/s**（Python 逐字符统计） |

> 测量事故留痕：第一轮 wordcount 误用 `wordcount.count --file` —— 那是**剪贴板文本版**（收 `text`
> 参数），报"缺少参数 text"。**工具的"计数版/文件版"命令对（`count` / `countFile`）参数不同**，
> 测吞吐前要先对契约（同 §3.1：先读清单再调）。

## 三、💭 提示项（4 条，均不阻塞）

| # | 项 | 数字 | 说明 |
|---|---|---|---|
| 💭-1 | `volume.enumerate` 句柄 +1/轮 | 8 轮 +9 | GC 锯齿量级（§一已证明这类增长可回收）。留观，不修 |

| 💭-3 | **CLI 固定开销 ~570 ms** | `ezt --version` = 566 ms | 纯 apphost 启动底噪（框架依赖 + 沙箱环境）。**所有**小命令的墙钟都被它主导（`core ping` 585 ms、`list` 709 ms）。对交互 UX 有感的命令（托盘唤出后的第一条）值得将来评估：ReadyToRun/Trimming 或常驻 CLI。**现在不动**（测量即可，无功能影响） |

## 四、静态热路径审查（2 个最热循环）

| 位置 | 结论 |
|---|---|
| `VolumePrimitives.ReadMft` 主循环（:106-159） | ✅ **健康**：① 64 KB 输出缓冲区**循环外分配一次**、`fixed` 复用（不是每批新建）；② 游标零推进守卫（:154）防死循环；③ `HighUsn = long.MaxValue` 的坑有注释钉住；④ 句柄 try/finally（安全面已审） |
| `Index/VolumeWorker` 批消费循环（:120-193） | ✅ **健康**：① `MaxBatches` 防御上限 + `ct` 贯穿；② 游标**不透明令牌**语义有注释（数值单调比较被真卷实测否掉的历史在案）；③ 重放消化 / FRN 复用更新 / 不可达兜底三分支显式；④ 每记录 `store.TryAdd` 是字典操作，无 O(n²) |

👍 顺带记录 3 条已做对的事：① `handles.enumerate` 修后耗时 15 轮全稳（1.5~1.7 s）；② 两个热循环的
