## 1. 缺口 ①：暂停索引没有用户入口

### 1.1 先说清这不是"加个开关"

协议侧 `search.pauseIndexing` / `search.resumeIndexing` 早就通了（selftest 26.5 钉住，含幂等与
`status.indexing.paused` 同步）。缺的只是入口。但**入口不是纯 UX 加法**：

> ⚠️ **暂停之后，索引不再跟进 ⇒ 搜索结果会静默变旧。** 沉默的"暂停"与
> W3-e-2 禁止的"静默过滤"（S9′）是同一族缺陷：用户看到的结果是**过时的**，而界面什么都没说。
> **所以"暂停必须可见"是硬要求，不是可选项。**

### 1.2 三种入口 + 两种不推荐

| 方案 | 内容 | 优点 | 代价 | 判定 |
|---|---|---|---|---|

## 2. 缺口 ②：枚举失败的卷只有自由文本

### 2.1 现状与危害

`IndexBootstrap` 把失败拼进 `List<string> errors` → `service.LastError` 用「；」join。
后果是**守恒式被绕过**：真机实测无提权时 `volumes=0 + skippedVolumes=0`，而检测到 **2** 个卷
——`0 + 0 ≠ 2`，但**没有任何断言会红**，因为失败信息是自由文本。

> 这不是"缺个字段"，是**同一族缺陷的第三种形态**：
> W3-e-2 治好了"静默过滤"（skipped），这里漏了"尝试后失败"（failed）。

### 2.2 三种补法

| 方案 | 内容 | 优点 | 缺点 | 判定 |
|---|---|---|---|---|
| **A 结构化 `failedVolumes`** | 协议加 `failedVolumes: [{volume, code, message}]` + `detectedVolumes`；`lastError` 保留为人类摘要 | 可机读；**`indexed + skipped + failed == detected` 可断言**；UI 可给精确文案 | 协议加字段（**加法扩展**，与 `skippedVolumes` 同款先例，兼容） | ✅ **推荐** |
| B 塞进 `skippedVolumes` + 新 reason | 零新字段 | — | **语义混浊**：`skipped` = **从没试过**，`failed` = **试了没成**。合并后"是配置问题还是环境问题"永远分不开 | ❌ |
| C 只改文案 | 最小 | — | 还是不可机读 ⇒ 本次缺口原样 | ❌ |

### 2.3 关键设计：两族状态，不要合并

```
VolumeClassifier.SkipReason   （预扫描决定，从未尝试）
  NotFixed / NotReady / NoDriveLetter / UnsupportedFileSystem

VolumeFailure.FailureKind     （尝试后失败，新增）
  AccessDenied(5) / NotReady(21) / DeviceNotConnected(1167) /
  UnrecognizedVolume(1005) / InvalidDrive(12) / JournalNotActive(1179) / Other(code)
```

Win32 码 → 文案（`ReasonText` 同风格）：
`5 访问被拒绝（需要管理员权限）` / `21 卷未就绪` / `1167 设备未连接` /
`1005 无法识别的文件系统（卷可能受损或未格式化）` / `12 驱动器号无效` / `1179 卷未启用变更日志` / 其它**原码透传**（不吞）。

## 3. 缺口 ③："自喂回路"成因未分离

### 3.1 先纠正一个容易走错的方向（重要）

**不要把"排除安装根"当成解法。** 追不平的根因**不是"我们索引了自己"**，而是：

> **我们自己的日志/审计写入，发生在正被 tail 的那个卷上 ⇒ 每次 `readUsn` 都带回我们自己刚写的新记录。**

即便把 `…\install` 从**索引结果**里排除，那几行日志**照样进 journal**，`Drain` 照样读到新记录。
所以「排除」只能治"搜索结果里有噪音"，**治不了追不平**。

**而且追不平已经不再是紧急问题**：目标点收敛（主出口，到自举开始时的 journal 尾就停）
+ 无进展保护 + 有界上限（200k 批 / 10 s）⇒ 最坏情况 10 s 内**给出原因并降级**，不再无限空转。
所以 ③ 现在是**取证题**，不是止血题。

### 3.2 四种取证手段

| 方案 | 内容 | 优点 | 代价 | 判定 |
|---|---|---|---|---|
| **A `Drain` 来源诊断（常驻）** | 失败时输出被应用记录的 **Top-N 文件名 + 归属判定**（是否落在 `DataRoot` 下） | 一击定音；**任何用户环境自证**（符合本项目"诊断做常驻能力"纪律，W3-b 教训④）；可断言 | 小改代码 + 一条 selftest | ✅ **推荐（主）** |
| **B 安装根搬卷对照** | `ezt core start --elevate --install-root C:/ezt-root`，把 `.ezidx` 复制过去，再 `--volumes D:` | 零代码、5 分钟；直接分离"安装根是否元凶" | 需 UAC；只回答"是不是安装根"，不回答"是不是别的进程" | ✅ **推荐（对照）** |
| C `fsutil usn readjournal D: csv` 现场抓 | 提权窗口跑，`findstr` 过滤时间窗内的文件名 | 零代码；看全量 | 需 UAC；只能看"谁在写"，**证明不了是不是我们的 Drain 触发的** | ⏸ 备选 |
| D ETW `Microsoft-Windows-Kernel-File` | `FileIoWrite` 事件 + `ProcessId` | 精确到进程 | 需管理员 + ETW 会话管理 + **.NET 无原生封装**（要引 `Microsoft.Diagnostics.Tracing.TraceEvent`），且 Direct I/O / 内存映射会绕过该提供程序 | ❌ 过重，只为回答一个是非题 |

### 3.3 方案 A 的设计

```
DrainResult 增加：
    IReadOnlyList<RecordSource> TopSources   // (Name, Hits, UnderDataRoot)
    bool SelfInflicted                       // Top-N 全部/多数落在 DataRoot 下
```

诊断输出示例（`StoppedBecause` 之后另起一行，不塞进错误消息）：

```
[ezt-index] 追不平（18432 批 / 10001 ms）——记录来源 Top5：
              logs/audit-20260925.log ×15233（本安装根）、
              index/vol-000000007C153E60.ezidx ×3941（本安装根）、
              其它 ×77  ⇒ 判定：自喂（SelfInflicted=true）
```

**为什么放在 `DrainResult` 而不是日志**：可被 selftest 断言 ⇒ 突变能红（否则又是一条"看起来在守"的断言）。

### 3.5 无论取证结果如何，都要落的一条结论

| 结论 | 说明 |
|---|---|
| **安装根不要放在被索引的卷上** | 只要日志落在被 tail 的卷上，`Drain` 就必然读到自己的记录。有界化让它**可降级**，但每次自举多花最多 10 s 是不必要的 |
| **更好的方向：诊断日志不落被索引卷** | 审计日志改为**内存环形缓冲**（崩溃可接受丢失）或强制落系统盘。这是**拍板项**，见 §4 |

> ⚠️ 注意边界：这两条是**运维建议 / 二期设计**，不是"当前有 bug"。当前行为已经**可见且可降级**。

### 4.1 ⚠️ P4 更正：原推荐 (b) 撤回，改判 (a) 不做 ⛔ **本节结论已被 §4.1.1 推翻**（保留为推理链的一环）

**为什么撤回**（拍板后核代码时的发现，不是口味问题）：

1. **正确的"排除"必须在扫描期做**，而扫描期拿不到路径。
   `QueryEngine` 的扫描段只持有 `(Key, Frn, Store, Pos)`，路径是**收敛到 ≤ K 个候选之后**才回溯的
   （`QueryResult.Hits[].Path` 那时才有值）。要"不把安装根的命中算进 `Total`"，就得在扫描期判定
   归属 ⇒ 每个候选走一次父链。
2. **而"扫描期走父链"正是设计方案 §5.2 标为 🔴 不可接受的做法**
   （原文：`每候选走父链 = 百万次二分，🔴 不可接受`，§5.5 已登记为"路径深度不参与扫描期打分"）。
   P4(b) 的正确形态与该既有架构决策**正面冲突**。
3. **廉价的近似做法会跨过 S9′ 红线**：
   - 按**文件名**排除（复用 `CollectOwnNames`）—— `core.json` / `audit-*.log` 这类名字在别处撞车
     就会让**用户的真文件从搜索里消失**，且无任何提示 ⇒ 正是 W3-e-2 禁止的"静默过滤"。
   - 只在 **Top-K 之后**按 `Path` 前缀过滤（命中对象里已有 Path，成本≈0）——返回条数会少几条而
     `Total` 不变，出现"共 N 条但翻不到"的不一致；要修就得把 `Total` 也在扫描期扣，回到第 1 条。
4. **收益本就是化妆级的**：落到被索引卷上的自有文件只有 `core.json` / `vol-*.ezidx` /
   `logs/audit-*.log` 几个，用户搜到它们的概率与困扰都极低。

**结论**：P4(a) 不做，登记为**已知设计边界**（不是缺陷）。真要做得先改 §5.2 那条 🔴 决策
（例如引入"扫描期可用的路径前缀位图"），那是**独立一期**，需要单独设计。
**与追不平无关**这一点不变（§3.1）：排除只影响搜索结果，`Drain` 照样读到我们自己的写入。

#### 4.2.1 ⚠️ 二次核对（2026-09-25）：上面那个 200 ms 也**不能直接抄**，且发现第三个互相矛盾的数字

**(1) 唯一实测样本已经超 200 ms。** 现存唯一的真索引查询数字是 `_scratch/manual/probe-wait.json`：
`elapsedMs=510`（子串 `ezt`、208 万条、`hits=10`）。它是**冷态单样本**（首次查询要 page-in `.ezidx`），

⇒ 200 ms 这个数必须**带上"热态 + P95 + 分模式"的前置**才成立，否则不要写进 DoD。

**(2) 防抖参数有两个互斥值，说明它是**误移植**。** 设计文档里同一条 stdio 链路写了两个数：

| 出处 | 防抖 | 说明 |
|---|---|---|
| 设计方案 §5.4.1 / `InputThrottle.cs`（**落地用的**） | **150 ms** | 为**面板 `input` 节点**定：代价口径是"一次 `tool.panel.data` 进程往返"（协议 §3.7.3） |

搜索窗是**原生 WPF 直连 `ezt-index`（stdio）**，链路里**没有**面板回传那一跳 —— 150 ms 是给另一条路定的。
`SearchSession` 复用它做代码复用是对的，但**常量取值没有跟着路径重新论证**。

**(3) 端到端下限是结构性的，不是调优问题。** 感知延迟 = `min(防抖, 最短间隔)` + `search.query` 往返 + 首屏渲染：

| 分量 | 值 | 出处 |
|---|---|---|
| 防抖（停顿后） | 150 ms | `InputThrottle.DebounceMs` |
| 最短间隔（连打中） | **80 ms** | `InputThrottle.MinIntervalMs` |
| 首屏渲染 200 条 | **48~55 ms** | `--probe-search-ui` 的 `renderMs`（实测 49.6 / 50.9 / 48.4 / 54.4） |

| 真索引规模 | 208 万条（≈ 夹具 2.08×） | `status.totalFiles=2081786` |

⇒ `80 + RTT + 48 ≈ 128 ms + RTT`，**DoD 写的 50 ms 在任何参数下都不可能出现**。
（50 ms 这个量级其实**正好等于算法段**：前缀 16 / 子串 21.9 / 模糊 65.7 就在它附近 —— 怀疑原文是"匹配段预算"被写成了"端到端"。）
