### 0.2 两种 shell 的三个差异（踩过的）

| 差异 | Git Bash | PowerShell |
|---|---|---|
| 调 exe | `./src/.../ezt.exe` 或全 Windows 路径 | 必须用调用运算符：`& "D:\...\ezt.exe"` |
| 设环境变量 | `export VAR="x"` | `$env:VAR = "x"` |

## 1. 上轮遗留项

### A1 · 启动提权 Core（**所有"真索引"类测试的前置**）

> ### ⚠️ 别开管理员窗口 —— UAC 由这条命令自己弹
>
> `ezt core start --elevate` 内部用 `ShellExecute` + `runas` 动词派生 Core，
> **UAC 是它弹的**，不是你的 shell 弹的。所以在**普通（非管理员）Git Bash / PowerShell**
> 里跑就行，只要在弹窗上点"是"。
>
> **为什么别开管理员窗口**（这是头号翻车点，已实测踩到）：新开的"管理员终端"是一个
> **全新 shell** ——
> 1. **工作目录回到 `~`** ⇒ `./src/...` 立刻 `No such file or directory`；
> 2. **之前 `export` 的环境变量全部丢失** ⇒ `$EZTOOLS_INSTALL_ROOT` 变空 ⇒
>    `--data-root ""` 退化到默认根，而 `core.json` 落到另一个根 ⇒ 索引进程去隔离根找
>    ⇒ 报 `Core 不可达`（`-32017`），**看起来像 Core 崩了**。
>
> 一句话：**提权的是 Core，不是你的终端。**

**Git Bash（普通窗口）：**

```bash
cd /d/01-项目代码/Eztools
export DOTNET_ROOT="D:/dotnet10"
ROOT="D:/01-项目代码/Eztools/_scratch/manual/install"

# 显式 --install-root：不依赖环境变量继承，两个根必定一致
./src/Eztools.Cli/bin/Debug/net10.0/ezt.exe core start --elevate --install-root "$ROOT"
```

**PowerShell（普通窗口）：**

```powershell
Set-Location D:\01-项目代码\Eztools
$env:DOTNET_ROOT = "D:/dotnet10"
$ROOT = "D:/01-项目代码/Eztools/_scratch/manual/install"
& .\src\Eztools.Cli\bin\Debug\net10.0\ezt.exe core start --elevate --install-root $ROOT
```

> `ROOT` 用 shell 变量 + 显式传 `--install-root`，是为了让"Core 登记的根"与
> "索引进程读 `core.json` 的根"**在语法上就是同一个值**，不靠环境变量能不能继承。
> （若你更习惯环境变量形态：`export EZTOOLS_INSTALL_ROOT="$ROOT"` 也可以，
> `--install-root` 优先级更高，两者都设时以参数为准。）

**过程**：弹 UAC → **点"是"**（脚本无法静默获取提权，这是它必须手工的根因）。

**该看到什么**：

```
Core 已启动：pid=<数字>  提权=True  版本=<x.y.z>
        管道=eztools-core-<hash>
```

**核对**：

```bash
./src/Eztools.Cli/bin/Debug/net10.0/ezt.exe core status --install-root "$ROOT"
```

应看到：

```
Core 端点：pid=<数字>  提权=True  版本=<x.y.z>
        管道=eztools-core-<hash>
        状态：运行中 ✓
```

关键两个字是 **`提权=True`**。若这里是 `False`，后面 A2/A3 必然失败 —— 不用往下猜。

> 记下 `pid`，后面项 B1 会用到。
> 提权 Core 是**特权层**：它读 MFT/USN 需要管理员令牌，无提权则 `volume.readMft` 回
> `ElevationRequired`，索引建不起来 —— 这解释了为什么 A2/A3/F1 都必须先做 A1。

**A1 专属的两个坑（都实测过）**

**坑 1 · 不要把 `core start` 管进 `head` / `grep` —— 会挂住不返回。**

```bash
# ✗ 别这样：终端会一直卡住
./src/Eztools.Cli/bin/Debug/net10.0/ezt.exe core start --elevate | head -5

# ✓ 这样：重定向到文件，跑完再 cat
./src/Eztools.Cli/bin/Debug/net10.0/ezt.exe core start --elevate \
    > _scratch/manual/core-start.txt 2>&1
cat _scratch/manual/core-start.txt
```

根因：Core 被派生为**脱离的独立进程**（设计如此 —— 它必须活过启动它的那条命令），
而该子进程**持有管道的写端** ⇒ `head` 永远等不到 EOF。父进程 `ezt.exe` 其实早就退了。
（这条对 `ezt-index`、`Desktop --probe-*` 同理：**要往文件写，别往 `head` 里灌**。）

**坑 2 · `core start` 是幂等的 —— 残留的非提权 Core 会把你的 `--elevate` 短路掉。**

```
Core 已在运行（pid=<数字>，提权=False），无需重复启动。
```

看到 `提权=False` 就是：**机器上已有一个非提权 Core 占着坑**，这次 `--elevate` 没生效。
此时 `--probe-usn` 照样回 `-32017`，极易误判成"提权没用"。修法：

```bash
./src/Eztools.Cli/bin/Debug/net10.0/ezt.exe core stop --install-root "$ROOT"    # → Core 已停止（pid=…）
ls "$ROOT/core.json"    # 应报 No such file or directory（端点已摘除）
./src/Eztools.Cli/bin/Debug/net10.0/ezt.exe core start --elevate --install-root "$ROOT"
```

> 顺带：不带 `--elevate` 的 `core start` 也能起来一个 Core（管道登记齐全、只是没有
> 管理员令牌），别拿它当"提权版"用 —— 它只会给你 `ElevationRequired`。

**坑 3 · ★★★ 别在命令里手打 / 粘贴中文路径 —— 粘歪了会凭空造出一个目录。**

实测（2026-09-25，真踩）：

```bash
$ ROOT="D:/01-项目代码/Eztools/_scratch/manual/install"     # 你输入的
$ ROOT="D:/01-Ŀ/Eztools/_scratch/manual/install"            # 终端回显的 ← 中文被压坏
$ ls -d /d/01-?                                            # 结果 D:\ 根下真的多了个 01-Ŀ
```

那个异形目录里有 `core.json` + 两个 `.ezidx` + `logs/`，**共 99 MB**。

**为什么这个坑最难查**：

1. **只有输入方向坏，输出方向是好的** —— `core status` 打印的 `Core 端点：pid=… 提权=True`
   里中文完全正常。于是"终端能显示中文"给了你**错误的信心**。
2. **"成功"与"错位"同时成立**：`core.json` 落在异形根，索引也建到异形根；
   而 `--probe-usn` / `core status` 用的是**同一个变量** ⇒ 两边自洽 ⇒ **照样回 `ok:true`**。
   于是 A3 会**报告完全成功**，只是所有产物都在一个你从没打算用的目录里。
   —— 这是 S9′（静默错位）的又一变体：**没有一处报错，只有一处路径不对。**

**修法：让 shell 自己算路径，绝不手打。** 附带先把结果 `echo` 出来核对（锚点）：

```bash
cd /d/01-项目代码/Eztools          # 这一行的中文若粘歪，cd 会**直接失败** —— 比静默错位好
ROOT="$(cygpath -m "$(pwd)")/_scratch/manual/install"
echo "$ROOT"                        # 必须是 D:/01-项目代码/Eztools/_scratch/manual/install
```

- `$(pwd)` 由 shell 产生 ⇒ **不存在手工粘贴环节**，中文一定是对的；
- `cygpath -m` 给"盘符 + 正斜杠"形式（`D:/01-...`），exe 能吃；
  **别用 `$(pwd)` 裸值** —— 那是 `/d/01-...` POSIX 形式，传给 exe 必 file not found。

> **通用纪律**：**凡要交给 exe 的路径，先 `echo` 一遍**。本项目路径天生含中文，
> 这个坑会反复出现。若已经踩到、D:\ 根下多了个异形目录，
> **先 `ls -R` 看清内容再决定删不删**（里面只有 `core.json`/`.ezidx`/`logs` 就是纯试验产物；
> 万一混进了别的东西，别删）。

### A2 · USN 同步层真通路（`--probe-usn`，acceptance 里那条 **SKIP**）

**为什么手工**：`acceptance.sh` 的 7.1c 步骤检测到 `core.json` 缺失就显式跳过
（"提权 Core 未运行；补测 = `ezt core start --elevate` 后重跑"）。**SKIP 不等于通过**。

**Git Bash：**

```bash
./src/Eztools.Index/bin/Debug/net10.0/ezt-index.exe --probe-usn C: \
    --data-root "$ROOT"
```

**PowerShell：**

```powershell
& .\src\Eztools.Index\bin\Debug\net10.0\ezt-index.exe --probe-usn C: `
    --data-root $ROOT
```

> ★ **变量必须与 A1 同源**（2026-09-25 实测踩到）：A1 建立的是 **shell 变量 `ROOT`**，
> 这里若照抄旧版写成 `$EZTOOLS_INSTALL_ROOT`，而那个环境变量没 `export` 过 ⇒
> `--data-root ""`（空）⇒ 找不到 `core.json` ⇒ **同样回 -32017**——错误文案说
> "Core 未提权/未运行"，极具误导性（Core 明明好好的）。**-32017 有两个成因**：
> ① 真没提权（回 A1）；② **根/变量错位**（先 `echo "$ROOT"` 核对非空，再确认与
> A1 是同一个值）。判据表里的"-32017 = 预期"只指 ①。

**该看到什么**（单行 JSON）—— 以下是**本机 2026-09-25 实测原样**：

```json

 "heartbeatError":"FSCTL_WRITE_USN_CLOSE_RECORD 失败（Win32 错误 1）"}
```

**判据（acceptance 用的同一条）**：

| 判据 | 实测值 | 说明 |
|---|---|---|
| `ok == true` | ✅ `true` | 通路打通 |
| `journalId > 0` | ✅ `133101787182104337` | USN journal 是活的 |
| `records > 0` | ✅ `490` | `readUsn` 真读到了记录，不是空 |

> **`heartbeatOk:false` 是"预期降级"，不是失败 —— 别被它带偏。**
> 这是已登记的 **S9 偏差**：心跳用的 `FSCTL_WRITE_USN_CLOSE_RECORD` 在现代 Windows 上
> **只接受文件句柄，不接受卷句柄**（实测 Win32 错误 1 = `ERROR_INVALID_FUNCTION`），
> 而索引进程持有的是卷句柄。因此心跳**显式降级**并**打印原因**。
> 风险已由 `readUsn` 的 `NotActive` 覆盖（journal 被删会当场报出来），
> 所以**不引入每卷标记文件**。详见设计方案 §4.5 的 S9 条目。
>
> ★ 判据是"**它有没有说话**"，不是"它有没有成功" —— 这正是 S9 家族要的：
> **降级可以，静默不可以**。

**这条跑通 ⇒ `acceptance.sh` 里那条 7.1c 的 `SKIP` 可以关掉了**（SKIP 的原因是
"提权 Core 未运行"，现在条件已满足）。

**没做 A1 时会看到什么**（本机实测，用来区分"没提权"与"真故障"）：

```json

 "error":"journal 不可用（未开启/删除中）或 Core 未提权/未运行"}
```

`rc=1` + `win32=-32017`（Core 不可达）= **没提权，不是功能坏了** —— 回去做 A1。

> **注意 `--data-root` 必须与 A1 的安装根一致** —— 探针靠该根下的 `core.json`
> 找到 Core 的命名管道；根不一致 ⇒ 报"Core 不可达"，而那看起来像 Core 崩了。

### A3 · 真卷全量建索引 + 条数对账（**重，~1 分钟级，可选但证据价值最高**）

**为什么手工**：真卷有 160 万级文件；把它做进自动化会让每次验收跑十几分钟，
且**依赖提权**（见 A1）。

> ### ⚠️ 本条是**交互式 stdio 服务**，必须**单独**执行 —— 不要跟别的步骤一起贴
>
> `ezt-index` 不带 `--probe-*` 时就是一个**读 stdin 的 JSON-RPC 服务端**，它会一直活着
> 等帧。所以：
> 1. **它前面的步骤、后面的步骤都不能在同一段粘贴里** —— 粘贴内容会被它当 stdin 吃掉；
> 2. 它**拒绝非 JSON 帧**是**设计如此**（不是崩溃）—— 你会看到一屏

>    这是它在**明确告诉你喂了垃圾**，比静默忽略好得多；
> 3. **退出方式**：在它等输入时敲下面这一行再回车（优雅停止，rc=0）：
>
>    ```
>    {"jsonrpc":"2.0","id":1,"method":"tool.stop"}
>    ```
>
>    ⚠️ **必须裸写这一行** —— 注释前缀**不能**跟着敲进去（`#   {"jsonrpc"…}` 不是合法 JSON，
>    照样会被当"非 JSON 帧"拒掉，而那些行又会被后续的粘贴带进服务端，看起来像"退出指令失效"）。
>
>    或者直接 `Ctrl+C`（粗，但省事）。

**为什么手工**：它**真的拉起一个 ezt-index 子进程**跑 stdio 往返。在自动化里跑，
需要处理进程回收（本项目踩过"沙箱按进程树回收"的误判），属于环境依赖分支。

**Git Bash（零提权冒烟 —— 期望 `-32001`）：**

**Git Bash（要"真命中" —— 加 `--wait-ready`，**本机 2026-09-25 实测原样**）：**


> ### ⚠️ 为什么必须加 `--wait-ready`
> 宿主托管的 `ezt-index` 是**后台自举**：`ping` 立刻能回，索引还在建。探针原来 ping 一回来
> 就 `query` ⇒ **必然** `-32001`。实测整个探针只花 **478 ms**，连"自举完成"都没走到 ——
> 那不是"索引没就绪"，是**"我们没等"**。默认 `--wait-ready 0` 保持旧行为（零提权冒烟不变慢），
> 要真命中就显式等待；探针会**无论等不等都先查一次 `search.status` 并落盘**，
> 于是 `-32001` 自带解释（`ready` / `totalFiles` / `volumes`）。

**实测真命中（`.ezidx` 已热启动即可，★ 不需要提权 Core）：**

```json
{"ping":{"ok":true,"version":"0.1.0","pid":29152},
 "status":{"ready":true,"totalFiles":2081786,"volumes":["C:","D:"],"skipped":0,"paused":false},
 "readyWaitMs":639,"statusCalls":7,
 "query":{"ok":true,"total":6175,"hits":10,"elapsedMs":510}}
```

**两种环境两种期望，都要认得**：

| 环境 | 期望输出 | 说明 |
|---|---|---|
| **零提权 + 无 `.ezidx`** | `status.ready=false` + `query.code=-32001` | `-32001` 是"索引未就绪"的**结构化**错误 —— 证明"进程起来了、协议通了、错误分层了"。**默认（不传 `--wait-ready`）就是这个形态**，约 0.5 s 返回 |
| **有 `.ezidx`（无论是否提权）** | `status.ready=true` + `query.ok=true` + `total>0` | **真命中**。需传 `--wait-ready <ms>`；`readyWaitMs` 就是自举落地用了多久（实测热启动 639 ms） |

> ⚠️ 若回的是其它错误码（如 `-32603` 内部错误）或 `ping.ok=false`，
> 那是**真问题**，不是"环境没到位"。`-32001` 才是预期内的"未就绪"。

> ⚠️ `status.volumes` 为空且 `totalFiles=0` 而 `readyWaitMs` 已经等满 ⇒ 自举**没成功**

### D1 · 暂停 / 恢复索引（W3-e-1）★ 有一个**已知缺口**

#### D1a · 协议级冒烟（无需提权，秒级）

**脚本已备好**：`_scratch/manual/pause-probe.py`（已在本机实跑，5/5 PASS）：

```bash
python _scratch/manual/pause-probe.py
```

**本机实测输出**：


#### D1b · 真效果级（需 A1 + A3，观察"停止消费、不丢游标"）

### E1 · "跳过必须可见"（W3-e-2）★ 本轮最值得手工做的一条

**为什么手工**：需要**环境里真有一个非 NTFS 固定卷**。本机现状（实测）：

```
C:  NTFS  固定  146.5 GB
D:  NTFS  固定  329.1 GB
```

**两个都是 NTFS ⇒ 在当前环境下"跳过"恒为空**，所以：
负向面**免夹具可做**，正向面需要**造一个 exFAT 卷**（下面给了 VHD 夹具）。

#### E1a · 负向（免夹具，1 分钟）：全 NTFS 环境**不该出现"跳过"字样**

**脚本已备好**：`_scratch/manual/status-probe.py`（可直接跑，无需自己粘代码）：

```bash
python _scratch/manual/status-probe.py
```

> ★ **这个脚本为什么必须写成长活进程轮询**：自举跑在 ezt-index 的**后台线程**，
> `service.SkippedVolumes` 是自举**结束后**才落到服务面的。
> 若像"一次性管道"那样把 `search.status` 与 `tool.stop` 一起灌进去，
> 进程会在自举落地**之前**就退出 —— 你看到 `volumes=[]` **并误判成"分类器没工作"**。
> （第一版本文档就是这么写的，实跑当场证伪 —— 记在这里，省下一个人重踩。）

**本机实测输出（无提权 Core）**：

```
volumes        = []
skippedVolumes = []
ready          = False  totalFiles = 0
lastError      = 卷 C: 枚举失败（code=-32017）: Core 特权服务未运行（无端点登记）…；
                 卷 D: 枚举失败（code=-32017）: Core 特权服务未运行（无端点登记）…
```

**判据**：

- `skippedVolumes == []` —— 全 NTFS ⇒ 无跳过（**这是负向面，成立**）；
- 于是搜索窗的卷清单行**不含**"跳过"字样
  （verify-desktop 的 `noSkipText` 断言守的就是这条）。

> ⚠️ **计数守恒在这一档「不可判」**，别当成失败。原因（实跑确认）：
> 无提权 Core 时卷会落到**第三档「枚举失败」**，而它**只出现在 `lastError` 文案里**，
> **既不进 `volumes` 也不进 `skippedVolumes`**。所以此刻是
> `0（已索引）+ 0（跳过）≠ 2（检测到）`——**正确**。
> 计数守恒要在**做完了 A1（提权 Core）**之后才可判：那时卷才会真正进 `volumes`。
> （见文末 §5 缺口表第 4 条：失败卷目前只有自由文本、没有结构化原因枚举。）

#### E1b · 正向（需造 exFAT 夹具）：跳过**可见且带原因**

**夹具**：挂一个 64 MB 的 exFAT VHD。**需要管理员**（diskpart）。

> ⚠️ VHD 文件放**纯 ASCII 路径**（如 `D:\_skiptest\`）。
> diskpart 脚本按 OEM 代码页读，中文路径可能出乱码 —— 本项目已有"中文路径交给外部 CLI 翻车"的先例。


**设计决定**：V1 **只在自举时定卷**，运行期**不监听** 卷的插入/移除

5. **重启索引进程后**（关掉托盘再开，或 `--probe-search` 触发一次），该卷**从索引里消失**。

**判据**：行为与 §7.4.1 一致 —— 即"运行期不跟随，重启后收敛"，
**且这条限制是写下来的**（不是悄悄存在）。这就是 W3-e-3 要求的

   | 资源管理器（选中某文件） | 搜索窗出现 |
   | 一个**以管理员运行**的程序（如管理员 PowerShell） | ⚠️ **预期可能无效** —— Windows 的 UIPI 机制不允许普通进程向提权窗口注入/抢焦点。这是**平台限制**，不是缺陷 |
   | 全屏游戏 / 视频 | 可能不出现（独占全屏） —— 同为平台行为 |

3. 每次唤出后按 `Esc` 关掉，再切程序。

**判据**：在上述**普通**前台程序里**每次都能唤出**。
"管理员程序里不行"不算失败，但要**知道**它为什么不行（UIPI）。

### G2 · 通道延迟实测 ✅（判据**已三段拆**，2026-09-25 实测已回填）

**为什么当初标"手工"**：它是 W3 计划里**最后一个未被自动化关闭的闸门（G2）**，
原语义是"每次按键一次 `tool.panel.data` 往返"的延迟；落地形态改为
**宿主直连索引进程（stdio）**，往返路径更短。

> ### ✅ 2026-09-25 结论：原 `≤ 50 ms（含防抖）` **作废**，判据改三段拆
>
> | 原 DoD | 与节流参数的关系 | 处置 |
> |---|---|---|
> | 输入 → 结果 **≤ 50 ms**（**含防抖**） | 落地节流是 `min(防抖, 最短间隔) + RTT + 首屏渲染`，**结构上 ≥ 80 + 48 ≈ 128 ms** | **作废**（50 ms 量级其实**正好等于算法段**：前缀 16 / 子串 21.9 / 模糊 65.7 ms —— 怀疑原文是"匹配段预算"被写成了"端到端"） |
>
> **判据三段拆**（已落地）：
>
> | 段 | 判据 | 现状 |
> |---|---|---|
> | ① **匹配段**（扫描 + 构建） | **P50 ≤ 50 ms @2M** | ✅ selftest W3-b-1（夹具 100 万条：前缀 16.0 / 子串 21.9 / 模糊 65.7 ms） |
> | ② **传输段**（`search.query` 往返） | **热态 P95** 报告值（前缀/子串分列，2M） | ✅ 实测 **前缀 p50/p95 = 1/1 ms · 子串 p50/p95 = 4/4 ms** |
> | ③ **感知段**（端到端） | **仅报告，不设闸** | ✅ 见下（探针 `latency` 段常驻） |
>
> 另 **参数归位**：搜索窗防抖由面板的 **150 ms** 改回设计 §6.2 的 **30 ms**（`SearchSession.DebounceMs`）。
> 30 < 最短间隔 80 ⇒ `InputThrottle.Fire` 里那条最短间隔从"防御性"变成"承重"，断言 25.6 钉住（突变 M-G1/M-G2）。

**已实测数字**（2026-09-25，真机热启动 `.ezidx`，**208 万条**，`--probe-search --probe-warmup 3 --probe-repeat 20`）：

| 段 | 首枪（冷态单枪） | 热态 P50 | 热态 P95 | max |
|---|---|---|---|---|
| 前缀 `ezt`（`total=485`） | — | **1 ms** | **1 ms** | 501 ms |
| 子串 `ezt`（`total=6171`） | **534 ms** | **4 ms** | **4 ms** | 517 ms |

- `readyWaitMs=666`（热启动就绪耗时）；**首建路径 `readyWaitMs=17,312 ms`**（211 万条 / 双卷 / 提权 Core，2026-09-25 补测，见 §G2-a 实测结果）。
- **`max≈500 ms` 是首个采样仍在冷/JIT 路径**，**不是**稳态 —— 这就是"早先唯一实测样本 `elapsedMs=510`
  不能拿去对 P95 闸"的原因（冷/热、单样本/P95 是两个不同的量；本轮首枪冷态报 **534 ms**）。
- ⇒ **传输段实测比 50 ms 判据还宽 10× 以上**，G2 **不再构成风险**；回退路径 ③（新窗型号）**无需启用**。

## 4. 操作纪律（本项目踩出来的，手工测试时同样适用）

1. **写真实磁盘 / 起进程**：若在 WorkBuddy 的沙箱里跑，`bash` 工具需显式**关闭沙箱**，
   否则 `rm`/写文件会"exit 0 但文件毫发未动"（静默失败）。在你自己的 Git Bash / PowerShell
   里跑没有这个问题。
2. **删文件**：本机 WorkBuddy 内**回收站不可用**（COM 与 `Microsoft.VisualBasic.FileIO`
   均被安全策略拦截）⇒ 无回收站兜底时**先二次确认再永久删**。
   本文涉及的删除只针对**你自己刚建的试验目录**（`D:\_w3bound`、`D:\_skiptest`）。
3. **POSIX 路径绝不交给 exe**（§0.2）。
4. **先看二进制时间戳再下结论**（§0.1）—— "改了没反应"九成是旧二进制。
5. **SKIP ≠ PASS**：A2 在 acceptance 里是 **1 条 SKIP**（提权分支未满足）；

### B2 · 自喂取证（缺口⑤ 方案 B：把安装根搬离被索引卷）

**为什么还要做**：代码侧（`Drain.TopSources`）已经能自证，但它回答的是**"谁在写"**；
搬卷对照回答的是**"搬走之后还追不平吗"** —— 两者独立，都值得记一笔。

**做法**（需一次 UAC）：

```powershell
# 1) 把 Core 的安装根/审计日志挪到 C:（D: 就不再有我们的写入）
ezt core stop
ezt core start --elevate --install-root C:\ezt-core-root

# 2) 只索 D:（避开 C: —— C: 上必然还有系统写入，会污染结论）
ezt-index --volumes D: --data-root C:\ezt-core-root

# 3) 看诊断里的 Top 来源：应该**不再**出现我们的文件名，且不再报"追不平"
```

**判据表**：

| 观察 | 结论 |
|---|---|
| 搬走后 `D:` 不再追不平 | **自喂确认**（我们的写入是主因）⇒ 文档写"安装根不要放在被索引的卷上" |
| 搬走后 `D:` 仍追不平，且 Top 来源全是**非自有**文件 | 主因是 **D: 上的其它写入者**（常驻进程/更新器）⇒ 文档写"D: 类高写入卷靠有界化降级" |
| 搬走后 `D:` 仍追不平，且 Top 来源**仍有自有名字** | 说明还有我们没识别到的落点 ⇒ 扩充 `CollectOwnNames` 的目录清单（`dataRoot` / `logs/` / `index/`） |
