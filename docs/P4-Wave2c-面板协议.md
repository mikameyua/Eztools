## 1. 范围界定（先说清做什么、不做什么）

### 1.1 做什么

| # | 交付物 | 说明 |
|---|---|---|
| 1 | `contributes.panels[]` 清单字段 | 工具声明"我有一个面板"，含 id / title / size / commands |
| 2 | 契约层模型 + 解析 + 校验 | `ToolPanel` record + `ManifestParser` 分支 + 诊断码 |
| 3 | 宿主 → 工具 的**面板数据通道** | `tool.panel.data` 请求；工具返回 `{nodes:[...]}` |
| 4 | 工具的**面板动作**通道 | 面板上的控件点击 → 复用**已有的** `tool.invoke`（不新增方法） |
| 5 | 宿主侧 WPF 渲染器 | `PanelWindow`：把 `nodes[]` 渲染成 WPF 控件树 |
| 6 | 入口 | 托盘菜单「面板」子菜单 + `ezt panel <toolId> [panelId]` 命令行 |
| 7 | `weight: full` 一致性闸门 | `panels` 仅在 `weight: full` 下可用 |

### 1.2 **明确不做**（写在这里是为了防止范围蔓延）

| 不做 | 理由 |
|---|---|
| ❌ 工具自带 HTML/WPF 代码作为面板 | 那等于让工具进程往宿主进程注入 UI —— 与"工具进程隔离"的架构前提冲突。**声明式 + 宿主渲染**是唯一路径 |
| ❌ WebView2 / 内嵌浏览器 | D3 已否决：§15.3 实测 WebView 会带来 50~100 MB，**会推翻 D1 的 220 MB 预算** |
| ❌ 面板 ↔ 工具的**实时双向**推送 | Wave 2c 只做**拉取式刷新**（打开时拉 + 用户点刷新 + 宿主事件触发）。推送需要工具侧长连接语义，属未来增量 |
| ❌ **键盘事件通道**（宿主把按键流透传给工具） | 🔴 **V1.3 明确否决**。这是 **Wave 3 的前置决策点（G1）**：三个候选里选了"`input` 节点"而不是"键盘事件通道"，因为后者**等于让工具进程接收按键流 —— 那是键盘记录器的形状**。正经用途（搜索框）= `input` 节点已覆盖；其余用途我们不要。详见 §3.7.2 对照表 |
| ❌ 工具 → 宿主 主动要求"重绘我的面板" | 同上。V1 靠"面板窗口每 N 秒/每次聚焦时重新拉"解决 |
| ❌ 面板自带的样式/主题/布局自由 | V1 用宿主统一间距与主题；工具只能选"控件种类"，不能控制像素 |
| ❌ `weight: lite` 的工具开面板 | 只有 `full` 档可声明 `panels`（见 §6） |
| ❌ `search` 贡献点 | 与本协议无关；已于 2026-09-23 从设计方案 §4.5 删除（无消费方） |

> **一句话**：V1 的面板 = **一个由工具数据驱动、由宿主渲染的只读数据视图 + 按钮**。
> 不是"工具把 UI 塞进宿主"，也不是"宿主给工具一块画布"。

## 2. 清单声明（`contributes.panels`）

### 2.1 形状

```jsonc
{
  "id": "mytool",
  "weight": "full",                    // ★ 前置：非 full 一律不可用（§6）
  "needs": ["ui.panel"],               // ★ 声明面板能力（§4.4 收敛集内）
  "contributes": {
    "commands": [
      { "id": "mytool.refresh", "title": "刷新", "handler": "refresh" },
      { "id": "mytool.clear",   "title": "清空", "handler": "clear" }
    ],
    "panels": [
      {
        "id": "main",                  // 面板 id，工具内唯一，[a-z0-9-]
        "title": "我的面板",            // 窗口标题（也用于托盘菜单项文字）
        "description": "查看当前状态",   // 可选，展示在窗口副标题
        "width": 640,                  // 可选，默认 640，钳制 [320, 1600]
        "height": 480,                 // 可选，默认 480，钳制 [240, 1200]
        "refreshMs": 0                 // 可选，0 = 不自动刷新；>0 时每 N ms 重拉一次，钳制 [500, 60000]
      }
    ]
  }
}
```

### 2.2 字段表（**全部字段，无遗漏**）

| 字段 | 类型 | 必填 | 默认 | 校验规则 | 违反时的诊断 |
|---|---|---|---|---|---|
| `panels` | array | 否 | 无面板 | 必须为数组；非数组 → 忽略整个字段 | `contributes.panels-not-array`（Warning） |
| `panels[].id` | string | **是** | — | `^[a-z0-9][a-z0-9-]*$`，≤64，面板内唯一 | 缺失 → `contributes.panel-missing-id`（**Error**） |
| `panels[].title` | string | 否 | 取 `id` | 非空字符串，≤128 | — |
| `panels[].description` | string | 否 | null | 自由文本 | — |
| `panels[].width` | int | 否 | 640 | 钳制到 `[320, 1600]`，越界 → 钳制并 Warning | `contributes.panel-size-out-of-range`（Warning） |
| `panels[].height` | int | 否 | 480 | 钳制到 `[240, 1200]` | 同上 |
| `panels[].refreshMs` | int | 否 | 0 | 0 或 `[500, 60000]`；其他值 → 归 0 并 Warning | `contributes.panel-refresh-out-of-range`（Warning） |

**为什么 `id` 缺失是 Error 而其他是 Warning**：`id` 缺失意味着宿主无法路由数据请求
（`tool.panel.data` 的 `panelId` 指谁？）——这是**结构性缺陷**，该面板根本无法工作。
其余字段都有合理默认值，降级可用。

### 2.3 重复 id

同一工具内 `panels[].id` 重复 → 后者被忽略 + Warning（码 `contributes.panel-duplicate`）。
**与 `commands` 的重复处理同口径**（`contributes.command-duplicate`）。

### 2.4 命令引用校验

`panels[].commands[]` 若声明了，则其中每个 id 必须在本工具的 `contributes.commands` 里存在，
否则 Warning（码 `contributes.panel-unknown-command`）——**与 `menus` / `hotkeys` 同口径**
（见 `ManifestParser` 现有的 `MenuUnknownCommand` / `HotkeyUnknownCommand`）。

> **设计理由**：面板上的按钮点击后走的就是 `tool.invoke`。若引用的命令不存在，
> 用户会看到"按钮能点、点了报未知命令"——这是最差的失败模式（能显示但不可用），
> 必须在加载期就警告。

## 3. 数据通道：`tool.panel.data`（**新增协议方法**）

### 3.1 方向与方法名

| 项 | 值 |
|---|---|
| 方向 | **宿主 → 工具**（请求，工具必须回复） |
| 方法名 | `tool.panel.data` |
| 常量 | C# `ProtocolMethods.ToolPanelData`；Python `protocol.TOOL_PANEL_DATA` |

> ⚠️ 契约层**两侧必须只有一份定义**（`ProtocolMethods.cs` 与 `protocol.py`）——
> 写错方法名会导致"面板一直是空的"这类难查症状。

### 3.2 请求参数

```json
{
  "toolId": "mytool",
  "panelId": "main",
  "context": {
    "reason": "open"          // open | refresh | host-event
  }
}
```

| 字段 | 说明 |
|---|---|
| `panelId` | 要哪个面板的数据（对应 §2 的 id） |
| `context.reason` | 为什么拉：`open`（窗口刚打开）/ `refresh`（用户点刷新或定时）/ `host-event`（宿主状态变了，如工具被启用） |

### 3.3 返回载荷（**核心 schema**）

```json
{
  "title": "我的面板",                    // 可选：覆盖清单里的 title（动态标题）
  "nodes": [                             // ★ 必填：节点数组，可为空数组
    { "type": "heading", "text": "当前状态" },
    { "type": "text",    "text": "共 3 个文件待处理" },
    { "type": "kv",      "items": [["路径", "D:\\tmp"], ["大小", "12 MB"]] },
    { "type": "list",    "items": ["a.txt", "b.txt", "c.txt"] },
    { "type": "buttons", "items": [
        { "label": "刷新", "commandId": "mytool.refresh" },
        { "label": "清空", "commandId": "mytool.clear", "style": "danger" }
    ]},
    { "type": "separator" }
  ]
}
```

### 3.4 节点类型表（V1 六种 + V1.2 `image` + **V1.3 `input`**）

| `type` | 必需字段 | 可选字段 | 渲染为 |
|---|---|---|---|
| `heading` | `text` | — | 加粗大字（FontSize 16，SemiBold） |
| `text` | `text` | `wrap`（默认 true） | 普通文本段落 |
| `kv` | `items`（`[[k, v], ...]`） | — | 两列键值表（左列灰、右列深） |
| `list` | `items`（`[...]`） | — | 项目符号列表 |
| `buttons` | `items`（`[{label, commandId}]`） | `style`：`default` \| `danger` | 横排按钮，点击 → `tool.invoke` |
| `separator` | — | — | 一条水平分隔线 |
| `image` | `path` | `alt`、`maxHeight` | 图片（**只读本地文件**，等比缩放到 `maxHeight` 内） |
| **`input`** | `key` | `value`、`placeholder`、`submitCommandId` | 输入框（**V1.3**）。值**随 `tool.panel.data` 的 `inputs` 回传** |

> **`image` 是 V1.2 增量（2026-09-23 补）**，V1 原只有前 6 种。加它的**唯一动机**是速览：
> "二进制文件只看元信息"这条限制里，图片是最常见、也最不该被一句话挡在门外的一类。
> 详细的字段语义、安全边界与降级规则见 **§3.6**（本协议新增一节，与节点表配套读）。
>
> **`input` 是 V1.3 增量（2026-09-23 定稿）** —— 它打破的是 V1 的另一条边界："只读 + 按钮"。
> **动机**：Wave 3 的搜索窗必须能打字。**方式**：把输入做成**一个节点 + 一次数据回传**，
> 而非键盘事件流（**理由见 §3.7.2 的对照表**，那一格"键盘记录器的形状"是决定性的）。
> ✅ **已实现**（2026-09-24，§12.2 七步全部完成）—— 本节含 10 条验收断言（§3.7.8），
> 分布见各断言行；WPF 侧的失焦/重绘/回传都有突变验证背书。

**未知 `type` 的处理**：**跳过该节点并渲染为一条灰色提示**（"⚠ 未知节点类型 xxx（宿主版本过旧？）"）。
**不报错、不白屏** —— 与"清单未知字段一律忽略"的前向兼容原则一致。
这条规则**也是 `image` / `input` 的前向兼容保证**：旧宿主遇到它们会跳过 + 提示，
而**保住面板其余内容**（见 §3.6.5 / §3.7.7 的版本协商说明）。

> **为什么不给节点加 id / 事件绑定**：V1 是**整体重绘**模型——工具每次返回完整 `nodes[]`，
> 宿主清空重画。局部更新需要 diff 语义与节点标识，那是 V2 的事。
> 这个取舍换来的是**工具侧零状态**：工具每次只需回答"当前该显示什么"，不需要记住上次画了什么。

### 3.5 校验与容错（工具侧返回不规范时）

| 情形 | 宿主行为 |
|---|---|
| 返回非对象 / `nodes` 非数组 | 显示错误面板：「工具返回格式不正确」+ 原始返回的前 500 字符（截断） |
| `nodes` 为空数组 | 渲染「（此面板当前无内容）」 |
| 单个节点字段缺失（如 `heading` 无 `text`） | 跳过该节点 |
| 单个节点字段类型不符 | 跳过该节点 |
| 返回超时 | 显示超时提示 + 重新拉取按钮（超时沿用 `weight: full` 的 120s 默认，可用 `timeoutMs` 覆盖） |
| 工具崩溃 / 已禁用 | 显示对应原因（复用现有异常文案） |

> **总原则**：**面板错误不弹对话框、不中断宿主**（与清单诊断同一条设计约束）。

### 3.6 `image` 节点规范（V1.2 增量，2026-09-23）

#### 3.6.1 形状

```json
{ "type": "image", "path": "D:\\photos\\a.png", "alt": "a.png", "maxHeight": 320 }
```

| 字段 | 必需 | 语义 |
|---|---|---|
| `path` | ★ | **绝对路径**（本地文件）。宿主要自行 normalize 后读盘 |
| `alt` | — | 读不出图时的替代文案（默认取 `path` 的文件名） |
| `maxHeight` | — | 显示高度上限（DIP）。默认 **320**，钳制到 `[32, 1200]` |

> **为什么是"文件路径"而不是"内嵌 base64"**：工具与宿主**同机**（工具是本地子进程），
> 让工具把图片字节塞进 JSON-RPC 帧会把帧撑爆 —— 一张 4 MB 的 PNG 经 base64 变 5.4 MB，
> 还要在两侧各留一份内存。给路径、由宿主读盘，**帧大小与图片大小无关**。
> 代价是宿主必须自己做安全校验（见 §3.6.2），这个代价是值得的。

#### 3.6.2 安全边界（**硬约束，宿主侧必须全部实现**）

| # | 规则 | 违反时 |
|---|---|---|
| S1 | 只读 `path`，**绝不写、绝不删** | — |
| S2 | **不支持任何远程协议**（`http://` / `https://` / `ftp://` / `file://` 一律拒绝） | 降级为 `alt` 文本 |
| S3 | 拒绝目录、拒绝不存在的路径 | 降级为 `alt` 文本 |
| S4 | 文件体积上限 **32 MB**（超过不读） | 降级提示「图片过大（>32 MB），未预览」 |
| S5 | 解码用 `BitmapImage` + `BitmapCacheOption.OnLoad`，**并立即 `Freeze()`** | — |

> **S2 是本节最重要的一条**：`BitmapImage.UriSource` 支持 `http(s)://`，若直接透传工具的 `path`，
> 一个工具就能让宿主**代替它发起网络请求**（绕过工具自己的 `network` 能力闸门，
> 也泄漏"这台机器在看什么图"）。所以宿主**只接受本地路径**，且必须用
> `BitmapImage.StreamSource` + 自打开 `FileStream`（而非 `UriSource`）来加载 ——
> 从 API 选择上就杜绝远程加载的可能。**这是"工具不能越权"在渲染层的兑现。**

> **S5 的 `Freeze()` 不是可选优化**：不冻结的 `BitmapImage` 绑定到 UI 后，
> 每次布局都可能触发重解码；冻结后是纯数据，可跨线程复用且不再变化。
> `OnLoad` 则保证读盘在**构造时一次完成**，不会在窗口绘制时才去碰那个文件
> （否则文件被删/被占用会在绘制阶段抛，落进"节点渲染失败"的兜底，比在构造时报错更难查）。

#### 3.6.3 降级路径（**图读不出来不是错误，是状态**）

任何一步失败都**降级成一个 `text` 节点**（含 `alt` 文案 + 一句原因），**不跳过、不报错、不白屏**。
原因文案分三类，**不要合并成一句"读取失败"** —— 用户的下一步动作完全不同：

| 原因 | 文案 |
|---|---|
| 不支持该格式 / 解码失败 | `⚠ 无法显示图片（格式不受支持或文件损坏）：{alt}` |
| 超出体积上限 | `⚠ 图片过大（{size} > 32 MB），未预览：{alt}` |
| 远程协议 / 路径非法 / 不存在 | `⚠ 无法显示图片（{具体原因}）：{alt}` |

#### 3.6.4 与"二进制文件只看元信息"的关系（**这条限制被部分松开**）

§11 第 7 条原写"二进制文件只看元信息，不预览内容"，**`image` 节点落地后该条要分情况**：

| 类别 | 结论 |
|---|---|
| **图片**（PNG / JPEG / GIF / BMP / WebP…） | ✅ **可预览**（`image` 节点）—— 2026-09-23 起 |
| 压缩包 / 音视频 / 可执行文件 / 其他 | ❌ 仍只看元信息 —— 不是"没做"，是**没有对应节点**（要还原它们得做 `code`/`table`/播放器，那是另一期的事） |

> 判定仍走 **magic 而非扩展名**（与全项目一致）：`PNG` = `\x89PNG\r\n\x1a\n`、`JPEG` = `\xFF\xD8\xFF`、
> `GIF` = `GIF87a`/`GIF89a`、`BMP` = `BM`、`WebP` = `RIFF....WEBP`。

#### 3.6.5 版本协商（旧宿主怎么办）

宿主不认识 `image` ⇒ 按 §3.4 的未知类型规则**跳过 + 一条灰字提示**，面板其余内容照常。
**工具不需要探测宿主版本**：发出去就行，旧宿主自然降级。
这与"清单未知字段一律忽略"是同一条前向兼容原则 —— **新工具可以在旧宿主上跑，只是少一块图**。

#### 3.6.6 验收口径（进 `verify-desktop.py` §1c 与 `verify-preview.py`）

| # | 断言 | 反例 |
|---|---|---|
| 19.1 | 含 `image` 节点的面板 → 自检控件树里 **`Image` 计数 == 1** | 渲染层把 `image` 也吃掉（与未知类型同待遇）→ 失败 |
| 19.2 | `path` 指向**不存在**的文件 → 渲染出 `text` 提示，**且面板其余节点照画** | 整包失败 → 失败 |
| 19.3 | `path` 是 **`http://…`** → **拒绝**（渲染成提示、**不发请求**） | 原样透传给 `UriSource` → 失败（S2 的守卫） |
| 19.4 | 速览一张真 PNG → 节点里有 `image` 且 `path` 指向该文件 | 图片被判成"二进制文件" → 失败 |
| 19.5 | 速览一张 `.png` 扩展名但内容为**纯文本**的假图 → **不是** `image`（按 magic 判） | 只看扩展名 → 失败 |

### 3.7 `input` 节点规范（**V1.3 增量**，2026-09-23）

> **这一节是 Wave 3（极速文件搜索）的前置契约。** 动机见 §11 第 1、10 条：
> V1.2 的面板是"只读 + 按钮"，**没有任何输入能力**；而搜索窗的核心就是"边打字边出结果"。
> 本节把"输入"补上，**方式是把输入变成一个节点类型 + 一次数据回传，而不是一条键盘事件流**。

#### 3.7.1 形状

```json
{ "type": "input", "key": "q", "value": "", "placeholder": "输入关键字…", "submitCommandId": "search.query" }
```

| 字段 | 必需 | 语义 |
|---|---|---|
| `key` | ★ | **回传标识**。宿主把当前输入值放进下一次 `tool.panel.data` 的 `inputs` 里，键就是它 |
| `value` | — | 初始值（默认 `""`）。**只在该 `key` 首次出现时生效一次**（§3.7.6 —— 整体重绘**不得**用它重置控件，否则抹掉用户正在打的字，21.6）|
| `placeholder` | — | 空值时的灰色提示文案 |
| `submitCommandId` | — | 可选：按 Enter 时触发的 `tool.invoke` 命令（须在 `contributes.commands` 里存在，校验口径同 §2.4） |

> **为什么必需字段是 `key` 而不是 `value`**：本协议是**整体重绘 + 工具侧零状态**模型（§3.4 末注）。
> 工具每次返回完整 `nodes[]`，用它表达"当前该显示什么"。**输入值不属于"该显示什么"** ——
> 它是**用户刚产生的状态**，由宿主持有并回传。所以节点只声明"这里有个叫什么名字的输入框"，
> 而不负责携带用户的输入。若把 `value` 设成必需，工具就得**记住**用户打了什么再原样回填 ——
> 那正好是零状态模型要避免的。

#### 3.7.2 回传路径（**本节的核心，与 §3.3 配套读**）

输入值**不在**面板数据里往宿主送，而是**在工具下次拉数据时由宿主带过去**：

```jsonc
// 宿主 → 工具（请求）
{"jsonrpc":"2.0","id":7,"method":"tool.panel.data","params":{
  "toolId":"search","panelId":"main",
  "context":{"reason":"refresh"},
  "inputs":{"q":"report"}          // ★ 本面板上所有 input 节点当前值的快照
}}
```

| 规则 | 说明 |
|---|---|
| **只带上本面板的** | `inputs` 只含 `panelId` 对应面板里的 `input` 节点（按 `key`） |
| **都是字符串** | 一律 string；**工具负责解释**（转数字、trim、判空由工具做） |
| **未出现 = 空** | 某 `key` 没在 `inputs` 里 ⇒ 按 `""` 处理（不要断言"一定有"） |
| **快照语义** | 送的是**发送那一刻**的值，不是"变更事件序列"。工具不应假设能收到每一次按键 |
| **`key` 重复** | 同一面板内 `key` 重复 ⇒ **后者被忽略 + Warning**（口径同 §2.3 的 `panels[].id`） |

> **⚠️ 这是"轮询式"而不是"推送式"，是**有意**的。** 代价与收益：
>
> | | 推送式（键盘事件通道） | **轮询式（本节方案）** |
> |---|---|---|
> | 每次按键 | 宿主推一个事件 | 工具主动拉一次（或宿主按节奏拉） |
> | 工具侧状态 | 要维护"当前输入缓冲" | **零状态**：拉到的就是全部 |
> | 能力边界 | 工具能收到**它没在看的**按键 | 只能拿到**自己面板上那个框**的值 |
> | 安全形状 | 🔴 **键盘记录器的形状** | ✅ 无从越界 |
>
> 右下那格是**决定性**的：一个"锦上添花"的搜索框，不该换来让工具进程接收按键流的代价。
> 这与 §3.7.4 的聚焦语义合起来，构成这条通道的**全部能力边界**。

#### 3.7.3 谁能拉、什么时候拉（**节流是宿主的责任**）

| 触发 | 是否拉取 |
|---|---|
| 面板窗口**刚打开** | ✅ 拉一次（`reason: "open"`） |
| 用户在 `input` 里**打字** | ✅ 按**节流节奏**拉（见下） |
| 用户点刷新 / 定时 `refreshMs` 到点 | ✅ 拉（`reason: "refresh"`） |
| 宿主状态变化（工具被启用等） | ✅ 拉（`reason: "host-event"`） |
| 面板窗口**未聚焦** | ❌ **不拉**（见 §3.7.4） |

**节流参数（宿主侧硬约束）**：

| 参数 | 值 | 理由 |
|---|---|---|
| 防抖窗口 | **150 ms** | 打字停顿才发请求，避免每键一次往返 |
| 最短间隔 | **80 ms** | 连续输入时的上限频率；工具响应慢也不排队 |
| **请求合并** | 节流窗口内多次变更 ⇒ **只发最后一次** | 中途的值工具看不到，也不需要看到（只要最终值） |
| **乱序丢弃** | 沿用 §3.3 的 `epoch` 语义 | 见 §3.7.5 |

> **⚠️ 工具方必须假设"收不到每一次输入"。** 这条要写进工具作者文档 ——
> 它是**契约的一部分，不是实现细节**。工具若依赖"每个字符都会来一次"，就会在快速输入下漏字。

#### 3.7.4 聚焦语义（**安全边界，硬约束**）

| # | 规则 | 违反时 |
|---|---|---|
| F1 | `inputs` **仅在承载该 `input` 节点的面板窗口处于聚焦状态时**才回传 | 越权（后台面板持续上报用户输入） |
| F2 | 窗口**失焦 ⇒ 停止上报**，并**清空**已缓存值（下次聚焦重新开始） | 越权 + 误把上一次的输入当作本次 |
| F3 | 宿主**绝不**把 `input` 的值写进日志 / 诊断包 / 崩溃转储 | **可能含敏感词**（用户搜过什么） |
| F4 | 宿主**绝不**把 `input` 的值发给**第三方**（含遥测、更新检查） | 同上 |
| F5 | `input` 的值**不持久化**（窗口关闭即丢） | 攒出一份"用户搜索历史" |

> **F1 是这套方案"不做键盘记录器"的兑现点。** 对比一下两者：
> 键盘钩子能读到**任意窗口、任意时刻**的按键；本方案只能读到**"用户正看着这个面板时，
> 往这个面板的输入框里打的内容"** —— 后者是**用户主动给这个工具的**，前者不是。
> **边界就在这里，且它可测**（验收 21.4 直接断"未聚焦 ⇒ 不回传"）。
>
> **F3~F5 是把"值"当敏感数据处理**。用户搜"离职合同 2026"是完全正当的，
> 但它不该躺在宿主的日志文件里 —— 这条与 §8.3「独占资源」同级，属于**产品伦理约束**。

#### 3.7.5 时序与陈旧值（**必须显式处理**）

沿用 §3.3 的 `epoch` 机制，但**输入场景下更尖锐** —— 因为打字天然比刷新快：

| 场景 | 后果 | 应对 |
|---|---|---|
| 用户打完 `report`，`rep` 的慢响应后到 | 显示 `rep` 的结果，但框里是 `report` ⇒ **看起来像 bug** | 工具回传 `epoch`；宿主**丢弃**过期 `epoch` 的返回 |
| 防抖期间用户继续打字 | 中间值被合并丢弃 | **预期行为**（只发最后一次） |
| 工具响应超过下一次节流窗口 | 请求堆积 | 宿主**同一面板同一时刻只允许一个在途请求**；新的到达则**取消**旧的（或等旧的后直接发最新值，不排队） |

> **⚠️ 工具侧的正确写法**：处理 `tool.panel.data` 时**用请求里带的值**去算，
> **不要**用"上次收到的值 + 增量"。工具应该是**无状态纯函数**：
> `inputs → nodes`。这条同时保证了 §3.7.4 的 F5（没有可持久化的东西）。

#### 3.7.6 降级路径（与 §3.6.3 同口径：**读不出来是状态，不是错误**）

| 情形 | 宿主行为 |
|---|---|
| 旧宿主不认识 `input` | **跳过 + 一条灰字提示**（同 §3.4 未知类型）—— 见 §3.7.7 |
| `key` 缺失 / 非字符串 | 跳过该节点 |
| `key` 重复 | 保留第一个 + Warning |
| 面板被整体重绘时 `value` 与用户当前输入不同 | **保留用户当前输入**（重绘不该吞掉打字）—— 见下注 |

> **最后一条是个容易做错的地方**：本协议是整体重绘模型，工具每次返回完整 `nodes[]`。
> 若工具返回 `{"type":"input","key":"q","value":""}`，**不能**把用户已经打好的 `report` 抹掉 ——
> 那会在每次结果刷新时清空搜索框（**最刺眼的可用性 bug**）。
>
> **判据**：`value` 只在**该 `key` 首次出现**（或面板被显式重置）时生效；
> 之后由宿主持有用户输入，直到窗口关闭 / 失焦清空。
> **工具想真正清空输入框，应当返回一个带新 `key` 的节点**（或触发整面板重建）——
> 把"重置"做成**显式动作**，而不是靠 `value` 的副作用。

#### 3.7.7 版本协商

V1.2 → **V1.3**。**加节点类型是向后兼容的扩展**（不改已有节点语义），故记为次版本递增而非 V2.0。

| 方向 | 行为 |
|---|---|
| **新工具 → 旧宿主** | 旧宿主按未知类型**跳过 + 提示**，面板其余照画。工具**不需要探测宿主版本**（同 §3.6.5） |
| **旧工具 → 新宿主** | ✅ 完全无关：旧工具不发 `input` 节点，新宿主自然不当有输入框 |
| **新宿主 + 新工具** | 宿主在 `tool.panel.data` 请求里**总是**带 `inputs`（可能为空对象）；工具不需要时忽略即可 |

> `inputs` 是请求里的**新增可选字段** ⇒ 旧工具收到它会**忽略**（其解析器不认这个键），
> 这是既有前向兼容原则（"清单未知字段一律忽略"）的自然结果，**无需版本协商**。

#### 3.7.8 验收口径（将进 `verify-desktop.py` / `verify-preview.py`）

| # | 断言 | 反例 |
|---|---|---|
| 21.1 | `ezt panel --text` 渲染 `input` 节点 → 输出**可读表示**（如 `[输入框 key=q value=""]`） | 打「⚠ 未知节点类型 'input'」→ 失败 |
| 21.2 | 含 `input` 的面板 → WPF 控件树里 **`TextBox` 计数 == 可渲染节点数**（本夹具 = **3**：2 个合法 + 1 个 submit 未声明照渲染；缺 key 的被跳过。2026-09-24 实施时修正 —— 原写 "== 1" 是按单节点假象估的，与验收夹具不符） | 被当未知类型跳过 / 缺 key 的也渲染 → 失败 |
| 21.3 | 回传路径：设 `key=q` 的输入框值 → 下一次 `tool.panel.data` 请求的 `inputs.q` **等于该值** | 请求里没有 `inputs` → 失败 |
| 21.4 | ★★ **负向**：面板**未聚焦**时 ⇒ **不回传** `inputs`（或 `inputs` 为空） | 后台仍上报 → 失败（**F1 的守卫**） |
| 21.5 | ★★ **负向**：失焦后再聚焦 ⇒ **不带上**失焦前的旧值 | 旧值复活 → 失败（**F2 的守卫**） |
| 21.6 | 整体重绘时工具回传 `value: ""`，但用户已输入 ⇒ **输入框内容不被抹掉** | 每次刷新清空搜索框 → 失败（§3.7.6 注） |
| 21.6b | 工具把 input 拿掉再放回 ⇒ 该 key **视为重新首现**、节点 `value` 重新生效（值复位；payload 定义"存在"，§3.7.2）。**实施后补**（2026-09-24 复盘加固） | 缓存未随成功渲染裁剪 ⇒ 放回后旧值仍被首现规则挡住 → 失败 |
| 21.7 | 节流：连续快速输入 N 次 ⇒ 实际发出的 `tool.panel.data` 请求数 **< N**（且有下限） | 每键一次 → 失败 |
| 21.8 | `submitCommandId` 引用了不存在的命令 ⇒ **首次拉取期 Warning**（码 `contributes.panel-unknown-command`） | 静默接受，按 Enter 报未知命令 → 失败 |
| 21.9 | 反向：`input` 节点**不改变**已有 6 种 + `image` 的渲染行为 | 加 `input` 后 `image`/`buttons` 出问题 → 失败 |
| 21.10 | 反向：**非** `input` 节点的面板 ⇒ 请求里 `inputs` 为**空对象**（不是 `null`、不是缺字段） | 字段形态不一致 → 工具侧解析各自为政 → 失败 |

> **21.4 / 21.5 是本节最重要的两条** —— 它们是 §3.7.4 F1/F2 的守卫。
> 「输入通道」这类能力的风险不在"能不能用"，而在"边界有没有守住"，
> 所以**负向断言比正向断言更重要**。
>
> **⚠️ 21.8 的措辞是"首次拉取期"而不是"加载期"**（2026-09-23 实施时修正）：
> 节点是**工具运行时返回的**，清单加载期宿主根本看不到 `submitCommandId` ——
> 写"加载期"会让人去 `ManifestParser` 里找一个**永远不存在**的校验点。
> 判据落在**诊断码**上（`contributes.panel-unknown-command`），时刻由"节点何时可见"决定。
> 见 §12.2 第 1 步的取舍说明。

## 4. 动作通道：面板按钮 → `tool.invoke`（**复用，不新增方法**）

### 4.1 语义

`buttons` 节点的 `commandId` 指向**本工具已声明的命令**。点击时宿主：

1. 调 `InvokeCommandAsync(commandId, args)` —— **走的是与托盘菜单完全相同的通路**；
2. `args` 传 `{ "panelId": "<当前面板 id>" }`（让工具知道自己是从哪个面板点过来的）；
3. **等返回**（按钮进入禁用态）；
4. 完成后**自动重拉面板数据**（`reason: "refresh"`）—— 这是 V1 的"局部刷新替代品"。

### 4.2 为什么复用 `tool.invoke` 而不是新增 `tool.panel.action`

- **命令已经是一等公民**：有 id、有 handler、有超时、有 `weight` 闸门、有环检测。
  新增一套 panal 专用的动作方法 = 把这五样各复制一份（且都要再测一遍）。
- **工具侧零新概念**：面板按钮就是"带个 panelId 参数的普通命令"，SDK 不用加 API。
- **环检测天然成立**：`tool.invoke` 已在既有链里（见 P4 §2.2），新通道会被同一套逻辑覆盖。

### 4.3 危险操作

`style: "danger"` 只影响**按钮配色**（红），**不加二次确认**。
确认语义属工具自己的 handler 职责（工具可以返回"需要确认"的节点再让用户点第二次）。
**宿主不为工具的业务判断兜底。**

## 5. 宿主侧渲染（原生 WPF）

### 5.1 窗口

| 项 | 结论 |
|---|---|
| 载体 | 新增 `src/Eztools.Desktop/PanelWindow.cs`（`Window`，与 `SettingsWindow` 同构） |
| 尺寸 | 取清单 `width`/`height`，用户可拖拽调整（不持久化，V1） |
| 标题 | `"{工具名} — {面板 title}"` |
| 位置 | `WindowStartupLocation.CenterScreen` |
| 主题 | 复用 `SettingsWindow.ApplyModernTheme()`（同样的 iNKORE 主题初始化） |
| 刷新按钮 | 窗口右上角一个「刷新」按钮（手动 `reason: "refresh"`） |
| 状态栏 | 底部一行：`上次刷新 HH:mm:ss · 耗时 Nms` |

### 5.2 多面板

一个工具有多个面板 → 托盘「面板」子菜单里每一项对应一个窗口。
**同一面板重复打开**：复用已开窗口（激活到前台 + 立即重拉），**不新开**。

### 5.3 线程与阻塞（**本项目踩过两次的区域，特别说明**）

- 拉数据是 `await` 异步（`weight: full` 超时可达 120s），**绝不在 UI 线程同步等**（见 P2 托盘 `InvokeAsync` 的注释）。
- 定时刷新用 `DispatcherTimer`（WPF，跑在 UI 线程），回调里 `await` 拉数据。
- 面板窗口关闭时**必须停掉定时器并退订宿主事件**（Wave 2a 的 `Subscribe` 返回 `IDisposable`）。

### 5.4 与事件总线的关系（Wave 2a 的消费方）

面板窗口订阅 `HostEventBus`，收到 `ToolEnabledChanged` / `ToolStopped` / `RegistryReloaded` 时：
- 若事件 `ToolId` == 本面板的工具 → 用 `reason: "host-event"` 重拉；
- 否则忽略。

> 这是 Wave 2a 事件总线的**第二个真实消费方**（第一个是托盘的气泡与 Resident 区段刷新）。
> Wave 2a 当初的"不做开放总线"决策在这里得到验证：**内部事件刚好够用**。

## 6. `weight: full` 的一致性闸门

### 6.1 规则

| 规则 | 违反时 |
|---|---|
| 声明了 `panels` 但 `weight != full` | **Error**：`contributes.panels-require-full`。理由：`weight` 决定进程模型，而面板需要常驻可复用的进程 + 长超时 |
| `weight: full` 但未声明 `needs: ["ui.panel"]` | **Warning**：`needs.panel-without-ui-panel`（漏了声明的能力提示，不阻塞） |
| `weight: full` 的工具未实现 `tool.panel.data` handler | **运行时**错误（非加载期）：打开面板时报"工具未实现 panel 数据接口"，错误码 `MethodNotFound` |

> **为什么是 Error 不是自动升档**：`weight` 是**作者对进程模型的显式选择**（含超时、依赖策略），
> 宿主静默改写它 = 让工具以作者没预期的形态运行（`script` 档的"用完即退"语义会消失）。
> 与"写了但不认识的 weight 回退 + Warning"不同——那是**拼写错误**，这是**能力组合矛盾**。

### 6.2 `weight: full` 的其余增量（本次一并落地）

`full` 档此前只有枚举值与超时，无任何独占特性。本次给它**两条**真实差异：

| 能力 | script | lite | full |
|---|---|---|---|
| `host.log` / `host.notify` | ✅ | ✅ | ✅ |
| `host.storage.*` / `host.primitive.call` / `host.invokeTool` / `host.progress` | ❌ | ✅ | ✅ |
| `panels` 贡献点 | ❌ | ❌ | ✅ |
| `tool.panel.data` 方法 | ❌ | ❌ | ✅ |
| 默认超时 | 10s | 30s | 120s |

> **注**：`tool.panel.data` 是**宿主 → 工具**方向，不是"工具调用的宿主 API"，
> 所以它不走 `EnsureApiAllowed` 白名单（那条闸门管的是工具→宿主）。
> 但宿主在**发起** `tool.panel.data` 前要检查档位——**闸门在发起侧，不在处理侧**。

## 7. 入口

### 7.1 托盘

`TrayMenuBuilder` 在工具分组内追加「面板」子菜单（仅当该工具有 panels）：

```
工具分组
├── 命令 A
├── 命令 B
└── 面板            ← 新增（仅当 panels 非空）
    ├── 我的面板
    └── 状态面板
```

工具**只有面板没有菜单**时，也该出现（否则面板无处可达）。

### 7.1b 热键直达面板：`hotkeys[].opensPanel`（2026-09-21 补，V1.1）

托盘入口要"点两下"，对速览这类**看一眼前台文件**的功能太重。所以热键声明上补一个字段：

```json
"hotkeys": [
  { "command": "mytool.show", "default": "Ctrl+Alt+P", "input": "shellSelection",
    "opensPanel": "main" }
]
```

| 项 | 口径 |
|---|---|
| 类型 | 字符串，面板 id（**本工具**声明的） |
| 语义 | **命令成功后**打开；失败/拿不到上下文时**不开**（让用户先看到气泡里的解释） |
| 缺省 | 无 → 只弹气泡（与 P2 行为一致，向后兼容） |
| 非法引用 | 诊断 `contributes.hotkey-unknown-panel`（**Warning**，非 Error）：热键本身是好的，只是"顺手开面板"落空 |
| 非法时的处理 | **保留热键、清空 `opensPanel`** —— 连键一起丢会让用户以为"键坏了"，而真相是"面板名写错了" |
| 复用已有窗口 | 必须**重拉数据**（`PanelWindow.RefreshAsync`），否则窗口跳到前台、内容还是上一次的 |

**校验时机是硬约束**：`hotkeys` 在解析顺序上排在 `panels` **之前**（约 105 行）。
若在热键循环里做交叉校验，那时 `panels` 为空 ⇒ **每一条合法声明**都被判成"面板不存在"，
满屏假诊断把真问题淹没。校验必须放在 `ParsePanels` 之后。
（`scripts/_step15_w2c.sh` 的 `badopenspanel` + `okopenspanel` 成对夹具守这个时机。）

### 7.2 命令行

```bash
ezt panel                      # 列出所有工具的面板（toolId.panelId + title）
ezt panel mytool               # 列出该工具的面板
ezt panel mytool main          # 拉取并打印面板数据（JSON，便于脚本断言）
ezt panel mytool main --text   # 人类可读渲染（缩进树）
```

**为什么 CLI 要有**：验收脚本需要一个**不依赖 GUI** 的断言入口。
`ezt panel <toolId> <panelId>` 直接走 `tool.panel.data`，与 WPF 窗口读的是同一条通道 ——
这样"面板数据链路"可以进自动化，只有"WPF 真的画出来了"需要 GUI 验证（用 `--selfcheck` 模式）。

## 8. 工具侧 SDK

### 8.1 handler 注册

```python
from eztools import Tool

tool = Tool()

@tool.handler("panel_data")          # 名字固定为 panel_data（宿主按 handler 名路由）
def panel_data(args):
    panel_id = args.get("panelId")
    if panel_id == "main":
        return {"nodes": [
            {"type": "heading", "text": "当前状态"},
            {"type": "text", "text": f"共 {count()} 个文件待处理"},
            {"type": "buttons", "items": [
                {"label": "刷新", "commandId": "mytool.refresh"},
            ]},
        ]}
    return {"nodes": []}
```

**handler 名固定为 `panel_data`**（不是每个面板一个 handler）。
理由：面板 id 已在 `args.panelId` 里，一个 handler 用 `if/switch` 分派即可；
每个面板一个 handler 会让 `tool.json` 复杂化，而收益只是省一次分支。

### 8.2 SDK 改动

- `protocol.py`：加 `TOOL_PANEL_DATA = "tool.panel.data"`。
- `tool.py`：`_dispatch` 加一个分支 → `self._handlers.get("panel_data", 默认实现)`。
  默认实现返回 `{"nodes": []}`（**不报错**）——与 `tool.recover` 的"明确告知未实现"不同，
  因为空面板是合法状态（工具确实没东西可显示）。

## 9. 验收口径（将落地为 `scripts/_step15_w2c.sh`）

**判据设计要求**（依据 `docs/验收断言审视清单.md`：判据 = "改成假值测试还会不会过"）：

| # | 断言 | 反例（改成假值必须失败） |
|---|---|---|
| 15.1 | `ezt panel` 列出面板，且**输出里含具体 panelId** | 若实现返回空列表 → 失败 |
| 15.2 | `ezt panel probe main` 返回的 JSON `nodes` **长度 > 0** | 若返回空数组 → 失败 |
| 15.3 | 返回的 `nodes[0].type` **等于期望的具体值**（如 `heading`） | 若渲染层把 type 丢掉 → 失败 |
| 15.4 | 含 `buttons` 节点时，其 `commandId` **能解析到已声明命令** | 若引用了不存在的命令 → 失败 |
| 15.5 | `weight: lite` 的工具声明 `panels` → **加载期 Error** + 断言诊断码字符串 | 若静默接受 → 失败 |
| 15.6 | `weight: full` 且声明 panels 的工具 → **无 Error 诊断** | 若被误判 → 失败 |
| 15.7 | 未知 `type` 的节点 → **被跳过但面板整体仍渲染**（返回 ok，节点数少 1） | 若整包失败 → 失败 |
| 15.8 | `panels[].id` 缺失 → 诊断码 `contributes.panel-missing-id` | — |
| 15.9 | `width` 越界（如 99999）→ **被钳制到 1600** 且出 Warning | 若原样透传 → 失败 |
| 15.10 | 工具返回非对象 → 宿主报告格式错误但**不崩溃**（退出码仍 0） | 若抛异常 → 失败 |
| 15.11 | `refreshMs` 越界（如 10）→ 归 0 且出 Warning | — |
| 15.12 | 面板按钮走 `tool.invoke`：同 `commandId` 的命令**能被真实调用并返回结果** | 若只冒泡不调用 → 失败 |

> **不写"面板窗口能打开"这类断言**：它需要 GUI 会话，进不了 `acceptance.sh`。
> 改由 `--selfcheck` 覆盖：构造窗口**不显示**、检查控件树节点数与预期一致后退出。
>
> **落地情况（2026-09-21）**：15.1~15.12 全部落地在 `scripts/_step15_w2c.sh`（**24 条断言**，
> 因为部分条目拆成了"正例 + 对照"两半，例如 15.5/15.6 的档位闸门、15.9/15.11 的钳制与归一化）。
> GUI 侧由 `scripts/verify-desktop.py` 的 §1c 覆盖（**10 条**）：`PanelWindow.InventoryForSelfCheck`
> 真拉一次 `tool.panel.data` 并装配控件树，断言 Button=2 / Separator=1 / Grid=1 / WrapPanel=1 /
> 尺寸取自清单（720×520 而非默认 640×480）/ 空面板有提示 / 未知节点跳过但保住其余 /
> 非对象载荷渲染成提示而非崩溃。
>
> **踩到的两个坑（值得记下来）**：
> ① `panels[].id` 缺失在实现里曾被路由到 `Warn` 委托而非 `Error` —— 诊断码对、**严重级别错**，
>   而级别决定 `doctor` 的 `healthy` 判定。`ParsePanels` 原先只接收 `Action<string,string> warn`，
>   没有 Error 出口 ⇒ 协议 §2.2 的"必须 Error"被静默降级。**教训**：解析器只暴露一半的诊断通道时，
>   协议里写"Error"的地方会自然退化成 Warning，且没有任何编译期或测试期信号。
> ② 自检的控件计数最初走 `VisualTreeHelper`，把模板展开的内部零件也数进去（2 个按钮数成 8 个），
>   且未 `Show()` 的窗口根本没有可视化树。改走**逻辑树**后计数才等于"我放了什么"。

## 11. 已知限制（诚实清单）

1. **只读 + 按钮**：V1 不支持输入框、下拉框、复选框等交互控件（工具想要输入 → 用命令 + 配置 schema）。
   > 🔼 **2026-09-23 部分松开（V1.3 条文）**：新增 **`input` 节点**（§3.7），
   > **输入框**这一类补上了。**其余交互控件（下拉框 / 复选框 / 单选 / 滑块）仍不做** ——
   > 它们都能用"命令 + 配置 schema"表达，而输入框不能（搜索必须能打字）。
   > ⚠️ **只有条文、尚未实现**；`input` 的能力边界（**不含**键盘事件流）见 §3.7.2 / §3.7.4。
2. **整体重绘**：无 diff、无局部更新、滚动位置在刷新后会重置。
3. **无双向推送**：工具不能主动让面板刷新（靠定时 `refreshMs` 或用户点刷新）。
4. **无面板状态持久化**：窗口尺寸/位置不记（V1）。
5. **`weight: full` 仍无"独立进程组"语义**：目前 `full` 与 `lite` 共用同一套进程管理路径，
   差异只在闸门与超时。若将来 `full` 需要"独立宿主进程 + 异步"（§5.1 原文），需单独一期。
   > ✅ **2026-09-23 更新：已拍板"补齐"**（不采用"确认够用"）。
   > 触发点是 **Wave 3 极速文件搜索** —— 索引进程需要崩溃隔离（否则索引崩了拖垮托盘）。
   > 语义细节见 `docs/Eztools-设计方案.md` **§5.1** 的「独立进程的语义补齐」段；
   > 落地批次 = **W3-a-1**（与实施计划 §0.3 **N2** 对应）。
   > ⚠️ 本条**保留原文不删** —— 它是 Wave 2c 当时的真实状态记录，删掉就丢了演进过程。
6. **`ezt panel --text` 的渲染是简化版**：只做缩进树，不追求与 WPF 视觉一致。
   ⚠️ **CLI 渲染器不认 `image` 节点**（2026-09-23 补记）：`PanelCommand.cs` 的 `RenderNode`
   只覆盖 `heading` / `text` / `kv` / `list` / `buttons` / `separator`，`image` 落入 `default`
   分支 ⇒ `ezt panel` 看图片时打印 `⚠ 未知节点类型 'image'`。
   这是**有意的取舍**（CLI 无渲染负担，"保留原文比跳过更有用"），
   **不是**"忘了做"—— WPF 侧已有完整 `RenderImage()`（§3.6 / 设计方案 §30）。
   断言钉在 `verify-preview.py` 20.8（按钮契约）与 `verify-desktop.py` §1c（WPF 渲染）。
7. **二进制文件只看元信息，不预览内容**（2026-09-22 明确 · **2026-09-23 部分松开**）：
   这不是"没做"，是**节点集的直接推论** —— V1 只有 6 种基础节点，**2026-09-23 起新增 `image`**
   （共 7 种），但仍**没有** `code` / `table`，而"能显示富内容"的两条路都已否决
   （WebView2 → D3；工具自带 HTML → 与进程隔离冲突）。
   ⚠️ 注意区分**三件难度差一个数量级的事**：
   - **提取纯文本**（PDF/Word → 文字）——**不需要动本协议**，现有 `text` 节点就够，
     障碍只在"工具侧缺一个解析库"（许可必须与 GPL-3.0 兼容；轻依赖 vendor 到工具 `Lib/`）。
     **PDF 已于 2026-09-22 落地**（pypdf，§28）；**Office 三格式已于 2026-09-23 落地**（§29）。
   - **显示图片**——已新增 `image` 节点（**§3.6**，2026-09-23）。
     速览现在对**图片**给图、对**压缩包 / 音视频 / 其他二进制**仍只给元信息。
   - **还原版式 / 播放音视频 / 展示表格**——仍属独立一期（未排期）。
     实测的能力边界、三个判定缺陷与待决项见设计方案 §26.4、§28、§29。
8. **`image` 节点只接受本地路径、单张、无交互**（2026-09-23）：
   不支持远程 URL（安全边界 S2，见 §3.6.2）、不支持多图轮播、不支持点击放大 ——
   最后一条如需，做法是**再发一个 `image` 节点**（`maxHeight` 调大），而不是给节点加状态。
   这与"整体重绘 + 工具侧零状态"的模型一致。
9. **多选只预览第一个，不翻页**（2026-09-23 补记 · 竞品对照后的明文决策）：
   `inputPaths` 有多个时，面板**只渲染第 1 个**，其余以 `list` 节点列出
   （`tools/preview/main.py` 的 `_head_nodes`；断言见 `verify-preview.py` 20.7）。
   ⚠️ **这是与同类产品的自觉差异，不是遗漏**：PowerToys Peek / QuickLook 的多选语义是
   "**在选中集内用方向键连续翻页**"，而本项目**做不到** —— 原因见第 1 条（只读 + 按钮）
   与第 3 条（无双向推送）：面板**没有键盘事件通道**，翻页只能靠按钮，体验远逊于竞品。
   追平需要给面板引入"当前第几个"的**队列状态**，与"整体重绘 + 工具侧零状态"模型冲突，
   属**独立一期**，未排期。
   > 竞品对照（2026-09-23）：Peek 官方文档原文 "Select multiple files in File Explorer
   > for previewing to scroll only between selected ones" —— 即"多选 = 缩小翻页范围"。
   > 若要改成本项目语义，`verify-preview.py` 20.7 会红 —— 那是提醒同步改本条。
10. **面板无键盘事件通道 ⇒ 无法做"方向键切文件 / Esc 关闭"这类交互**（2026-09-23 补记）：
    竞品（Peek / QuickLook）的核心交互高度依赖键盘（Space 开关、←/→ 切文件、Esc 关闭、Enter 打开）。
    本协议 V1 **没有**把键盘事件从宿主透传给工具的通道 —— 这既是限制也是**安全边界**
    （工具进程不接收宿主输入事件流，与进程隔离模型一致）。
    ⇒ 速览把这些动作退化为**面板按钮**（`preview.reload` / `preview.openExternal`）；
    若将来要做键盘导航，需先在本协议里**新增一条交互通道**，属独立一期。
    > 🔼 **2026-09-23 澄清（V1.3 之后的边界）**：本条**仍然成立**，且现在有了明确的**取舍理由**。
    > V1.3 补的是 **`input` 节点**（§3.7）—— 它让工具能拿到**自己输入框里的值**，
    > **但没有**、也**不会**给工具一条"按键流"。两者的区别是本协议最重要的一条线：
    >
    > | | `input` 节点（V1.3 做了） | 键盘事件通道（**仍然不做**） |
    > |---|---|---|
    > | 工具能看到什么 | **只有**自己面板上那个框的当前值 | 任意窗口任意时刻的按键 |
    > | 是否用户主动 | ✅ 用户往那个框里打的 | ❌ 用户在别处打的也来 |
    > | 形状 | 声明式节点 + 拉取 | **键盘记录器** |
    >
    > ⇒ 本条记的"方向键切文件 / Esc 关闭"**依然做不到**（那需要事件，不是值）。
    > 若将来真要做，**必须先论证**它不能被"按钮 + `input`"替代 —— 否则不开这条口子。

>   只有节奏错，普通断言抓不到）；M-D Reset 不清待发 ⇒ 2 红（F2 守卫）。

> ### ⚠️ 第 5 步的两个坑（提前写在这里，因为都是"看起来对但不生效"型）
>
> **1. 失焦清空必须真的清**（21.5）：WPF 里把"失焦"挂在 `Window.Deactivated` 上，
> 而 `TextBox.LostFocus` **在面板内部切焦点时也会触发** —— 挂错事件会导致
> "点一下按钮，输入就被清空"。**判据落"值"不落"事件"**（断"失焦后不带旧值"）。
>
> **2. 整体重绘不能吞掉打字**（21.6）：本协议是**清空重画**模型（§3.4 末注），
> 天真实现会把输入框一起重建 ⇒ **每次结果刷新，用户打了一半的字就没了**。
> 修法是让 `value` **只在 `key` 首次出现时生效**（§3.7.6 注），
> 或重绘时按 `key` **复用已有控件实例**。**必须写 21.6 这条断言**，
> 否则这个 bug 在代码审查里极难看出（两个模块各自都对，是组合出的错）。
