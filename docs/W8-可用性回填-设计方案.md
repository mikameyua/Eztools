## §1 功能概述

### 1.1 一句话

**把"配置/状态与实际不一致"的两处说谎修成"必须说得清为什么，且必须给得出出口"。**

### 1.2 两个缺陷（B1 / B2）

#### B1 — 索引状态误报：Core 未跑时报"正在建索引…"

**症状**（用户 2026-10-02 实机发现）：

提权 Core（`ezt-core.exe`）不在运行时，UI 把"索引不可用（Core 未启动）"误报成"**正在建索引…**"。用户**永远等不到建好**，也不知道要去启动 Core。

**端到端链路（已逐点核实）**：

```
① Core 未运行，ezt-index 自举时读 MFT 失败
   src/Eztools.Index/CoreMftClient.cs
   ⇒ throw MftReaderException(PrimitiveErrorCodes.CoreUnavailable /* -32017 */,
       "Core 特权服务未运行（无端点登记）。建索引需要先 `ezt core start --elevate`。")

② 结构化传播（VolumeWorker → VolumeClassifier）
   src/Eztools.Index/VolumeClassifier.cs
   Classify(-32017) => FailureKind.CoreUnavailable
   FailureText[CoreUnavailable] = "Core 特权服务未运行（建索引需要它）"

③ 自举收尾 —— ★ 死锁在这里形成
   src/Eztools.Index/IndexBootstrap.cs
   errors.Add(...) ; failedVolumes.Add(VolumeClassifier.Failure(...)) ; continue
   ...
   if (targets.Count > 0) { service.InstallVolumes(targets); }   // ← 唯一的 Ready=true 出口
   if (errors.Count > 0) { service.LastError = string.Join("；", errors); }

   ★★ 所有卷都失败 ⇒ targets.Count == 0 ⇒ InstallVolumes 从不调用
      ⇒ SearchService.Ready 永远 false ⇒ 且无重试

④ 协议把两件事压成同一个错误码
   src/Eztools.Index/IndexRpcServer.cs:376
   if (!service.Ready) { await WriteErrorAsync(id, RpcErrorCodes.SearchNotReady /* -32001 */,
                                                "索引准备中（ready=false）"); return; }
   ★ "真在建" 与 "Core 没起来所以根本建不了" 都回 -32001

⑤ 宿主把它读成"索引未就绪"
   src/Eztools.Host/Search/SearchIndexClient.cs
   QueryAsync：error 帧 ⇒ throw SearchIndexException(code, message)

⑥ ★ 误报就在这一行生产出来
   src/Eztools.Host/Launcher/FilesProvider.cs · MapError
   ex.Code == RpcErrorCodes.SearchNotReady
     ⇒ new LauncherError(LauncherErrorKind.IndexNotReady, ex.Code,
          "正在建索引（首次全量约 10 秒级，取决于文件数）—— 打字会自动重试", ex.Message)

⑦ 渲染
   src/Eztools.Desktop/SearchWindow.cs · RenderResults
   if (model.Errors.TryGetValue(LauncherProviderRegistry.Files, out var filesError))
       { _status.Text = filesError.UserText; _statusRight.Text = ""; return; }
```

**第二个未分流的显示面**（同一缺陷的另一半，容易漏）：

```
src/Eztools.Desktop/SearchWindow.cs · ApplyVolumeSummary
   if (!status.Ready) { _volumesLine.Text = "索引准备中…（后台自举进行中，结果暂不可搜）";
                        ScheduleVolumePoll(); return; }
   ★ 同样把"Core 没起来"写成"后台自举进行中" ⇒ 用户看到的是一个永远在转、永远不会转完的状态
   ★ 并且 ScheduleVolumePoll 每 500ms 重拉一次，看起来"有进展"，实际恒不变
```

**严重度**：**不是"体验差"，是"功能事实上不可用"** —— 文件搜索在"没先手动启 Core"这个**常见前置**下 100% 阻断，且 UI 主动给出错误指引（"打字会自动重试"→ 试一万次也不会好）。

#### B2 — 启动器配置热生效：改了配置不生效

**症状**（用户 2026-10-02 实机发现）：

`launcher.alias` / `launcher.usage` / `launcher.providers` 改完**需重启托盘**才生效。用户实测：`usage=false` 写进配置后，`usage.json` **仍在增长** —— 配置系统说"已保存"，运行中的程序行为不变。

**根因**：配置**读取层没有问题**（`ConfigStore.Load` 每次都真读文件，无缓存）；问题在**消费时机**：

```
src/Eztools.Desktop/TrayApplication.cs · EnsureSearchWindow()（第 1189 行）
   第 1197 行  var (prefs, configError) = LauncherPrefs.FromConfig(_host!.Configs);
   第 1209 行  if (prefs.UsageEnabled) { _usage = new LauncherUsageStore(...); _usage.EnsureLoaded(); }
   第 1216 行  var (parsedAliases, aliasError) = LauncherAliases.FromConfig(_host.Configs);
   第 1225 行  var providers = LauncherProviderSet.Build(prefs, ...);
   第 1235 行  _searchWindow = new SearchWindow(client, providers, ...);
   ★ 而 EnsureSearchWindow 第 1191 行：if (_searchWindow is not null) { return; }  ← 一次性

⇒ 窗口活着的期间，prefs / aliases / _usage / providers **全部冻结在首次创建那一瞬间**
```

**已存在的挂点**（★ 这是本项修法成本极低的原因）：

```
src/Eztools.Desktop/TrayApplication.cs · ToggleSearchWindow()（第 1277 行）
   EnsureSearchWindow();
   _appsProvider?.InvalidateIfChanged();   // ← W7-b 已经在"每次唤出"做一次指纹比对
   _searchWindow!.Toggle();
★ 同一位置加一次 launcher.* 配置指纹比对即可，不需要新增触发点
```

**严重度**：**误导性（"静默说谎"）**。用户改了配置、程序说保存成功、行为不变 ⇒ 用户会开始怀疑整个配置系统。比"改不了"更糟，因为没有任何反馈说明"要重启"。

### 1.3 两条红线的对账

| 红线                                | 出处                              | B1 命中                      | B2 命中              |
| --------------------------------- | ------------------------------- | -------------------------- | ------------------ |
| **降级/告警类信号必须有可达出口**（先问"写到哪、谁收得到"） | `docs/代码审查规范与流程.md` §3.3 · §3.9 | ✅ `-32017` 精确文案**全链路无人接收** | ✅ "需要重启才生效"从未告诉任何人 |
| **配置写了不生效 = 静默退化**                | 同上（S 家族）                        | ✅ 用户被引导去"打字重试"             | ✅ usage 关了还在写盘     |

> **为什么这决定了"不单独立项"**：红线级问题**没有"要不要做"的裁量空间**。W8 提供的是波次容器与验收面，不是可行性论证。

### 1.4 正确行为（用户原话）

> "合理的做法是托盘检测到 Core 不可达时，状态行给'**搜索需要启动核心服务，点此启动**'之类的可达出口（提权必须过 UAC，宿主不能静默拉起，但可以一键触发）。"

三个硬要求，逐条落进需求：

1. **托盘能检测到 Core 不可达** ⇒ FR-1
2. **状态行给出可达出口**（一个能点的东西）⇒ FR-2
3. **提权必须过 UAC，宿主不能静默拉起，但可以一键触发** ⇒ FR-3 + NFR-1

## §2 需求

### 2.1 功能需求（FR）

| #            | 需求                                                                                                                                            | 验收要点                                                                            |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| **FR-1**     | **三态区分**：索引"未就绪"必须能区分 ①**正在建索引**（正常，等即可）②**索引不可用 · Core 未运行**（需用户动作）③**索引不可用 · Core 在跑但未提权**（需用户动作，且能说清已连上但权限不够）                              | 三种前置各自可构造 ⇒ 三条断言分别验证文案与可点性                                                      |
| **FR-2**     | **两个显示面都分流**：`_status.Text`（结果区状态行，`FilesProvider.MapError` 出口）与 `_volumesLine.Text`（卷清单行，`ApplyVolumeSummary` 的 `!Ready` 分支）**都必须分流**，不得只修一个 | 两条断言，分别针对两个控件；★ 只修一个 ⇒ 另一个仍然说谎                                                  |
| **FR-3**     | **可达出口**：检测到"Core 未运行/未提权"时，状态行提供**可点击**的动作"启动核心服务"，点击 ⇒ 经由 `Verb="runas"` 提权启动 `ezt-core.exe`（**过 UAC**）                                     | 断言"可点"（`ToolTip`/`Tag` 存在，照 `OnVolumesLineClick` 既有模式）+ 手工项 M1 验证真弹 UAC         |
| **FR-4**     | **文案可自证原因**：出口文案必须包含"为什么"（"搜索需要启动核心服务"），不得只说"不可用"                                                                                             | 文案断言（含关键词） + 手工目测                                                               |
| **FR-5**     | **失败显式回显**：UAC 被取消 / 启动失败 / 启动后仍未就绪 ⇒ 状态行**原地更新**为失败原因，**不得**静默留在原状态                                                                          | 三条断言（取消 / 失败 / 起了但没通）；★ 照 `TrayApplication.SetSearchPausedAsync` 的"失败不缓存假已知值"模板 |
| **FR-6**     | **启动成功后自动刷新**：Core 起来后，索引侧状态应能自愈到"正在建索引…"或直接可用，**无需用户重启托盘**                                                                                   | 手工项 M2（真机：点启动 → 等 Core 起 → 索引自举 → 状态行变化）                                        |
| **FR-7**     | **诊断信息贯通**：`SearchStatusDto` 暴露协议已有的 `lastError` 字段（`IndexRpcServer` 已恒定回它，宿主消费面未取），供出口文案取"最具体的失败原因"                                          | 协议层断言 + `ezt search status --json` 层断言（★ 遵审查规范硬规则⑥：**新增协议字段两层都要测**）             |
| **FR-8**（B2） | **配置热生效**：`launcher.alias` / `launcher.usage` / `launcher.providers` 变更后，**下次唤出搜索窗即生效**，不需重启托盘                                                | 三键各自的"改 → 唤出 → 生效"断言（含 usage=false ⇒ **不写盘**）                                   |
| **FR-9**（B2） | **配置变更可见**：检测到配置变更而重建窗口时，**必须有一处可见回显**（状态行或气球提示都行），禁止静默重建                                                                                     | 断言"变更有回显" + 突变验证（摘掉回显 ⇒ 变红）                                                     |

### 2.2 非功能需求（NFR）

| #         | 需求                | 说明                                                                                                                                  |
| --------- | ----------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| **NFR-1** | **UAC 必过，禁静默拉起**  | Core 的任何启动路径都必须 `UseShellExecute=true` + `Verb="runas"`。**本项目不存在也不得新增任何"宿主自行拉起提权 Core"的路径**（含后台线程、计划任务、服务）。用户取消 UAC ⇒ 视为用户决策，只回显不重试 |
| **NFR-2** | **宿主零特权**         | 宿主对 Core 的探测**只读端点信息**（`CoreEndpoint.TryRead` + `IsPidAlive`），不连接、不握手、不改 `core.json`。清理陈旧端点仍归 CLI/Index 侧                           |
| **NFR-3** | **菜单构建不得同步等管道往返** | `TrayApplication` 菜单在 UI 线程同步构建（既有注释明确禁掉的写法："同步等一次管道往返正是本项目禁掉的写法"）⇒ 可达性检测必须**异步 + 带缓存**                                             |
| **NFR-4** | **检测不得引入可感延迟**    | 每次唤出搜索窗的附加成本 ≤ 数毫秒量级（与既有 `InvalidateIfChanged` 同档）。端点探测是**读一个 JSON 文件 + 一次 pid 存活检查**，不得引入管道往返                                      |
| **NFR-5** | **探针零副作用**        | 新增探针不得真弹 UAC（`--probe-*` 一律只跑检测与文案分流，不真启动）。★ 探针装配纪律沿 W7 §5                                                                          |
| **NFR-6** | **零回归**           | 见 §9.1 判据口径；既有 `FilesProvider.MapError` 的"正在建索引…"文案在**真在建**情形下**逐字不变**                                                              |
| **NFR-7** | **禁区**            | `src/Eztools.Core/**` **零改动**（安全面刚闭环，见 `代码审查报告-安全面专项-2026-09-29.md`）；`src/Eztools.Index/**` 改动**必须逐条论证并登记破例**（见 §8 决策 D3）           |

### 2.3 非目标（明确不做，防膨胀）

| 不做                                             | 理由                                                                                                                                                          |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Core 常驻自启 / 注册为服务 / 开机自启**                   | 用户明确要求"提权必须过 UAC"。任何常驻化都会绕过 UAC 或制造一个常驻提权进程 ⇒ 安全面倒退                                                                                                         |
| **静默拉起 Core（含"假装提权"的降级）**                      | NFR-1，绝对禁止。无提权 Core 时索引**根本不能用**（MFT 需提权），降级只会产生另一种谎言                                                                                                       |
| **`ezt-index` 自举重试机制**                         | 属"第二半"缺陷，但改动落在 `src/Eztools.Index/**`（W7 §10.1 第 27 行列为本波禁改目录）。**降级为 W8 的可选项**：先在不破约定的前提下把**出口**做出来（"点此启动"比"自动重试"更符合用户原话）；若实现时发现不重试就做不到 FR-6，再单独立项（见 §8 D3） |
| **索引进度条 / 百分比**                                | 协议已有 `indexing.filesDone/filesTotal`，但这是**新功能**，不属本波                                                                                                        |
| **把 Core 状态做成托盘常驻项（菜单里一个"Core：未运行"）**          | 会让菜单构建被迫取状态（破 NFR-3）。本波只做"出错时给出出口"，不做常驻状态面板                                                                                                                 |
| **B1 顺带重构 `LauncherErrorKind` 枚举语义**           | 新增枚举成员即可（`CoreUnavailable` / `CoreNotElevated`），不改既有成员语义（`IndexNotReady` / `IndexUnavailable` 保留原义）                                                         |
| **给 `launcher.providers` 做运行时热插拔 provider 实例** | W7 §2.3 已明确不做。本波 B2 只做"**变更 ⇒ 重建窗口**"，不做"**同一窗口内换集合**"（并发装配问题仍不碰）                                                                                           |

## §3 整体架构

### 3.1 一句话架构

**在"发现错误"与"告诉用户"之间，插一层"Core 可达性判定"，把单一的 `-32001` 分流成三种可判定状态，并为其中两种挂上可点击的出口。**

### 3.2 分层与依赖方向

沿用 W7 §3.2 的硬理由（纯逻辑落 Host 让 Cli selftest 能测；Win32/UI 落 Desktop 避 CA1416 破警告基线），本波不破例：

```
┌─ Eztools.Host（纯逻辑，无 UI/Win32）────────────────────────────┐
│  CoreAvailability.cs        （新建）Core 可达性判定（纯函数式）  │
│  CoreAvailabilityProbe.cs   （新建）探测：读端点 + pid 存活      │
│  Launcher/LauncherContracts.cs  → LauncherErrorKind 扩两成员    │
│  Launcher/FilesProvider.cs      → MapError 分流（三态）          │
│  Search/SearchIndexClient.cs    → SearchStatusDto 补 lastError   │
│  Launcher/LauncherConfigFingerprint.cs （新建）B2 配置指纹       │
└─────────────────────────────────────────────────────────────────┘
        ↑ 只读引用（NFR-2）
┌─ Eztools.Desktop（UI/Win32）───────────────────────────────────┐
│  SearchWindow.cs      → 两个显示面分流 + 出口点击 + 失败回显     │
│  TrayApplication.cs   → ToggleSearchWindow 加配置指纹比对        │
│  CoreLauncher.cs      （新建）Verb="runas" 提权启动（复用实现）  │
│  LauncherUiProbe.cs   → 新增探针模式                             │
└─────────────────────────────────────────────────────────────────┘
```

**分层守卫（G7，W7-b 新增）约束**：

- `src/Eztools.Host/Launcher/` **禁** UI 依赖（`System.Windows*` / `System.Drawing`）⇒ `CoreAvailability` 与 `LauncherConfigFingerprint` 落 Host 时**不得**引入任何 UI 类型。
- 两侧**都禁**引用 `Eztools.Core` ⇒ Core 可达性判定**不能**引用 Core 程序集（这也正合 NFR-2：只读端点文件，不调 Core 代码）。

### 3.3 五步数据流（B1）

```
① 用户唤出搜索窗，输入触发 files provider 查询
   ↓
② FilesProvider 收到 SearchIndexException(-32001)
   ↓
③ ★ 分流的唯一决策点：FilesProvider.MapError 变 MapError(ex, availability)
      availability = CoreAvailabilityProbe.Snapshot()   ← 缓存的、非阻塞的
   ├─ 真在建（availability 说 Core 在跑且提权） ⇒ IndexNotReady（文案逐字不变）
   ├─ Core 未运行        ⇒ IndexUnavailable + CoreUnavailable + canLaunch=true
   └─ Core 在跑但未提权  ⇒ IndexUnavailable + CoreNotElevated + canLaunch=true
   ↓
④ LauncherError 带 canLaunch ⇒ LauncherResultSet ⇒ LauncherRenderModel
   ↓
⑤ SearchWindow.RenderResults 分流：
      canLaunch ⇒ _status.Text = "搜索需要启动核心服务，点此启动"
                  _status.Tag = LaunchAction（可点）
      否则      ⇒ 原样（"正在建索引…" 或 "搜索出错（code）：msg"）
```


### 3.4 探测的时机与缓存（NFR-3/NFR-4）

**铁律：探测只在"已经知道出错了"之后发生，绝不在正常路径上预探。**

| 时机                               | 是否探测                | 理由                           |
| -------------------------------- | ------------------- | ---------------------------- |
| 菜单构建（`AppendSearchIndexSection`） | ❌ **禁止**            | NFR-3：UI 线程同步构建，任何阻塞都是卡菜单    |
| 正常查询成功                           | ❌ 不探                | 成功不需要解释                      |
| **查询回 `-32001`**                 | ✅ **探一次**           | 只在需要解释时才付代价                  |
| `ApplyVolumeSummary` 见 `!Ready`  | ✅ **探一次**（异步）       | 卷清单行的同一缺陷面                   |
| 缓存有效期                            | **2 秒**（常量，见 §10.4） | 出口点击后要能很快自愈（FR-6），但连续打字不得每次探 |

**探测成本**：`CoreEndpoint.TryRead` = 读一个 JSON 文件（~200B）；`IsPidAlive` = 一次 pid 检查。合计 **微秒~毫秒级**，且**发生在后台线程**。**不含管道握手**（NFR-2：只读端点，不连）。

## §4 交互契约

### 4.1 状态行三态文案矩阵

| availability               | `_status.Text`                                        | 可点 | `_status.Tag`               |
| -------------------------- | ----------------------------------------------------- | -- | --------------------------- |
| `CoreOk`（在跑且提权）            | `正在建索引（首次全量约 10 秒级，取决于文件数）—— 打字会自动重试`（**逐字不变**，NFR-6） | ❌  | `null`                      |
| `CoreNotRunning`           | `搜索需要启动核心服务，点此启动`                                     | ✅  | `LauncherAction.LaunchCore` |
| `CoreNotElevated`          | `核心服务未提权，搜索用不了 —— 点此以管理员身份重启`                         | ✅  | `LauncherAction.LaunchCore` |
| `CoreProbeUnknown`（探测本身失败） | 回落到"正在建索引…"**并附诊断**（见 §11.3 兜底）                       | ❌  | `null`                      |
| 其他错误（非 -32001）             | `搜索出错（{code}）：{message}`（**逐字不变**）                    | ❌  | `null`                      |

> **`CoreProbeUnknown` 为什么回落到"正在建索引"**：探测失败时**没有证据**说 Core 不可用，而在三种可能里"正在建索引"**不会误导用户去做破坏性动作**（最坏结果是多等一会儿）；反过来若误报"Core 未运行"并给出一个点了没用的按钮，用户会去反复启动、甚至怀疑安装损坏。**不确定时给最保守的陈述** —— 但**必须带诊断**（§11.3）。

### 4.2 卷清单行（第二个显示面）

| availability        | `_volumesLine.Text`            | 可点      |
| ------------------- | ------------------------------ | ------- |
| `CoreOk` 且 `!Ready` | `索引准备中…（后台自举进行中，结果暂不可搜）`（逐字不变） | ❌（保持原状） |
| `CoreNotRunning`    | `索引不可用：核心服务未运行（点此启动核心服务）`      | ✅       |
| `CoreNotElevated`   | `索引不可用：核心服务未提权（点此以管理员身份重启）`    | ✅       |

**`ScheduleVolumePoll` 的处置**：`CoreNotRunning` / `CoreNotElevated` 时**停止 500ms 轮询** —— 因为轮询在"Core 没起来"时**永远不会变好**，只会制造"它在努力"的假象。改为**用户点击出口成功后**再重启轮询（FR-6）。★ 这条要有断言（"不可用时不轮询"）——否则"看起来在转"本身就是这个缺陷的一部分。

### 4.3 出口点击的完整交互

```
点击"启动核心服务"
  ↓
① _status.Text 立即改为："正在启动核心服务（请在系统弹窗中允许）…"   ← 立刻给反馈，不等 UAC 返回
   （防"点了没反应"，尤其是 UAC 弹窗出现在另一个屏幕/被遮挡时）
  ↓
② 异步调 CoreLauncher.LaunchElevatedAsync()   （后台线程，Verb="runas"）
   ↓
③ 分三路：
   ├─ 用户取消 UAC          ⇒ _status.Text = "已取消启动核心服务（搜索仍不可用）"   [FR-5]
   ├─ 启动抛异常            ⇒ _status.Text = "启动核心服务失败：{message}"          [FR-5]
   └─ 进程起来了            ⇒ _status.Text = "核心服务已启动，正在建立索引…" + 重启轮询 + 失效探测缓存
                              ↓ 等 Core 登记端点（轮询 TryRead，≤8s，照 CoreCommand.StartAsync）
                              ↓ 超时仍未登记 ⇒ _status.Text = "核心服务启动后未登记端点（可能被拦截）—— 请从菜单重试"
  ↓
④ 全程**不阻塞 UI 线程**，不改动 providers/窗口结构
```

**为什么"立刻给反馈"是必须的**：UAC 弹窗可能出现在另一个屏幕、可能被遮挡、可能 1~2 秒才出现。没有即时反馈 ⇒ 用户会连点，可能触发多个 UAC 弹窗。

### 4.4 B2 的交互契约

| 触发                          | 行为                                                                                              |
| --------------------------- | ----------------------------------------------------------------------------------------------- |
| 唤出搜索窗（`ToggleSearchWindow`） | 算一次 `launcher.*` 配置指纹；与窗口创建时的指纹比对                                                               |

**为什么是"重建窗口"而不是"原地换 provider 集合"**：W7 §2.3 已排除热插拔（并发装配问题）。重建窗口是**本项目已有的、被验证过的**路径（`_searchWindow.Closed += (_,_) => _searchWindow = null;` 自愈逻辑就是为它写的）⇒ **零新机制**。

| 2  | `MapError(ex, CoreOk)` ⇒ `IndexNotReady` 且文案**逐字等于**"正在建索引（首次全量约 10 秒级，取决于文件数）—— 打字会自动重试"             | selftest              | 改任一字 ⇒ 红                                    |
| 3  | `MapError(ex, CoreNotRunning)` ⇒ `Kind=IndexUnavailable` + `CanLaunch=true` + 文案含"启动核心服务"             | selftest              | 摘掉 `CanLaunch` ⇒ 红                          |
| 4  | ★ **`-32001` 的三种来源分流**：真在建 ⇒ 不出按钮；Core 未运行 ⇒ 出按钮；其他失败 ⇒ 出**诊断**不出按钮（R9）                               | selftest + acceptance | 把 R9 的 `lastError` 判据摘掉 ⇒ "其他失败"变成"出按钮" ⇒ 红 |
| 5  | `SearchStatusDto.LastError` 从协议贯通到 DTO（★ **两层都测**：协议原样回 + CLI `--json`）                               | acceptance            | 删 CLI 层字段 ⇒ 红（同族第 3 次踩过的坑）                  |
| 6  | `LauncherConfigFingerprint` 对三键各自的变更敏感、对无关键不敏感                                                        | selftest              | 指纹算法漏一个键 ⇒ 红                                |
| 7  | ★ **`usage=false` 后不再写盘**（B2 的原始症状）                                                                   | 探针/手工                 | 不重建窗口 ⇒ usage.json 仍增长 ⇒ 红                  |
| 8  | **配置变更后有可见回显**（FR-9）                                                                                  | 探针                    | 摘掉回显 ⇒ 红                                    |
| 9  | ★ **`CoreNotRunning` 时停止 `_volumesLine` 轮询**（§4.2 的"假努力"）                                             | 探针                    | 不停轮询 ⇒ 断言"轮询计数不增长"失败 ⇒ 红                    |
| 10 | **菜单构建路径零探测**（NFR-3 反向断言）：构建 `AppendSearchIndexSection` 期间探测调用计数 = 0                                  | selftest（计数器注入）       | 在菜单构建里加探测 ⇒ 计数 >0 ⇒ 红                       |
| 11 | 探针**不真弹 UAC**（NFR-5）：`--probe-*` 全程 `CoreLauncher` 调用计数 = 0（且断言探针**确实走到了**出口分流分支 —— ★ 正向对照，防"整轮没跑"也绿） | 探针                    | 探针里真调 Launch ⇒ 红；去掉分流分支 ⇒ 正向对照红             |


**断言纪律（逐条适用）**：

- 每条断言必须**落数字或退出码**（禁 `cmd | grep -q`）
- **"什么都没发生"是最弱的断言** ⇒ 每条静默类断言必须配**正向对照** + **定长泵**
- **跳过必须计数**（守卫 G6）并明说"满额随之少 N"
- **禁用"被上游结构保证"的恒真断言**（踩坑 §2.33③）
- 探针**就绪信号不得用"行数 > 0"**（踩坑 §2.35①）⇒ 一律用**渲染日志**

### 10.3 关键实现细节（★ 最易写错的地方）

| # | 点                                            | 说明                                                                                                                                     |
| - | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 1 | ★★ **`CoreAvailabilityRules.Decide` 必须是纯函数** | 它是唯一能被 selftest 全量真值表覆盖的地方。若把 IO 混进去，就只剩手工验证 ⇒ 回到"靠人眼发现误报"的老路。**IO 全在 Probe，判定全在 Rules**                                               |
| 2 | ★★ **`CanLaunch` 的默认值必须是 `false`**           | 既有 `LauncherError` 构造点有若干处；给默认值 ⇒ **零改动**；若给 `true` 默认 ⇒ 每个既有错误都长出按钮                                                                   |
| 3 | ★ **`Unknown` 的兜底**                          | 见 §4.1 / D4。**这是本波最容易做错的一格**：探测失败时给"启动核心服务"按钮 = 把不确定变成误报                                                                               |

## §11 异常与边界

### 11.1 探测的边界情形

| 情形                                                 | 判定                | 理由                         |
| -------------------------------------------------- | ----------------- | -------------------------- |
| `core.json` 不存在                                    | `CoreNotRunning`  | 无端点 = 没起                   |
| `core.json` 存在但解析失败                                | `Unknown`         | 可能是半写状态（原子写失败）⇒ 不据此给指引     |
| `core.json` 存在，pid 已死                              | `CoreNotRunning`  | 陈旧端点（Index 侧会清理，宿主只读）      |
| `core.json` 存在，pid 活着但**不是 `ezt-core`**            | `Unknown`         | ★ pid 复用！**必须按进程名复核**（R1④） |
| `core.json` 存在，pid 活，是 `ezt-core`，`Elevated=true`  | `CoreOk`          | 真在建                        |
| `core.json` 存在，pid 活，是 `ezt-core`，`Elevated=false` | `CoreNotElevated` | ★ 仅在 D2 选定"用端点字段"时可达       |
| 读 `core.json` 抛异常（权限/IO）                           | `Unknown`         | 探测层失败 ⇒ D4 兜底              |

### 11.2 UAC / 启动的边界情形

| 情形                       | 处理                                                    |
| ------------------------ | ----------------------------------------------------- |
| 用户取消 UAC                 | `Cancelled` ⇒ 状态行"已取消启动核心服务（搜索仍不可用）"（FR-5）。**不重试、不催** |
| 已有 Core 实例在跑（exitCode 3） | 视为成功（幂等，照 `CoreCommand.StartAsync`）⇒ 直接进"等端点登记"       |
| 启动后 ≤8s 未登记端点            | `NotRegisteredAfterWait` ⇒ "启动后未登记端点（可能被拦截）—— 请从菜单重试" |
| 启动命令本身失败（文件不存在等）         | `Failed(reason)` ⇒ "启动核心服务失败：{reason}"                |
| 点击时窗口已被关闭                | 忽略（无 UI 可更新）；进程照常启动（不因 UI 消失而放弃）                      |

### 11.3 探测失败（`Unknown`）时的兜底 —— ★ 决策 D4 的具体化

```
_status.Text = "正在建索引（首次全量约 10 秒级，取决于文件数）—— 打字会自动重试"
               + （若 lastError 非空）"\n诊断：{lastError 摘要}"
```

- **回落到"正在建索引"**：仅陈述事实（`Ready=false`），**不引导任何动作** ⇒ 不会误导。
- **附诊断**：满足红线的"必须说得清为什么"——即便我们不知道原因，也要把**已知的原始诊断**摆出来。
- ★ **不得**在此格出"启动核心服务"按钮（这就是 D4 与"报不可用"的分界）。

### 11.4 `lastError` 非 Core 类失败时的处置（R9）

```
若 lastError 非空 且 不含 Core 相关关键词（"Core"/"特权"/"提权"/"端点"）
  ⇒ 不出启动按钮；显示 "索引建立失败：{lastError}"
```

★ 这一格的存在理由：`LastError` 是**所有**失败摘要的汇合处（卷枚举/权限/IO 都会进）。**盲目给启动按钮 = 让用户去启动一个已经在跑的东西**。

### 11.5 明确否决清单（防止反复重提）

| 否决                             | 理由                                                        |
| ------------------------------ | --------------------------------------------------------- |
| 宿主后台静默拉起 Core                  | NFR-1，绝对禁止                                                |
| 把 Core 注册成 Windows 服务 / 计划任务   | 绕 UAC 或制造常驻提权进程 ⇒ 安全面倒退                                   |
| 在托盘菜单里同步显示 Core 状态             | 破 NFR-3（菜单 UI 线程同步构建）                                     |
| 用 `IsConnected`/管道探测判断 Core 存活 | 破 NFR-2（零特权只读）；且本项目已记录 `IsConnected` 不可靠（RI-6 期间的方案 A 被否） |
| 把探测做成"每 N 秒轮询"的后台任务            | 无谓 IO + 探测价值只在出错瞬间                                        |
| 给"启动核心服务"提示加关闭开关               | 出口不可关（红线）                                                 |

## §15 命名与术语

| 术语                     | 含义                                                              |
| ---------------------- | --------------------------------------------------------------- |
| **availability / 可达性** | Core 是否在跑且具备建索引所需权限（本波引入的判定对象）                                  |
| **三态**                 | `CoreOk` / `CoreNotRunning` / `CoreNotElevated`（+ `Unknown` 兜底） |
| **出口 / 可达出口**          | 审查规范 §3.9 的概念：降级信号必须有一条"用户够得着"的路径。本波中是"点此启动"                    |
| **一键触发 vs 静默拉起**       | 前者 = 用户点击 ⇒ 弹 UAC ⇒ 用户确认才启动；后者 = 程序自行启动 ⇒ **本项目禁止**             |
| **分流**                 | 把同一个 `-32001` 按 availability 映射到不同 `LauncherErrorKind` 与文案      |
| **假努力**                | 本波新增的反模式：`CoreNotRunning` 时仍在 500ms 轮询，制造"正在进展"的假象              |
| **保守落点**               | 不确定时的默认陈述选"最不误导"的那一个（D4：`Unknown` ⇒ "正在建索引"）                    |
| **指纹 / B2 指纹**         | `launcher.*` 三键**有效值**的摘要，用于判断"窗口是否该重建"                         |

### 7.2 与方案的偏差（逐条含原因）

| # | 方案原写 | 实际做法 | 原因 |
|---|---|---|---|
| ① | "0 个新文件"（`CoreAvailability` 塞进 `FilesProvider.cs`） | **新建 `CoreAvailability.cs`** | 本项目结构是"一概念一文件"（`FuzzyMatcher`/`LauncherPrefs`/`LauncherUsageStore` 皆如此）。往 `FilesProvider` 里塞三态枚举 + 采集 + 判定 + 缓存会让那个文件同时承担"查询包装"与"环境探测"两件事。**"精简"指的是不搞流程包装，不是把不相干的代码挤进一个文件**。 |
| ② | `FilesProvider` 的探测参数**必填** | **可选，默认 `Unknown`** | 探针与 `SearchUiProbe` 有 **13 处** `new FilesProvider(client)`，而那些是 W7 "**文件项渲染零变化**"（FR-10）的证据链 —— **一行都不该为 W8 而改**。默认值让它们零改动，代价是"忘了注入会静默退回旧文案"，因此改走**正向断言**兜住：`corestatus` 探针验"注入了就分流"，37.2~37.4 走真实查询链路（见偏差③）。 |
| ③ | 断言直接调 `FilesProvider.MapError` | **走 `QueryAsync` + 假传输** | `MapError` 是 internal（Cli 看不见）。更重要的：直调映射函数会漏掉最可能的回归 —— **装配时忘了把探测传进 provider**。走真实链路让 37.2~37.4 同时守住"注入生效"这件事（"什么都没发生"类断言必须配正向证据）。 |
| ④ | 配置指纹"托盘内联，不新建类" | **上移到 `LauncherPrefs.Fingerprint`** | 它必须有机器断言（**漏一个键 = 那项配置静默不生效**，而"静默不生效"正是 B2 的原始症状）。放在 Desktop 私有方法里 selftest 测不到。 |
| ⑤ | 两个显示面都给"点此启动" | **动作入口单点**：状态行可点，卷清单行只说事实（"…点上方状态行启动"） | 两个出口会形成两套话术，且卷清单行的点击语义已被"暂停时点击=恢复索引"占用（`ToolTip is not null` 判定）—— 复用同一个入口必然产生歧义。 |
| ⑥ | 用 `_status.TextChanged` 事件把"文案变更 ⇒ 可点性归零"做成默认 | **逐处显式声明** `SetStatusLaunchable(false)` | WPF 的 **`TextBlock` 没有 `TextChanged` 事件**（首版按设想写了，编译当场报 CS1061）。`DependencyPropertyDescriptor` 可行但要手工 `RemoveValueChanged`，对每次重建窗口的路径是泄漏隐患。改为显式：状态行 16 处赋值点逐一声明（新增赋值点由注释 + 探针断言约束）。 |
| ⑦ | （未提及） | **索引进程 `Dispose` 丢后台线程** | 实测发现 `Dispose()` 走 `tool.stop` 并 `WaitForExit(3 s)`，而重建发生在**热键/点击路径**（UI 线程）⇒ 同步等就是卡住整个托盘。`Flush` 同理。两者都无"完成后才知道结果"的依赖，故丢 `Task.Run`。代价是可能短暂并存新旧索引进程（新进程懒启动 + 用户还要打字，实际窗口很小），取舍为不卡 UI。 |
| ⑧ | （未提及） | **重建时一并重置 `_usage`** | 实现时发现"`usage=false` 后文件仍在长"的**另一半**根因：`EnsureSearchWindow` 只在启用时新建 store、**从不清旧实例** ⇒ 即使重建窗口，旧的 `UsageRecorder` 仍持有旧 store 继续写。不重置就是修了一半。 |
| ⑨ | 出口点击后"通知托盘重建窗口" | `CoreLaunchRequested` 返回后 `SearchWindow` 先判 `_disposed` 再回显 | 成功路径会在回调里重建窗口 ⇒ 本实例已被关闭，往废弃窗口写字没有意义、还会给事后调试留假证据。 |
| ⑩ | 手工清单只有 M1/M2/M3 三项（v1.0 清单） | **追加机器化**（2026-10-03）：`CoreLauncher` 的可判定部分抽成**四个纯函数** —— `BuildStartInfo`（提权参数）/ `MapLaunchFailure`（1223 ⇒ Cancelled）/ `DecideWaitStep`（就绪判定单轮）/ `MessageFor`（结局文案）；探针 `corestatus` 加 `launch` + `echo` 两段；`verify-desktop.py` 加 **8 条**断言。手工项缩到**三段真正不可自动化**的。 | 菲比指出"能自动化跑的有些步骤" —— **复查确认他是对的**。最严重的一条：**"是不是真的走了 UAC 提权"是 NFR-1 红线，却只靠人眼看弹窗**（这正是审查规范 §3.9 要求必须有机器证据的那类）。缩完剩下的三段是：① **真 UAC 弹窗**（操作系统行为，弹窗只能弹在真人面前）② **1223 的平台假设**（代码里只能 `new Win32Exception(1223)` 验映射，**证不了"真取消时抛的就是 1223"**）③ **真按热键触发"下次唤出"**（键盘注入在本项目是禁区）。★ 一条值得记的区分：**能机器化的是"代码对假设的处理"，机器化不了的是"假设本身成不成立"** —— 所以 M2 不是重复劳动。 |
