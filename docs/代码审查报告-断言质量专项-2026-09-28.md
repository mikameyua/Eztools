## 二、🔴 AQ-1（已修）`verify-desktop` live 段：2 条断言**静默跳过且不计数**

### 位置
`scripts/verify-desktop.py` ·「live 变体（真链路 lei/LEI 大小写）」段

### 现象与证据（**突变实验**，不是推断）

| 步骤 | 结果 |
|---|---|
| 正常跑（夹具在） | 通过 **153** / 失败 0 |
| 把夹具 `_scratch/manual/g2first2/index` 挪走 | 通过 **151** / 失败 0 —— **少了 2 条，汇总行没有"跳过"字样** |
| 日志里的唯一痕迹 | 一行 `info("live 探针跳过：未找到现成索引夹具…")` —— **不计数** |

**两次都报"失败 0"。** 任何人看"通过 151 / 失败 0"都会认为验收正常 ——
而这台机器上已经有 **2 条断言从未执行**。

### 为什么定 🔴（两条独立理由叠加）

1. **跳过不计数**（M15 / 技能 §二.1）：通过数变成**依赖环境的随机变量**，
   且这个漂移**没有任何信号**。本仓早就有这条纪律（`_step17_ocr.sh` 的 `SKIPPED += 2` +
   "满额随之少 2"文案），但这一段漏了 —— 同一项目两种做法。
2. **依赖手工夹具**（技能 §七「被测对象必须显式钉住，不能靠环境恰好如此」）：
   夹具 `_scratch/manual/g2first2/index` 是**手工作坊产物**，而 `_scratch/` 被 `.gitignore`
   ⇒ **干净机器 / CI 上必然跳过** ⇒ 这 2 条断言在自动化里**长期等于不存在**。

### 修法
两条跳过路径**各自精确计数**（数一遍再写 —— 技能提醒过"注释写跳过两条、实际三条"）：
- 夹具缺失 ⇒ `SKIPPED += 2`（退出码断言 + ★★大小写断言都没跑）
- 夹具在但未就绪 ⇒ `SKIPPED += 1`（只有 ★★大小写断言被跳过，退出码断言照跑）

并打**现场快照**（夹具路径 + 怎么补），让"跳过"变成可观测量。

### 修复后的同一突变（对照）

```
修复前： 通过 151 / 失败 0
修复后： 通过 151 / 失败 0 / 跳过 2（环境依赖分支未满足，总断言数因此少于满额）
         [跳过] 2 条 live 断言：未找到现成索引夹具 …\g2first2\index
```

## 三、🟡 AQ-2（已修）`--probe-clip-ocr` 语言包缺失：3 条断言静默跳过、不计数

### 位置
`scripts/verify-desktop.py` · 1c-7「图片 OCR 提字」段

### 现象
探针的设计是**对的**（语言包缺失时如实落盘 `skipped="no-language-pack"` 并返回 0，
不伪装成功）；验收侧也**读了**这个信号（`if ocr.get("skipped"):`）—— 但那个分支
**只打一行 `info(...)`，`SKIPPED` 没有递增**。

⇒ 本机没装 OCR 语言包时，**3 条 ★/★★ 断言静默不执行**，通过数少 3，汇总行不显示"跳过"。

### 同项目内的不一致（这是本条的定性依据）
`scripts/_step17_ocr.sh` 的同口径分支写的是：

```bash
SKIPPED=$((SKIPPED + 2))
printf '  [跳过] OCR 语言包缺失（rc=7，R1 环境依赖分支）—— 语言计数断言跳过，满额随之少 2\n'
```

**同一项目、同一个环境条件，两种做法。** 本次对齐到前者（计数 + 明说满额少几条）。

### 顺带修的「名字与判据不符」（技能 §四：名字也是契约）

```python
# 改前：名字说"按跳过处理"，判据只是 returncode == 0
ck("图片 OCR 提字探针退出码 0（语言包缺失时按跳过处理）", r.returncode == 0, ...)
```

而 `TrayApplication.RunProbeClipOcr` 的注释明写**语言包缺失时退出码 0**
⇒ 这条断言在跳过路径上会**计成 PASS**，名字却让人以为"它知道自己在跳过"。
改为如实描述判据：`…（语言包缺失时探针如实落盘 skipped 并返回 0，不算失败）`。

### 补的 8 条断言（`ezt runtime payloads`）

它是 `runtime install` **找包的前提**（install 的输入就是这份清单），三面却全零命中 —— 典型的纯空白格子。

设计上刻意区分两类（**本次审计刚换来的两条教训**）：

| 类别 | 断言 | 环境依赖 |
|---|---|---|
| **形状（无条件跑）** | 退出码 0 · JSON 数组可解析 · 六字段齐全 · `runtime` 均为 python · `version` 形如 `X.Y.Z` · `size` 均 > 0 · **每个 `path` 都指向真实存在的文件（0 悬空）** | 否 |
| **数量（环境依赖）** | 载荷条数 ≥ 1 | 是（`payload/` 被 gitignore，干净机器上为 0 ⇒ **跳过并计数**，附补法） |

细节：
- `path` 用 **JSON 解析**而非 `grep/cut` —— JSON 里是转义反斜杠（`"D:\\01-..."`），
  grep 拆必然踩转义坑（踩坑全集 §2.17⑤ `\uXXXX` 同族）
- 解析失败时 6 个统计量全部输出 `PARSE_FAIL` ⇒ 下游每条断言**响亮失败**，
  **不许靠 `:-默认值` 侥幸通过**（已单独验证该路径）
- 显式传 `--install-root`（§七：不能靠 cwd/默认值凑巧）

### 11.1 ① live 段夹具依赖 → **把未就绪侧改成无条件断言**（比"补夹具"更好的解法）

原建议是"用 `ezt-index` 现场建索引"。**调研后否掉了这条**：

| 事实 | 结论 |
|---|---|
| `ezt-index` **没有"立即建索引"的入口**，索引走 MFT 枚举 | 需要**提权 Core**（W3 手工清单里的 G2-a 步骤含一次 UAC） |
| ⇒ 夹具**没法**在无人值守的验收里自动构造 | "自动补夹具"这条路走不通 |

**换了个方向**（技能 §二 的判据：*"一条断言能否无条件跑，取决于它的前置状态能否**总能**被构造出来"*）：

> 那段断言要的前置是「**有**一个已就绪的索引」—— 构造不出来；
> 但它的**互补面**要的前置是「**没有**索引」—— 而"没有索引"**总能构造**：一个全新的唯一临时根就是。

于是把 live 探针拆成两条互补路径：

| 路径 | 前置 | 断言数 | 可跑性 |
|---|---|---|---|
| **未就绪侧**（新增 1c-6b） | 全新唯一临时根（`_scratch/vd-empty-root/<pid>`） | **5 条** | ✅ **无条件跑** |
| 已就绪侧（原 1c-6） | 手工索引夹具 | 2 条 | ⚠️ 环境依赖（跳过并计数，提示里给出可复制的构造步骤） |

**新增的 5 条无条件断言**（实测空根的探针输出正是 W3-d-1 的契约）：

| 断言 | 实测值（空根） |
|---|---|
| 空索引根上探针退出码 0（未就绪不是失败） | rc=0 |
| 空根如实报未就绪（**夹具有效性前提**，防"恰好就绪"） | `ready=false` |
| ★★ 未就绪时状态行说自己**正在建索引**（不是空白、不是假零数据） | `"正在建索引（首次全量约 10 秒级…）—— 打字会自动重试"` |
| ★ 未就绪时卷清单行说明"索引准备中" | `"索引准备中…（后台自举进行中，结果暂不可搜）"` |
| ★ 反向：未就绪时 `items=0` **且**状态行有解释（零值不许与"没搜到"混淆） | `items=0` + 文案 ≥8 字 |

> 最后一条正是踩坑全集 §2.24② 的「**异步快照零值必须区分"没有"与"还没查"**」——
> 这条契约以前**只由人工手测覆盖**，现在它进了无条件断言集。

### 11.2 ② actions：不是"零覆盖"，是**声明了但没有消费方**

调研推翻了上一轮的定性（原判"覆盖空白"）：

| 证据 | 结果 |
|---|---|
| `ezt invoke filehash.action.hashFile` | ❌ `未找到命令`（只认 `commands`） |
| 全仓 grep `.Actions` | 只有 `ManifestParser` 解析 + `ezt list/info` **列举** —— **无任何派发路径** |
| `when` 是否被求值 | **从不**（无消费者） |
| 设计文档 §4.5 贡献点表 | 标 `✅ P0`、用途写"文件、选中文本动作（右键 / 拖入）" |

**这与 `search` 当年完全同型** —— 而该表自己的注释就写着这件事是必须防的：
*"凡'文档里列了但代码没有'的贡献点必须显式标状态 —— 否则读文档的人会把'写在表里'当成'已经能用'"*。

处置（三件）：
1. **设计文档 §4.5 状态列更正**：`actions` 改为「P0 只做了**解析 + 列举**；`when` 无消费者、**派发未实现**」，并加一段说明（含与 `search` 同型的对照 + 待拍板项）。
2. **acceptance 新增 5 条断言**（第 3b 节）：4 条钉**已实现的解析契约**（每条目都带 `actions` 键 / 必为数组 / 至少 1 条声明 / 每条 `id·title·when·handler` 四字段非空）
   + 1 条**钉住"不可派发"这个当前限制**（`ezt invoke <actionId>` 必须给出"未找到命令"而非静默成功）。
   最后这条是**故意设的更新点**：将来实现派发时它会变红，提示同时更新文档与断言。
3. **台账登记**：`actions` 要么"不做"（照 `search` 前例从表里删）、要么排期实现派发 —— 现状"两条声明挂着没有消费方"是第三种，应尽快收敛。

### 11.2.1 ★ 补的断言当场又抓出第 4 处缺口：`ezt list --json` 丢了 `handler`

新加的四字段断言（`id·title·when·handler` 必须齐全）**第一次跑就红了** —— 复现后定性明确：

| 展示面 | actions 元素含哪些字段 |
|---|---|
| `ezt list --json` | `id` · `title` · `when` —— **漏 `handler`** |
| `ezt info`（同一文件另一处） | `id` · `title` · `when` · **`handler`** ✓ |
| → 同一份声明的**两个展示面不一致** | 读 `list --json` 的人**无法判断 handler 解析出来没有** |

同一段代码里 `commands` 分支**是带 `handler` 的**，唯独 `actions` 分支漏了 ⇒ 属遗漏而非有意精简。
修法：补上 `["handler"] = a.Handler`（1 行）。

### 11.3 ④ 跳过必须计数 → 已机器化（**G6**），首扫即抓到第 3 处真实缺口

新增 `scripts/review-guards.py` 的 **G6**：扫码时只要有「给人看的跳过文案」
（sh 的 `printf/echo`、py 的 `info(...)`），附近 6 行内就必须出现 `SKIPPED` 计数。

**精度设计**（避免把"断言名里含跳过"误报）：只认**输出语句**，
`check "…跳过…"` / `ck(…)` 是**断言名**不是跳过通知 ⇒ 一律排除；注释行排除。
突变验证：**21 条**（新增 G6 正向 1 条 + 反向 1 条）。

**首扫命中 1 处真实缺口**（不是误报）：

```
verify-desktop.py:1418  info("NotifyIconSettings 键不存在（更早的 Windows 版本），跳过")
```

分析后确认它是**真缺陷**：那条 info 描述的"跳过"不是跳过断言，而是**取证前提不成立**
（更早的 Windows 没有该注册表键）—— 但下面的断言 `ck("托盘图标已登记进通知区域", len(found) > 0)`
**照样跑**，于是缺键的机器会**假红**。
修法：改成真正的**跳过并计数**（`SKIPPED += 1` + 说明"满额随之少 1"）——
与本次 AQ-1/AQ-2 的修法同一口径。

> 这一处是 G6 上线**后立刻**抓到的：说明"把纪律机器化"不只是防未来，还能把**同一模式的历史遗留**一次扫干净。
