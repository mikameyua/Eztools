## 二、🔴 AQ-1（已修）`verify-desktop` live 段：2 条断言**静默跳过且不计数**

### 位置
`scripts/verify-desktop.py` ·「live 变体（真链路 lei/LEI 大小写）」段

### 现象与证据（**突变实验**，不是推断）

| 步骤 | 结果 |
|---|---|
| 正常跑（夹具在） | 通过 **153** / 失败 0 |
| 把夹具 `_scratch/manual/g2first2/index` 挪走 | 通过 **151** / 失败 0 —— **少了 2 条，汇总行没有"跳过"字样** |
| 日志里的唯一痕迹 | 一行 `info("live 探针跳过：未找到现成索引夹具…")` —— **不计数** |

**两次都报"失败 0"。** 任何人看"通过 151 / 失败 0"都会认为验收正常 ——
而这台机器上已经有 **2 条断言从未执行**。

### 为什么定 🔴（两条独立理由叠加）

1. **跳过不计数**（M15 / 技能 §二.1）：通过数变成**依赖环境的随机变量**，
   且这个漂移**没有任何信号**。本仓早就有这条纪律（`_step17_ocr.sh` 的 `SKIPPED += 2` +
   "满额随之少 2"文案），但这一段漏了 —— 同一项目两种做法。
2. **依赖手工夹具**（技能 §七「被测对象必须显式钉住，不能靠环境恰好如此」）：
   夹具 `_scratch/manual/g2first2/index` 是**手工作坊产物**，而 `_scratch/` 被 `.gitignore`
   ⇒ **干净机器 / CI 上必然跳过** ⇒ 这 2 条断言在自动化里**长期等于不存在**。

### 修法
两条跳过路径**各自精确计数**（数一遍再写 —— 技能提醒过"注释写跳过两条、实际三条"）：
- 夹具缺失 ⇒ `SKIPPED += 2`（退出码断言 + ★★大小写断言都没跑）
- 夹具在但未就绪 ⇒ `SKIPPED += 1`（只有 ★★大小写断言被跳过，退出码断言照跑）

并打**现场快照**（夹具路径 + 怎么补），让"跳过"变成可观测量。

### 修复后的同一突变（对照）

```
修复前： 通过 151 / 失败 0
修复后： 通过 151 / 失败 0 / 跳过 2（环境依赖分支未满足，总断言数因此少于满额）
         [跳过] 2 条 live 断言：未找到现成索引夹具 …\g2first2\index
```

## 三、🟡 AQ-2（已修）`--probe-clip-ocr` 语言包缺失：3 条断言静默跳过、不计数

### 位置
`scripts/verify-desktop.py` · 1c-7「图片 OCR 提字」段

### 现象
探针的设计是**对的**（语言包缺失时如实落盘 `skipped="no-language-pack"` 并返回 0，
不伪装成功）；验收侧也**读了**这个信号（`if ocr.get("skipped"):`）—— 但那个分支
**只打一行 `info(...)`，`SKIPPED` 没有递增**。

⇒ 本机没装 OCR 语言包时，**3 条 ★/★★ 断言静默不执行**，通过数少 3，汇总行不显示"跳过"。

### 同项目内的不一致（这是本条的定性依据）
`scripts/_step17_ocr.sh` 的同口径分支写的是：

```bash
SKIPPED=$((SKIPPED + 2))
printf '  [跳过] OCR 语言包缺失（rc=7，R1 环境依赖分支）—— 语言计数断言跳过，满额随之少 2\n'
```

**同一项目、同一个环境条件，两种做法。** 本次对齐到前者（计数 + 明说满额少几条）。

### 顺带修的「名字与判据不符」（技能 §四：名字也是契约）

```python
# 改前：名字说"按跳过处理"，判据只是 returncode == 0
ck("图片 OCR 提字探针退出码 0（语言包缺失时按跳过处理）", r.returncode == 0, ...)
```

而 `TrayApplication.RunProbeClipOcr` 的注释明写**语言包缺失时退出码 0**
⇒ 这条断言在跳过路径上会**计成 PASS**，名字却让人以为"它知道自己在跳过"。
改为如实描述判据：`…（语言包缺失时探针如实落盘 skipped 并返回 0，不算失败）`。

### 补的 8 条断言（`ezt runtime payloads`）

它是 `runtime install` **找包的前提**（install 的输入就是这份清单），三面却全零命中 —— 典型的纯空白格子。

设计上刻意区分两类（**本次审计刚换来的两条教训**）：

| 类别 | 断言 | 环境依赖 |
|---|---|---|
| **形状（无条件跑）** | 退出码 0 · JSON 数组可解析 · 六字段齐全 · `runtime` 均为 python · `version` 形如 `X.Y.Z` · `size` 均 > 0 · **每个 `path` 都指向真实存在的文件（0 悬空）** | 否 |
| **数量（环境依赖）** | 载荷条数 ≥ 1 | 是（`payload/` 被 gitignore，干净机器上为 0 ⇒ **跳过并计数**，附补法） |

细节：
- `path` 用 **JSON 解析**而非 `grep/cut` —— JSON 里是转义反斜杠（`"D:\\01-..."`），
  grep 拆必然踩转义坑（踩坑全集 §2.17⑤ `\uXXXX` 同族）
- 解析失败时 6 个统计量全部输出 `PARSE_FAIL` ⇒ 下游每条断言**响亮失败**，
  **不许靠 `:-默认值` 侥幸通过**（已单独验证该路径）
- 显式传 `--install-root`（§七：不能靠 cwd/默认值凑巧）

## 七、审计方法自身的 2 次纠错（**值得记，与守卫 G4 同族**）

| # | 我一度以为 | 实际 | 教训 |
|---|---|---|---|
| 1 | `ezt payloads` 是顶层子命令且零覆盖 | 实跑报 `未知命令: payloads` —— 它是 **`ezt runtime payloads`**（嵌套子命令）。我提取命令清单用的是 `grep 'case "..."'`，**扁平提取把嵌套 case 也当成了顶层命令** | **候选清单必须与另一来源交叉核对** —— 与守卫 G4 上"字符串被剥掉导致插值调用丢失"是同一族错误 |

### 八.1 ★ 我新加的断言**自己红了一次** —— 而且这是最好的证据

补的 8 条断言第一次跑验收时：**`通过 396 / 失败 6 / 跳过 2`**，6 个 FAIL **全是我新加的**。

| 项 | 事实 |
|---|---|
| 根因 | `$PY` 定义在**第 252 行**（step 3 附近），而 step 2 在**第 165 行** ⇒ 那条命令退化成 `"" -I -X utf8 -c …`（`command not found`，**stderr 被 `2>/dev/null` 吞掉**） |
| 项目**早就知道**这个坑 | 第 257 行写着：「放在这里而不是第 2 步，是因为 `$PY` 在上一行才可用（第 2 步时它还没定义）」—— 当年是**把断言挪走绕过去**，根因一直没修 |
| 为什么这次没被静默吞掉 | 我把判据写成"取值缺失 ⇒ **响亮失败**"（`${PAY_MISS:-none}` 而不是 `:-0`）⇒ 解析片段拿不到值时，6 条断言**全部变红** |

**这条比它修的那个 bug 更有价值**：它同时证明了
① 变量/函数的**定义顺序**也是契约（与文件上方 `winpath` 被提前是同一族，那里写着"断言的位置本身也是契约"）；
② 判据"缺失即响亮失败"这个习惯，会在**你以为自己很小心的时候**救你一次 ——
   若当初写成 `${PAY_MISS:-0}`，这 6 条会**静默全绿**，而它们其实什么也没验证。

**修法**：`$PY` 提到工具函数区（第 68 行，step 2 之前），全文只定义一次；
并把第 257 行那句"因为 `$PY` 还没定义"改成"根因已修，此处只是历史位置"。
