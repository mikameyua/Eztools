## §1 目标与痛点

### 1.1 功能目标

给 Eztools 的文件搜索（W3）加一层**用户可控的索引范围裁剪**，让 191 万条全盘索引在日常使用中变成"我真正关心的那部分"：

1. **排除规则** —— 声明式地把 `node_modules` / `.git` / `bin` / `obj` / `target` 等子树整棵剔出结果集，并**让落盘的 `.ezidx` 里不再有它们**（见 §2.4：这条要靠"排空 + 落盘前压缩"，**不是**靠"不写"）。
2. **`pathFilter` 补齐** —— 它在协议里已冻结"限定扫描/过滤根目录"，但**过滤语义从未实现**（只校验不生效，见 §2.3）⇒ 本波要**真正实现它**（§4.5）。
3. **可见性** —— 状态行必须显示"排除了多少、限定了什么、**有没有生效**"，且**改规则后必须看得见变化**（否则又是一次"说假话"，见 §8 R4）。

### 1.2 痛点（按实际证据排序，非推测）

| # | 痛点 | 证据 | 频次 |
|---|---|---|---|
| P1 | **噪声淹没结果**：搜 `config` 出来几百个 `node_modules` 里的配置 | 索引实测 **1,911,112 条**（W8 实测），无任何排除机制 | 每天 |
| P2 | **`pathFilter` 是"假实现"**：协议已冻结过滤语义，实现只校验、不过滤、也不报"未生效" | `IndexRpcServer.cs:303-333`（校验后丢弃）· `W3-搜索协议.md:74`（语义原文）· 全仓 `(?i)pathfilter` 8 处**全是解析/校验/自测** | — |

### 1.3 非目标（预防范围膨胀）

- ❌ **不做内容搜索**（协议 §6 第 1 条 Out）。
- ❌ **不做正则 / 元数据过滤（按大小/时间筛）**（同属协议 Out 边界）。

## §2 查证结论（**先看这节，方案形态由它决定**）

> 全部为 2026-10-04 逐行读码结果。**其中 §2.3 推翻了 v1 的核心判断**（v1 以为 `pathFilter` 只缺调用方）。

### 2.1 ✅ `OwnScope` 是**查询期**排除，不是扫描期（v1 结论属实，保留）

**v1 分析阶段的错误**：以为 `OwnScope` 在自举期就把自有子树剔出索引。**实际不是**。

证据（`QueryEngine.cs`）：

```
:212  if (_volumes[ce.Store].Own?.Contains(ce.Frn) == true)        ← 子集路径
:341  if (own is not null && own.Contains(frns[slot])) continue;   ← ScanStore 全扫路径
```

两处都在**查询期**。自举期 `VolumeWorker` 是**无条件 `TryAdd(frn, parent, name, flags: 0)`**（`VolumeWorker.cs:163`）—— 自有子树的条目**照样写进 `.ezidx`**。

**对本波的三条直接影响**：

| 影响 | 说明 |
|---|---|
| **省盘必须发生在"落盘前"** | 排除判据是 `HashSet<ulong>.Contains(frn)`，但它只能在 store 建好、且**在 `Persister.Save` 之前**摘除才有省盘效果（见 §2.4/§3.4）。v1 写的"放在 `TryAdd` 之前即可"与它自己选的三趟法矛盾，v2 已改正 |
| **锚定时机是个真问题** | `OwnScope.Mark(store, ...)` 需要**已建好的 store**（要从 store 反查 FRN）。而排除要发生在**落盘之前** ⇒ **鸡生蛋**。解法见 §3.3 |
| **USN 增量期必须同判** | `QueryEngine:1028` 已有 `target.Own?.Extend(records)`，排除集合也要走同一条路，否则"自举时排除、增量时不排除"= 漏排除 |

### 2.2 ✅ 自举期 `flags: 0` ⇒ 隐藏/系统位在存量索引里恒为 0（v1 结论属实，保留）

证据：`VolumeWorker` 枚举只有 `TryAdd(..., flags: 0)`；唯一的 `MapFlags` 调用在 `UsnApplier.cs:80`（增量路径）；`IndexBootstrap.cs:26` 注释原文"readMft 无 attributes"。

**推论（硬结论）**：排除机制**不能建在 flags 位上**。这排除了"加一个 `Excluded` flags 位"这条看起来最省事的路（v1 §5.2 又提了一次 `ContainsFlags（可为 Excluded 位）`，与本节自相矛盾 ⇒ v2 已删，见 §5.2）。

### 2.3 ⚠️ **`pathFilter` 不是死代码，是"半截实现"**（**v1 判断错误，本条重写**）

**v1 的说法**：`pathFilter` 是"实现完备但无调用方"的死代码，W11 只需"接线"。
**复核结果**：**过滤语义根本没有实现**。

证据（`IndexRpcServer.cs:303-333`，`search.start` 的全部处理）：

```csharp
if (request?["params"] is { } p && p["pathFilter"] is { } pfNode)
{
    if (pfNode is not JsonValue v || !v.TryGetValue<string>(out var pf))
```

### 2.6 ★★ W11-a 开工前的两处**设计纠正**（2026-10-04，实施时发现）

> 这两条都是"照字面实现会错"的地方。按 §12.1 的判据（"查实再动手"）在写码前先纠正，
> **没有照错前提返工** —— 这正是 §2 整节存在的意义。

**纠正一：§4.2 的"规则命中的是**目录**本身"按字面实现不了（自举期无法判目录）。**

`VolumeWorker.cs:163` 是 `store.TryAdd(frn, parent, name, flags: 0)` ⇒ 存量索引里
`EntryFlags.Directory` **恒为 0**（§2.2 已记，但当时只推论到"隐藏/系统位不可用"，
**没推到"连目录位也不可用"**）。而 §4.2 又要求"命中的是目录本身"—— 两者冲突。

**处置（按本方案自己的风险纪律定）**：目录性**由父字段推导** ——
「一条记录是目录 ⟺ 它出现在某个条目的父字段里（含卷根自指）」。
实现上只对**候选**做判定（候选通常几十~几千个），故只需一趟 O(n) 父字段扫描 + 两个小集合，
不做"给全部目录建索引"那笔大分配。

**已知代价（如实登记）**：**空目录**（尚无任何子项）不会出现在父字段里 ⇒ 判不成目录 ⇒
它自己不被摘除。方向是**漏排除**（用户仍可能搜到那个空目录壳），落在**安全侧** ——
与 §3.1 选 B 的理由同一条纪律：*"漏排除 = 可见；误排除 = 文件静默消失 = S9′ 红线"*。
一旦该目录有了子项，规则立即对它生效。**这条必须写进手工清单 M1 的观察项。**

**纠正二：§11.2 那条"排除 `a` 后 `a/b/a` 仍在结果里"与子树传播**自相矛盾**，作废。**

`a/b/a` 的外层 `a` 命中规则 ⇒ 内层 `a` 已在外层 `a` 的子树内 ⇒ **传播必然覆盖它**，它不可能"仍在结果里"。
原断言是从 `OwnScope`（**路径**锚定）搬来的 —— 那里"链"要逐级核对，这里**名字匹配根本没有链可核**。

**处置**：该条改为**真正要守的东西**（两条，都可断言）：
1. **等值匹配，不做子串**（`node` 不命中 `node_modules`）—— 已在 selftest **W11-1** 落地；
2. **传播只向下、不横向**：兄弟子树（`src/main.ts`）与父级不受影响 —— 已在 **W11-7** 落地；
3. 嵌套同名目录（`a/b/a`）**应被覆盖**（这是正确行为，不是误排除）—— W11-7 的夹具含 `8` 号
   嵌套同名目录，断言它**在**作用域内。

R1（误排除红线）的真正防线因此是上面 1+2，而不是"核父链"。

## §3 方案选型

### 3.1 三个候选方案

| | 方案 A：查询期过滤（复用 `OwnScope` 形态） | **方案 B：自举末尾剔除 + 落盘前压缩 + 查询期双闸**（推荐） | 方案 C：独立排除索引 |
|---|---|---|---|
| 做法 | 只在 `ScanStore` 加 `Contains` 判据 | 第 0 趟全量枚举 → 第 1 趟标排除 → 第 2 趟排空 → **落盘前 Compact** → 查询期再判一次（防增量漏网） | 另建一张"排除 FRN 表"持久化 |
| 落盘 `.ezidx` | ❌ 不变（191 万条全在） | ✅ **变小**（前提：**必须落盘前 Compact**，见 §2.4） | ✅ 变小 |
| 锚定时机 | 无鸡生蛋 | ⚠️ 有（§3.3） | ⚠️ 有（同样问题） |
| 增量期正确性 | ✅ 天然（每次查询都判） | ✅ 双闸 | ⚠️ 需额外维护 |
| 新增持久化 | 无 | 无 | ❌ 要升 `.ezidx` 格式版本 ⇒ **全体用户重建索引** |
| 实现量 | 小（半天） | 中（**3~4 天**，含压缩与断言） | 大 |
| 漏排除的方向 | — | **少排除**（可见，安全方向） | — |

**选 B**。理由三条：

1. **P1 的痛点本质是"噪声占资源"**：噪声既占**每次全表扫描的解码开销**（`ScanStore` 逐槽位 `Encoding.UTF8.GetChars`），也占**磁盘与热启动 mmap**。方案 A 只治"搜不到"，噪声仍在每次扫描被解码 ⇒ 只治表面。
2. **方案 C 要升格式版本** ⇒ 全量用户重建一次。这与 `OwnScope.cs:23` 类注释里那条既有判断（*"加侧表要让 `.ezidx` 升格式版本，代价与收益不成比例"*）是同一条纪律，不重复犯。
3. **方案 B 的失败方向安全**：漏排除 = 用户仍能搜到 = 可见；误排除 = 文件静默消失 = S9′ 红线（靠锚定核父链与双向断言防，见 §4.2 / §11.2）。

### 3.2 为什么不做"扫描期按路径过滤"

完整版会在 `VolumeWorker.EnumerateVolumeAsync` 里对每条记录做路径判定。**但扫描段只持有 `(Key, Frn, Store, Pos)`，没有路径**（路径要收敛到 ≤K 个候选后才回溯）⇒ 要按路径判定就得每候选走一次父链 —— 这正是 W3 设计方案 §5.2 标为 🔴 **不可接受**的做法（百万次父链）。

**W11 复用 FRN 标记范式**（`OwnScope` 已证明）：锚定出 FRN 集合 → 扫描期一次 `HashSet.Contains` ⇒ 每候选 O(1)。**这是本波唯一可接受的技术路线。**

### 3.3 ★ 鸡生蛋问题的解法：三趟法

**问题**：`OwnScope.Mark` 要从**已建好的 store** 反查目录 FRN；而排除要在**落盘之前**生效。

**解法（照 `OwnScope` 的 `MaxSweepRounds` 同款思路）**：

```
第 0 趟  无过滤全量枚举（现状行为）                    → store 建好
第 1 趟  FrScope.Mark(store, volume, rules)            → 算出被排除的 FRN 集合（Anchored/Count/Reason）
第 2 趟  store.SweepRemovals(excluded)                 → 标墓碑，返回摘除数
第 3 步  if (摘除数 > 0) store.Compact()               → 真正回收槽位与名字堆字节  ← ★ v2 新增，不可省
第 4 步  Persister.Save(...)                           → 落盘的 .ezidx 里没有它们
```

**为什么不改成"单趟边建边过滤"**：`FrScope` 的传播依赖"父 ∈ 集 ⇒ 子 ∈ 集"，而父必须已被标记才能标记子。虽然 NTFS 满足"父 FRN < 子 FRN"、且 `OwnScope` 的 `SweepDescendants` 正是吃这个不变量（`OwnScope.cs:212` 注释原文），但 `Mark` 本身要先**锚定**（在 store 里按名字找叶子），锚定对象只能是**已建好的** store ⇒ 单趟仍需"暂存待判区"。三趟法用一次内存内的 O(n) 扫描换掉这套暂存逻辑，**复杂度与风险都更低**，故选它。

**代价（必须登记）**：第 0 趟仍要全量枚举（**磁盘 IO 省不掉**），且第 3 步的 `Compact` 是一次 **O(n) 重排 + 约 100 MB 级瞬时分配**（191 万条时：5 个并行数组 + 名字堆精确打包）。实测成本待 M2 确认（R6）。

### 3.4 ★ 为什么"排空"之后必须"压缩"（v2 新增）

见 §2.4：`Persister.Save` 会**连同洞与死堆字节一起落盘**，且 `Compact` 在生产里**从不被调用**。所以：

- 只排空 ⇒ 结果对了、解码省了，但**盘一点没省**（v1 的主卖点落空）。
- 排空 + 落盘前 `Compact` ⇒ 槽位与名字堆精确打包，`HoleCount == 0`，文件真正变小。

**判定（D6 已拍板）**：**排除集非空（摘除数 > 0）就在 `Persister.Save` 之前 `Compact` 一次**，**不使用 25% 阈值**。理由：25% 阈值是为**运行期增量删除**设计的（那些洞随时可能被 `TryAdd` 复用，合并要挑空闲）；而自举末尾**即将整体落盘**，此刻回收是纯收益、且可预测。阈值语义原样保留给运行期。

### 4.2 规则语法：**目录名**而不是 glob

**决策（D2）**：只支持"目录名"（如 `node_modules`），不支持 `**` / `*` / `?`。

理由三条：

1. **锚定只能按名字做**：`OwnScope.FindAnchor` 的做法是"先按 UTF-8 字节长度预筛，再 `memcmp` 叶子名"（`OwnScope.cs:153-170`，零解码）。要支持 glob 就得对**每个候选的名字**跑匹配器 ⇒ 从"字节长度预筛 + 一次 `memcmp`"退化成"百万级候选逐个匹配" ⇒ **性能不可接受**。
2. **glob 在这个场景几乎不产生价值**：`node_modules` 是不分名的固定串；用户真正想要的是"凡是叫这个名字的都排掉"，恰好是等值语义。
3. **可解释性优先**：报错时能说清"排除了 3 个名为 `node_modules` 的目录"，比"排除了 12480 个匹配 `*/node_modules/*` 的路径"更有用。

**匹配口径**（三条都要有断言）：

- **等值 + 大小写不敏感**（NTFS 本身大小写不敏感）
- **锚定必须核父链**（照抄 `OwnScope.ChainMatches`，`:176-206`）⇒ 目录**在**被排除目录内**不会**被连带排除（否则 `src/node_modules` 里的 `node_modules` 也被排 ⇒ 误排除）
- **规则命中的是目录本身**；目录**内**的条目靠子树传播排除

### 4.3 数据流（三趟法 + 落盘前压缩）

```
自举（IndexBootstrap.RunAsync）
  ├─ 卷枚举 → VolumeClassifier（三档分类，零改动）
  ├─ 第 0 趟：VolumeWorker.EnumerateVolumeAsync（枚举逻辑零改动）
  ├─ 第 1 趟：FrScope.Mark(store, volume, rules)        → ExcludeScope（Anchored/Count/Reason）
  ├─ 第 2 趟：store.SweepRemovals(excludeScope)         → 摘除数（复用既有 Remove 墓碑语义）
  ├─ 第 3 步：if (摘除数 > 0) store.Compact()           → HoleCount = 0，堆精确打包   ← D6
  └─ 第 4 步：Persister.Save（体积下降 + 洞归零）

查询（QueryEngine）
  ├─ ScanStore（:341 一带）：排除闸 excluded?.Contains(frn) 与 包含闸 include?.Contains(frn)
  ├─ 子集路径（:212 一带）：同口径（两条路径必须一致，见 R7）
  └─ USN 增量（:1028 旁）：target.Excluded?.Extend(records) 与 target.Include?.Extend(records)
```

**为什么查询期还要留一道闸**（不是冗余）：

> 锚定发生在自举期/启动期，之后用户新建的 `node_modules` 不会进 `excluded` 集合。增量期 `Extend` 只能补标**已锚定目录下的新条目**，**补不了"新建的排除目录本身"**。
> ⇒ 兜底：**索引进程启动时重跑一次 `FrScope.Mark`**（O(n) 一次，与 `OwnScope` 热启动重算同款代价，其类注释原文"热启动后重算一次 O(n) 廉价扫描"）。
> ⇒ **只有"重建"才会连磁盘一起瘦身**（D1 与 §4.7）。

**一次扫描标全部规则**（v2 实现注）：`FrScope.Mark` 接收**规则集合**，单趟遍历 store 时用"叶子名 → 规则"查表命中，**不要为每条规则各扫一遍**（32 条规则会放大成 32 趟 O(n)）。

### 4.5 `pathFilter` 的实现（**v1 判错，本节重写**）

**它现在的真实状态**：`search.start` 里校验完路径就丢弃（§2.3）⇒ **过滤语义零实现**。

**实现形态（D3 已拍板）**：**查询期"包含闸"**，与排除闸共用同一套 FRN 作用域机制。

| 项 | 设计 |
|---|---|
| 语义 | `pathFilter = R` ⇒ 只返回**落在 R 子树内**的条目；空 ⇒ 不限定（全盘） |
| 机制 | 用 `FrScope` 锚定 R 并前向传播出 `IncludeScope`（与 `ExcludeScope` 同一类型、同一算法，**只是判据方向相反**）。查询期：`include is not null && !include.Contains(frn) ⇒ 跳过` |
| 落点 | 锚定在 `IndexRpcServer.HandleSearchStartAsync`（`:303-333`）里做，结果挂到 `VolumeTarget.Include`（与既有 `Own` 同位，`VolumeWorker.cs:53`） |
| **生效时机** | **下一次 `search.start`**。协议 `§3.1` 原文："何时调用：搜索窗打开时；`pathFilter` 变更时" ⇒ **既不需要重建索引，也不需要重启索引进程**（v1 的"必须重启"作废） |
| 增量维护 | `VolumeTarget.Include?.Extend(records)`，与排除闸同一处（`:1028` 旁） |
| **锚定失败的处置（D8）** | **fail-open + 显式出口**：`Anchored=false` ⇒ 包含闸**不生效**（不隐藏任何结果），但状态行与 `search.status` **必须报** `pathFilterAnchored=false` + `Reason`（"索引里找不到该目录"）。照 `OwnScope` 先例（未锚定恒 false 且 `Reason` 可见）—— **宁可宽，不可静默**；fail-closed 会让一个配置笔误把搜索整个变空 |
| 体积影响 | 包含集是"留下"的集合，**不产生墓碑、不涉及 `Compact`** |

**跨卷语义（v3 补，必须显式定，不能含糊）**：

`Include` **按卷独立判定**。限定 `D:\01-项目代码` 时：

| 卷 | 处理 | 理由 |
|---|---|---|
| **D:**（限定所在卷） | 锚定 `D:\01-项目代码` 子树，**只留该子树内条目** | 语义主体 |
| **C: 及其他卷** | **整卷不产出结果**（不是"不受限定"） | ★ 否则"限定"名存实亡 —— 用户限定了 D 盘却仍搜得到 C 盘文件，等于没限定。**这条必须写进 §11.2 的负向断言** |

> ⚠️ 若将来想支持"多卷并列限定"，那是 `pathFilter` 从"单一根前缀"扩到"列表" = **协议语义变更**，本波不做（§1.3 非目标）。


> ⚠️ **为什么不是"扫描期限定"**：协议措辞是"限定扫描/过滤根目录"，但**扫描期无法按路径判定**（§3.2）。本波把语义**收敛为查询期过滤**，并在 `W3-搜索协议.md` 的措辞上补一句"过滤在查询期生效"（协议条文澄清，**不加字段、不改错误码**）。

### 4.6 隐藏文件开关：单列（D4 = X1）

按 §2.2，自举期 `flags` 恒 0 ⇒ `EntryFlags.Hidden` 对存量索引**无效**（只对之后被改动过的条目生效）。且它的修复前提是"自举期能拿到 attributes"，而 `readMft` 原语**不返回 attributes**（`IndexBootstrap.cs:26` 原文）⇒ 要么改特权原语（`Eztools.Core`，须走提权评审），要么自举后补一次全表属性扫描（多一轮 IO）。

**判定：W11 不做**，登记为独立波次（建议 **W11-e 或单列**），前置 = "readMft 原语扩展"或"独立属性扫描"。理由：它是**独立缺陷**（"落盘没人用"），不是 W11 的目标（"让结果集更准"）⇒ 符合"修 A 不要把 B 塞进同一波"的纪律（W8 vs W9 的教训）。

### 4.7 已知限制：运行期新建的排除目录（v2 显式登记）

**现象**：索引进程已在跑时新建的 `node_modules`（典型：刚 `git clone`），**不会被自动锚定** ⇒ 其内容仍会出现在结果里、也仍写进盘。

**为什么不做实时**：`WM_DEVICECHANGE` 式的实时机制与无消息循环的索引进程错配，且并发时序复杂 —— W3 卷热插拔已因同样的理由拍板不做完整方案（W3 §7.4.1）。

**两个既有出口**：

| 手段 | 效果 | 代价 |
|---|---|---|
| **重启索引进程** | 启动时重跑 `FrScope.Mark`（§4.3）⇒ **结果立刻正确** | 便宜（O(n) 一次，不重建、不落盘瘦身） |
| **重建索引**（D1 的出口） | 结果正确 **且** 磁盘瘦身（排空 + 压缩 + 落盘） | 重（实测 71+20 MB 量级、分钟级，W8 M1） |

## §12 坑与教训

### 12.1 ★ 我在分析阶段犯的三个错（记录以防重犯）

**错一（v1 已记）**：以为 `OwnScope` 在自举期排除。逐行读码发现它在**查询期**（`QueryEngine:212`/`:341`）。
**错二（v2 才查出）**：以为 `pathFilter` "实现完备、只是没接线"。实际**过滤语义零实现**（`IndexRpcServer.cs:303-333` 校验完就丢弃）。
**错三（v2 才查出）**：说 `Host` 引用 `Index`、`Index` 不是 `net10.0` 类库、`selftest` 测不到它 —— 三条全错，而且**只要打开两个 `.csproj` 就能看到**。
**错四（v3 才查出，v2 也漏了）**：v2 查了"索引侧有没有实现 `pathFilter` 过滤"，判为"只差实现"，**但没查"谁调 `search.start`"** ⇒ 实际是**两侧各半截**（协议有 + 索引侧有处理 + 客户端**零调用方**）。v2 的推理链是：`pathFilter` 有解析 → 有错误码 → 有自测 → "实现完备，只缺调用方"。**错在"有解析/校验/错误码"被我当成了"功能实现"** —— 而"调用侧有没有人调"是**另一条独立的链**，必须单独查。

**共同教训**：**"我看到那段代码"≠"它在那条路上"，"有解析/校验"≠"功能实现了"，"凭印象的依赖方向"≠"看 `.csproj` 的依赖方向"。**
判别法：**顺着值往下追一步** —— v1 看到 `pathFilter` 有解析、有错误码、有自测，就判定"实现完备"；只要再追一句"`pf` 之后去哪了"，立刻就能看到它没了。这与 W10 的 TFM 教训（`Host` 引用不了 `Clipboard`）同族。
★ **v3 追加的判据（本次最通用的一条）**：**查"某能力是否实现"时，必须同时查两侧 —— 实现侧（有没有真的算）与调用侧（有没有人调）**。两侧各查一遍的成本极低（各一次 grep），漏掉任一侧的后果是**整套验收全绿而功能根本不存在**。这已经是同一个错误的第 N 次现身（§2.43 断言守副本、W10 的 TFM、v1 的 `OwnScope` 排除时机、v2 的 `pathFilter`），**值得当成一条常驻检查项**。
⇒ **§2 整节 + §0.2 整节就是把这些"我以为"逐条查实的结果**；跳过这两节会照错前提实现一遍再返工。

## §13 术语

| 词 | 含义 |
|---|---|
| **排除规则** | 用户声明的目录名列表；命中目录的**整棵子树**不落盘、不出结果 |
| **锚定（Anchor）** | 从已建 store 反查某目录自身的 FRN；**必须核父链**才算锚定成功 |
| **前向传播** | 父 ∈ 集 ⇒ 子 ∈ 集，一趟升序扫描覆盖整棵子树 |
| **墓碑（Tombstone）** | `nameLen == 0xFFFF` 的槽位，标记已删除（不搬数据，**会在落盘时保留**） |
| **三趟法** | 全量建 → 标排除 → 排空（+ **落盘前 Compact**），绕开"锚定需要已建 store"的鸡生蛋 |
| **双闸** | 自举期排空 **+** 查询期再判一次 |
| **`FrScope`** | FRN 子树作用域（锚定 + 传播 + 增量维护）；**同一类型两种用法**：`ExcludeScope`（排除）/ `IncludeScope`（`pathFilter` 包含） |
| **`ownScopes` 先例** | 既有状态面，形状 = `Anchored`/`Count`/`ExtendedByUsn`/`Reason`，W11 照抄 |
