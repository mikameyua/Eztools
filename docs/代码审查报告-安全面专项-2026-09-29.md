## 二、🔴 RI-1（已修）审计降级的告警**在提权 Core 上不可达** —— 安全链路的降级＝完全静默

### 2.1 证据链（每一环都实测／源码可复核）

| # | 事实 | 证据 |
|---|---|---|
| 1 | 审计失败的告警出口是 **stdout** | `AuditLog.Warn()` → `CoreConsole.Say()` → `Console.WriteLine`（`AuditLog.cs`） |
| 2 | **只有非提权启动才收集 stdout** | `src/Eztools.Cli/CoreCommand.cs:133-137`：`if (!elevate) { RedirectStandardError = true; RedirectStandardOutput = true; }` |
| 3 | **提权路径的 stdout 无人接收** | 同文件 `:121-122` 注释原文：「提权只能走 ShellExecute（UAC 限制）……**ShellExecute 会把它吞掉**」；`:127` `UseShellExecute = elevate` |
| 4 | **提权才是常态形态** | 需提权原语（`volume.readMft` / `volume.queryJournal` / `volume.readUsn` / `volume.writeUsnClose`）与 W3 索引都依赖提权 Core；`Program.cs` 另有 `--from-task`（计划任务＝必然提权） |
| 5 | **没有任何替代出口** | `grep -rn "Failures" src/` ⇒ **只有 `AuditLog.cs` 自己的定义，零消费者**；`core.json` 无该字段；`ezt core status` 不显示 |

**合并结论**：提权 Core 上，审计写失败 → 告警写进一个无人接收的 stdout → `IOException` 被
`// review-guards:allow-empty-catch :: stdout 断了不致命` 吞掉 ⇒ **告警从未到达任何人**，
且 `Failures` 计数无人可读。审计可用性降级＝**完全静默**。

### 2.2 为什么定 🔴（而不是 🟡）

1. **命中红线 2** —— "安全闸被移除/放宽而无并发替代措施"里的**审计被跳过**：此处不是审计失效，
   而是**审计失效这件事本身不被报告**，等价于把安全链路的降级做成零信号。
2. **与已实证的坑同族** —— 规范 §7.3 FAQ 12「安全闸在提权环境下失效」的原案例是
   `CurrentUserOnly` 在提权进程**静默死亡**（`CoreServer.cs:407-409` 有记录）。本次是同一形态的第二次出现。
3. **★ 这是"修了一半"** —— 上一轮（`docs/代码审查报告-静态守卫首跑-2026-09-28.md` §三）
   我已把 `AuditLog` 从"只有注释承诺告警"改成"真的调用告警"，但**验证方式是读代码**
   （"代码里有 `Warn` 调用"），**没验证送达路径**。纸面成立、送达率为零。

### 2.3 修法（已落地）

| 改动 | 内容 |
|---|---|
| `src/Eztools.Core/AuditLog.cs` | 告警**加第二条出口**：落 `logs/core-audit-health.log`（`WriteHealthFile`）。类注释写明"两条出口缺一不可"及各在哪一形态可达 |
| `src/Eztools.Core/CoreServer.cs` | `core.hello` / `core.ping` 响应新增 **`auditFailures`** 字段（0 = 健康）—— 运维侧唯一能读到"审计正在丢"的通道 |
| `scripts/_step12_p3.sh` | 新增 **12.11b 反向断言**：把 `install/logs` 换成同名**文件** ⇒ 制造审计写失败 ⇒ 断言 `auditFailures ≥ 1`（详见 2.4） |

### 2.4 验证（不是"改完就算"）

| 手段 | 结果 |
|---|---|
| 构建 | `dotnet build Eztools.sln` ⇒ **0 错误 / 7 警告**（警告基线未变） |
| 实跑协议帧 | 起真 Core 后连管道发 `core.ping` / `core.hello` ⇒ **两响应均含 `auditFailures`，值 0** ✅ |
| 反证"非提权可达、提权不可达" | 非提权路径下 `logs/host-ezt-core-*.log` **确实生成**（stdout 有人收）；提权路径按源码 `UseShellExecute` 无重定向 ⇒ 无人收 |
| **新增反向断言**（12.11b） | **故意制造审计写失败**后 `auditFailures ≥ 1` —— 证明"降级可被观察到"，而不只是"字段存在" |

### 2.5 ★ 本条换来的通用教训（已进规范）

**告警／降级类的修复，必须验证"告警能到达谁"，不能只看"代码里有告警调用"。**

- 判据：**在目标运行形态下**（提权／无父进程／无控制台）走一遍，确认接收者存在；
- 反模式：以"我加了 `Console.WriteLine` / 日志调用"作为修复完成的证据。
- 已写入规范 §3.9.1 的检查说明与 §7.3 FAQ 12 的处置列。

### 2.6 ★ 修 RI-1 时挖出的同族缺口（**RI-3**，已修）：CLI **白名单式**构造输出，静默吞字段

**现象**：Core 侧 `ping` 响应加上 `auditFailures` 之后，`ezt core ping --json` 里**没有这个字段**
（首次跑验收时新断言就是这么红的）。

**根因**：`src/Eztools.Cli/CoreCommand.cs` 的 `PingAsync` 是**手工重建** result：

```csharp
var result = new JsonObject {
    ["pong"] = true, ["pid"] = …, ["elevated"] = …, ["version"] = …,
};   // ← Core 协议层新增的字段不会自动进来
```

**为什么算缺口而不是笔误**：**白名单式透传**的固有风险 —— 任何在 Core 协议层新增的字段，
只要 CLI 不同步加一行，就被**静默丢弃**（不报错、不警告、无信号）。

**同族第 3 次**（前两次都真实发生过）：

| # | 位置 | 丢的字段 | 发现方式 |
|---|---|---|---|
| 1 | `ezt list --json` | action 的 `handler` | 2026-09-28 断言语审（补断言时首跑就红） |
| 2 | `ezt list --json` vs `ezt info` 表格 | 两个展示面不一致 | 同上 |
| 3 | **`ezt core ping --json`** | **`auditFailures`** | **本次（RI-1 的新断言红了）** |

**修法**：`PingAsync` 补该字段，并在代码处留注释警示"白名单式构造"（防下一个人再踩）。

**★ 方法论价值 —— RI-1 的教训在另一个层面的复现**：
它暴露了「**在协议层加字段 ≠ 在 CLI 层能用**」。若只做协议层验证（直连管道 ✅ 通过），
**这一层会被完整漏掉**。

> **可复用的验证纪律**：改动跨越"协议层 → CLI/UI 层"时，**两层都要测** ——
> 直连管道测协议（证明 Core 做对了）**和** `ezt <cmd> --json` 测端到端（证明字段没在层间丢）。
> 本次正是后者把 RI-3 暴露出来的。

## 三、🟡 RI-2（建议，未改行为）审计里的 `toolId` 是**客户端自报**、无校验

**位置**：`CoreServer.cs:311` —— `var toolId = request["params"]?.GetString("toolId");`

**现象**：同一个方法里对 `callerPid` 有明确注释强调"不采信客户端自报（连接时由内核 `GetNamedPipeClientProcessId` 给出）"，
但紧邻的 `toolId` **直接取请求参数、不校验**，随后原样写入审计与 `PrimitiveContext`。

**影响**：
- 审计记录里"是哪个工具干的"**不可作为证据** —— 任何通过闸 2 的进程（同用户、≥ Medium）都可冒用任意 `toolId`；
- 唯一可信的调用方标识是 `callerPid`；而 PID 会复用，事后追查需要额外的进程映像路径才能定位。

**为什么定 🟡 而不是 🔴**：这不是可利用的漏洞（边界仍是"有限原语 + 参数校验 + 审计"），
而是**审计证据强度**问题 —— 且它已被现有设计部分覆盖（PID 可信）。

**建议（二选一，未实施）**：
1. 审计条目增加 **`callerImage`**：用已验证的 `callerPid` 反查进程映像路径（可信，因为 PID 来自内核）；
2. 或至少在审计里把 `toolId` 标注为 `toolId(self-reported)`，避免后人误当权威。

## 四、🔴 RI-4（已修）`handles.enumerate` 每次调用**泄漏一整张句柄表**（7~9 MB，线性累积）

### 4.1 证据（先实测，再下结论）

| 项 | 内容 |
|---|---|
| 位置 | `src/Eztools.Core/Primitives/HandlePrimitives.cs` · `Enumerate()` ← `QueryHandleTable()` |
| 缺陷 | `QueryHandleTable` 用 `Marshal.AllocHGlobal(size)` 分配 1 MB~256 MB（本机实测表大小约 8 MB）。**失败路径**有 `Marshal.FreeHGlobal`，**成功路径却直接 `return buffer`**，而 `Enumerate` 拿到后**从不释放** ⇒ 每调一次泄漏一整张表 |
| 实测（修复前，同一 Core 连续调用 4 次） | 基线 34620 KB → 43716 → 50996 → 59084 → 67032 KB（**+9096 / +7280 / +8088 / +7948 KB**） |
| 影响 | Core 是**常驻特权进程** ⇒ 约 8 MB/次，百余次调用即泄漏到 GB 级；OOM 会连特权服务一起杀掉 |

### 4.2 为什么定 🔴

1. **每次调用必发生**，不是罕见路径 —— 且已实测复现（4 次 +32 MB，线性、从不回收）；
2. Core 是长驻服务，**没有自愈路径**（不重启进程就不会回收）；
3. **同项目内有正确对照**：`VolumePrimitives` 对两处 `CreateFileW` 一律 `try/finally { CloseHandle }`（已核）⇒ 可见这是**疏忽**，不是设计取舍。

### 4.3 修法与验证

修法（**最小 diff，原主体一行未动**）：把扫描主体抽成 `Scan(buffer, …)`，`Enumerate` 用 `try/finally` 释放 buffer。

验证（同一 Core 连续调用）：**前 3 次斜率从 8.0 MB/次降到 3.9 MB/次** ✅

> ⚠️ **修复没有让增长归零** —— 剩余约 3.9 MB/次是**另一个**泄漏源，见 §六 RI-6。

## 六、🔴 RI-6（**未修 · 待拍板**）客户端超时后 Core 侧**不取消** ⇒ 挂起线程**逐次累积**

### 6.1 现象（实测，同一 Core 连续 8 次调用）

| 次 | 返回 | Core 内存 |
|---|---|---|
| 1–3 | ✅ `count≈400`，单次约 **7.7 s** | 34568 → 46356 KB |
| **4–8** | ❌ **全部 `-32011`「原语执行超时」** | 54424 → 63024 → 76104 → 84540 → **97160 KB**（**加速**） |

⇒ **一旦超时，后续调用几乎必然也超时**（第 4 次起 100% 失败），内存同时加速增长。

### 6.2 根因链

1. 超时是**客户端**判定的：`PrimitiveCommand.cs:88` 打 `-32011` 后 `return 2`，CLI 退出 ⇒ 连接断开；
2. **Core 侧不知道** —— `spec.Execute` 拿到的 `ct` 是**连接级** token，只在 `Ctrl+C` / `core.shutdown` 时取消；
3. `HandlePrimitives` 的 supervisor 循环以 `!ct.IsCancellationRequested` 为退出条件 ⇒ **继续跑**；
4. 每次调用都**新开一批** supervisor/worker 线程，而本机必然有句柄让 `NtQueryObject` **永久挂起**（类注释自己写了这个硬限制）⇒ 挂起线程**逐次累积**；
5. ⇒ 内存涨 + 扫描变慢 ⇒ 更易超时 ⇒ **正反馈**。

### 6.3 ★ 本条**推翻**了代码注释里的一个安全假设

`HandlePrimitives` 类注释声称：「泄漏上界 = **挂起句柄数**，进程退出时自动回收」。

**实测上界是「挂起句柄数 × 调用次数」** —— 因为每批 worker 都是**新线程**，同一批句柄会被**反复挂起**。
"有限上界"的论证不成立 ⇒ 这不是"可接受的取舍"，而是**每次调用都在加重**。

### 6.4 修法选项（**方案 A 已实测并回滚**）

| 选项 | 做法 | 代价 | 状态 |
|---|---|---|---|
| ~~**A. 断开检测**~~ | 原语执行期监视连接，客户端放弃即取消该原语的 `ct` | 不动协议；需把 pipe 传入执行路径 + 轮询任务 | ❌ **已实测失败并回滚**（见 §6.5） |
| **C. 挂起句柄黑名单** | 记住"被判定挂起"的 `(pid, 句柄值)`，下次扫描前跳过 | **治本**；但句柄值会复用 ⇒ 有**误跳**风险（宁可少几个结果，也不要 OOM） | ⏳ **推荐 · 下一轮实施** |
| B. Core 侧自我保护超时 | `CancelAfter(N)` 给"无人等待的计算"一个上界 | 与客户端 `--timeout` 语义冲突（客户端可合法等 300 s），N 取不出一致值 | — |
| D. 原语单飞保护 | 同一原语同时只允许一个在跑，第二次直接拒绝 | 只防"叠加"，**不防"逐次累积"** ⇒ 效果有限 | — |

### 6.5 ★ 方案 A 的实测记录 —— 为什么必须回滚

按"把取消绑到真实信号"的思路实现并实测，得到三条结论：

| 结论 | 证据 |
|---|---|
| **① `NamedPipeServerStream.IsConnected` 不可靠** | 第一版用它判断，客户端断开后**仍返回 true** ⇒ 监视任务**静默失效**（代码改了、毫无效果、不报错）。改用 `PeekNamedPipe`（不消费数据）后才拿到信号 |
| **② 拿到信号也解决不了问题** | `NtQueryObject` 挂起是**内核硬限制、无法取消**。取消只能让 supervisor 提前退出、`Execute` 更快返回（**5.2 s vs 7.7 s**）——**每次调用仍新建一批 worker 线程，挂起的那批照样残留** ⇒ 累积与 `durationMs` 递增（6.3 → 12.9 → 19.3 s）**照旧** |
| **③ 且引入了稳定性回归** | 加了该机制后，Core 在连续调用第 3 次后**进程消失**（端点被摘除 ⇒ 走的是正常退出路径，`host-ezt-core-*.log` 无异常）——机理未查明，**不宜带着它上线** |

⇒ **回滚**。（回滚后实测：连续 5 次调用 Core **全程存活**。）

### 6.6 ★ 回滚时**保留**的独立修复：审计原来说谎

`ExecutePrimitiveAsync` 原先**先记 `ok:true`、再写响应**。于是"调用方已放弃、结果没人收到"会被记成一条
**成功的审计**，紧接着写响应失败又补一条 IOException。实测抓到的这组双记录：

```json
{"primitive":"handles.enumerate","ok":true,"durationMs":5213.8}
{"primitive":"handles.enumerate","ok":false,"durationMs":5252.7,"error":"IOException: Pipe is broken."}
```

改为：**先写响应，成功之后才记 `ok:true`**；并新增 `catch (IOException)` 专门分支，
把「结果未送达（连接已断开，调用方可能已超时放弃）」与「Core 内部错误」**区分开** ——
否则审计会把排查方向引向 Core 自己。

**回滚后实测**（连续 5 次，Core 全程存活）：

```json
{"ok":false,"durationMs":6269.8, "error":"结果未送达（连接已断开，调用方可能已超时放弃）：Pipe is broken."}
{"ok":false,"durationMs":12865.6,"error":"…同上…"}   ← durationMs 递增 = RI-6 本身仍未解决
```

> **本条的方法论价值**：我按"最优解"实现了一个方案，**实测把它否掉了**。
> 若不是每一步都实测（而不是"改完就宣布修好"），会上线一个**看似正确、实则无效且引入回归**的机制。
> 这正是规范 §3.7 7.8（新增/放宽检查必须带突变验证）与 §7.3 FAQ 4 的用法。

## 七、🟡 任务 ⑦（特权边界）的两个发现

### 7.1 🟡 RI-7（已修）`NormalizeVolume` 对 `\\.\` 前缀**直接放行** ⇒ 任意设备路径都能通过

**位置**：`src/Eztools.Core/Primitives/VolumePrimitives.cs` · `NormalizeVolume()`（4 个卷级原语的**唯一**参数校验点）

**缺陷**：原实现

```csharp
if (value.StartsWith(@"\\.\", StringComparison.OrdinalIgnoreCase))
{
    return value;          // ← 直接放行，不校验后面是什么
}
```

⇒ `volume` 可以是 `\\.\PhysicalDrive0`、`\\.\HarddiskVolumeShadowCopy1` 等**任意设备路径**。
而 `volume.writeUsnClose` 打开句柄时带 `GenericWrite`。

**为什么定 🟡**：卷级 IOCTL 在物理盘句柄上会失败，**实际不可利用**；但参数面被无必要地放宽 ——
这也属于"白名单里混进了黑名单式放行"。

**修法**：只接受单盘符（`C` / `C:`）或 `\\.\X:` 形式，其余拒绝。

**安全性依据（先核实再改）**：全仓**无消费方**依赖更宽的形式 ——
`volume.enumerate` 的 `kernelDevice` 没有任何回传调用点；唯一的 `\\.\F:` 用例来自
`SelfTestCommand.cs:1464` 的 `OrderVolumes`，仍是单盘符。

### 7.2 🟡 RI-8（未改行为）声明门槛**只在 Host 路径生效** ⇒ 可绕过 Host 直连 Core

| 项 | 内容 |
|---|---|
| 门槛位置 | `ToolHostManager.cs:1138-1146` —— `tool.Manifest.ElevatedPrimitives` 必须包含原语名，否则 `-32013`。**100% 在 Host 侧** |
| Core 侧 | `CoreServer.ExecutePrimitiveAsync` 只检查**原语是否存在**与 `RequiresElevation`，**不检查调用方是谁** |
| 可绕过性 | Core 的管道对**同用户 ≥ Medium 的任何进程**开放（闸 1 `CurrentUserOnly` / 闸 2 校验 SID + 完整性）⇒ 任何本地进程可实现一个自己的客户端**直连 Core**，完全跳过 Host 与声明门槛 |
| Core 能否分辨 | **不能** —— 它只拿得到 `callerPid`（内核给出）与自报的 `toolId`（见 RI-2） |

**这是缺陷吗？** **设计上不是** —— P3 方案 §6 明确写着「声明门槛……**清单是唯一授权面**，
运行时不做第二套仲裁（§4.4 同理：**不是伪安全**）」，即设计者知道它不是安全机制，
真正的边界是「有限原语 + 参数校验 + 审计」。

**但仍建议加注**（理由两条）：
1. **字段名与文档会误导**：`elevatedPrimitives` 这个名字、以及 SDK 里
   `Tool.primitive` 的注释「**清单是工具的唯一授权面**」，都会被读成"这是个授权约束"；
2. **它放大了 RI-4 / RI-6 的实际风险面** —— 泄漏与线程累积**不需要是 Eztools 工具**，
   任何同用户进程都能反复触发这两个原语。

**建议（未实施）**：在 `tool.json` 契约文档与 SDK 注释里补一句
「`elevatedPrimitives` 是**工具与宿主之间的约定**，不是安全边界；Core 的边界是有限原语 + 参数校验 + 审计」。
