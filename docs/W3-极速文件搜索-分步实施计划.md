### 0.1 Q1 结论：原生工具，不是 VS Code 扩展

| 维度 | VS Code 扩展 | **Eztools 原生工具** |
|---|---|---|
| **全局召唤** | ❌ 只能 `Ctrl+P`，且**必须先开 VS Code** | ✅ 任意程序里按热键即出（`RegisterHotKey`，已就绪） |
| 复用既有资产 | ❌ 用不到热键仲裁 / 托盘 / 面板 | ✅ 全部复用 |
| 运行时依赖 | ❌ 得带一套 Node | ✅ 无新增 |
| 与托盘生命周期 | ⚠️ 无关，两套入口 | ✅ 一致（`opensPanel` 直达） |
| 本质定位 | 寄生在编辑器里的子功能 | 操作系统级工具，与 Everything 同定位 |

**为什么"全局召唤"是决定性的**：Everything 的核心价值从来不是"能搜文件"——
Windows 自带的搜索也能搜。它的价值是**在任何地方按一下热键就能搜**。
真实使用场景几乎都是"我正在干别的，想起来要找某个文件"。
把搜索框关进 VS Code，等于把最常用的那条路径砍掉，只剩"我已经打开编辑器了顺手搜一下"。

**但必须正视一个硬冲突（这是本方案的真实成本）**：

> 面板协议 V1 明文**没有键盘事件通道**（§11 第 1 条「只读 + 按钮」、§11 第 10 条）。
> 而文件搜索天然需要 typing + ↑↓ + Enter。

⇒ 原生方案的 UI **不能靠现有面板协议实现**，须**新增一条交互通道**（独立一期，见 §0.3）。
**这不是可以绕过的实现细节，是协议级的前置依赖。**

### 0.2 Q2 结论：独立进程（`ezt-index.exe`）

| 维度 | 方案 A · 寄生托盘 | **方案 B · 独立进程** |
|---|---|---|
| **索引崩溃** | 🔴 整个托盘挂掉 —— 热键、速览、面板全失效 | ✅ 只影响搜索，可自动重启 + 热启动恢复 |
| **建索引期间** | 🔴 全量枚举 3~8 s 卡住消息循环，"托盘像死了" | ✅ 托盘完全不受影响 |
| 内存核算 | ⚠️ 67.8 + 40 MB 不可分，超标时说不清是谁 | ✅ 分别可测 |
| 延迟 | 略低（免 IPC） | ⚠️ 多一次 IPC（**亚毫秒级**，可忽略） |
| 实现成本 | ✅ 最省事 | ⚠️ 多一套进程管理 + IPC |

**为什么最终选 B**：A 的唯一优势是"实现省事"，但它把风险放在了最不该放的地方 ——
**一个"锦上添花"的搜索功能，不该有能力让整套工具集体失效**。
本项目 §8.2 已经为 `resident` 工具定义了崩溃治理（5 分钟 2 次阈值 + 必须先实现 `tool.recover`），
独立进程正好落在这个既有机制里，不需要发明新东西。

> ⚠️ 连带影响：面板协议 §11 第 5 条明文 **`weight: full` 目前仍无"独立进程组"语义**
> （`full` 与 `lite` 共用同一套进程管理路径）。所以"独立进程组"这件事本身
> **需要顺带补齐** —— ✅ **2026-09-23 已拍板：补齐**（不采用"确认够用"）。
> 语义定义见 `docs/Eztools-设计方案.md` §5.1「独立进程的语义补齐」；落地在 **W3-a-1**。

### 6.1 另有两个"决策闸门"（不是技术停手点，是待你拍板的）

| 闸门 | 位置 | 不拍板的后果 |

#### G1 结论（2026-09-23 拍板）：方案 ① —— 面板加 `input` 节点

| 项 | 内容 |
|---|---|
| **结论** | 给面板协议新增 **`input` 节点类型**：面板声明输入框，宿主渲染；**输入值随 `tool.panel.data` 回传给工具** |
| **为什么不选 ②（键盘事件通道）** | ② 等于让工具进程接收按键流 —— **这是键盘记录器的形状**，与"工具进程不接收宿主输入事件流"的隔离模型正面冲突（风险登记 R15） |
| **为什么不选 ③（新窗型号）** | ③ 最彻底但等于给面板协议开专用特例；**只有当 G2（延迟）超标时才回退到它** |
| **核心取舍** | 把"输入"变成 **一个节点类型 + 一次数据回传**，而不是一条持续事件流 —— 既满足搜索需求，又不打开"工具监听键盘"的口子 |
| **已知代价** | 每次按键一次 `tool.panel.data` 往返 ⇒ **必须实测延迟**（记为 **G2**）。若 P95 超标则回退 ③ |
| **协议版本** | 现 V1.2 → 新增 `input` 节点 ⇒ **V1.3**（**不是** V2.0：加节点是**向后兼容**的扩展，不改已有节点语义） |
| **纪律** | **协议先行**：`input` 节点的协议条文 + 验收断言先落地并转绿，**再动 WPF**（与 Wave 2c 同一纪律） |

> ⚠️ **与既有 `image` 节点同构**：`image` 是 V1.2 的增量节点，`input` 是 V1.3 的增量节点 ——
> 两者都遵循"**加节点类型，不加事件流**"的既定扩展模式。这不是新机制，是既有模式的第三次应用。
