## 1. 先看实测：探针撞出来的四件事

写方案之前先做了一个一次性探针（`WinExe` + `NotifyIcon` + 真实读 `tools/*/tool.json`
的 `menus` 贡献点），把可能翻车的点先撞一遍。结论如下。

### 1.1 能力验证（全部通过）

| 验证项 | 结果 |
|---|---|
| `NotifyIcon` 在 `net10.0-windows` + `UseWindowsForms` 下可用 | ✅ 构造成功、可设图标、可挂右键菜单 |
| 菜单能从 `menus` 贡献点**自动合成**（无需为托盘写任何代码） | ✅ 2 条贡献点 → 2 个菜单项，两层结构正确 |
| 托盘图标**真的出现在通知区域** | ✅ 在 `HKCU\Control Panel\NotifyIconSettings` 查到登记记录 |
| 单实例 Mutex | ✅ 第二个实例退出码 **3**，且不干扰已在运行的托盘 |
| 常驻稳定性 | ✅ 消息循环正常，被杀后无残留进程 |
| 点击 → 起工具进程 → 拿回结果 | ✅ 错误能原样返回、退出码正确传递 |

**关于"图标真的显示了"**：这一点原本无法自动验证（托盘是交互式的）。办法是查 explorer 登记表
`HKCU\Control Panel\NotifyIconSettings\<hash>` —— 图标出现时 explorer 会在这里建一条
`ExecutablePath` 记录。探针的 exe 路径确实在里面。这比"构造没抛异常"硬得多。

### 1.2 ★ 一个真问题：两个菜单项点了都跑不起来

现有 4 个工具里，有 2 个已经声明了托盘菜单（P0 时就写了）：

```json
{ "location": "tray", "command": "filehash.hash",  "group": "file" }
{ "location": "tray", "command": "wordcount.count", "group": "text" }
```

探针真的点了它们，结果是：

```
wordcount.count → [错误] wordcount 的 tool.invoke 返回错误: ValueError: 缺少参数 text
filehash.hash   → [错误] filehash 的 tool.invoke 返回错误: ValueError: 缺少参数 path（或 paths / files）
```

**两个都失败。** 原因不在代码，在**契约**：

> `menus` 贡献点允许声明任何命令，但**契约里从没说"参数从哪来"**。
> 而托盘菜单点击时**没有任何上下文**——不像 `actions`（有选中的文件）。

这个缺陷的症状很隐蔽：菜单能显示、点击有反应、进程真的起来了，用户看到的却是一句"缺少参数"。
**菜单是"假能用"的** —— 与 P0 阶段那几个"不报错、只静默失效"的坑同一类。

**修法**（P2 必须做，否则托盘做出来就是"能点但都失败"）：

1. **契约扩展**：`menus` 项增加可选字段 `input`，声明输入来源。

   | `input` 取值 | 含义 | 宿主行为 |
   |---|---|---|
   | `none`（默认） | 无上下文，命令自足 | 传 `{}` |
   | `clipboard` | 以剪贴板文本为主输入 | 读剪贴板，注入到约定字段 |

2. **约定字段**：`input` 声明后，宿主把取到的内容放进 `args["input"]`（字符串）。
   工具侧从 `args["input"]` 取——**宿主不需要知道各工具的参数名叫什么**（`path` / `text` / ……）。
   这样避免"宿主硬编码参数名"的耦合。

3. **真正的规则**（一句话）：**能进托盘的命令，要么零参可执行，要么声明了 `input`。**

4. **不能靠 manifest 静态校验**：handler 是动态的，宿主无法静态知道它要不要参数。
   所以这条规则**只能靠验收断言守住** —— 对每个托盘项真的调一次，断言不出现"缺少参数"。
   这正是本项目已有的原则：**断言要落在可检验的东西上**。

> **现有两个工具怎么改**（P2 一并处理）：
> - `wordcount.count` → `"input": "clipboard"`（它的 hotkey 描述本来就写着"统计剪贴板文本"，完全自洽）
> - `filehash.hash` → `"input": "clipboard"`（校验剪贴板里的路径）
>
> 两者都需要在工具侧把 `args["input"]` 映射到自己的参数名，这是**工具自己的职责**。

### 1.3 一个 UX 陷阱：图标默认藏在溢出区

查到的记录里 `IsPromoted` 是**空**（未提升）。意思是：**图标默认在任务栏的溢出区（小三角里），
用户首次运行时看不到它** —— 会以为程序没启动。

这是真实产品必须处理的，不是可选项。方案见 §6.3。

### 1.4 打包体积：WinForms 与"裁剪"不兼容（但要分两步说）

| 形态 | 实测体积 | 说明 |
|---|---|---|
| 框架依赖（Release） | **198 KB** | 5 个文件。目标机器需装 .NET 10 运行时 |
| 自包含 | **118 MB** | 271 个文件。WinForms 带进了 `System.Windows.Forms` / `System.Drawing`；**WPF 没有被带进来**（0 个 `PresentationCore`） |
| 自包含 + 裁剪 | **37 MB** | ⚠️ 默认**构建直接失败**，见下 |
| 纯控制台对照（无托盘） | 78 MB / 裁剪 22 MB | 上一轮实测 |

**默认构建会直接报错**：

```
error NETSDK1175: 启用剪裁时，不支持或不推荐使用 Windows 窗体。
```

用 `-p:_SuppressWinFormsTrimError=true` 可以绕过，绕过之后：
- 产物体积 **37 MB**
- **零条 IL 警告**（说明 .NET 10 的 WinForms 其实带好了 trim 注解，SDK 只是策略上禁止）
- 实测能跑：图标显示、通知区域登记、消息循环、菜单合成**全部正常**
- 全程 `DOTNET_ROOT` 指向不存在的目录 → **自包含确实自带运行时**

**我的判断：P2 用 WinForms，接受"绕过 SDK 限制"**。理由：
1. 37 MB 实测可用，比不裁剪的 118 MB 好 3 倍
2. **不支持的组合仍是风险**（未来 .NET 版本可能真不兼容）。但 .NET 10 是 LTS、支持到 2028-11，
   且我们只用了 `NotifyIcon` + `ContextMenuStrip` + 气泡这三个控件，属于很小的子集
3. 替代路径（用 P/Invoke `Shell_NotifyIcon` 自己写托盘）能避开这个风险，但要自己实现
   `CreatePopupMenu`/`TrackPopupMenu`/`WM_COMMAND` 一套，是几百行 Win32 代码 + 长期维护负担
   —— 违反"这段我能不能维护"的判据
4. **后路仍在**：真要换 P/Invoke，需要重写的只有菜单那一层，不影响宿主与工具契约

> 这个决定**到 P4 打包时才真正生效**（P2 开发期一律用框架依赖，198 KB）。
> 现在只是把"选 WinForms 会不会把路堵死"这个问题排掉 —— 答案是**不会**。

### 1.5 内存：会打破"常驻 0 MB"的记录

| 项 | 实测（工作集） |
|---|---|
| 托盘进程（常驻，Release） | **≈ 50 MB** |
| 对照：单次 `ezt invoke` 峰值 | 59 MB（**调用完就退出**，常驻 0 MB） |

设计文档 §15 记的「**常驻总量 0 MB**」是 P0 的实况 —— 托盘引入后这条**必然变成 ≈50 MB**。
§15 的预算需要相应修订（见 §7）。

## 3. 工程形态：为什么必须是**独立项目**

`OutputType` 是编译期属性，一个项目只能取一个值：

| | 需要 | 冲突 |
|---|---|---|
| `Eztools.Cli` | `Exe`（控制台）—— `ezt doctor` / `invoke` 的输出用户必须能直接看到 | 改成 `WinExe` 会让**所有命令行输出消失** |
| `Eztools.Desktop` | `WinExe` —— 常驻进程不能顶着一个黑窗 | 用 `Exe` 会一直显示控制台窗口 |

所以分两个项目不是偏好，是平台约束。

**额外收益**：`Eztools.Cli` 保持 `net10.0`、**不背 WinForms 依赖**（框架依赖体积维持 ~600 KB，
而不是涨到 800+ KB）；将来 P1b 的设置窗口也进 `Eztools.Desktop`，GUI 职责集中在一处。

**命名**：叫 `Desktop` 而不是 `Tray`，因为它将来不只做托盘。

**用户视角要说清**：
- 日常使用 → 双击 `Eztools.Desktop.exe`（托盘出现）
- 命令行 / 脚本 / CI → `ezt.exe`
- 安装器（P4）的快捷方式指向前者

## 4. 菜单合成规则

**组织维度是 `group`，不是工具。**

用的人的视角是"我想对文件做什么"（文件 / 文本 / 系统），而不是"我想用哪个工具"。
两个工具都声明 `group: "file"` 时会**自然合并到同一组**，这正是想要的效果。

```
托盘图标（右键）
├── 文件
│   └── 计算文件哈希          ← filehash
├── 文本
│   └── 统计文本              ← wordcount
├── ──────────
├── 刷新菜单
├── 打开配置目录
├── 查看日志
├── ──────────
└── 退出
```

规则：
- 条目文本用**命令的 `title`**（不是工具名）——用户关心动作，不关心是哪个工具实现的
- `group` 为空 → 直接挂顶层
- 组名做一次映射（`file`→文件、`text`→文本、`system`→系统），未知组名原样显示
- **一个坏清单不拖垮托盘**：解析失败只记日志并跳过（与宿主注册表的容错策略一致）
- `location` 不是 `tray` 的项不处理（主界面菜单属于 P1b）

**菜单刷新时机**：在 `ContextMenuStrip.Opening` 事件里重建，而不是定时轮询。
零开销、且总是最新 —— 用户在 CLI 里 `disable` 了一个工具，下次弹菜单就看不到它。

## 5. 进程模型

### 5.1 托盘 = 主宿主（推荐）

```
Eztools.Desktop.exe（常驻）
  ├── EztoolsHost（进程内，持有 ToolHostManager）
  │     └── 点击菜单 → host.Processes.InvokeCommandAsync(...)
  └── NotifyIcon + 菜单
```

而不是"点一次起一个 `ezt.exe invoke` 子进程"。理由：

| | 进程内宿主 | 起子进程 |
|---|---|---|
| 每次点击开销 | 省掉 ~450 ms 的宿主启动 | 每次 +450 ms |
| `resident` 工具保活 | ✅ 可以（这正是 P2 接下来要做的） | ❌ 做不到 |
| 清单扫描 | 启动时一次 | 每次重扫 |
| 失败模式 | 工具崩溃可能影响托盘（需熔断兜底） | 天然隔离 |

**当前定位要求托盘是"治理者"而不是"启动器"** —— 统一托盘入口、热键仲裁、独占资源仲裁
都需要一个长期活着的宿主。所以选进程内。

同时**保留子进程模式作为降级路径**（探针已验证可行）：工具连续崩溃触发熔断后，
可选择"只调子进程"模式，避免拖垮托盘本体。

### 5.2 单实例与并发

| 关系 | 处理 |
|---|---|
| 两个托盘实例 | **Mutex 单实例**（已实测有效）。第二个实例提示"已在运行"后退出（退出码 3） |
| 托盘 vs `ezt` CLI | **允许并存**，但共享状态要保护 |
| 工具进程 | 各自独立，由宿主管理 |

托盘与 CLI 并存的具体问题与对策：

| 共享资源 | 风险 | 对策 |
|---|---|---|
| `%APPDATA%\Eztools\state.json`（启用/禁用） | 同时写 → 覆盖 | **原子写 + 文件锁**（`ConfigStore` 已有原子写，state 要用同一套） |
| `config/<toolId>.json` | 同上 | 同上（P1a 已实现原子写） |
| 宿主日志文件 | 两个进程交错写同一文件 | **按进程分文件**：`host-<name>-<pid>.log` 或 `host-cli.log` / `host-desktop.log` |
| 运行时部署 | 同时 `runtime install` | 部署目录写 `.installing` 锁文件，后到者等待/跳过 |

**不做的事**：托盘与 CLI 之间不做 IPC 转发。CLI 保持完全独立（它是开发/运维工具，
用户日常不用）。这条边界要在文档里写清楚，避免将来有人给它加"发消息给托盘"的机制
——那会引入一整套 IPC 复杂度，收益很小。

### 5.3 退出语义

「退出」菜单项 → 停止所有工具进程（先 `tool.stop` 再 kill tree）→ 退出。
因为退出 = 所有 resident 工具停掉，**给一次气泡提示**（"已退出，工具已全部停止"），但不做二次确认
（确认框对托盘程序很烦人）。

## 6. 交互细节

### 6.1 执行反馈

点击菜单项后需要反馈。三种情况的处理：

| 情况 | 反馈 |
|---|---|
| 成功且返回短结果 | 气泡通知显示结果摘要（如 filehash 的哈希值） |
| 成功但无结果 | 气泡"完成"（约 2 秒，不打扰） |
| 失败 | 气泡显示错误摘要 + 记日志；**不弹模态对话框** |

**长任务**：`weight: task` 的命令要有进度反馈 —— 但 `task` 生命周期属于 P2 后续项。
P2 托盘阶段先不做进度条，只保证"点了有反应"。

### 6.2 图标资源

托盘需要一个 `.ico`（多尺寸：16/20/24/32，Win11 会按 DPI 缩放）。
- 位置：`src/Eztools.Desktop/assets/eztools.ico`
- 现在**没有**任何图标资源。建议先做一个简单的几何占位（后续可换），而不是拖住托盘开发
- 探针用的是 `SystemIcons.Application`（系统默认图标），正式实现不能这样——会跟别的程序撞脸

### 6.3 首次运行：引导到溢出区（必须做）

实测发现图标默认落在溢出区（`IsPromoted` 为空）。所以第一次运行时：

1. 托盘图标出现后，弹一次气泡：**"Eztools 已启动，图标在任务栏溢出区，可拖出固定"**
2. 记录"已提示过"（存 `state.json`），只提示一次
3. 不做的事：**不去自动修改用户的托盘设置**（那是用户的桌面，不该被程序改）

| 预算项 | 原值 | 现状 | 含托盘后 | 处置 |

但要把"P0 实测 0 MB"改成"托盘引入后 ≈50 MB"。

`scripts/budget.sh` 要相应补两条断言：托盘产物体积、托盘常驻内存。

## 8. 验收标准

**可自动断言的**（进 `acceptance.sh` 第 9 步）：

| # | 断言 |
|---|---|
| 1 | **每个托盘菜单项都能被零参调用成功**（§1.2 那条规则的守门人；这是最重要的一条） |
| 2 | 菜单合成：给定 `tools/` 目录，条目数与 `menus.location=tray` 的贡献点数一致 |
| 3 | 分组正确：同 `group` 的命令合并到一个子菜单 |
| 4 | 坏清单不拖垮托盘：放一个语法错的 `tool.json`，菜单仍能正常合成 |
| 5 | 单实例：第二个实例退出码 3 |
| 6 | `input: clipboard` 注入：设置剪贴板内容后触发，断言工具拿到了该内容 |
| 7 | 无残留进程：托盘退出后工具进程全部回收 |

**无法自动断言的（必须诚实标注）**：

| 项 | 为什么 | 怎么办 |
|---|---|---|
| 鼠标真的点了菜单项 | 托盘是交互式的，自动化只能到"程序化触发 handler"为止 | 手工验证清单（写进验证手册） |
| 气泡通知的观感 | 同上 | 手工 |
| 图标在通知区域的实际外观 / DPI 缩放 | 同上 | 手工 |

> 这条边界与 P0 的经验一致：**能自动化的部分必须自动化，不能自动化的要明说，不能含糊**。
> 探针已经证明"图标真的登记进通知区域"**可以**自动断言（查注册表），这条会进验收脚本。

## 9. 明确不做（P2 托盘阶段）

| 不做 | 为什么 |
|---|---|
| 托盘菜单里放"设置"项 | 设置窗口是 P1b，UI 栈还没定。先放"打开配置目录"占位 |
| 热键仲裁、独占资源仲裁 | 是 P2 的另两件，各自独立交付（见 §10） |
| `panels` 面板 | P4；且它需要 UI 栈 |
| 长任务进度条 | 依赖 `weight: task` 生命周期 |
| 主界面菜单（`location: "main"`） | 属于 P1b |
| 自动固定图标到任务栏 | 不该改用户的桌面设置（§6.3） |
| 托盘与 CLI 之间的 IPC | 收益小、复杂度高（§5.2） |
