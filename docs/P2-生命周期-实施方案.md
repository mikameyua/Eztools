# P2 尾巴实施方案 —— `resident` / `task` 生命周期（含 `tool.recover`）

> **状态**：✅ 已实施（2026-09-20，三个决策点按推荐默认值执行；落地记录见设计方案 §21）。
> **范围**：P2 尾巴 3 项中的生命周期项；Job Object（✅ 已落地，见 `ToolJobObject.cs`）与
> 日志诊断包导出（✅ 已落地，`ezt diag`）不在本方案内。
> **量级**：1~2 天（宿主行为 + 托盘集成 + 验收断言）。

## 1. 现状

- `tool.recover` 协议方法与 **SDK 接收侧已就绪**（P0 时铺好）；
- 宿主侧只有 `transient` 行为：调用完即回收，无常驻、无恢复；
- 托盘/热键/独占资源仲裁（§17/§19）已就绪，常驻工具的状态展示有现成载体；
- **Job Object 已引入**（`ToolJobObject.cs`，kill-on-close）——常驻工具**不能**挂进宿主的
  kill-on-close Job（宿主死常驻工具必须活），这是本方案最先要处理的交互点。

## 2. 决策记录（2026-09-20 按推荐默认值拍板并实施）

### 决策 1 · `task` 的触发机制
| 选项 | 内容 |
|---|---|
| **A（建议）** | 宿主启动时跑一次（`tool.json` 声明 `lifecycle: "task"`），跑完自动退出；`schedule` 字段留 P4 |
| B | 支持 `schedule`（间隔/定时），宿主内置调度器 |

理由：A 覆盖"启动期初始化/预热"类需求，零调度器复杂度；B 的真实需求场景（无外部 cron 的定时工具）目前不存在。

### 决策 2 · `resident` 的恢复语义
| 选项 | 内容 |
|---|---|
| **A（建议）** | 崩溃自动重启，复用现有崩溃熔断（10 分钟 3 次→禁用），重启间隔指数退避 |
| B | 崩溃后置 `needs-recover` 状态，等 `tool.recover` 显式唤醒 |

理由：A 无需人工干预即恢复服务，熔断兜底防重启风暴；`tool.recover` 协议保留给"禁用后手动恢复"语义。

### 决策 3 · 托盘交互
| 选项 | 内容 |
|---|---|
| **A（建议）** | 常驻/任务工具进托盘菜单：状态项（运行中/已禁用）+ `tool.recover` 入口 |

理由：托盘基础设施现成，成本低；没有入口的话常驻工具对用户不可见。

## 3. 实施要点

1. **Job Object 交互**：`ToolJobObject.Assign` 按 `lifecycle` 分流——`transient`/`task`
   挂宿主 kill-on-close Job（现状不变）；`resident` **不挂**（独立生命周期，宿主退出后存活，
   由下次启动/`tool.recover` 接管）。
2. **宿主侧**：`ToolHostManager` 增加 resident 注册表（工具 id → 运行实例），宿主退出时不回收；
   `task` 即发即忘。
3. **SDK 侧**：`tool.recover` 接收已有，补宿主发送侧（恢复时下发）。
4. **验收**（追加进 `acceptance.sh` / selftest）：
   - `lifecycle: "task"` 工具在宿主启动时被执行一次并退出；
   - `resident` 工具跨多次调用保持同一进程（pid 不变）；
   - `resident` 崩溃后自动重启（新 pid，状态恢复）；
   - 连续崩溃 3 次触发熔断禁用；
   - Job 交互：宿主退出后 transient 工具不残留、resident 进程存活。

## 4. 明确不做（本方案边界）

- `schedule` 调度器（P4 评估）；
- 常驻工具的配置热更新（现有配置推送通路天然覆盖，不另行设计）；
- Windows 服务形态的常驻（P3 已定推迟，同理）。
