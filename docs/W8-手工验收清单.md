## 2. 手工项（三段，都不可自动化）

### M1 · 核心服务缺席 ⇒ 点出口 ⇒ 过 UAC ⇒ 索引真的建起来（端到端）

**这条是本波的核心**：它同时验证"界面说了实话"与"点了真的有用"。

> **本项已自动化的部分**（不必手测，见 §1）：出口出现与可点性 · 点击是否真的接到宿主动作 ·
> 启动参数是否真的提权 · 取消如何识别 · 就绪判定 · 失败后出口是否保留。
>
> **★ 手工只剩最后一段**：真弹 UAC → 真点「是」→ **Core 真的起来** → **索引真的重新自举** → 能搜到文件。
> 这一段跨了两件自动化环境里做不到的事：**操作系统提权**（弹窗只能弹在真人面前）与
> **真进程的重新自举**（要 Core 真的跑起来、真的读 MFT）。

#### 第 0 步：先确认你当前处于哪种状态

按 `Ctrl+Alt+S` 唤出搜索窗 → 输入任意一个字母（如 `a`）→ **看底部那行小字**：

| 你看到的 | 含义 | 接下来 |
|---|---|---|
| **搜索需要启动核心服务，点此启动** | 正是 M1 要测的场景 | ✅ 继续第 1 步 |
| 正在建索引（首次全量约 10 秒级…） | 核心服务其实在跑（或探测无结论） | 先跑第 1 步的"停掉核心服务"，再看一次 |
| 能直接搜出文件 | **索引已经建好了**（热加载不需要核心服务）⇒ M1 场景不成立 | 见 §3「想强制复现」 |

#### 第 1 步：确认核心服务真的没在跑

```bash
cd "D:/01-项目代码/Eztools" && DOTNET_ROOT=D:/dotnet10 ./src/Eztools.Cli/bin/Debug/net10.0-windows10.0.19041.0/ezt.exe core status
```

```powershell
Set-Location 'D:\01-项目代码\Eztools'; $env:DOTNET_ROOT = 'D:\dotnet10'
& '.\src\Eztools.Cli\bin\Debug\net10.0-windows10.0.19041.0\ezt.exe' core status
```

- **期望输出**：`Core 未运行（无端点登记）。启动：ezt core start`
- 如果显示 `running ...` ⇒ 先停掉它：把上面命令的 `status` 换成 `stop`（**别接管道**），跑完再 `status` 一次确认。

#### 第 2 步：启动托盘

```bash
cd "D:/01-项目代码/Eztools" && DOTNET_ROOT=D:/dotnet10 ./src/Eztools.Desktop/bin/Debug/net10.0-windows10.0.19041.0/Eztools.Desktop.exe
```

```powershell
Set-Location 'D:\01-项目代码\Eztools'; $env:DOTNET_ROOT = 'D:\dotnet10'
& '.\src\Eztools.Desktop\bin\Debug\net10.0-windows10.0.19041.0\Eztools.Desktop.exe'
```

- **期望**：托盘区出现 Eztools 图标（可能被折叠进"隐藏的图标"里，点 `^` 展开）。

#### 第 3 步：唤出搜索窗并触发错误

按 **`Ctrl+Alt+S`**（★ 搜索热键；**不是** `Ctrl+Alt+O` —— 那是屏幕取字 OCR）→ 输入 `a`。

- **期望 A**：底部状态行显示 `搜索需要启动核心服务，点此启动`
- **期望 B**：**鼠标移到这句话上，指针变成小手**；停一秒会浮出提示 `点击启动核心服务（会弹出系统授权窗口）` ← 这两点一起确认"可点性看得见"

#### 第 4 步：点一下那句话

- **期望 A（立刻）**：状态行变成 `正在启动核心服务（请在系统弹窗中允许）…`
  ← ★ 这一句是**故意先给**的：UAC 弹窗可能 1~2 秒才出现、或被别的窗口挡住，没有即时反馈用户会连点
- **期望 B（1~2 秒内）**：屏幕变暗，弹出 UAC 授权窗（标题含 `ezt-core.exe`，或"你要允许此应用对你的设备进行更改吗？"）

#### 第 5 步：在 UAC 上点「是」

- **期望 A**：状态行变成 `核心服务已启动，正在重建索引…`
- **期望 B**：搜索窗**关闭并重新打开**（不是 bug —— 索引进程必须重启一次才能重新自举，见设计方案 §2.1）
- **期望 C**：新窗口底部**卷清单行**显示 `索引准备中…（后台自举进行中，结果暂不可搜）`

> ★ **已知行为（不是缺陷）**：重建窗口会**清空输入框** —— 新窗口是全新实例。重新输入即可。
> 理由：索引正在重建，旧结果本来就已经失效。

#### 第 6 步：等索引建好，搜一个真实文件

等 **10 秒 ~ 1 分钟**（取决于文件数量），输入一个你知道真实存在的文件名片段（如 `report`、`简历`）。

- **期望**：能搜出文件 ⇒ **M1 通过**
- 中途搜不到是正常的：卷清单行会停在"索引准备中…"，等它变成"已索引 N 个卷 · M 项"再试。

**副作用须知**：本项会真实启动一个**提权**进程（`ezt-core.exe`）。测完可停掉：

```bash
cd "D:/01-项目代码/Eztools" && DOTNET_ROOT=D:/dotnet10 ./src/Eztools.Cli/bin/Debug/net10.0-windows10.0.19041.0/ezt.exe core stop
```

```powershell
Set-Location 'D:\01-项目代码\Eztools'
& '.\src\Eztools.Cli\bin\Debug\net10.0-windows10.0.19041.0\ezt.exe' core stop
```

### M2 · 取消 UAC ⇒ 回显 + 出口保留（**验平台假设**）

**目的**：两件事。

1. **代码侧**（**已自动化**，`corestatus.echo`）：取消后状态行显示"已取消…"、**出口仍在**、文案不带"失败"字样。
2. **★ 平台侧（本项独有、不可自动化）**：Windows 在用户点「否」时**确实抛 `Win32Exception(1223)`** ——
   这是**代码里无法自造的假设**。测试里我只能 `new Win32Exception(1223)` 来验映射对不对，
   但那**证明不了"真取消时抛的就是 1223"**。若某个 Windows 版本换了这个码，
   用户就会看到"启动失败：操作已被用户取消"而不是"已取消启动核心服务" —— **只有真机点一次才能钉住**。

- **前置**：同 M1 第 0~3 步（核心服务没在跑，状态行显示出口）。
- **步骤**：点状态行 → 等 UAC 弹出 → 点 **「否」**（或直接点弹窗右上角 × 关掉）。

**判据（两条都要满足）**：

1. 状态行显示 `已取消启动核心服务（搜索仍不可用）`
2. **出口还在**：鼠标移到这句话上**仍然是小手**，再点一下会**再次弹出 UAC**

> ★ 第 2 条是本项的重点：如果取消一次按钮就消失，用户只能去命令行解决 —— 而那正是这个修复想替他省掉的。

### M3 · 改配置热生效（`usage=false`，**不重启托盘**）

**目的**：这是 W8·B2 的原始症状 —— 旧版改完必须重启托盘，且用户实测"`usage=false` 写进去了、`usage.json` 还在长"。

> **本项已自动化的部分**：配置指纹对 providers / usage / alias 三键各自敏感（selftest **37.5**）·
> store 禁用时**彻底不读写**（selftest **36.6**）· `launcher.usage` 两层闭环（acceptance 8.5c）。
>
> **★ 手工只剩编排那一段**："托盘**正在跑**时改配置 → **下次唤出**（不重启托盘）→ 行为真的变了"。
> 它必须**真按一次热键**才能触发 —— 键盘注入在本项目是**禁区**
> （键盘链刚以"换实现"收口，见踩坑全集 §2.25~§2.30），所以这一段只能人来做。

#### 第 1 步：先让系统记点数据

托盘在跑 → `Ctrl+Alt+S` → 搜一个应用（如 `code` 或 `记事本`）→ **Enter** 启动它。

#### 第 2 步：记下 `usage.json` 的修改时间

```powershell

```

```bash
cd "D:/01-项目代码/Eztools" && ls -l "$(cygpath "$APPDATA")/Eztools/launcher/usage.json"
```

- **期望**：显示一个时间（例如 `10:05:33`）。**把这个时间记在纸上/截图**，第 6 步要对比。

#### 第 3 步：关掉频次记忆

```bash
cd "D:/01-项目代码/Eztools" && DOTNET_ROOT=D:/dotnet10 ./src/Eztools.Cli/bin/Debug/net10.0-windows10.0.19041.0/ezt.exe config set desktop launcher.usage false
```

```powershell
Set-Location 'D:\01-项目代码\Eztools'; $env:DOTNET_ROOT = 'D:\dotnet10'
& '.\src\Eztools.Cli\bin\Debug\net10.0-windows10.0.19041.0\ezt.exe' config set desktop launcher.usage false
```

- **期望**：提示写入成功。

> ★★ **不要重启托盘**。这是本项的关键 —— 旧版必须重启才生效，修复后的正确行为是"**下次唤出**即生效"。

#### 第 4 步：让"下次唤出"发生

按 **`Esc`** 收掉搜索窗 → 再按 **`Ctrl+Alt+S`** 唤出。

- **期望**：窗口重新出现（若配置确已变更，窗口会被**重建**，看起来像闪了一下）。这一步同时验了"配置变更可见"。

#### 第 5 步：再启动一两个应用

搜 `记事本` / `code` → Enter 启动。

- **期望**：应用正常启动（关掉频次记忆不该影响启动功能本身）。

#### 第 6 步：再看 `usage.json` 的修改时间

```powershell
Get-Item "$env:APPDATA\Eztools\launcher\usage.json" | Select-Object LastWriteTime
```

```bash
cd "D:/01-项目代码/Eztools" && ls -l "$(cygpath "$APPDATA")/Eztools/launcher/usage.json"
```

- **判据**：与第 2 步**一模一样** ⇒ **M3 通过**（关闭期间一个字都没记、也没碰文件）
- **旧版症状（不该再出现）**：时间被推到刚才那一刻 ⇒ 说明配置仍未热生效

## 3. 想强制复现 M1 的场景

> 只在**第 0 步显示"能直接搜出文件"**时才需要（说明索引已建好，热加载不依赖核心服务，于是没有出口可点）。

索引是**派生数据**（丢了会自动重建），删掉它即可回到"未建"状态：

```powershell
# 先确认要删的目录（应该只含 index / 若干 vol-*.ezidx）
Get-ChildItem "$env:LOCALAPPDATA\Eztools\index" | Select-Object -First 5 Name

# 确认无误后删除
Remove-Item -Recurse -Force "$env:LOCALAPPDATA\Eztools\index"
```

```bash
cd "D:/01-项目代码/Eztools" && ls "$(cygpath "$LOCALAPPDATA")/Eztools/index" | head -5
```

> ⚠️ **只删 `index` 子目录** —— **不要**删 `%LOCALAPPDATA%\Eztools` 整个（里面还有 bin / logs / runtimes）；
> **更不要**碰 `%APPDATA%\Eztools`（那是你的配置与 `usage.json`）。
> 删完下次搜索会重新全量建索引（**10 秒级~更久**，取决于文件数），期间搜不到东西属正常。

## 4. 症状速查（出问题时先看这里）

| 症状 | 先查什么 | 结论方向 |
|---|---|---|
| 状态行**仍然**显示"正在建索引…"，没有出口 | 跑 `ezt core status` | 核心服务其实在跑 ⇒ 不是本缺陷；或探测拿不到结论（`Unknown` 格 ⇒ 按设计保守回落） |
| 点了状态行**没弹 UAC** | 看状态行是否变成"正在启动…" | 变了但没弹 ⇒ 可能被安全软件拦（状态行会显示"未登记端点"）；没变 ⇒ 鼠标没点在那一行上 |
| 弹了 UAC，点「是」后**搜不到文件** | 看卷清单行文案 | 显示"索引准备中…" ⇒ 还在建（等）；显示"索引不可用：…" ⇒ 另一次失败，看 `%LOCALAPPDATA%\Eztools\logs` |
| 改 `usage=false` 后文件**还在长** | 确认第 4 步做了"下次唤出"没有 | 没做 ⇒ 设计如此（生效时机 = 下次唤出）；做了还长 ⇒ **这是本波要修的症状，报我** |
| 热键按了没反应 | 是否有别的程序占用 `Ctrl+Alt+S` | 本仓专门的排查脚本：`python scripts/probe-hotkey-free.py` |
| 跑 `verify-desktop.py` 报"未知参数或错误：--install-root"，或"热键项…rc=6" | **先跑一次 `acceptance.sh`** | ★ **假失败**：`verify-desktop.py` 依赖 `acceptance.sh` 先建好 `_scratch/accept/`（install-root / config-root / tools-dir）—— 单独跑必然缺。这两条在 acceptance 里一直是 PASS |
| 验收里"设置窗口恢复默认热键"红（`registered=False`） | `python scripts/probe-hotkey-free.py` 看该组合键是否被外部占用 | **环境冲突**（如 `Ctrl+Alt+O/X/C` 被别的常驻软件占着）⇒ 断言已按三态判定**跳过并计数**；不是代码问题 |

> ★ **跑验收的顺序**（2026-10-03 实测教训）：**先 `acceptance.sh`，再 `verify-desktop.py`**。
> 反过来跑会看到上面第一行的两条假失败 —— 那会让人误以为代码坏了。
