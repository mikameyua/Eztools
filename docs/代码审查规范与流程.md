# 代码审查规范与流程（Eztools）

> **角色**：本项目**代码审查的唯一规则出处**（规则 / 分级 / 流程 / 模板）。
> **状态**：✅ 现行（v1.0，2026-09-28 立）。
> **适用范围**：`src/`（8 个 .NET 项目）、`tools/**`（Python 工具）、`sdk/python`、`scripts/**`（bash / PowerShell）、`docs/**`（**本项目文档即契约，文档变更同样入审**）。
> **不适用范围**：`PowerToys/`（上游参照克隆，只读对照）、`spike/`（一次性技术验证）、`_scratch/` `_review/`（本机临时区）、`dist/` `payload/`（构建产物）。
> **上游依据**：`docs/README.md` §2 权威层级 · `docs/验收断言审视清单.md` §11/§12/§13（断言方法论 M1~M15 / 静默失败 S1~S17）· `docs/踩坑全集.md` §2.13~§2.32 · `docs/参考来源.md`（外部代码借用许可）· `docs/Eztools-设计方案.md` §15.4（功能完整性 > 预算）。

## 1. 审查目标与适用范围

### 1.1 目标（本项目的具体目标，不是通用口号）

| # | 目标 | 针对的本项目历史病灶 |
|---|---|---|
| G1 | **合并前拦住"静默失败"** | S1~S17 登记册：解析器缺 Error 出口、`switch` 无 `default` 静默丢弃未知参数、`rc=0` 但没做事、断言挂在环境依赖分支里空转 |
| G2 | **拦住契约漂移** | `volume.readMft` 的 `limit` 被单缓冲突破；`panels` 长期"文档有、代码零命中"；SDK 指纹遮蔽 |
| G3 | **保住"改了真的生效"** | 增量构建不拷 DLL、多 TFM 残留目录（`net10.0-windows\` 死产物踩过 2 次） |
| G4 | **约束安全边界** | 工具代码永不进 Core、无通用 Win32 后门、`CurrentUserOnly` + 对端令牌双闸、每条调用含拒绝均审计 |
| G5 | **让审查结论可复核** | 报告必须"有结论 + 有回归证据 + 有遗留台账"，结论可用 grep / 验收输出 / 命令复现 |

> **一句话**：审查的目标不是"看起来干净"，而是**让"没生效 / 没被测 / 越了界"这三件事在合并前暴露**。

### 1.2 三层防线（先分清责任，别指望人工审出机器能查的东西）

| 层 | 覆盖什么 | 手段 | 不覆盖什么 |
|---|---|---|---|
| ① **自动化闸门**（必须绿） | 行为回归、契约结构、文档引用存在性 | `scripts/acceptance.sh` · `scripts/verify-desktop.py` · `selftest` · `scripts/check-doc-refs.py --strict` · `dotnet build` | 设计意图、威胁模型、弱断言 |
| ② **人工审查**（本文主体） | 正确性、契约一致性、安全边界、可维护性、**断言本身的质量** | 8 维度清单（§3）+ 突变验证 | 大规模行为回归（交回 ①） |
| ③ **运行期观测** | 真实设备 / 真实权限 / 真实输入 | 手工验收清单（各波 `*-手工验收清单.md`）+ 探针 | 覆盖率（靠抽样，不是全量） |

### 1.3 触发条件（满足任一即入审）

| 触发 | 要求 |
|---|---|
| 常规功能提交（`feat` / `fix`） | 标准审查（§4.2 主干流程） |
| **契约面变更**（协议字段 / `tool.json` schema / 错误码 / 贡献点） | 必须**先于代码冻结**并专项复核；引用协议文档小节号 |
| **安全面变更**（`Eztools.Core`、提权原语、管道 ACL、令牌校验、审计） | 加一名安全复核人；必须给"对抗面"结论 |
| **验收脚本 / 断言变更**（`acceptance.sh` / `verify-desktop.py` / `_step*.sh`） | 加严专用清单（§3.7）；**放宽检查必须带突变验证** |
| **文档变更**（`docs/**`） | 跑 `check-doc-refs.py --strict`，0 悬空 |
| 每波收口 | 阶段审（§6.2） |
| 性能敏感路径（索引 / 全表扫描 / 常驻进程） | 加性能复核人；给出实测数字而非估计 |

## 2. 审查前准备

### 2.1 作者侧：提交前必须自检的 5 件事（不满足则不派审）

| # | 动作 | 证据要求 |
|---|---|---|
| 1 | 跑三闸门 | 贴 **FAIL=0** 的原始汇总行（如 `结果: 通过 N / 失败 0`）；拒绝"我跑了没问题" |
| 2 | 写变更自述 | 用 §8.1 模板：**改了什么 / 为什么这么改 / 契约面有无变化 / 已知限制 / 怎么复现验证** |
| 3 | 标注契约面 | 是否触碰协议 / `tool.json` schema / 错误码 / SQLite 表结构；触碰则给出**受影响文件清单** |
| 4 | 认领已知限制 | 未做的部分必须显式写"未做"，**不接受沉默**（沉默 = 幽灵代码温床） |
| 5 | 给出复现命令 | 一条可直接粘贴的命令（含必要环境变量），让审查者能自己复核 |

### 2.2 审查者侧：读什么（顺序固定，别跳）

1. `docs/README.md` §2 —— 确认这份改动的**权威文档是哪一份**（别拿实施计划当设计依据）。
2. `docs/Eztools-设计方案.md` 对应小节 + 该波 `*-设计方案.md` —— 确认**意图**。
3. `docs/踩坑全集.md` §2.13~§2.32 中**与本模块相关的节** —— 先看是否已有前车之鉴。
4. **同模块的历史审查报告**（`docs/代码审查报告-*.md`）—— 确认将要提的意见**不是已被判定"不采纳"的**（§5.4）。
5. 该模块的**验收脚本对应段落** —— 确认"声称的行为"确实被断言覆盖（M1：分清"弱断言"与"零覆盖"）。

### 2.3 环境准备（本项目特有，跳过会得到假结论）

| 坑 | 前置动作 |
|---|---|
| 提权 Core 常驻会锁住 `bin/` 下 DLL | 改代码前先 `ezt core stop`；构建报 `MSB3027` 时看它点名的文件 |
| **热键相关的验收失败** | **先跑 `scripts/probe-hotkey-free.py`** —— `RegisterHotKey` 失败多半是**别的进程占了这个组合键**（实测 `Ctrl+Alt+W` 返回 1409），不是代码回归。探针会打印 `[OK]/[占用]` + 错误码 + 处置建议 |
| `DOTNET_ROOT` 未设 → 用错 SDK | 构建/运行前 `export DOTNET_ROOT=D:/dotnet10`（PATH 默认 7.0 会拒绝 net10） |
| 多 TFM 残留目录 | 确认跑的是当前 TFM 输出目录，不是 `net10.0-windows\` 之类死产物 |
| 沙箱静默拦截磁盘写删 | 写真实磁盘 / 起进程的验证命令需显式关闭沙箱，否则命令退 0 但文件毫发未动 |
| 探针上下文无消息泵 | 交互类探针必须有裸泵（`PeekMessage` → `Dispatch`），否则键盘管线不喂 |

## 3. 审查检查项

> **使用方式**：按 §3.1~§3.8 逐维度过；§3.9 是**一票否决红线**（任一命中即阻断）；§8.4 是可打印打勾的速查表。
> **级别标记**：🔴 阻断（必须修）· 🟡 应修（本次或紧随其后）· 💭 提示（可排期）· 👍 表扬（值得推广的做法）。

### 3.1 维度一：正确性与契约一致性

| # | 检查项 | 判据 / 怎么查 | 级别 |
|---|---|---|---|
| 1.1 | 契约漂移：实现与文档/协议声明的字段、语义、上限是否一致 | 逐字段对照协议文档；边界值（上限/下限）必有断言 | 🔴 |
| 1.2 | **幽灵代码**：定义了但无调用点的"已修复" | 全仓 grep 方法名，调用点数必须 ≥1（本项目已踩：`IsPidAlive()` 定义了却没人调，30s 假死"修复"其实没落盘） | 🔴 |
| 1.3 | **名存实亡 flag**：参数被静默丢弃 | `switch` 必须带 `default` 报错；`rc=0` ≠ 参数生效 | 🔴 |
| 1.4 | 错误码族混用 | 同一处错误只说"错误码"时必须指明族（如 `-32017` 属哪一族）；不同族的码不得复用 | 🟡 |
| 1.5 | 早返回 / 守卫顺序 | 守卫必须在"第一次调用之前"定义（本项目已踩：bash 函数定义在使用之后 ⇒ 断言静默空转） | 🔴 |
| 1.6 | 注释与实现是否一致（注释腐化） | 类头/方法注释描述的机制 = 代码实际机制；不一致按 🟡 起 | 🟡 |
| 1.7 | 占位是否"干净" | 未实现的功能必须**显式**回 `NotSupported` 并带文案，不得静默返回空 | 🔴 |
| 1.8 | **新增协议字段是否真的端到端贯通** | 协议层（Core）/ 转发层（CLI・Host）/ 展示层 常见的**白名单式构造**（手工 `new JsonObject{...}`）⇒ 新字段**不自动透传**，漏一行就**静默丢弃**（不报错、无警告）。<br>**判据：改协议时两层都测** —— 直连协议测一次（证明服务端做对）+ `ezt <cmd> --json` 端到端测一次（证明没在层间丢）。<br>**同族已 3 次**：`ezt list --json` 漏 `handler` → 同文件 `list` 与 `info` 两展示面不一致 → `ezt core ping --json` 漏 `auditFailures`（2026-09-29 安全面专项审 RI-3） | 🔴 |

### 3.2 维度二：静默失败与失败可见性（**本项目最高频，单列**）

> 判据来源：`docs/验收断言审视清单.md` §12 静默失败登记册（S1~S17）。新增一条同类问题即注册新编号。

| # | 检查项 | 怎么查 | 级别 |
|---|---|---|---|
| 2.1 | 解析器 / 分派器是否有 **Error 出口** | 未知输入必须走显式失败分支，不得"什么都不匹配然后成功返回" | 🔴 |
| 2.2 | 异常是否被 `catch` 吞掉 | UI 入口 / 消息回调里的 `catch` 是静默坟场：必须落日志 + 有可见出口（状态行 / 气泡）。**已机器化**：`scripts/review-guards.py` G1（裸空 catch = 🔴）。确实要吞的场合必须写豁免标记 `// review-guards:allow-empty-catch :: <理由>` —— 见 §3.9.1 | 🔴 |
| 2.3 | 失败是否有**用户可见出口** | 语言包缺失、卷读取失败、解码失败等必须"结构化错误码 + UI 文案"双出口 | 🔴 |
| 2.4 | 断言是否挂在**环境依赖分支**里 | 环境不满足时是"跳过并计数"还是"静默空转"？跳过必须计入 `SKIPPED`（满额 = PASS + SKIPPED 自洽） | 🔴 |
| 2.5 | 是否存在"改宽松"的检查 | 任何**放宽**检查的改动，必须自带**突变验证**（证明它仍会红） | 🔴 |
| 2.6 | 数值型断言取 0 / 空值 | 先怀疑**采样工具**，再怀疑被测对象（M11） | 🟡 |
| 2.7 | "必要"判据是否在真实负载下成立 | 终局判据不能只看必要条件（如"读到空批才算追平"在持续写入的卷上永不成立） | 🔴 |
| 2.8 | 是否只在探针上下文成立 | 探针绿 ≠ 生产绿：确认消息泵、焦点、进程上下文一致 | 🟡 |

### 3.3 维度三：安全与特权边界

| # | 检查项 | 判据 | 级别 |
|---|---|---|---|
| 3.1 | 工具代码是否越界进入 Core | 铁律：**工具代码永不进入特权层**；Core 只暴露命名原语 | 🔴 |
| 3.2 | 是否引入"通用 Win32 后门" | 禁止任何形式的任意系统调用转发（设计铁律） | 🔴 |
| 3.3 | 管道 / IPC 访问控制 | `CurrentUserOnly` **必须显式设置**（在提权进程里会静默失效，必须手工验证）+ 对端令牌核名双闸 | 🔴 |
| 3.4 | 提权原语是否有声明门槛 | 工具侧 `elevatedPrimitives` 声明 + 宿主侧校验，两侧都要有 | 🔴 |
| 3.5 | 审计是否含**拒绝**路径 | 每条调用（含被拒）都留审计；被拒记录应带验证出的对端 PID | 🟡 |
| 3.6 | UIPI / 低完整性对抗面 | 低完整性进程读取受限内容的行为要有明确结论（读不到 → 显式占位条目，不静默丢） | 🟡 |
| 3.7 | 外部代码借用是否合规 | 借前读 `docs/参考来源.md` 问三句（许可 / 抄的范围 / 如何标注）；GPL-3.0-or-later 兼容性 | 🔴 |
| 3.8 | 敏感数据落盘 | 日志 / 诊断包里不得出现明文凭据；诊断包需脱敏 | 🔴 |
| 3.9 | **降级／告警类信号是否有可达出口** | 先问"这条告警写到哪、**在那个运行形态下谁收得到**"：提权 Core 的 stdout **无人接收**（`UseShellExecute` ⇒ 无重定向，代码注释原文"ShellExecute 会把它吞掉"）⇒ **只走 stdout 的告警＝静默**。至少要有**一条不依赖 stdout / 父进程存活**的出口（文件 或 协议字段）。<br>**反模式**：以"我加了 `Console.WriteLine` / 日志调用"作为修复完成的证据 —— 那是**纸面成立、送达率为零**（RI-1 实证） | 🔴 |

### 3.4 维度四：跨进程 / 并发 / 生命周期

| # | 检查项 | 判据 | 级别 |
|---|---|---|---|
| 4.1 | stdio JSON-RPC 分帧 | `\n` 分帧、**逐帧 flush**；Python 侧 `-I -X utf8 -u`；stdin **禁 BOM** | 🔴 |
| 4.2 | 请求-响应配对 | 工具→宿主的请求必须**逐条回复**，不得丢帧或乱序 | 🔴 |
| 4.3 | JsonNode 复用 | 挂过父的 Node 不得复用（需 `DeepClone`）；`JsonSerializer` 大小写敏感 | 🔴 |
| 4.4 | 进程回收 | 子进程/进程组按**进程树**回收；单实例锁冲突要有明确退出码（不是超时） | 🟡 |
| 4.5 | 取消与关停 | 长调用必须接 `CancellationToken`；不得传 `CancellationToken.None` 让宿主关停陪等 | 🟡 |
| 4.6 | 线程优先级 / 异步续体 | `THREAD_MODE_BACKGROUND_BEGIN` 是线程语义，async 续体会丢优先级（泵必须同步） | 🟡 |
| 4.7 | 常驻进程锁文件 | 常驻实例会锁 `bin/` DLL ⇒ 必须在文档/错误信息里给出"先停再改"的指引 | 💭 |
| 4.8 | **原生（非托管）资源生命周期** | `Marshal.AllocHGlobal` / `CreateFileW` 句柄 / `DuplicateHandle` 副本等，**成功与失败路径都必须释放**；若成功路径把资源返还给调用方，必须写明**谁负责释放**。<br>实证：`QueryHandleTable` 成功路径 `return buffer` 后无人释放 ⇒ 每次调用泄漏一整张句柄表（RI-4，实测 7~9 MB/次）。<br>**可实测判据**：同一进程连续调用同一原语 N 次，内存**不得线性增长** | 🔴 |
| 4.9 | **调用方放弃后，服务端计算能否停止** | 客户端超时/断开后，服务端不得继续跑"没人等"的计算 —— 否则每次放弃都留下一份资源（线程/栈/句柄）。**取消信号要绑真实信号**（如连接断开），而不是猜一个阈值。<br>实证：`handles.enumerate` 客户端超时后 Core 照跑、每次新开一批 worker ⇒ 挂起线程累积 ⇒ 第 4 次起必然超时（RI-6） | 🔴 |

### 3.5 维度五：性能与资源

| # | 检查项 | 判据 | 级别 |
|---|---|---|---|
| 5.1 | 是否在热路径做全表扫描 | 全量枚举 / 逐句柄 `OpenProcess` 类操作必须给出复杂度与实测数字 | 🟡 |
| 5.2 | **单次调用的资源增量是否与调用次数解耦** | 常驻服务上，任何"每次调用新增一份不回收资源"（内存 / 线程 / 栈 / 句柄）都会累积到 OOM。**验证手法：连续调用 N 次并记录内存与线程数，看是否线性增长** —— 实测优于读代码（RI-4 / RI-6 都是这样抓到的）。<br>⚠️ 注意区分"真泄漏"与"GC 惰性"：看**后段斜率是否持续**，而非单点数值 | 🔴 |
| 5.2 | 上限参数是否真的生效 | 内存/条数上限必须被内层循环尊重（本项目已踩：`limit` 被单缓冲突破数百条） | 🔴 |
| 5.3 | 日志是否无界增长 | 追踪日志需轮转或截断；常驻进程尤其 | 🟡 |
| 5.4 | 大缓冲 / 固定栈缓冲 | 固定大小缓冲必须有"溢出即跳过并计数"的行为，不误报也不静默丢 | 🟡 |
| 5.5 | 冷启动 vs 热路径分开断言 | 冷态单样本不能对**分位数闸**（M15）；首建与热启动的量级差异要分别记录 | 🟡 |
| 5.6 | 性能结论的取证方式 | 引"实测数字 + 采集条件"（条数 / 卷数 / 是否提权），禁凭估计 | 🟡 |

### 3.6 维度六：可读性与可维护性

| # | 检查项 | 判据 | 级别 |
|---|---|---|---|
| 6.1 | 命名 | 与既有风格一致（C#：`PascalCase` 类型 / `_camelCase` 私有字段；Python：`snake_case`；脚本：`assert_xxx` 谓词式） | 💭 |
| 6.2 | 死代码 | 无调用点的私有方法、赋值后无人使用的变量、`if` 分支永假 | 🟡 |
| 6.3 | 函数长度 / 圈复杂度 | 参考阈值：函数 ≤ 50 行、圈复杂度 ≤ 20 触发讨论（**是讨论触发线，不是硬闸**） | 💭 |
| 6.4 | 注释解释"为什么" | 关键取舍（如"为何不回退方案③""为何不做 DIP 估算"）必须写下来（M12：决策要连同前提一起记） | 🟡 |
| 6.5 | 注释覆盖 | 参考值 ≥ 15%（本仓 `src/Eztools.Core` 实测 14.23%）；**不设硬性 KPI** | 💭 |
| 6.6 | 🔴 **行宽不是判据** | 80/120 字符规则**已明确判定"不采纳"**（长行是有意取舍，见 §5.4）；**不得再提** | — |

### 3.7 维度七：测试与验收断言质量（**改验收脚本时必须专项过**）

> 方法论来源：`docs/验收断言审视清单.md` §11（M1~M15）与 §13。速用判据如下。

| # | 检查项 | 判据 | 级别 |
|---|---|---|---|
| 7.1 | 断言是否**落数字或退出码** | 禁 `cmd \| grep -q`、禁 `A && B \|\| C && D` 这类会互相污染的写法 | 🔴 |
| 7.2 | 弱断言 vs 零覆盖 | 弱断言（恒真/恒假/子集判据）**必须修**；整块逻辑零覆盖**更严重**，优先级最高（M1） | 🔴 |
| 7.3 | 断言名 = 契约 | 断言名描述的行为必须与判据一致（"描述与事实不符"是弱断言的一种） | 🟡 |
| 7.4 | 判据引用的字段**真实存在** | 引用不存在的字段 ⇒ 恒真/恒假（M3） | 🔴 |
| 7.5 | 是否有**反向断言** | 防"一律 X"：既要"该报的报出"，也要"不该报的不出现" | 🟡 |
| 7.6 | 结构约束是否**正反双向** | 既要"新实现三符号存在"，也要"七件旧干预符号不得复活" | 🟡 |
| 7.7 | 顺序是否被断言 | 顺序也是契约（如"函数先定义后调用"、事件先后） | 💭 |
| 7.8 | 新增/放宽检查是否带**突变验证** | 突变 = 故意注入缺陷，断言必须变红；"删掉没变红"要先分辨原因（M4） | 🔴 |
| 7.9 | 断言总数是否漂移 | 满额 = PASS + SKIPPED 必须自洽；断言的**位置**（早于首次调用）也是契约。**已机器化**：守卫 G6 抓「有跳过文案却没有 SKIPPED 计数」—— 2026-09-28 断言语审抓到 3 条「假绿通道」后新增 | 🟡 |
| 7.10 | 两条闸走同一路径时能否分辨**谁在拦** | 必须能分辨是哪条闸生效（M13） | 🟡 |
| 7.11 | 结构断言是否被注释误伤 | 剥注释行再匹配（朴素的子串匹配会被注释误红） | 💭 |
| 7.12 | 判据是否与**上游保证**冲突 | 若某字段被上游**强制保证**（缺则整条丢弃、空则回退默认值）⇒「该字段非空/存在」是**恒真断言**；若上游**根本不校验**该字段 ⇒「必须非空」是**判反**。**写法**：先读上游实现确认哪些字段被保证、哪些可选，再用**正向值对照**（与源文件逐字段相符）替代「非空」<br>**实证**：2026-09-29 `actions` 契约断言第一版写「四字段非空」——`ManifestParser.cs:461-479` 里 `id`/`handler` 空则整条跳过、`title` 空则回退为 `id`（三者恒真），而 `when` 完全不校验（判反）。被突变验证抓出后改为双向契约（完整保留 + 残缺拒绝 + 逐字段相符） | 🔴 |
| 7.12 | 删断言的合法性 | 删除断言必须给出理由与替代覆盖，且写进报告 | 🔴 |

### 3.8 维度八：文档与引用一致性

| # | 检查项 | 判据 | 级别 |
|---|---|---|---|
| 8.1 | 引用完整性 | `python scripts/check-doc-refs.py --strict` 必须 **0 悬空** | 🔴 |
| 8.2 | 待建 / 退役标记 | 待建文件加 `（新建）` 前缀；退役写 `—— 已更名/已删除`（须紧跟路径、24 字符内） | 🟡 |
| 8.3 | 不重复定义 | 同一决定只能有一个出处，其余写指针；状态列是**硬要求** | 🔴 |
| 8.4 | "文档写了" ≠ "已经能用" | 状态标记必须与代码一致；引用未实现内容必须显式标注 | 🔴 |
| 8.5 | 变更记录 | 文档文末必须有 `## 变更记录` 表；新文档必须登记进 `docs/README.md` §3 | 🟡 |

### 3.9 🔴 一票否决红线（任一命中即阻断，不允许"下次改"）

1. 引入通用 Win32 后门，或让工具代码进入特权层。
2. 安全闸被移除/放宽而无并发替代措施（`CurrentUserOnly` 消失、令牌校验被绕过、审计被跳过）。
3. 静默失败：未知输入被静默忽略（缺 `default` / 缺 Error 出口）。
4. 幽灵代码：宣称已修复但无调用点。
5. 断言被削弱 / 删除而无替代覆盖，或放宽检查无突变验证。
6. 三闸门任一非绿而声称"可合并"。
7. 引用了不存在的文档路径 / 小节号（`check-doc-refs.py --strict` 报红）。
8. 违背 `docs/Eztools-设计方案.md` §9.3 安全铁律，或 `docs/参考来源.md` 的许可分级。

### 3.9.1 已机器化执行的红线（自 2026-09-28 起）

红线不能只写在文档里 —— "提不提"取决于审查者记不记得。以下几条已由 `scripts/review-guards.py`
固化为检查，并挂在 `scripts/acceptance.sh` 第 20 步（**判据 = 该步 FAIL=0**）：

| 检查 | 抓什么 | 级别 | 对应条目 |
|---|---|---|---|
| **G1** | 空 `catch`（剥掉注释后无任何语句） | 🔴（裸空）/ 🟡（仅注释） | 红线 3、§3.2 |
| **G2** | **字符串 `case`** 的 `switch` 无 `default` | 🔴 | 红线 3、§3.1 1.3 |
| **G3** | 验收脚本出现 `\| grep -q` 或 `A && B \|\| C && D` | 🔴 | §3.7 7.1 |
| **G4** | `private` 方法全仓只有定义处一次出现（幽灵代码候选） | 🟡 | 红线 4、§3.6 6.2 |
| **G5** | 项目 TFM 与 `bin/` `obj/` 下实际 TFM 目录不一致（死产物） | 🟡 | §3.4 4.7、踩坑全集 §2.31 |
| **G6** | 断言脚本出现「跳过」文案、附近却没有 `SKIPPED` 计数 | 🟡 | §3.7 7.9、§7.3 FAQ 16 |

**两条纪律（都靠机制而不是自觉）**：

1. **刻意沉默必须变成机器可见的声明**。确实需要吞异常的场合，写：
   ```csharp
   catch (IOException)
   {
       // review-guards:allow-empty-catch :: 临时目录清理失败不影响断言结论，系统 temp 兜底
   }
   ```
   标记写在**块内**或**紧邻 `catch` 的上一行**（写在 `try` 上方不算 —— 那是在标注 `try`）。
   **只写标记不写理由 = FAIL**：否则"随手加个标记"就能取消检查，等于把闸门拆了还亮绿灯。
   豁免数量会被验收断言**落数字**（EXEMPT=n），防止它变成黑洞。
2. **行宽（80/120 字符）明确不在检查集内**，且守卫会主动打印"不检查"。
   这条"不采纳"裁决（见 §5.4 与 `docs/README.md` §3.6）已被 `_step19_review_guards.sh`
   的反向断言钉住 —— **后人顺手把行宽加回来会让验收红**。

### 4.1 主干流程图

```
作者自检（§2.1 五件事）
   │  不达标 → 退回作者，不派审
   ▼

   ▼
初审（8 维度清单 + 突变验证）  ──┐
   │                              │ 意见分级（§5.1）
   ▼                              │
出意见（🔴/🟡/💭/👍，逐条给判据）  │
   ▼                              │
作者处理（🔴 必修；🟡 本次或紧随；💭 入台账）
   ▼
复验（只验 🔴/🟡 的修复 + 回归）
   │  未通过 → 回初审（禁止"边修边合"）
```

### 4.2 角色与职责（小团队可兼任，但**职责不可省**）

| 角色 | 职责 | 不可兼任的边界 |
|---|---|---|
| **作者** | 自检、写变更自述、按意见修复、给回归证据 | — |
| **主审** | 过 8 维度清单、给分级意见、复验修复 | **不得审自己当天写的代码**（冷却 24h 或切上下文重读） |

| **裁决人** | 处理"作者与主审分歧 / 意见已被判不采纳仍被提出" | 裁决依据**必须引用文档**（设计方案 / 踩坑全集 / 断言清单），不得凭偏好 |

### 4.3 时限（避免审查成为瓶颈）

| 级别 | 响应时限 | 说明 |
|---|---|---|
| 安全面 / 契约面变更 | **24 小时内**出初审结论 | 这类改动越晚发现问题代价越大 |
| 常规功能提交 | **1 个工作日** | 超时未审 → 作者可向裁决人升级 |
| 🔴 复验 | **4 小时内**（同一工作日内） | 阻断项不允许跨夜挂起 |
| 🟡 处理 | 本次提交内或**紧随的一次提交** | 放入台账必须有排期 |
| 💭 处理 | 入 `docs/未完成项与待决清单.md` | 无排期即为"接受现状"，需显式记录 |

### 4.4 单人 / 小团队降级模式（本项目的实际形态）

| 模式 | 做法 | 补偿机制 |
|---|---|---|
| **A. 无第二人** | AI 审查（8 维度清单 + 突变验证）+ 自动化闸门充当"第二双眼睛" | ① **冷却自审**：提交后隔 ≥24h 或换全新上下文重读；② 强制"写变更自述"（写不出来通常说明想清楚了一半）；③ 每波收口必须做一次**专项审**（§6.2） |
| **B. 有 2~3 人** | 模块交叉审（按模块而非按功能分派，避免同模块互审盲区） | 安全面变更**必须**跨人 |
| **C. 单人 + 外包/外部** | 只对外包部分做**契约面 + 安全面**审查 | 契约文档先冻结 |

### 4.5 提交与合并约定

- 提交信息前缀：`feat:` / `fix:` / `docs:` / `chore:`（沿用本仓既有历史）。
- 一个提交一个意图；**契约变更与行为变更不得混在同一提交**。
- 合并前必须贴出：闸门汇总行 + 本次改动的验证命令。

## 5. 审查意见的分级与处理

### 5.1 四级定义（**不引入新的字母编号**，与既有 S/M/R 编号族不冲突）

| 标记 | 名称 | 定义 | 合并影响 | 处理方式 |
|---|---|---|---|---|
| 🔴 | **阻断** | 会导致错误行为、静默失败、安全边界破坏、契约破坏；或命中 §3.9 红线 | **阻止合并** | 必须修 + 复验 |
| 🟡 | **应修** | 影响正确性/可维护性/可观测性，但有临时缓解 | 不阻止合并（须登记排期） | 本次或紧随提交修 |
| 💭 | **提示** | 风格、命名、文档补充、可选优化 | 不阻止合并 | 入台账，可长挂 |
| 👍 | **表扬** | 值得推广的巧妙解法 / 干净的抽象 | — | 写进报告，作为后续参照 |

> **为什么不用 S1/S2/S3**：本仓 `S1~S17` 已被"静默失败登记册"占用（`docs/验收断言审视清单.md` §12），`M1~M15` 被断言方法论占用，`R1~R17` 被风险表占用。为避免"同名不同义"，**审查意见编号统一用 `RI-<n>`（Review Item）**，级别只用上面的表情 + 中文名。

### 5.2 意见书写格式（每条都必须能被独立复核）

```
🔴 RI-3 契约漂移：`limit` 上限被单缓冲突破
位置：`src/Eztools.Core/Primitives/VolumePrimitives.cs` · ParseRecords
现象：外层循环用 records.Count < limit 控制，内层把 64KB 缓冲全部解析进结果，
      单次返回条数可超 limit 数百条 → 接口契约漂移。
为什么是阻断：调用方按 limit 分配/截断，超发会被静默截断，表现为数据缺失而非报错。
建议：limit 传入 ParseRecords，内层循环同样判 records.Count < limit。
复核方式：<一条可粘贴的命令或用例>
```

要求：
1. **给位置**（文件 + 方法/行）。
2. **给现象**（不是"有问题"，是"在什么输入下会怎样"）。
3. **给为什么**（为什么这个级别、会引发什么后果）。
4. **给建议**（可执行）。
5. **给复核方式**（命令 / 用例）。
6. 不确定时**提问**，不要断言（"这里是否考虑了 X？"优于"你漏了 X"）。

### 5.3 争议与升级

| 情形 | 处理 |
|---|---|
| 作者不认同意见 | 作者给出**反证**（命令 / 实测）；谁主张谁举证 |
| 双方僵持 | 升级裁决人，裁决**必须引用文档**；裁决结论写进报告 |
| 意见与本仓既有裁决冲突 | **以既有裁决为准**（除非裁决的前提被证伪 —— 本项目已有"前提被证伪后改判"的先例，允许推翻，但必须书面记录新前提） |

### 5.4 "不采纳"必须留痕（**本项目最有价值的规则**）

- 任何被判定"不采纳"的意见，**必须**在 `docs/README.md` §3 对应文档行的**引用建议列**写明白（例如 `代码审查报告-全面对照-2026-09-20.md` 那行标注的"🔴 明确不采纳（80 字符行噪音，长行是有意取舍）—— 别当待办修"）。
- 未留痕的"不采纳"= 无效裁决，下一轮审查一定会被重复提出，团队会反复在同一个问题上争论。
- 留痕格式：`🔴 明确不采纳（<一句话理由>）` 或 `📁 归档（<理由>）`。
- **能机器化的"不采纳"要连检查一起钉住**：光写"别当待办修"仍靠人记；写成**反向断言**才是终局。
  实例：行宽规则的"不采纳"已由 `scripts/_step19_review_guards.sh` 的一条反向断言守住
  （守卫必须仍声明"行宽不检查"，且 `--selftest` 里有一条 300 字符长行的**零命中**断言）——
  **后人把行宽加回来，验收会红**。这是本条规则的执行版。

## 6. 审查周期与反馈机制

### 6.1 三级节奏

| 周期 | 时机 | 范围 | 产出 |
|---|---|---|---|
| **增量审** | 每次提交 / 每个子任务完成 | 本次改动 + 直接联动点 | 意见（`RI-<n>`）+ 修复回归 |
| **阶段审** | 每波收口（Wave 级） | 该波全部改动 **对照** `docs/Eztools-设计方案.md` §12 路线图逐项核对 | `（新建）docs/代码审查报告-<范围>-<日期>.md` |
| **专项审** | 每月或每 2 波，轮转 | ① 安全面 ② 性能面 ③ **断言质量面** | 专项报告 + 台账更新 |

> **专项审为什么必须有"断言质量"这一档**：本项目"测试全绿但功能其实是坏的"已多次发生（弱断言、零覆盖、断言挂在环境分支），这类问题的唯一系统性解法就是**定期用 M1~M15 清单普审一遍断言**，而不是等它被真人手测撞出来。

### 6.2 阶段审的最低动作（对照检查）

1. 打开 `docs/Eztools-设计方案.md` §12，逐项标注：✅ 完成 / ⚠️ 部分完成 / ❌ 未做。
2. 对"部分完成"必须列出**缺失清单**（本项目已踩：P2 标题未打 ✅ 但正文只提"托盘已完成"，完成度一读之下容易误判为全清）。
3. 核对文档一致性：过时陈述优先级最高（"诚实清单"过时比缺失更有害）。
4. 逐项给证据（grep / 验收输出 / 手测记录），**结论必须可复核**。

### 6.3 反馈机制（报告落盘规范）

| 要求 | 说明 |
|---|---|
| 落盘位置 | `（新建）docs/代码审查报告-<范围>-<日期>.md`（命名沿用既有 `<主题>-<日期>` 惯例） |
| 头部必备 | 范围 / 方式 / 结果（🔴 n · 🟡 n · 💭 n） |
| 结论必备 | 修复清单（文件 + 具体改动）+ **回归证据**（闸门数字） |
| 遗留必备 | "遗留建议（不阻塞）"分节，逐条给排期建议 |
| 归档 | 报告本身要登记进 `docs/README.md` §3，并标注状态（现行 / 归档 / 不采纳） |

### 6.4 遗留项去向（**不留台账 = 必然遗忘**）

- 所有 💭 与未修的 🟡 → 写入 `docs/未完成项与待决清单.md`。
- 所有"暂不修但已知"的限制 → 写入对应 `*-设计方案.md` 的已知限制小节（如 §20.4 的用法）。
- 审查中发现的新坑 → 写入 `docs/踩坑全集.md` §2（编号续增）。
- 审查中发现的**静默失败新形态** → 在 `docs/验收断言审视清单.md` §12 注册新编号。

### 6.5 度量（**供改进，不与个人绩效挂钩**）

| 指标 | 定义 | 期望方向 |
|---|---|---|
| **阻断项逃逸数** | 合并后才被发现（如手工验收才撞到）的 🔴 数量 | ↓ 越低越好（核心指标） |
| 复验返工率 | 🔴 复验不通过的比例 | ↓ |
| 静默失败复发 | 同类问题重复登记的次数（对照 S 族） | ↓ |
| 断言净变化 | 新增 vs 删除/放宽（删必须带理由） | 净增或持平 |
| 闸门数字趋势 | PASS 增长 + FAIL 恒为 0 | PASS ↑ / FAIL = 0 |
| 报告闭环率 | 有结论 + 有证据 + 有台账 的报告占比 | → 100% |

> ⚠️ **明确禁止**：把"提了多少意见""谁的问题多"做成排名。那会诱导大家只提安全意见（挑软柿子），反而降低审查价值。

**关于静态扫描器的实测结论（2026-09-28）**：

- 对 `src/Eztools.Core` 实测：分析 16 个 `.cs` / 2537 行 / 注释覆盖 14.23% ⇒ 输出 **🔴 0 · 🟡 0 · 💭 1**。
- 那**唯一一条**是"代码行过长（132 字符），建议不超过 80 字符"—— 正是本仓已明确判定**"不采纳"**的规则（`docs/README.md` §3.6）。
- 华为规范评分对非 Java 文件为 `null`（该项目为 C# + Python，评分维度不适用）。

> **结论**：通用静态扫描器在本项目**只能当"第三只眼"**，输出需人工判真伪；**主闸门是项目自有的行为验收 + 结构断言**，人工审查负责机器查不到的"意图 / 契约 / 威胁模型 / 断言质量"。**绝不能把扫描器全绿当作"可合并"。**

### 7.3 常见问题应对（FAQ，全部来自本项目真实历史）

| # | 现象 | 处置（先做什么） |
|---|---|---|
| 1 | "改了但没生效" | ① 查 DLL/产物时间戳；② 确认不是**多 TFM 残留目录**（`net10.0-windows\` 死产物，踩过 2 次）；③ 构建加 `--no-incremental` |
| 2 | "验收数字和手跑不一致" | **先怀疑"它们看的不是同一个东西"**：比时间戳 + 确认脚本里的 TFM 变量，比读代码快得多 |
| 3 | "功能没生效"（用户侧） | 先确认用户跑的是**哪个二进制**（启动路径是否指向旧输出目录） |
| 4 | "测试全绿但功能是坏的" | 走 §3.7：区分弱断言与零覆盖 → 用**突变验证**证明断言非空；删断言必须带理由 |
| 5 | "探针绿了，真人操作还是不行" | 探针上下文 ≠ 生产上下文：检查消息泵（裸泵）、焦点建立时机（延迟再钉一次焦点）、观测面是否跟着控件走 |
| 6 | "文档说做了，代码里没有" | 状态列 + `check-doc-refs.py --strict`；把"文档有代码零命中"列为 🔴 |
| 7 | "同一问题被反复提出" | 查 `docs/README.md` §3 是否已标"不采纳"；**未留痕的裁决无效**（§5.4） |
| 8 | "意见提了但没人做" | 分级 + 合并门禁（🔴 归零才能合）+ 台账（💭 必须有排期或显式接受） |
| 9 | "审查太慢拖进度" | 只对**触发条件命中的改动**做全量人工审；其余走"闸门 + 抽查"。时限见 §4.3 |
| 10 | "单人项目谁审我" | 降级模式 A（§4.4）：AI 审查 + 闸门 + 冷却自审 + 每波专项审 |
| 11 | "提意见得罪人" | 意见只针对**代码与事实**（附命令可复核）；度量不与个人绩效挂钩（§6.5） |
| 12 | "安全闸在提权环境下失效" | 这类"静默失效"必须**手工验证**（`CurrentUserOnly` 在提权进程里静默死亡已是实证案例）；不能只看代码写了。**降级／告警类修复同理**：必须验证"告警能到达谁" —— `AuditLog` 的告警只走 stdout，而提权 Core 的 stdout 无人接收（RI-1 实证，2026-09-29）。判据见 §3.3 3.9 |
| 13 | "审查意见与设计文档冲突" | 以 `docs/README.md` §2 权威层级为准；若前提被证伪，允许改判但必须书面记录新前提 |
| 14 | "修一个带出三个" | 先做**关联模块影响面核对**（§3.1 契约面 + 联动点表），把"影响面清单"作为意见的一部分 |
| 15 | "热键注册数比预期少" | **先跑 `scripts/probe-hotkey-free.py`** 区分"键被别的程序占用"与"代码没注册"。实测案例：`Ctrl+Alt+W` → `GetLastError=1409`，同组其它键全部可注册 ⇒ 环境冲突。**别先去改 `RegisterHotKey` 调用** |
| 16 | "我在协议层加了字段，端到端却读不到" | 查**转发层是不是白名单式构造**（手工 `new JsonObject{…}` 只挑几个字段）—— 新字段不会自动进。两层都要测：直连协议 + `ezt <cmd> --json`（2026-09-29 安全面专项审 RI-3 实证，同族第 3 次）。判据见 §3.1 1.8 |

### 7.4 反模式清单（明确禁止，逐条对应真实教训）

| 反模式 | 为什么禁止 |
|---|---|
| 把"文档里写了"当成"已经能用" | 已踩两次：`panels` 长期"文档有代码零命中"，`search` 贡献点因此被删 |
| 用**注入负结果**给技术路线判死刑 | 旧观测是在自建干预污染下取得的，曾导致错误结论（"环境级吞键"已作废） |
| 放宽检查而不带突变验证 | 放宽后的检查"绿得毫无提示"，等于取消检查 |
| 用"跳过"掩盖失败 | 跳过必须计数（满额 = PASS + SKIPPED），否则数字会漂移 |
| 幽灵代码式"修复" | 定义了没人调 = 没修；"计划修复但未落盘"必须显式标注 |
| 静默吞掉未知参数 | `switch` 无 `default` ⇒ 用户以为改了其实没改 |
| 拿待决清单当规格 | 它只记状态，不定义接口；查"怎么设计"必须回到设计方案 |
| 在注释里写含引号的命令（bash） | **注释中仍会做命令替换**，本项目已炸过一次 |
| 把 `cmd \| grep -q` 当断言 | 退出码会被管道吞掉 ⇒ 恒真 |
| 把扫描器全绿当可合并 | 扫描器对本仓 C# 的实测输出为 0 严重 / 0 一般，且唯一一条是已判不采纳的规则 |
