## 1. 主线操作步骤（第一次做，就照这条走）

**用 Git Bash**（不是 PowerShell——原因见第 9 节）。下面每一块都可以整段复制粘贴。
每步都写了"该看到什么"，对不上再往下查第 8 节。

### 步骤 0 · 打开终端并设好两个变量

打开 **Git Bash**。

先执行这四行：

```bash
cd /d/01-项目代码/Eztools
R="/d/01-项目代码/Eztools"
E="$R/src/Eztools.Cli/bin/Debug/net10.0/ezt.exe"
export DOTNET_ROOT="D:/dotnet10"     # 🔴 不能省，原因见下
```

> ℹ️ **`DOTNET_ROOT` 这一行为什么不能省**
>
> `ezt.exe` 是**框架依赖**应用。它的 apphost 只在两处找 .NET 运行时：
> ① `DOTNET_ROOT` 指向的目录；② 注册表里的默认安装位置（`C:\Program Files\dotnet`，那里只有 7.x）。
> **它不扫 PATH** —— 实测把 `D:\dotnet10` 前置到 PATH 仍然无效。
>
> 漏了这一行会直接报：
> `You must install or update .NET to run this application.`
> `Framework: 'Microsoft.NETCore.App', version '10.0.0'`
>
> （根本原因是本机 SDK 装成了便携版 —— `C:\Program Files\dotnet` 不可写，没并入系统。）

- `cd` 是为了让后面 §2~§5 里那些**相对路径**的命令也能直接照抄；
- `$R` / `$E` 是为了本节的命令**换目录也不失效**（更抗误操作）。

> **如果 `cd` 报 `bash: $'\E[200~cd': command not found`**，那是终端的粘贴问题，
> 不是命令写错了 —— 先按 §10 ③ 修掉（一次性），再重开终端回来做。
> 这个坑不修的话，你在终端里的**所有**粘贴操作都会失败。

### 步骤 1 · 构建（约 1 秒）

```bash
# 本机 .NET 10 SDK 是便携安装（C:\Program Files\dotnet 不可写，没并入系统），用全路径调用
DOTNET="D:/dotnet10/dotnet.exe"
"$DOTNET" build "D:/01-项目代码/Eztools/Eztools.sln"
```

**该看到**：`已成功生成`，且**0 个警告 0 个错误**。

> ℹ️ **为什么是 `D:/dotnet10/dotnet.exe` 而不是直接敲 `dotnet`**：
> 系统的 `dotnet` 仍指向 `C:\Program Files\dotnet` 里的 7.0.410，那个版本**不支持 net10.0**，
> 会报 `NETSDK1045: 当前 .NET SDK 不支持将 .NET 10.0 作为目标`。
> 想让 `dotnet` 直接可用，把 `D:\dotnet10` 加进 PATH 即可（可选，见 §9）。

> ⚠️ 这里的路径必须是**盘符形式**（`D:/...`），不能写成 `/d/01-...`。
> 原因：`dotnet` 是 Windows 程序，而 MSBuild 把以 `/` 开头的参数当作**开关**，
> 于是 `/d/...` 会被解析成"未知开关 MSB1001"。这条与第 10 节 ① 是同一类问题的另一面：
> **可执行文件自己的路径**由 bash 解析（POSIX 写法没问题），但**传给它的参数**里的路径要走 Windows 形式。

> 之后为了少打字，设一个变量（本次终端有效）：

```bash
E="/d/01-项目代码/Eztools/src/Eztools.Cli/bin/Debug/net10.0/ezt.exe"
```

（绝对路径，在哪个目录都有效。）

### 步骤 2 · 体检：这台机器现在是什么状态（约 1 秒）

```bash
$E doctor
```

**该看到**（这是**开发形态**，工具与 SDK 来自仓库，完全正常）：

```
── 安装与来源 ──────────────────────────────────────────────
  安装根             C:\Users\ishe\AppData\Local\Eztools
  布局形态           开发（安装根未铺设，工具与 SDK 来自仓库）
  [ OK ] 宿主程序　仓库（当前运行位置）
  [ OK ] 内置工具　4 个 · 来源 仓库
  [ OK ] Python SDK　仓库
  [ OK ] 运行时载荷　仓库
  [ OK ] 已部署运行时　python 3.13.14
  [ OK ] 配置目录　C:\Users\ishe\AppData\Roaming\Eztools\config
```

结尾还应有 `[ OK ] 宿主就绪，可以调用工具（4 个可用）`。

**关键点**：`安装与来源` 这一节是告诉你**每样东西有没有、从哪来**。
"来源 仓库" 不是问题——你现在就是在开发机上从仓库跑。

### 步骤 3 · 冒烟：能发现工具、能调用工具（约 3 秒）

```bash
$E list
$E invoke echo.echo --text "你好 🍡"
```

**该看到**：

- `list`：表格 4 行（`echo` / `filehash` / `probe` / `wordcount`），来源列全为 `repo`
- `invoke`：先一行 `[ OK ] 完成，用时 xxx ms`，然后是

```json
{
  "echo": "你好 🍡",
  "length": 4,
  "byteLength": 11
}
```

**关键点**：`echo` 字段里必须**原样**是"你好 🍡"。看到 `\u4F60\u597D` 这种转义就是编码环节坏了。

> ⚠️ **先确认 emoji 真的进了命令行**，否则你会"以为验过了，其实验的是另一个字符串"——
> 命令退出码 0、JSON 也干净，但 `length` 是 **3** 而不是 4，因为 emoji 在**输入环节**就丢了。
> 这类"验证行为本身静默失效"比功能坏掉更麻烦：它给的是一个**假绿灯**。
>
> 定位用这一条（看终端到底把什么交给了 bash）：
>
> ```bash
> printf '%s' "你好 🍡" | od -An -tx1
> ```
>
> - 结尾是 `... 20 f0 9f 8d a1` → emoji 进来了，可以继续往下查
> - 结尾只有 `... 20`（一个空格）→ emoji 根本没进来，下面这条就不用往下看了
>
> 确认是输入环节丢的，用**字节构造**绕过终端（不依赖你能不能打出 emoji）：
>
> ```bash
> $E invoke echo.echo --text "$(printf '你好 \xf0\x9f\x8d\xa1')" --quiet
> ```
>
> **对账口径**（比肉眼可靠）：`byteLength` = 汉字数×3 + ASCII 数×1 + emoji 数×4。
> `你好 🍡` → `length` = **4**、`byteLength` = 2×3 + 1×1 + 1×4 = **11**。
> 只看"长得对不对"会被终端字体骗过去，数字不会。

### C1 干净安装 + 部署运行时（可反复做）

```bash

$E dirs            # 此时应看到大部分是 · （尚未创建）
$E doctor          # 期望：本次新建 11 个目录
$E runtime install # 期望：解压 1324 个文件 → 落位 → SDK 植入
$E runtime list    # 期望：python 3.13.14，隔离=是，可用=✓
$E selftest        # 期望：通过 22 / 失败 0
```

嫌慢可以用 `--dry-run` 先看会做什么而不落盘：

```bash
$E install --dry-run          # 只报告将复制什么
```

做完清理（**注意用相对名删除，原因见第 10 节**）：

```bash

( cd /d && rm -rf _ezt-verify )
```

> ⚠️ **路径必须是 Windows 形式**（`D:/...` 而不是 `/d/...`）。
> Git Bash 的 POSIX 路径交给 .NET 可执行文件后会被按**当前盘符**解析，
> 目录照样建、命令照样退出 0，只是建在 `D:\d\...` 这种地方。这是我实测踩了三次的坑。

### C2 核心标准：新增工具 = 新增目录，宿主一行代码不改

```bash
mkdir -p _scratch/devtools
cp -r sdk/python/template _scratch/devtools/greeter
# 改 id 与显示名（模板里是 my-tool / 我的工具）
sed -i 's/my-tool/greeter/; s/我的工具/问候工具/' _scratch/devtools/greeter/tool.json

$E list --tools-dir _scratch/devtools            # 期望：表格里多出 greeter，来源 dev:devtools
$E invoke greeter.run --text 菲比 --tools-dir _scratch/devtools
$E info greeter --tools-dir _scratch/devtools     # 看它的贡献点与配置 schema 自动被解析
```

**关键点**：从复制模板到调用成功，`src/` 下**没有任何文件被改动**。这就是 P0 的验收标准本身。

（`_scratch/` 已在 `.gitignore` 里，验证完 `rm -rf _scratch` 即可。）

### C3 已安装形态：脱离仓库也要能跑

这一步回答"装到机器上以后还能不能用"——它和"从仓库里能跑"是**两件事**：

```bash
D="D:/_ezt-deploy"; rm -rf "$D"; mkdir -p "$D/bin"
cp src/Eztools.Cli/bin/Debug/net10.0/ezt.exe src/Eztools.Cli/bin/Debug/net10.0/*.dll src/Eztools.Cli/bin/Debug/net10.0/*.json "$D/bin/"

export EZTOOLS_INSTALL_ROOT="$D/install"
export EZTOOLS_CONFIG_ROOT="$D/cfg"

( cd "$D/bin" && ./ezt.exe install --from "D:/01-项目代码/Eztools" )
# 期望：4 个工具 → 安装根；并把 sdk/ payload/ bin/ 一并铺好

( cd "$D/bin" && ./ezt.exe doctor )     # 期望：安装完整度全 [ OK ]
( cd "$D/bin" && ./ezt.exe runtime install )
( cd "$D/bin" && ./ezt.exe selftest )   # 期望：通过 22 / 失败 0

unset EZTOOLS_INSTALL_ROOT EZTOOLS_CONFIG_ROOT
( cd /d && rm -rf _ezt-deploy )
```

**为什么必须有这一步**（实测发现的缺口）：
宿主的工具源与 SDK 来源是"先看安装根、再向上找仓库根"。于是从仓库里跑一切正常，
但把 `ezt.exe` 单独放到别处时，安装根下的 `tools\` 与 `sdk\` 是空的、向上又找不到仓库根
——**一个工具都发现不到**。所以"安装"不是拷个 exe 就完事，必须用 `ezt install` 把三样东西铺进安装根。

### C4 看工具详情与配置 schema

```bash
$E list --commands        # 11 条可调用命令，命令 id → 工具 → handler 一目了然
$E info filehash          # 贡献点表（命令/动作/热键/菜单）+ 配置项表
$E info wordcount         # 3 个配置项：开关 / 下拉枚举 / 数字范围
```

**关键点**：`info` 里那张"配置 schema"表，就是 P1 设置页将要渲染的数据源。
这些内容全部读自各工具的 `tool.json`，**宿主没有一行针对某个工具的 UI 代码**。

## 5. D 档：反向验证（证明它真的在管事）

正向全绿也可能是"假通过"。下面几条是**故意弄坏**，看宿主是否如实报告。

### D1 一个坏清单不该拖垮其它工具

```bash
mkdir -p _scratch/devtools/bad-json
printf '%s' '{ "id": "bad", "name": ' > _scratch/devtools/bad-json/tool.json

$E list --tools-dir _scratch/devtools      # 期望：好的工具照常列出
$E doctor --tools-dir _scratch/devtools    # 期望：报出具体错误 + 文件名
echo "退出码=$?"                            # 期望：1（有 Error 级诊断）
```

**期望看到的**：诊断行形如
`[错误] manifest.invalid-json: JSON 解析失败: Expected depth to be zero ... [<路径>]`，
同时结论会写清"**相关清单已被拒绝注册，其余工具不受影响**"。
不该发生的事：弹窗、崩溃、整个宿主拒绝启动。

### D2 调用别人写错的命令

```bash
$E invoke no.such.command --text x; echo "退出码=$?"    # 期望：2，并列出可用命令的提示
$E info no-such-tool;               echo "退出码=$?"    # 期望：4
```

### D3 禁用 / 启用（"已启用" ≠ "已加载"）

```bash
$E disable filehash
$E invoke filehash.hash --path README.md; echo "退出码=$?"   # 期望：2，提示"处于禁用状态"
$E list                                                        # 期望：filehash 仍被列出（禁用不注销清单）
$E enable filehash
$E invoke filehash.hash --path README.md --quiet               # 期望：恢复可用
```

最后一条应该打印 `hash` 字段。你可以独立核对：用别的工具算同一个文件的 SHA256，两者必须一致。

### D4 工具挂起 → 必须被超时回收、且不留进程

```bash
$E invoke probe.hang --json '{"seconds":600}' --timeout 2000; echo "退出码=$?"
# 期望：约 3 秒后报错退出（2），不是永远卡住

tasklist | grep -i python      # 期望：无输出（没有残留的 python 进程）
```

### D5 工具崩溃 → 必须被检测，且不误熔断

```bash
$E invoke probe.crash --json '{"exitCode":3}'; echo "退出码=$?"   # 期望：2，报"进程已退出(exit=3)"
$E invoke probe.echo --text ok --quiet                            # 期望：正常返回（单次崩溃不该禁用工具）
```

### D6 缺运行时 → 报错必须可执行，而不是静默失败

把 `ezt` 装到仓库外并故意不带载荷：

```bash
D="D:/_ezt-nopayload"; rm -rf "$D"; mkdir -p "$D/bin"
cp src/Eztools.Cli/bin/Debug/net10.0/ezt.exe src/Eztools.Cli/bin/Debug/net10.0/*.dll src/Eztools.Cli/bin/Debug/net10.0/*.json "$D/bin/"
export EZTOOLS_INSTALL_ROOT="$D/install" EZTOOLS_CONFIG_ROOT="$D/cfg"

( cd "$D/bin" && ./ezt.exe install --from "D:/01-项目代码/Eztools" --no-payload )
( cd "$D/bin" && ./ezt.exe runtime install ); echo "退出码=$?"      # 期望：1
( cd "$D/bin" && ./ezt.exe invoke echo.echo --text hi ); echo "退出码=$?"   # 期望：2

unset EZTOOLS_INSTALL_ROOT EZTOOLS_CONFIG_ROOT
( cd /d && rm -rf _ezt-nopayload )
```

**期望看到的**：明确写出"未找到可用的 python 运行时载荷"、应该放在哪个目录、
去哪拿（python-build-standalone 的 `install_only`）、以及开发期可用的临时办法。
不该发生的事：只说"失败了"、或者静默返回空结果。

## 7. 实测基准（拿你的结果对照，量级差太远就该查）

> **2026-09-19 在 .NET 10（SDK 10.0.401）下重测**：与 .NET 7 时代的数据基本一致，**升级没有性能回归**。
> 下表"现值"为 .NET 10 实测，"P0 时"为 .NET 7（2026-09-17）留档。

| 项 | 现值（.NET 10） | P0 时（.NET 7） |
|---|---|---|
| 解释器启动（嵌入式 + `-I -X utf8`） | 108 ms | 114 ms |
| 解释器启动（不隔离） | 240 ms（**隔离反而更快**） | 同 |
| `ezt version` | 150 ms | 161 ms |
| `ezt invoke` 端到端（含宿主启动 + 清单扫描 + 起进程 + 2 次 IPC 往返 + 回收） | **445 ms** | 约 440 ms |
| `[ OK ] 完成，用时 xxx ms` ← **宿主自报，不是端到端** | 190 ms | 同 |
| `ezt selftest`（22 项） | ~15 秒 | 同 |
| `bash scripts/acceptance.sh`（41 项，含两次运行时部署） | **27.7 秒** | 25.3 秒 |
| 运行时载荷 | 13.1 MB（1457 条目） | 同 |
| 首次解压 1324 个文件 | 首次 **30 秒** / 同内容再次 **1 秒** / 复用 **241 ms** | 同 |
| 真实安装根占用 | 约 44 MB | 同 |

> **首次 30 秒是正常的**：同一份载荷内容第二次解压只要 1 秒，说明是 Windows Defender 对
> **首次出现的新文件内容**的一次性扫描。但对用户来说首次安装的感知就是 30 秒
> —— 所以**安装器必须给进度反馈**。（安装器本身排在 **P4**，见设计方案 §12；
> 这条约束从"首次安装会卡 30 秒"成立那天起就有效，不因为安装器晚做而消失。）

> ⚠️ **上面两个 invoke 数字别搞混**（实测时差点当成"数据不一致"）：
> CLI 打印的 `完成，用时 190ms` 是宿主**内部计时**，起点在「已取得工具进程」，
> 终点在「拿到结果」—— **不含**宿主自身启动（~160 ms）与清单扫描。
> 而端到端 440 ms 是从你敲下回车到进程退出。
> 两个数都对，量的是**不同的段**：440 ≈ 160（宿主启动）+ 190（工具那一程）+ 回收与输出。

## 8. 常见症状 → 原因

| 症状 | 最可能的原因 | 怎么办 |
|---|---|---|
| 粘贴命令报 `bash: $'\E[200~cd': command not found` | 终端的 **bracketed paste** 标记漏进了命令行（粘贴时插入 `ESC[200~` / `ESC[201~`，readline 没识别成标记） | 见第 10 节 ④：在 `~/.inputrc` 里 `set enable-bracketed-paste off`，然后**重开终端** |
| `dotnet build` 报 `MSBUILD : error MSB1001: 未知开关` | 把 `/d/...` 这种 POSIX 路径当参数传给了 Windows 程序，`/` 被当成开关前缀 | 参数里的路径用盘符形式 `"D:/..."`（见第 10 节 ①） |
| `invoke` 永远卡住然后超时 | 工具往 **stdout** 写了非 JSON 内容（污染分帧），或没 flush | `ezt invoke ... --verbose` 看日志里有没有"stdout 出现非 JSON 输出" |
| 中文变成 `\u4F60` / 乱码 | 输出编码环节 | 先跑 `ezt selftest`，它有一条"UTF-8 逐字符无损"专门盯这个 |
| 一个工具都发现不到 | 工具目录里没有有效 `tool.json`；或安装根空、仓库根又找不到 | `ezt doctor` 看"工具清单"段与诊断 |
| 目录建了但文件在别处 | 传了 POSIX 路径给 exe（见第 10 节） | 路径改成 `D:/...` 形式 |
| `rm` 删不掉 / 删了但还在 | 环境的 safe-delete 拦截（见第 10 节） | `cd` 到父目录用裸名字删 |
| 工具被自动禁用 | 崩溃熔断触发（默认 10 分钟 3 次） | `ezt info <工具>` 看"禁用原因"，`ezt enable <工具>` 恢复 |
| `invoke echo.echo --text "你好 🍡"` 返回 `length: 3` | emoji 在**输入环节**就丢了（没打进命令行），不是编码 bug | 见第 10 节 ⑤：先 `printf ... \| od -An -tx1` 确认字节，或改用字节构造绕过终端 |

日志位置：`%LOCALAPPDATA%\Eztools\logs\host-<日期>.log` 与 `logs\<toolId>\`。

## 10. 环境注意（本项目最容易反复踩的两件事）

### ① 路径形态：POSIX 还是 Windows（同一个坑踩了三次）

Git Bash 的 `pwd` / `$TEMP` 给的是 POSIX 形式（`/d/...`、`/tmp`）。把它交给 .NET 或任何原生可执行文件后，
会被按**进程当前盘符**解析：

| 你给的 | 实际写到 |
|---|---|
| `/d/01-项目代码/Eztools/x` | `D:\d\01-项目代码\Eztools\x` |
| `/tmp/x`（cwd 在 D 盘） | `D:\tmp\x` |
| `/tmp/x`（cwd 在 C 盘） | `C:\tmp\x` |

命令退出码是 0、目录也确实建了，只是建在别处 —— 最难发现的一类错误。我实测踩了三次。

**规则（2026-09-19 更新，因为已经在同一项目里踩到三次）**：

| 场景 | 该怎么办 |
|---|---|
| 传给 **`ezt`** 的路径（命令行参数或环境变量） | **POSIX 形式照收** —— `ezt` 在所有路径入口做了归一化（`/d/x` → `D:/x`），不必再迁就 |
| 传给**别人的程序**（`dotnet` / `tar` / 原生 exe） | 必须 Windows 形式（一般 `盘符:/正斜杠`）。`tar -f` 例外：它把 `D:/x` 当 `host:path`，所以归档名要用裸文件名 + subshell `cd` |
| **自己写脚本**时 | 一律 `pwd -W` 或 `cygpath -m`，并加断言挡住非 Windows 形式 |

`scripts/acceptance.sh` 里有 `assert_winpath`：拿到非 Windows 形式会直接中止，不静默写错地方。

### ② 删除个人/临时文件时用"相对名字"

本环境注入了 safe-delete 机制，它把参数当"相对当前目录"解析，因此传**绝对 Windows 路径**会被拒绝，
表现为"命令没报错、目录却还在"：

```bash
rm -rf "$LOCALAPPDATA/Temp/mydir"                      # ❌ 可能静默失败
( cd "$LOCALAPPDATA/Temp" && rm -rf mydir )            # ✅ 实测可行
```

### ③ 粘贴命令报 `$'\E[200~cd': command not found`

终端的 **bracketed paste** 会在粘贴内容两端插入 `ESC[200~` / `ESC[201~` 标记，用来告诉
shell"这段是粘贴的"（这样多行粘贴不会被逐行立即执行）。但当 readline 没识别成标记时，
这些转义序列就变成了字面字符，被当成命令的一部分 → **每条粘贴进来的命令都失败**。

这会影响你在终端里的**所有**操作，不只是本项目。修法（一次性）：

```bash
cat > ~/.inputrc <<'EOF'
set enable-bracketed-paste off
EOF
```

然后**重开终端**（readline 只在启动时读这个文件）。想恢复默认就把那行删掉。

> 验证修好了：在终端里粘贴 `echo ok` 三个字，应当直接输出 `ok`，而不是报 `command not found`。

### ④ `tar` 的 `-f` 不吃盘符路径

`tar -f D:/x.tar.gz` 会被当成 rsh 的 `host:path`，报 `Cannot connect to D: resolve failed`。
用裸文件名 + subshell `cd` 定位。

### ⑤ emoji / 非 BMP 字符可能进不了命令行（2026-09-19 实测）

**现象**：`$E invoke echo.echo --text "你好 🍡"` 一切正常返回，但 `length: 3`、`byteLength: 7`
—— 说明送进工具的是 "你好 "（3 字符），emoji 被吞了。**宿主没有报错，也没有坏**，是字符串本身变了。

**怎么区分"链路坏了"和"输入丢了"**：

| 检查 | 命令 | 判据 |
|---|---|---|
| 终端 → bash | `printf '%s' "你好 🍡" \| od -An -tx1` | 结尾 `f0 9f 8d a1` = 进来了；只有 `20` = 没进来 |
| bash → 程序 | `$E invoke echo.echo --text "$(printf '你好 \xf0\x9f\x8d\xa1')" --quiet` | `length: 4` / `byteLength: 11` = 链路无损 |

第二行那条**不经过终端输入**（字节由 `printf` 直接构造），所以它能独立地把"输入环节"排除掉。
实测：本机这条返回 4/11，即**宿主 + SDK + 协议全程无损**，问题只在"怎么把 emoji 送进命令行"。

**要输入 emoji 时**：Windows 用 `Win` + `.` 呼出表情面板选，或直接用上面的字节构造写法。

> 这条写进手册的原因是**它会让验证静默失真**：命令成功、输出干净、退出码 0，
> 唯一不对的是 `length` 差 1。只靠肉眼比字符串，很容易把它当成通过。

### ⑥ 跑 `ezt.exe` 之前必须设 `DOTNET_ROOT`（2026-09-19 升级到 .NET 10 后新增）

```bash
export DOTNET_ROOT="D:/dotnet10"
```

**为什么**：本机 .NET 10 SDK 是便携安装（`C:\Program Files\dotnet` 不可写，没并入系统）。
而 `ezt.exe` 是框架依赖应用，apphost 只在两处找运行时：

| 它找的地方 | 本机情况 |
|---|---|
| `DOTNET_ROOT` 指向的目录 | 要你自己设 |
| 注册表记录的默认安装位置 | `C:\Program Files\dotnet` —— **只有 7.0.12 / 7.0.20** |

**它不扫 PATH。** 实测把 `D:\dotnet10` 放到 PATH 最前面仍然报错。不设就是：

```
You must install or update .NET to run this application.
Framework: 'Microsoft.NETCore.App', version '10.0.0' (x64)
```

`scripts/acceptance.sh` 已经内置了这一行，所以一键验收不需要你手动设。

> 更彻底的两种做法（**未落地，属 P4**）：① 用管理员权限把 .NET 10 SDK/运行时正式装到
> `C:\Program Files\dotnet`（与 7.x 并存，`dotnet` 与所有应用直接可用）；
> ② 打包时改成**自包含**发布（用户完全不需要装 .NET）——
> 后者与本项目"自带 Python 运行时、不依赖用户环境"的思路一致。

## 11. P3 特权层手动验证（需管理员令牌，约 5 分钟）

> **背景**：P3 的自动化验收（`acceptance.sh`）覆盖 13 项，但 4 项能力**需要管理员令牌**才能触发，
> 自动化跑不了，必须亲手验证：提权启动 · `readMft` 真实数据 · 计划任务自启 · 全量句柄扫描。
> 另有 1 项可选的对抗测试（低完整性进程被拒）。
>
> **在哪跑**：**自己终端的 Git Bash**（普通一个 + 管理员一个）。
> 开始菜单搜 "Git Bash" → 右键 → **以管理员身份运行**，就是管理员终端。
> ⚠️ **不要在 AI 助手会话里跑提权项**——UAC 弹窗没人能替你确认，且会话结束会清掉子进程树，Core 活不到下一条命令。

### M0 · 准备：两个终端，各设一次变量

**普通 Git Bash** 和 **管理员 Git Bash** 里各执行一遍：

```bash
E="/d/01-项目代码/Eztools/src/Eztools.Cli/bin/Debug/net10.0/ezt.exe"
export DOTNET_ROOT="D:/dotnet10"     # 🔴 老规矩，原因见第 10 节 ⑥
net session >/dev/null 2>&1 && echo 管理员 || echo 非管理员   # 确认身份（管理员终端必须输出"管理员"）
```

### M1 · 未提权基线（普通终端）

先看"没提权时它长什么样"，后面才好对照。

```bash
"$E" core start          # 不带 --elevate：Core 以普通令牌启动
"$E" core status         # 该看到：提权=False、运行中 ✓
```

```bash
"$E" primitive volume.readMft --args '{"volume":"C:","maxRecords":10}'; echo "退出码=$?"
```

**该看到**：`[-32015] ...`（ElevationRequired，退出码 2）。是**结构化拒绝**，不是崩溃、不是超时——这一条本身就是验收点。

```bash
"$E" primitive handles.enumerate --args '{"pid":4}' --json
```

**该看到**：空数组 `[]` 或寥寥几条。pid=4 是 System 进程——无论未提权还是提权都枚举不到它
（System 句柄需要 `SeDebugPrivilege`，Core 刻意不启用，见 M4 终审说明）。

### M2 · 提权启动与身份登记（管理员终端）

```bash
"$E" core stop           # 停掉 M1 的普通实例
"$E" core start          # 管理员终端里直接 start：子进程继承管理员令牌，不弹 UAC
"$E" core status         # 该看到：提权=True、运行中 ✓
"$E" core ping           # 该看到：pong ✓ pid=xxx 提权=True
cat "$LOCALAPPDATA/Eztools/core.json"   # 该看到："elevated": true、pid、pipeName、version
```

> 替代形态：普通终端跑 `"$E" core start --elevate`，会弹一次 UAC，确认后同样 elevated=True。两种等价。

### M3 · readMft 真实数据 + 游标续传（管理员终端）

```bash
"$E" primitive volume.readMft --args '{"volume":"C:","maxRecords":20}' --json
```

**该看到**：`records` 恰 **20 条**、每条有 `frn` / `parent` / `name`，`name` 是 C 盘真实文件名；
`done=false`、`cursor` 是个**非零整数**（= 本批最后一条记录的 FRN）。

> ⚠️ 2026-09-20 终审（三轮排查 + python 提权矩阵实验）：控制码 `0x0009_00B3`（44/NEITHER）
> **从来是对的**，中途两次改码全是误修。恒空的真凶 = `HighUsn` 传了 `ulong.MaxValue`——
> USN 是**有符号 LONGLONG**，`0xFFFF...FF` 即 **-1** → 过滤区间 [0,-1] 空集 → EOF(38)。
> 修后（`long.MaxValue`）单次调用返回 65400 字节真实记录；再见到空结果先确认 ezt-core.exe 是 18:34 之后的构建。

```bash
# 游标续传（自动衔接，不用手动替换任何占位符）：
OUT=$("$E" primitive volume.readMft --args '{"volume":"C:","maxRecords":20}' --json)
echo "$OUT"
CURSOR=$(printf '%s' "$OUT" | grep -o '"cursor": [0-9]*' | head -1 | grep -o '[0-9]*')
"$E" primitive volume.readMft --args "{\"volume\":\"C:\",\"maxRecords\":20,\"cursor\":$CURSOR}" --json
```

**该看到**：第二批也是 20 条。**第一条与第一批最后一条相同（frn 一致）是设计如此**——
截断续传语义是"游标 = 上一批最后一条记录"，下一批从它重放一条并消化，之后全是新记录。
对账口径：两批合并按 `frn` 去重后应得 **39 条**（20 + 20 − 1 重放）。
每批 ≤20 条说明 `maxRecords` 限流生效；游标不断推进说明没有"一次读全盘"的通道（刻意设计）。

### M4 · 句柄枚举链路验证（管理员终端）

> 2026-09-20 终审：全量扫描约 1~2 分钟 > CLI 30 秒超时（`The operation was canceled` = 预期）；
> `pid:4`（System）恒空也是预期——枚举 System 句柄需要 `SeDebugPrivilege`，Core 刻意不启用（最小权限）。
> 链路正确性用 **Core 自查**验证：

```bash
"$E" core start
CORE_PID=$(grep -o '"pid": [0-9]*' "$LOCALAPPDATA/Eztools/core.json" | head -1 | grep -o '[0-9]*')
"$E" primitive handles.enumerate --args "{\"pid\":$CORE_PID}" --json
```

**该看到**：若干条 `type: File` 的真实句柄——dotnet-diagnostic 管道、`ezt.core.<hash>` 管道、
audit 日志文件等（都是 Core 进程真实持有的）。
pid 过滤、DuplicateHandle、NtQueryObject、路径解析全链路由此证明。

**（可选）全量扫描**：加了 `--timeout` 后现在能跑了，约 1~2 分钟：

```bash
"$E" primitive handles.enumerate --json '{}' --timeout 300
```

**该看到**：数千条真实文件路径（内核路径已映射回盘符形式）。超时同样按退出码 2 + `[-32011]` 报告。

### M5 · 审计日志核对（管理员终端）

```bash
tail -n 20 "$LOCALAPPDATA/Eztools/logs/"audit-*.log
```

**该看到**：M1~M4 里每一次原语调用各有一条记录：原语名、调用方 pid、调用方用户、结果。
**一条都不能少**——审计完整性是 P3 的硬要求。

### M6 · 计划任务形态（管理员终端，免重启验证）

```bash
"$E" core stop
"$E" core install-task
# 该看到：计划任务 EztoolsCore 已登记 + 任务命令行

schtasks //Query //TN EztoolsCore
# 该看到：Status=就绪（Ready）。⚠️ Git Bash 里 schtasks 的开关必须写双斜杠 //，
# 单斜杠 /TN 会被 MSYS 当成 POSIX 路径转换掉（与第 10 节 ① 同一族坑）

schtasks //Run //TN EztoolsCore      # 免重启立即触发一次
sleep 3
"$E" core status                     # 该看到：提权=True（任务以 /RL HIGHEST 运行）
"$E" core ping

"$E" core uninstall-task             # 立刻收尾
schtasks //Query //TN EztoolsCore    # 该看到：任务不存在（INFO: 没有匹配项）
```

> 想 100% 确认"开机自启"，重启一次机器后直接跑 `"$E" core status`（该看到 running=true）再 `uninstall-task`。
> 不重启的话，上面 `schtasks //Run` 已经验证了"任务能以最高权限拉起 Core"这一核心行为。

### M7 ·（可选，对抗测试）低完整性进程被拒 —— ✅ 已实测（2026-09-24，判据修订）

前置：Core 正在运行（提权与否均可——本测试只验证"低完整性进程连不进"）。

> **⚠️ 2026-09-24 实测修订（Win11 25H2）**：
> 原命令 `runas /trustlevel:0x2000 ...` 在 25H2 上报 `1168: 找不到元素`——
> **seclogon 服务正常也报**，机制性失效（踩坑全集 §2.16）；
> PsExec 2.43 `-low` 同样**不降级**（实测 whoami 仍 High）。
> 现行方法 = `scripts/launch-lowil.ps1`（Add-Type 直接把当前令牌降到 Low 再 CreateProcessWithTokenW）。

准备（一次性，管理员 PowerShell）：

```powershell
New-Item -ItemType Junction -Path D:\eztj -Target "D:\01-项目代码\Eztools" | Out-Null  # ASCII 路径别名
New-Item -ItemType Directory -Force D:\tools\low | Out-Null
icacls D:\tools\low /setintegritylevel L   # 低完整性默认 no-write-up，输出目录必须打 Low 标签
```

运行：

```powershell
pwsh -File scripts\launch-lowil.ps1 -CommandLine 'cmd.exe /c D:\eztj\src\Eztools.Cli\bin\Debug\net10.0\ezt.exe primitive process.enumerate > D:\tools\low\m7out.txt 2>&1 & whoami /groups >> D:\tools\low\m7out.txt'
Start-Sleep -Seconds 10
Get-Content D:\tools\low\m7out.txt
```

**该看到（2026-09-24 实测修订，两处）：**

1. whoami 部分显示 `Mandatory Label\Low Mandatory Level  S-1-16-4096`（自证低完整性进程真实建立）；
2. ezt 输出 `[错误] Access to the path is denied.` —— **不是 `[-32016]`**。

**为什么不是 `[-32016]`**：命名管道对象**继承创建者的完整性标签**（提权 Core = High）；
低完整性客户端对 High 标签管道 open-for-write 在 **OS 层 MIC（no-write-up）即被拒**，
连接根本到不了 Core 的代码级身份闸。安全性目标（低完整性进程无法使用 Core）达成，
且比设计多一层防线；`-32016 CallerRejected` 保留为纵深防御兜底。

**差分证据**（定位拒点用，同法跑）：低完整性进程执行 `ezt core status`（纯文件读取，不连管道）
**正常输出** ⇒ 拒点确在管道 open，而非 CLI 文件访问。

清理：

```powershell
Remove-Item D:\eztj -Force; Remove-Item D:\tools\low -Recurse -Force
```

### M8 · 收尾清理（管理员终端）

```bash
"$E" core stop
"$E" core uninstall-task
schtasks //Query //TN EztoolsCore    # 期望：不存在
"$E" core status                     # 期望：Core 未运行（无端点登记）
```

### 结果判定

| 测项 | 通过判据 |
|---|---|
| M1 | readMft 未提权 → `[-32015]` 结构化错误；`pid:4` 句柄为空 |
| M2 | status / ping / core.json 三处一致：`elevated=true` |
| M3 | readMft 真实文件名 20 条 + 续传批次合并按 frn 去重 = 39 条（含 1 条设计内重放） |
| M4 | Core 自查（pid=Core）返回真实 File 句柄（管道/日志）；全量超时与 pid:4 空为预期（见 M4 说明） |
| M5 | 每次调用都有审计记录，一条不少 |
| M6 | 任务登记/触发/删除全程无报错，触发的 Core `elevated=true` |
| M7（可选） | 低完整性进程被拒 ✅（2026-09-24 实测：OS 层 MIC 拒绝，`[错误] Access to the path is denied` + whoami 自证 Low；判据修订见 M7 节） |
| M8 | Core 停净、任务删净 |

全部通过 = P3 手动验收完成。有对不上的，先看 `%LOCALAPPDATA%\Eztools\logs\host-ezt-core-*.log`（Core 崩溃现场）和 `audit-*.log`（调用记录）。
