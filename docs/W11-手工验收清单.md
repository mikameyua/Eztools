## §B 必须保留人工的项（4 项）

### B1 · 搜索窗真机链路（M1.4/M3 的 UI 半边）

**为什么必须人工**：热键 → 托盘 → 真窗口 → 真键盘焦点这条链是自动化禁区（W10 探针纪律：真注入会贴进运行探针的终端）；verify-desktop 只能用夹具装配证明渲染逻辑，"你按热键后看到的"只有人能确认。

| 步骤 | 操作（可复制） | 预期 | 判据 |
|---|---|---|---|
| 1 | `ezt config set desktop index.exclude node_modules` → **重启托盘** | 搜索窗可用 | 无报错气泡 |
| 2 | 热键唤出搜索窗，看**卷清单行**（底部） | `… · 排除 1 条规则（175,347 条）` | 数字 > 0 且与 §A A1 的 excludedFrns 一致 ⇒ 通过；看不见该段 ⇒ 失败 |
| 3 | 搜一个 `node_modules` **里**的文件名（§A 日志里的"目标"） | 搜不到 | 与 §A A1 一致 ⇒ 通过 |
| 4 | `ezt config set desktop search.pathFilter "C:\Windows"` → **不重启**，再次热键唤出 → 搜一个 `C:\Windows` 外的文件 | 搜不到；卷清单行出现 `· 限定 C:\Windows` | **不重启即生效** ⇒ 通过（M3 核心） |
| 5 | `ezt config unset desktop search.pathFilter` → 再唤出 | 限定段消失，范围外文件恢复 | 通过 |
| 6 | 收尾：`ezt config unset desktop index.exclude` → 重启托盘 | 排除段消失 | 恢复原状 |

### B2 · 重建出口真点击 + 真实索引重建耗时（M1.8/M2.3，供 R6）

**为什么必须人工**：① WPF 真点击不可自动化（自动化只做到"假宿主动作计数=1"，见 verify-desktop W11 组）；② 真重建要提权 Core + 分钟级等待，且删的是**真实索引文件**——自动化环境里做这种破坏性操作得不偿失（`--rebuild-real` 只在临时数据根里做）。

| 步骤 | 操作 | 预期 | 判据 |
|---|---|---|---|
| 1 | 保持 `index.exclude = node_modules`（B1 步骤 1 后的状态），先记当前体积：`dir "%LOCALAPPDATA%\Eztools\index\*.ezidx"` | 记下字节数 | —— |
| 2 | 热键唤出搜索窗 → **点击卷清单行**（悬停提示 = "点击重建索引（先停索引进程并删除索引文件，再全量重建…）"） | 状态行立即回显"正在重建索引…"，随后"索引重建已开始" | 点击有反应且回显 ⇒ 通过；点了没动静 ⇒ 失败 |
| 3 | 等重建完成（**记录耗时到 §C，供 R6**），再量体积：同步骤 1 命令 | 体积**小于**步骤 1（排除的子树不再落盘） | 变小 ⇒ 通过（R11 真实数据面）；不变小 ⇒ 失败 |
| 4 | 重启托盘后再看 `ezt search status` | `excludeRules` **规则条数不变**；`excludedFrns==0` 是**正确形态**（重建已把排除对象物理摘除，store 里没有 node_modules 可供重新锚定 —— 2026-10-07 修订，原"同量级"判据与实现语义冲突，见 §C.1-②） | 规则条数不变 ⇒ 通过 |

> 若想跳过手工等待：`python -I -X utf8 -u scripts/w11-acceptance.py --rebuild-real` 会在**临时数据根**里自动做两次真重建并输出耗时/体积对照（不动你的真实索引）；但"点真按钮"这半边仍需 B2 步骤 2 人工确认一次。

### B3 · 设置面板 16 字段滚动可达（R9）

**为什么必须人工**：verify-desktop 已断言 16 个字段**渲染存在**（映射清单），但"最底部的字段在窗口里**滚得到、看得见**"是视觉布局性质，机器断言不覆盖（历史事故：11 字段时底部项不可达）。

| 步骤 | 操作 | 预期 | 判据 |
|---|---|---|---|
| 1 | 托盘 → 设置 → 全局设置，滚到最底 | `搜索限定目录`（search.pathFilter）完整可见可编辑 | 滚得到 ⇒ 通过；被截断/滚不动 ⇒ 失败 |
| 2 | 数一遍字段总数 | 16 个 | 与 §A A0 的字段渲染清单一致 ⇒ 通过 |

### B4 · 运行期新建排除目录（§4.7 已知限制的确认）

**为什么必须人工**：需要**活的托盘索引进程**（USN tail 真实运转）——自动化脚本的索引进程是静态快照，测不出"增量期新建"这一形态。

> ⚠ **夹具必须是"名为 `node_modules`"的目录**（v2 修订，2026-10-07 首跑发现）：排除规则是**目录名等值匹配**（`node` 不命中 `node_modules`，selftest W11-1 钉住），首版夹具 `test-node_modules` **永远不该**被排除——它的"重启后仍搜到"是正确行为而非失败。

| 步骤 | 操作 | 预期 | 判据 |
|---|---|---|---|
| 1 | `index.exclude = node_modules`（B1 状态）+ 托盘已启动且索引就绪 | —— | —— |
| 2 | 在任意已索引目录下新建**名为 `node_modules`** 的目录并放一个唯一命名的文件（如 `w11-b4-probe.txt`） | —— | —— |
| 3 | 搜索该文件名 | **能搜到是预期**（§4.7：运行期新建不被自动锚定；方向 = 漏排除，安全侧） | 搜到 ⇒ 通过（限制如实）；文档与实际不符 ⇒ 失败 |
| 4 | **重启托盘** → 再搜 | 搜不到了（重启后重锚定：运行期新建的同名目录此时已在索引里，命中规则） | 消失 ⇒ 通过；仍能搜到 ⇒ 失败 |

## §D 已知限制（执行前必读，避免误判为 bug）

| # | 限制 | 出处 |
|---|---|---|
| 1 | 改 `index.exclude` 后需**重启托盘**才带新值（进程参数在 spawn 时定型）；`search.pathFilter` 则**每次唤出即生效**（开窗即发，无需重启） | W11 §4.7/D1 vs D3 |
| 2 | 只有**重建**（B2，删 .ezidx + 全量重建）才让 `.ezidx` 变小；重启/查询闸只保证结果正确 | D6/D1 |
| 3 | 运行期新建的排除目录不被自动锚定，重启索引进程后生效（B4 就是它的验收） | §4.7 |
| 4 | 空目录（无子项）不会被判定为目录 ⇒ 不被排除（漏排除 = 安全侧） | §2.6 纠正一 |
| 5 | `pathFilter` 限定到**卷根**不支持（无信息量），报"未生效" + 原因 | §4.5 边界 |
| 6 | `pathFilter` 只支持单一根目录、须在已索引卷上；跨卷时非限定卷**整卷不产出**（这是语义不是 bug） | §4.5 |
