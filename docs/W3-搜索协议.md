## 1. 通道与帧

完全复用工具协议的既有帧规则（本协议**不新造**任何传输语义）：

- JSON-RPC **2.0** over stdio（宿主 → `ezt-index.exe` 单向发起）；
- UTF-8 **无 BOM**、`\n` 分帧、逐帧 flush、stderr 独立读、调试信息绝不写 stdout
  （与 `docs/Eztools-设计方案.md` §四 硬约束 1~3 同源）；
- 工具 → 宿主的每条请求必须逐条回复（不回 = 挂起）。

方法名常量落位：`src/Eztools.Contracts/ProtocolMethods.cs`（W3-b-1；**本冻结阶段刻意不加**，
防止"常量先于消费者存在"变成死代码）。

## 2. `epoch` —— 乱序丢弃的核心机制（★ 必填）

### 2.1 所有权与语义

| 项 | 结论 |
|---|---|
| **谁生成** | **宿主**。每次发出 `search.query` 前 `epoch += 1`（`long`，单调递增，从 1 开始） |
| **谁校验** | **宿主**。索引侧只做**原样回传**（不做任何比较） |
| **必填性** | `search.query` 的 `params.epoch` 缺失或非整数 ⇒ JSON-RPC `-32602`（**不做默认值兜底** —— 兜底等于把乱序 bug 从"显式报错"变成"偶发闪现"） |
| **丢弃规则** | 宿主收到 `result.epoch != 当前最新 epoch` 的响应 ⇒ **静默丢弃**（不警告、不重试 —— 高频打字下警告本身是噪音；宿主侧留**丢弃计数器**供诊断，不进面板） |

### 2.2 为什么是"宿主校验 + 静默丢弃"而不是"索引侧拒绝"

乱序发生在**网络/进程调度层**（先发的后到），索引进程无从知道"这个响应算不算过期" ——
它只认识自己收到的那条请求。校验点必须放在**收齐响应的一侧**（宿主）。
这正是面板协议 V1.3 节流（§3.7.3）同款哲学：**陈旧数据在消费侧按序丢弃**。

### 2.3 典型时序（失败模式 → 协议如何防）

```
t0  宿主 → query(q="rep",  epoch=41)
t1  宿主 → query(q="report", epoch=42)      （t0 未返回，宿主不等待 —— 单在途请求管理见 §3.2）
t2  ← result(epoch=42, total=120)           ✅ 与最新一致，渲染
t3  ← result(epoch=41, total=8000)          ❌ 丢弃（静默）—— 若渲染就是"打完 report 显示 rep 的结果"
```

## 3. 方法

三个方法都是**宿主 → 索引进程**发起。索引进程不发起任何请求（无回调、无事件 —— 见 §6）。

### 3.1 `search.start`

> ✅ **实现状态（2026-10-04，W11-b 落地后更新）**：**全链已实现** ——
> 服务端过滤语义（校验后**真正锚定并挂查询期包含闸**，`IndexRpcServer.HandleSearchStartAsync`）、
> 客户端方法（`SearchIndexClient.StartAsync`，v3 补的"调用侧"层）、生产调用点
> （托盘 `ToggleSearchWindow` **开窗即发**，每次唤出重读配置 ⇒ 改 `pathFilter` 下一次唤出即生效）
> 全部就位。锚定结局随应答回传（`pathFilterAnchored` / `pathFilterReason`，加法扩展）。
> ⚠️ **空串语义（本节澄清，非 V2.0 变更）**：`pathFilter: ""` = **清除限定**（幂等）——
> 开窗路径在配置为空时用它确保无限定；缺省（不带 params）= 只复位管道，**不动**已有限定。

**何时调用**：搜索窗打开时；`pathFilter` 变更时。
（生产调用点 = 托盘 `ToggleSearchWindow` 唤出搜索窗时，fire-and-forget；`SearchSummonProbe`
live 分支也显式发一次并把应答落盘 `startAck` —— "开窗确实发过"由此可机断。）

```jsonc
// → ezt-index
{"jsonrpc":"2.0","id":1,"method":"search.start","params":{
  "pathFilter":"C:\\Users"}}          // 可选；缺省 = 只复位管道（不动已有限定）；"" = 清除限定
// ←
{"jsonrpc":"2.0","id":1,"result":{
  "ready":true,"totalFiles":1042331,
  "pathFilterAnchored":true,           // 加法扩展（W11-b）：限定是否锚定成功
  "pathFilterReason":"已锚定 C:\\Users：限定子树 N 条（其中 M 条由传播补齐）"}}
```

| 字段 | 类型 | 必填 | 语义 |
|---|---|---|---|
| `params.pathFilter` | string | 否 | 限定查询根目录（Windows 绝对路径）。索引侧**校验**该路径存在 ⇒ 不存在回 `-32002`。✅ **过滤语义已实现（W11-b）**：锚定该目录并在**查询期**挂包含闸（只返回落在子树内的条目；**非限定卷整卷不产出**）。生效时机 = 本次调用（不重建、不重启）。空串 = 清除限定。锚定失败（路径在磁盘但不在索引 / 卷根本身）⇒ **fail-open**：闸不生效（不隐藏任何结果），但 `pathFilterAnchored=false` + 原因可见 |
| `result.ready` | bool | ✓ | 索引是否已可查询（建索引期间 `false`，此时 `query` 会回 `-32001`） |
| `result.totalFiles` | int | ✓ | 当前索引内文件总数（诊断用；**不是查询结果数**） |
| `result.pathFilterAnchored` | bool | 否（带 `pathFilter` 时必回） | 加法扩展（W11-b）：限定是否锚定成功。`false` ⇒ 本次未隐藏任何条目，`pathFilterReason` 说明为什么 |
| `result.pathFilterReason` | string | 否（同上） | 加法扩展（W11-b）：锚定结局的人读原因 |

**副作用**：索引侧**清空递减式管道缓存**（设计方案 §5.3 的"上一轮结果集"）——
之后的 `query` 从全量扫开始。带 `pathFilter` 时还会**重建卷清单快照**（挂/摘包含闸）
⇒ 递减缓存随引擎重建一并清空（与上一句同向，幂等）。

### 3.2 `search.query`

**何时调用**：面板 `input` 节点经宿主节流后放行的每一次查询（**放行即交付**的是面板协议的事，
本协议不管节流 —— 宿主节流在先，`query` 在后，两层各管各的）。

```jsonc
// → ezt-index
{"jsonrpc":"2.0","id":7,"method":"search.query","params":{
  "q":"report","substr":false,"limit":200,"epoch":42}}
// ←
{"jsonrpc":"2.0","id":7,"result":{
  "epoch":42,"total":18421,"elapsedMs":6,"hits":[
    {"name":"report.docx","dir":false,"len":11,"frn":123456,
     "path":"C:\\Users\\ishe\\Desktop",
     "highlights":[{"start":0,"len":6}]}]}}
```

#### 3.2.1 请求字段表

| 字段 | 类型 | 必填 | 约束 | 违反 ⇒ |
|---|---|---|---|---|
| `q` | string | ✓ | 非空、长度 ≤ 260（NTFS 单组件上限） | `-32602` |
| `substr` | bool | ✓ | — | `-32602` |
| `limit` | int | ✓ | `1 ≤ limit ≤ 200`（Top-K 上限，设计方案 §5.4） | 超界 ⇒ `-32602`（**拒绝，不静默钳制** —— 钳制让"为什么结果少了"变成猜谜） |
| `epoch` | int | ✓ | 见 §2 | 缺失/非整数 ⇒ `-32602` |

`substr=false` = 前缀匹配（打字早期模式）；`substr=true` = 子串匹配。
匹配语义的精确定义（大小写折叠规则等）属**索引内部实现**，不在本协议面；
协议面唯一的契约是：**匹配发生在 `name` 上，不发生在 `path` 上**（Out 边界，§6）。

#### 3.2.2 响应字段表

| 字段 | 类型 | 必填 | 语义 |
|---|---|---|---|
| `epoch` | int | ✓ | **原样回传**请求里的 `epoch`（§2） |
| `total` | int | ✓ | **全库命中总数**（截断前）—— 与 `hits` 分离是硬契约：UI 显示"共 N 个结果"靠它，`hits` 只是 Top-K |
| `elapsedMs` | int | ✓ | 本次查询耗时（诊断/展示用） |
| `hits` | array | ✓ | Top-K 命中，**按相关性排序**（排序权属索引内部实现）；`total` 可大于 `hits` 数（截断），**不得小于** |
| `hits[].name` | string | ✓ | 文件名（不含目录） |
| `hits[].dir` | bool | ✓ | 是否目录 |
| `hits[].len` | int | ✓ | 文件名字符长度（`name.Length`，UTF-16 code unit） |
| `hits[].frn` | int | ✓ | NTFS File Reference Number（索引主键；宿主**不解析**，仅透传给"打开所在目录"等后续动作） |
| `hits[].path` | string | ✓ | 完整路径（用于展示与打开） |
| `hits[].highlights` | array | ✓ | 命中区间 `[{start, len}]`，**UTF-16 code unit**、**索引侧计算**（宿主绝不做匹配 —— 两端各算一遍必然漂移）。无命中段的极端情况回 `[]` |

> **为什么 `total` 与 `hits` 必须分离**：递减式管道下"命中 20 万条"是常态，把 20 万条
> 序列化过进程边界正是设计方案 §5.4 点名的尾延迟爆炸。`total` 告诉 UI"还有更多"，
> `hits` 只是"前 K 个"。

#### 3.2.3 宿主侧单在途请求

同一搜索窗**同时最多一个在途 `query`**：新查询到来时若上一条未返回，**不排队、不取消**
（JSON-RPC over stdio 无取消语义），直接发出新请求并用 epoch 丢弃旧响应。
请求堆积在结构上不可能（≥2 个在途 = 宿主 bug，断言 22.9）。

### 3.3 `search.status`

**何时调用**：托盘气泡 / 搜索窗底部状态条需要索引健康度时。**只读幂等**，不改变任何状态。

```jsonc
// → ezt-index
{"jsonrpc":"2.0","id":9,"method":"search.status","params":{}}
// ←
{"jsonrpc":"2.0","id":9,"result":{
  "ready":true,"totalFiles":1042331,
  "indexing":{"active":false,"phase":null,"filesDone":null,"filesTotal":null},
  "lastError":null}}
```

| 字段 | 类型 | 必填 | 语义 |
|---|---|---|---|
| `ready` | bool | ✓ | 同 `search.start` |
| `totalFiles` | int | ✓ | 同 `search.start` |
| `indexing.active` | bool | ✓ | 是否正在建/同步索引 |
| `indexing.phase` | string \| null | ✓ | `"initial"` / `"sync"` / `null`（不活跃时） |
| `indexing.filesDone` / `filesTotal` | int \| null | ✓ | 进度分子/分母；不活跃时 `null` |
| `lastError` | string \| null | ✓ | 最近一次内部错误的摘要（诊断用；**不替代** JSON-RPC 错误通道） |
| `excludeRules` / `excludedFrns` | int | ✓ | 加法扩展（W11-a）：生效的排除规则条数 / 排除作用域 FRN 总数（0/0 = 未配置；"配了但没命中"由卷级作用域原因表达） |
| `pathFilter` / `pathFilterAnchored` / `pathFilterReason` | string / bool / string | ✓ | 加法扩展（W11-b）：当前限定串（"" = 无）/ 是否锚定成功（false ⇒ 闸未生效，fail-open）/ 人读原因。与卷清单、ownScopes、skipped/failedVolumes 等运行期扩展字段同属实现面（V1.0 冻结表之外的字段均为加法扩展，消费方按需读取） |

## 4. 错误码表

**应用错误也必须走 JSON-RPC `error` 对象**（`result` 里塞 `{"ok":false}` 禁止 ——
宿主侧框架统一按 error 分支处理，绕过它 = 错误静默退化，S2 同族）。

| 码 | 名称 | 触发条件 | 宿主行为 |
|---|---|---|---|
| `-32700` | Parse error | 帧不是合法 JSON（框架层） | 记日志；连续出现 ⇒ 视为进程不健康 |
| `-32600` | Invalid Request | JSON-RPC 结构不合法（框架层） | 同上 |
| `-32601` | Method not found | 方法名不在本协议三方法内 | 记日志（版本错位信号：宿主新、索引旧） |
| `-32602` | Invalid params | §3.2.1 任意约束违反；`data.field` 标明字段名 | **宿主 bug**（参数由宿主构造）⇒ 记 Error 日志并停止该窗口的查询（不重试） |
| `-32603` | Internal error | 索引进程内部异常 | 记日志；面板显示"查询出错"降级文案 |
| `-32001` | `search.not-ready` | `ready=false` 时收到 `query` | 面板显示"索引准备中…"；**不重试**（等下一个用户输入自然重查） |
| `-32002` | `search.bad-path-filter` | `search.start` 的 `pathFilter` 不存在或不可读 | 面板显示路径无效提示；保持 `ready` 原状。✅ **已有生产触发路径**（W11-b：开窗即发 + CLI；错误路径不改变任何状态） |

## 5. 与面板协议（V1.3）的分工

| 关注点 | 归属 | 断言 |
|---|---|---|
| 按键怎么**进来**（输入框、节流、失焦） | 面板协议 §3.7（`input` 节点） | 21.x |

| 结果怎么**渲染**（虚拟化列表、高亮） | W3-d（宿主 WPF），受本协议 §3.2.2 字段约束 | W3-d 验收 |

## 6. 明确不做（Out 边界的协议面）

以下事项在协议层**留不下任何钩子**，追加 = V2.0 破坏性变更 + 单独立项（P0-1 Out 清单的对应条文）：

1. **内容搜索** —— 协议里没有内容字段；`q` 只匹配 `name`。
2. **正则匹配** —— `substr` 只有真假两态，无模式参数。
3. **基于路径的复杂布尔表达式** —— 无表达式字段；`pathFilter` 是单一根目录前缀。
4. **元数据过滤**（按大小/时间筛）—— hit 对象无此字段（结果属性回传另议）。
5. **事件流 / 推送** —— 索引进程不发起任何请求；结果同步只存在于 `query` 的响应里
   （与面板协议"拉取式而非键盘事件流"同哲学）。
6. **写入操作** —— 索引进程对文件系统**只读**（MFT 枚举 + 属性读），协议无任何写方法。
7. **会话 id** —— 单索引进程服务单搜索窗，`epoch` 足以表达序；多窗口 = 未来加字段的事。

## 7. 验收断言（22.1~22.9）

> 编号 22.x：20.x 已被 `verify-preview.py` 命令处理器组占用、21.x 已被面板 `input` 节点占用
> （面板协议 §3.7.8）。断言落点：**W3-b-4**（协议通路）与后续 W3 verify 脚本。
> 按 `docs/验收断言审视清单.md` §11 纪律：判据落**数字或错误码**，负向断言断"是哪个错"。

| # | 断言 | 抓什么 |
|---|---|---|
| 22.1 | `query` 响应的 `result.epoch` **原样等于**请求 `epoch`（含 `limit` 边界值 1 / 200 各一轮） | 索引侧改写/丢失 epoch |
| 22.2 | 任取响应：`total >= hits.length`（截断语义）；构造 `limit=1` 夹具 ⇒ `total=1 且 hits.length=1` | total/hits 混杂或反向 |
| 22.3 | `highlights` 每段满足 `start+len <= name` 的 UTF-16 长度，且夹具名含**非 BMP 字符**（如 emoji 文件名）时区间仍落在 code unit 网格上 | 索引侧用 UTF-8 字节偏移当 UTF-16 偏移（错位 bug） |
| 22.4 | ★★ **负向**：向宿主注入两个乱序响应（epoch 42 后到 41），宿主**最终渲染的是 42 的结果**、41 被**丢弃且丢弃计数 +1** | 宿主不校验 epoch（"打完 report 显示 rep 的结果"） |
| 22.5 | ★★ **负向**：`query` 缺 `epoch` ⇒ **-32602** 且 `data.field=="epoch"`（断言错误码与字段名，不只断言"出错了"——§30.6 教训） | 协议实现给 epoch 兜底默认值 |
| 22.6 | ★ 负向：`ready=false` 时 `query` ⇒ **-32001**（不是 -32603 兜底） | not-ready 与内部错误混作一团 |
| 22.7 | 负向：`limit=201` ⇒ **-32602**（拒绝而非钳制到 200） | 静默钳制 |
| 22.8 | 反向：连发 N 次 `search.status` ⇒ 索引侧 `totalFiles` 与 `ready` 不变、无副作用痕迹（幂等只读） | status 偷偷改状态 |
| 22.9 | 反向：宿主侧在任意时刻的在途 `query` 数 **≤ 1**（§3.2.3；断言落宿主计数器） | 请求堆积 |

**每条的突变义务**：22.4/22.5/22.6/22.7 落码时必须各配一个突变验证（删掉校验分支 ⇒ 断言必须红），
与 21.x 的 W-M 系列同规格。
