# 设置面板信息架构评审与改进方案（2026-09-30）

> 评审范围：`src/Eztools.Desktop/SettingsWindow.cs`（P1b schema 驱动渲染）+ `src/Eztools.Host/Config/HostSettingsSchema.cs`（desktop 宿主节 11 字段）+ `tools/*/tool.json`（7 个工具声明 config）。
> 结论先行：**骨架（schema 驱动、ConfigStore 单链路、CLI/窗口双入口）是健康的，问题集中在信息架构层** —— 节内平铺无分组、验收工具混入用户设置、热键管理分裂在两个界面、"技术参数"与"用户决策"不分层。
> **§六 影响核实（2026-09-30，CodeReviewExpert）**：逐条对代码核实后确认方向安全，但发现 4 个同批必改点（acceptance 豁免清单 / verify-desktop expected 集 / 探针绕过确认弹窗 / `configHidden` 进模型+双展示面），并上调方案 B 工作量至 3~4 天（工具热键"保存→重注册"链路现在不存在）—— 已全部回填正文。

## 一、现状盘点

### 1.1 设置面板实际内容（截至 2026-09-30）

左列表共 8 个节（1 宿主 + 7 工具），右栏为**纯平铺字段列表**（StackPanel 按 x-order 排序，无分组、无搜索）：

| 节 | 字段数 | 字段清单（按当前渲染顺序） | 性质 |
|---|---|---|---|
| 桌面宿主设置（desktop） | 11 | search.hotkey → ocr.hotkey → ocr.language → clip.enabled → clip.hotkey → clip.max-items → clip.image-retention-days → clip.blacklist → capture.hotkey → pick.hotkey → color.format | 全局 |
| 回显（echo） | 1 | uppercase | ⚠️ 协议验收工具 |
| 常驻探针（keepalive） | 0 | （空 schema，渲染"声明了 config 但没有任何字段"警告条） | ⚠️ 验收工具 |
| 启动任务（tasktool） | 0 | （同上，空 schema） | ⚠️ 验收工具 |
| 速览（preview） | 3 | maxTextBytes → maxLines → binaryProbeBytes | 真实工具，含技术参数 |
| 进程信息（pinfo） | 1 | limit | ⚠️ 特权链路 demo |
| 文件校验（filehash） | 3 | algorithm → uppercase → chunkSizeKb | 真实工具，含技术参数 |
| 文本统计（wordcount） | 3 | countWhitespace → language → maxFileSizeMb | 真实工具 |

另有 3 个工具热键（wordcount Ctrl+Alt+N / preview Ctrl+Alt+P / filehash Ctrl+Alt+H）**不在**设置窗口 —— 其覆盖改键只存在于 `ezt hotkeys set`（写 state.json 的 hotkeyOverrides）。

### 1.2 已确认做得好的（改进时必须保留）

1. **schema 驱动、零工具专属代码**：新工具声明 config 自动出现，窗口一行不改 —— 这是"新增工具不改宿主"标准的落地，任何方案都不能破坏。
2. **单配置链路**：窗口与 `ezt config` 改同一文件，校验/原子写/损坏恢复/孤键告警全复用 ConfigStore。
3. **损坏恢复与孤键告警条**（黄色 WarnBar）：用户可见、可判读。
4. **PasswordBox 不回显**：屏幕共享场景的正确默认。
5. **滚动容器修复 + selfcheck 滚动断言**：右栏可达性有自动化守护（W6-d 回归）。

## 二、存在的问题（按严重度排序）

### P1 🔴 未保存修改静默丢失（数据丢失级）

`OnToolSelected` 在切换左列表选中项时直接 `_fieldPanel.Children.Clear()` 重建 —— 用户改了 5 个字段没点"保存"，点一下左列表任何项，**全部修改无提示丢弃**。保存按钮是唯一的提交出口，但没有任何 dirty 状态指示（标题不加 `*`、切换不拦截、关闭窗口不拦截）。

### P2 🔴 热键管理分裂在两个界面（可发现性级）

- 宿主 5 个热键 → 设置窗口（config/desktop.json）；
- 工具 3+ 个热键的改键 → 仅 `ezt hotkeys set`（state.json hotkeyOverrides），设置窗口**零入口**；
- 热键仲裁视图（`ezt hotkeys list`，含占用/冲突归属）同样是 CLI-only。

用户心智里"改热键"是一件事，实际要猜它在哪个界面。设计方案 §3 描述的统一 UI 层是"设置窗口 · 托盘菜单 · **热键中心**"三件，热键中心至今没有 UI 载体。尤其 W6 的实测结论（Ctrl+Alt+X/C 本机不可注册）意味着**用户迟早要在设置里改热键自救**，热键入口的完整性不是锦上添花。

### P3 🟡 验收/演示工具混入用户设置面板（分类不清晰）

keepalive、tasktool 是生命周期验收工具，声明了空 `config: {properties:{}}`，结果在设置列表里各占一行、点开只有一条"没有任何字段"的警告条；echo（uppercase）、pinfo（limit）是协议/特权链路验证工具，其"设置项"对真实使用无意义。8 个节里 4 个是开发噪音 —— 随验收工具继续增加（acceptance 423 条背后的工具面），这个比例会恶化。

### P4 🟡 宿主节 11 字段平铺，顺序按"落地波次"而非用户心智（层级混乱）

x-order 1~11 严格按 W3 搜索 → W4 OCR → W5 剪贴板 → W6 截图/取色的**开发时间线**排列，导致：

- 5 个热键分散在 1、2、5、9、10 位，与各自功能的其它设置分离（如 ocr.language 夹在两个热键中间；color.format 与 pick.hotkey 相邻但语义分属"输出格式"与"触发方式"）；
- "热键 / 开关与容量 / 输出格式"三类决策混排在一屏，无视觉分组；
- 字段越多（W7 Launcher 会继续加），这个问题越线性恶化。

### P5 🟡 "用户决策"与"引擎参数"不分层（冗余 / 缺乏实际用途）

以下字段本质是**实现参数**，普通用户既不理解也没有调整动机（对自用工具集，默认值已合理）：

| 字段 | 默认 | 问题 |
|---|---|---|
| preview.binaryProbeBytes | 4096 | NUL 探测字节数，纯实现细节 |
| preview.maxTextBytes | 65536 | 描述写的是"JSON-RPC 单帧必须截断"——协议内部约束 |
| filehash.chunkSizeKb | 1024 | IO 分块大小，性能调优参数 |

它们与 maxLines、algorithm 这类用户能理解的选项平铺在同一列表里，抬高整节的认知负担。

### P6 💥 控件级易用性问题（体验层）

1. **热键字段是自由文本 TextBox**：靠手打 "Ctrl+Alt+S"，格式错误只能在保存时批量弹窗发现；无"按下即捕获"的录制控件。
2. **整数/数值字段用 TextBox**：min/max 提示藏在 ToolTip 里（悬停才可见），错误在保存时才暴露；无即时校验红框。
3. **Boolean 行的语义倒挂**：CheckBox Content = description（"关闭后：不监听剪贴板、不注册面板热键……"整段长文挂在勾选框旁），label（"剪贴板历史总开关"）反而在上一行 —— 长描述直接当控件文本，视觉上是两句话而非一个开关。
4. **左列表按 Name 的 Ordinal 码位排序**：中文按 Unicode 码位排（回显 → 常驻探针 → 启动任务 → 文件校验…），顺序对用户无意义，且全局节与工具节无视觉区分。
5. **secret 字段无"已设置"状态显示**：PasswordBox 的 configured 标记在内部 Tag 里，用户看不到当前是"已配置"还是"未配置"。

### P7 💥 扩展性缺口

ConfigSchema 不支持节内分组（无 x-group / x-advanced 类元数据），"分组"目前只能靠新增整节实现 —— 而新节 = 左列表多一项 = P3 的噪音制造机。字段级元数据缺失是 P4/P5 的根因。

## 三、改进方案

### 共同基座（三套方案都包含的清理，先做）

| # | 动作 | 理由 | 同批必改（§六 影响核实） |
|---|---|---|---|
| C1 | keepalive / tasktool 删除空 `config` 声明 | 空 schema 只产出噪音警告条；验收工具不需要用户设置。解析器本就容忍缺省（`ManifestParser.cs:330`），窗口按 `ConfigSchema is not null` 过滤（`SettingsWindow.cs:173`）⇒ 噪音行自动消失 | ★ `acceptance.sh` 的 `NO_SCHEMA_TOOLS` 显式豁免清单（:306）同批加入这两个工具，否则被判"schema 未解析"而红（该清单注释就是为"防按排除法烂掉"写的） |
| C2 | echo / pinfo（及后续验收工具）从设置面板隐藏：tool.json 加 `"configHidden": true`，schema 与 `ezt config` 链路保留 | CLI 调试入口不丢，用户面板降噪。⚠️ 解析器"未知字段一律忽略"（`ManifestParser.cs:32` 前向兼容）⇒ 只加 JSON 键**无害但惰性** | ★ ① 必须同步进 `ToolManifest` 模型 + 解析 + 窗口过滤；② verify-desktop 1b 的 expected 集硬编码含 echo/pinfo（:412-419），"覆盖全部 N 个 / 共渲染 22 个字段"两条断言同批改；③ `ezt list --json` 是否暴露 `configHidden` **显式决策**并配断言（否则即 RI-3"白名单吞字段"家族新成员） |
| C3 | schema 新增字段级元数据 `x-group`（组名）、`x-advanced`（bool） | P4/P5 的根因修复，三套方案共用。同 C2：未知元数据键被忽略，无害但惰性，须进 `ConfigSchema` 模型（现仅 `x-order`，:52） | ★ selftest 补两条解析断言（§3.1 1.8 双展示面纪律） |
| C4 | dirty 检测：字段变更 → 标题加 `*`；切换节/关窗未保存时确认拦截 | P1 是数据丢失级，任何方案下都必须修。Unset 语义不受影响（`SettingsWindow.cs:429` 现存） | ★ 确认弹窗会卡死 headless 自检探针：`ProbeSetField`/`ProbeSaveAsync` 程序化切节/保存时若触发模态确认，headless 下无人点"确定"⇒ 探针模式必须绕过拦截（加探针开关或走保存前清 dirty） |
| C5 | preview/filehash 的技术参数标 `x-advanced`，渲染为默认折叠的"高级"Expander | P5 | （依赖 C3 的模型落地） |

### 方案 A：轻量整理 —— 保持"一节一页"，只做分组与降噪

**结构**：左列表不变（8→4 个节）；右栏从平铺改为**组内分组**（GroupBox / 组标题分隔）。

**宿主节新分组与顺序**（x-order 重排）：

| 组 | 字段 |
|---|---|
| 全局热键 | search / ocr / clip / capture / pick 五个 hotkey（相邻排列） |
| 剪贴板历史 | clip.enabled → max-items → image-retention-days → blacklist |
| 屏幕取字 | ocr.language |
| 屏幕取色 | color.format |

**命名建议**：节名"桌面宿主设置"→"全局设置"（与工具节对仗，且它本来就不是"桌面"专属——CLI 同样消费）。

**归组调整**：仅重排 x-order + 补 x-group，字段本身零增删；C1~C5 全做。

**优点**
- 改动最小：schema 元数据 + 渲染规则（约一天级），ConfigStore / CLI / selfcheck 断言面几乎不动；
- 风险最低：不碰热键仲裁、不碰 state.json；
- P1~P5 全部缓解。

**缺点**
- 热键分裂问题**不解决**（工具热键仍在 CLI）；左列表仍是平铺清单，工具多了以后列表增长无结构；
- "热键中心"欠账继续挂着。

**适用场景**：想用最小成本先把噪音和明显混乱清掉；W7 Launcher 前的过渡形态。

### 方案 B：功能域重组 + 热键中心入窗（推荐）

**结构**：左列表改两级树；宿主节从"一个大节"拆为**按功能域导航**：

```
├─ 全局设置
│   ├─ 热键中心        ← 新增：统一热键入口（见下）
│   ├─ 搜索
│   ├─ 屏幕取字（OCR）
│   ├─ 剪贴板历史
│   └─ 截图与取色      ← capture.hotkey + pick.hotkey + color.format
└─ 工具
    ├─ 文本统计
    ├─ 文件校验
    └─ 速览
```

**热键中心**（本方案的核心增量）：
- 列出**所有**热键声明（宿主 5 个 + 各工具 contributes.hotkeys），显示当前生效值、来源（默认/覆盖）、仲裁归属与冲突状态 —— 数据全部已有（HotkeyClaim 仲裁 + hotkeyOverrides），只是搬进窗口；
- 宿主热键：编辑写 desktop.json（现链路不变）；
- 工具热键：编辑写 state.json hotkeyOverrides（复用 `ezt hotkeys set` 的同一写入口，**权威源仍是仲裁器**，CLI 与窗口改的是同一份 state，无新双写源）；
- ⚠️ **"保存即生效"没有现成链路（§六 核实结论，本方案唯一动到非 UI 层的点）**：`ToolRegistry` 只在启动时构建一次（`ToolRegistry.cs:127`），overrides 只在构建时读取（:158）；`_hostSettingsSaved` 回调只重注册**宿主**热键 —— 窗口写完 state.json 后托盘**不会**重建注册表。必须新增"写 state.json → 重建生效热键 → 重注册"路径，否则就是新的"保存成功但没生效"静默失败。

**归组调整**：
- ocr.language → "屏幕取字"组；search.hotkey → "搜索"组；color.format + capture/pick.hotkey → "截图与取色"组；clip.* → "剪贴板历史"组；
- 每组即左列表一个子项，渲染仍是 schema 驱动 —— 实现为"一个 schema 按前缀切分成多个虚拟节"或"schema 内 x-group + 左列表二级锚点"，推荐后者（schema 仍是单文件，导航层做锚点）。

**移除/合并**：C1~C5 全做；另外把"桌面宿主设置"更名为"全局设置"。

**优点**
- "改热键"一件事一个入口，可发现性问题根治；`ezt hotkeys` 与设置窗互通，用户不再需要知道 CLI 的存在也能自救热键冲突（W6 实测教训的直接回应）；
- 左列表二级树 = 分类结构，工具增长时结构稳定；
- 为 W7 Launcher 的功能域扩展（搜索/启动器设置）预留了自然挂点。

**缺点**
- 改动中等偏上：导航树 + 热键中心视图 + state.json 写入路径进窗口 + **工具热键"保存→重建→重注册"新链路**（§六 核实：该链路现在不存在）—— 按 **3~4 天**估（原估 2~3 天偏低）；selfcheck 的"设置清单"断言面需要适配（宿主节拆组后 `设置清单 desktop:` 的字段清单格式变化），`--probe-host-settings` 探针也要适配二级树导航；
- 热键录制控件若同批做，工作量再+1 天（也可先用文本框过渡）。

**适用场景**：W7 Launcher 之前把统一 UI 层补齐；工具数量还会增长的正解。

### 方案 C：设置中心 2.0 —— 在 B 之上加搜索、两列布局与即时校验

**在方案 B 全部内容之上追加**：

1. **顶部搜索框**：按 title/description/key 过滤，命中高亮并自动展开所在组（自用工具集字段总量 <50，本地过滤即可，不必动 W3 索引）。
2. **两列字段网格**：左列标签（title），右列控件；description 从 CheckBox 内容/ToolTip 改为标签下的次行小字**常显** —— 修掉 P6-3 的语义倒挂，描述可发现性从"悬停才见"提升为"直接可读"。
3. **即时校验**：数字字段失焦即校验（红框 + 行内错误文本），替代"保存时批量弹窗"；保存按钮只做提交，不再做第一次校验暴露。
4. **热键录制控件**：点击进入录制态，KeyDown 预览捕获组合键（WPF PreviewKeyDown，与本项目键盘注入坑 §2.27/§2.29 方向相反，是接收侧，风险低）；Esc 取消，冲突即时提示（调仲裁器预检）。
5. **secret 状态显示**：PasswordBox 旁显示"已配置 / 未配置"徽标。

**优点**
- 易用性/可发现性天花板：搜索直达、描述常显、错误即时、热键免手打；
- 与现代设置页（PowerToys/VS Code）习惯一致，长期形态最正确。

**缺点**
- 工作量最大（在 B 之上约 +3~5 天）；自动保存若做（本方案**不建议**做），"部分字段校验失败时能不能落盘"的语义要重推一遍，且与现有"空值=回落默认"的 Unset 语义有交互成本 —— 因此 C 保留"保存按钮 + dirty 拦截"模型；
- 录制控件是唯一的新交互原语，需要自己的验收探针（沿用 InventoryForSelfCheck 先例可做，但要看真实键盘焦点，headless 自检覆盖有限）。

**适用场景**：设置面板是日常高频使用面、且愿意投入一轮 UI 专波时。

## 四、三方案对比

| 维度 | A 轻量整理 | B 功能域+热键中心 ★推荐 | C 设置中心 2.0 |
|---|---|---|---|
| 解决 P1 丢改动 | ✅（C4） | ✅ | ✅ |
| 解决 P2 热键分裂 | ❌ | ✅ | ✅ + 录制控件 |
| 解决 P3 验收工具噪音 | ✅（C1/C2） | ✅ | ✅ |
| 解决 P4 平铺无分组 | ✅（组内分组） | ✅（二级树，更彻底） | ✅ |
| 解决 P5 技术参数 | ✅（x-advanced） | ✅ | ✅ |
| 解决 P6 控件体验 | 部分（C4） | 部分 | ✅ 全部 |
| 改动量 | ~1 天（无新增风险） | ~3~4 天（含热键重注册新链路，§六） | B + ~3~5 天 |
| 断言面影响 | 极小 | 中偏大：设置清单格式 + 热键断言 + acceptance 豁免清单 + verify-desktop expected 集 + 探针适配（§六） | 中大（新交互原语） |
| W7 之后的扩展性 | 工具多了列表仍会变长 | 功能域树稳定挂新组 | 同 B 且检索友好 |

**推荐路线**：**B 为主干，吸收 A 的全部清理项（C1~C5），C 作为后续增量波**。理由：
1. B 是唯一根治"热键分裂"的方案，而这正是 W6 刚踩过的实测坑（默认热键不可注册 → 用户必须能改）；
2. C1~C5 成本低、与 B 无冲突，可先行独立落地（即便最终选 A 也值得做）；
